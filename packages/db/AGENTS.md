# packages/db

Drizzle schema, migrations and (from M1a) repositories over SQLite in WAL mode. The daemon is the
only process that writes the database.

- `src/schema.ts` is the schema. Never edit a generated migration by hand.
- **Until the first published release (`v0.1.0`), the baseline is regenerated, not extended.** The
  baseline is `0000_init` (generated) plus `0001_decisions_fts` (the hand-written FTS5 DDL, made with
  `drizzle-kit generate --custom` and kept byte for byte). To change the schema: save
  `0001_decisions_fts.sql`, delete `drizzle/`, run `pnpm exec drizzle-kit generate --name init` and
  then `pnpm exec drizzle-kit generate --custom --name decisions_fts` in this package, and put the
  saved SQL back. Nothing migrates an old database: `migrateDatabase` refuses one made under an
  older baseline (`StaleSchemaBaselineError`), the daemon exits with code 3, and the builder deletes
  the data directory by hand.
- **From `v0.1.0` on, migrations are forward-only.** After changing the schema, run
  `pnpm --filter @10db/db generate` and commit the new file under `drizzle/`; never delete or
  regenerate a migration. A `--custom` migration is authored by hand once and never regenerated. A
  database migrated by a newer build is refused with `NewerSchemaError`, never wiped. A migration that drops a NOT NULL is a table rebuild (drizzle-kit writes it); `migrateDatabase` switches `foreign_keys` off around the migrations, because the pragma is a no-op inside their transaction and the rebuild's `DROP TABLE` would otherwise fail on rows that reference the table. It then runs `foreign_key_check` and throws `MigrationIntegrityError` on any dangling reference, since enforcement was off. Migration 0007 rebuilds `projects` (`gate_command` nullable) and `evidence` (`command` and `exit_code` nullable, for builder evidence).
- Every row has a prefixed UUIDv7 ID (`tsk_<uuidv7>`, sortable by creation) plus `created_at` and
  `updated_at` as ISO text.
  Settings-style tables keyed by a natural key are the first exception; append-only record tables
  (`events`, `tool_ops`, `evidence`, `handoffs`, `sources`; `created_at` only, none for `events`),
  immutable once written, are the second. Join tables keyed by their two foreign keys (`task_deps`)
  have no ID or timestamps.
- Every state change writes its row and appends its event in one transaction (M1a adds the helper). `composeKnowledgeText` is an exception: it composes stored Knowledge text at daemon start and appends no event (see Knowledge repositories).
- Full-text search lives in one module so the storage engine can change later.
- Tests use a real database file in a temp directory, never `:memory:`, so WAL and file paths are
  exercised. `createTestStore` copies a migrated template instead of migrating each store: about 2 ms
  against 27. The template sits in `10db-test-db-templates` under the temp directory, named by a hash
  of the shipped migrations and of `openDatabase` and `migrateDatabase`. It is used only from a real
  directory this user owns that nobody else can write, and each copy is checked for the shipped
  migrations; a damaged template is rebuilt in place, and an unsafe directory or a failed build means each store
  migrates its own. A test of migrating itself opens and migrates its own database, as
  `database.test.ts` does.
- The daemon bundle ships its own copy of `drizzle/`; pass its path to `migrateDatabase`.
- Repositories are synchronous functions over `DbReader` (reads) or `WriteContext` (writes); never open a second connection.
- `board_columns` holds the builder's human columns; `tasks.board_column_id` set means parked (never started: `insertWorkstream` refuses it), null means planned. `moveTask` refuses to park a task that a started dependent waits on.
- `cancelTask` removes a task that never started (status `cancelled`, row kept, decision `2026-10-28-remove-unstarted-task.md`); `listTasks` leaves cancelled tasks out, so a reader of the project's tasks never sees one. A task whose only run is `HELD` is removed too, and `cancelTask` cancels that run in the same write.
- Goals (`store/goals.ts`, goals spec §4, §5, §8, phase 1; migration 0021): `insertGoal` writes a `draft` goal, its tasks (`tasks.goal_id`), their `task_deps` and its `unproven` `goal_criteria` in the caller's transaction, turning brief keys into the TaskIds it makes, and answers `{ goal, taskIds }` (brief key to TaskId). For Shape's Convert it also takes `outsideKeys` (keys of tasks outside the brief) and `dependsOnOutside` (brief key to outside keys); with neither it writes what it always did. A repeated or unknown key, a dependency cycle, an unknown area or person, or an outside key that names no task of the project throws, so nothing is left behind. The owner defaults to the builder (handle `me`). `markGoalViewed` upserts `goal_views` and answers the previous mark, the digest's window.
- Shape (`docs/superpowers/specs/2026-11-02-10db-brainstorm-chat-design.md` §5.1, §6, §13; migrations 0027 and 0028): `shapes`, `shape_messages` (append-only), `shape_proposals` (Shape's own, one row per key in a conversation; `proposals` is unchanged) and `shape_links` (a CHECK keeps exactly one of goal, task or decision). A session belongs to a workstream or a shape, exactly one (CHECK `sessions_one_owner`): `insertSession` takes `workstreamId` or `shapeId`, `isLaneSession` narrows a row, and per-project usage resolves the project through either. The lane MCP endpoint refuses a Shape session's token. Migration 0027 adds `sessions.shape_id` by `ALTER TABLE` before 0028 rebuilds `sessions`, because drizzle-kit's rebuild copies every new column from the old table and fails on one it adds in the same step.
- Shape slice 2, migration 0029: `shape_files` and `shape_proposals.created_round`; a proposal's round is the round that last created, changed or moved it. Migration 0030: `shape_files.told_at`, set by `markShapeFilesTold` once a turn carries the file; `listUntoldShapeFiles` answers the rest, so a restart loses none.
- Shape slice 3, migration 0031: `task_lane_times` (Shape spec §8), one row per finished workstream: its session spans plus its gate spans (the `gate.started`/`gate.finished` events), written by `transitionWorkstream` on the move to `DONE` (`recordLaneTime`); `sessions_only` marks a workstream whose gate ran with no span recorded. Migration 0032 (`--custom`, never regenerated) backfilled every `DONE` workstream from its sessions alone, marked sessions-only; a workstream with a session that never ended gets no row. `similarTasks` ranks a project's finished tasks with lane time by the query's words in their title and description. `shape_shadow_answers` holds Jev's shadow answers (§9), one per message and decision; a project's opt-in is the app setting `shape.jev.<projectId>` (`getShapeJevOptIn`), off when absent. `findRecords` is `searchDecisions` with each hit's scope and `created_at`.
- Shape principles and questions, migrations 0039 and 0040 (generated, in two steps for the reason in the 0027/0028 note): `shape_questions` (a question Convert stores for goals phase 3, with its `for_who`, source messages and the `goal_id` or `task_id` it belongs to; `insertShapeQuestion`, `listShapeQuestions`) and `shape_links.principle_id` and `question_id` came by `ALTER TABLE` in 0039, and 0040 rebuilt `shape_links` so its CHECK `shape_links_one_target` demands exactly one of goal, task, decision, principle and question. `findRecords` now ranks current decisions and principles together by `bm25` and answers a `RecordHit` union.
- Shape slice 4, migration 0033 (generated): `shape_findings` (a reviewer's finding or a rehearsal question, per effort key and optional task key, with `state` open/resolved/dismissed and the task hash it read), `shape_rehearsals` (one mark per proposal, task key and task hash; written only by a closing report, so an interrupted rehearsal leaves none) and `shape_attachments` (a spec per effort, and the proposed eval stored at Convert; linked to the goal or task by `linkAttachments`). `store/shape-review.ts` holds them, plus `questionCardRates` (Inbox question cards per started task, converted against other, Settings › Decisions › Questions) and the project's one-way paths as the app setting `shape.oneWayPaths.<projectId>` (`getOneWayPaths`/`setOneWayPaths`; null while unset, the defaults then apply).
- Shape slice 6, migration 0034 (generated): `landing_groups` (id, project, title, the shape that proposed it) and `tasks.landing_group_id` (`store/landing-groups.ts`, Shape spec §10.4). `insertLandingGroup` writes the group and sets its tasks in the caller's transaction, refusing a task already in a group or from another project; `TaskDto.landingGroupId` is optional and nullable. `landingBatches` (`store/batches.ts`) lists the batches a group's tasks have run in, newest first. Nothing yet removes a group when its last task is removed.
- Knowledge repositories: `store/decisions.ts` (decisions, `supersedeDecision`, `withdrawDecision`, `listDecisions` and `getDecisionDto` with the derived state), `store/principles.ts` (principles: `insertPrinciple`, `confirmPrinciple`, `supersedePrinciple`, `retirePrinciple`, `withdrawPrinciple`, `listPrinciples`), `store/knowledge-list.ts` (`pageKnowledge`: one page of the Knowledge list and its total, narrowed by shelf, kinds, scope, area and search and sorted in one query; a search joins `rankedMatchesSql`'s ranked FTS rows and pages each kind's best in turn by `row_number()`), and `store/knowledge-search.ts`, which holds every full-text query (`searchDecisions`, `findRecords`, `searchDecisionIds`, `searchPrincipleIds`, `searchPrinciples`) and the FTS health check (`checkKnowledgeIndex`, `rebuildKnowledgeIndex`). Indexed Knowledge columns (a decision's `question`, `choice` and `rationale`; a principle's `statement`, `topic_key` and `source_quote`) are stored NFC, so a record stored decomposed meets the composed query `searchTerms` makes: every write passes them through `composed` (`store/compose.ts`), and a new indexed column must do the same and be added to `INDEXED_TEXT` in `knowledge-search.ts`. `composeKnowledgeText` (`knowledge-search.ts`) composes rows written before writes did; it runs at daemon start, goes through the FTS triggers, and emits no event, because it changes the encoding of the text and not the record (an exception to "every state change appends its event"). A search matches any whole word, ranked by `bm25`, for free text from an agent or a task; the Knowledge list passes `SearchMatch.AllPrefixes`, where every word must start a word of the record. `store/knowledge.ts` keeps sources, deviations and proposals. A current search never returns a superseded, withdrawn, retired or proposed record; `history: true` returns them all and `list*` label each with its state. A decision is superseded only through an explicit `supersedes_id` link; a confirmed principle also supersedes implicitly the current one with its topic key and target, while `supersedePrinciple` links explicitly and refuses a successor whose new key already has a current principle at its new target.
- Decisions: `withdrawDecision` writes `withdrawn_at`, `withdrawn_by`, a required `withdrawn_reason` (M3's tombstone, Shape spec §11) and, when the write named a source, `withdrawn_source_id`, and refuses a decision that a live successor supersedes (`ConflictError`) or that is already withdrawn; `searchDecisions` and `listRecentDecisions` skip withdrawn ones. No CHECK guards the columns: adding one rebuilds `decisions` and drops its FTS triggers.
- Principles (M3 knowledge; migrations 0035, 0037 and 0038 generated, 0036 `--custom`): `principles` holds a statement, a nullable `rationale`, a kind, a topic key, a target (`scope`, `project_id`, `area`; a `you` principle has no project), a stored status (`proposed`, `confirmed`, `retired`), `supersedes_id`, provenance (`source_id`, `source_quote`, `speaker`, `confirmed_by`/`confirmed_at`) and retired and withdrawn tombstones. `confirmed_source_id`, `retired_source_id` and `withdrawn_source_id` are nullable: the source of that act when the write named one, apart from the record's own `source_id`. A 409 on a record that isn't current names what to act on instead through `currentPrincipleOf` and `currentDecisionOf`, which go back past a withdrawn head and never name a retired one. A record's state is derived on read, never stored (decisions `2026-11-03-knowledge-records-have-a-target-and-a-derived-state.md` and `2026-11-03-principles-have-a-kind-and-a-topic-key-and-supersede-by-key-and-target.md`). `principles_fts` indexes statement, topic key and source quote through insert, update and delete triggers, keyed on the implicit rowid like `decisions_fts`; the rationale is not indexed. `0036_principles_fts.sql` is authored once and never regenerated. Like `decisions`, the withdrawn columns carry no CHECK. `decisions_supersedes_idx` and `principles_supersedes_idx` serve the successor lookup every read makes. `decisions.scope` is typed `KnowledgeScope`, the same vocabulary as Shape's `RecordScope`. `proposals.principle_id` (nullable, migration 0037) links a principle proposal to its proposed principle. `insertProposal` takes the `principleId`, and `getProposalDto` and `listProposals` read the proposed principle with it; `findOpenProposalCard` finds a proposal's open card.
- Shape calibration, migration 0041 (generated): `shape_links.size_told_at`, set by `markShapeLinksSizeTold` once a turn tells Claude the linked task finished outside its size, so a restart neither loses nor repeats the note (the same pattern as `shape_files.told_at`).
- Shape image budget, migrations 0043 (generated) and 0044 (`--custom`, never regenerated): `shape_files.inline_sent`, set by `markShapeFilesInline` for the files a turn sent as image blocks and cleared for the whole conversation when a fresh session starts (`fresh: true`), so it says what the live session's history holds and the daemon's `inlineBytesSpent` charges only that. 0044 marks every already-told file, which keeps the old count for conversations that existed before.
- Shape refused-image notices, migration 0045 (generated): `shape_files.unreadable_told_at`, set by `markShapeFilesUnreadableTold` in the write that sends a notice naming the file, so a refused Read names each file once. It is per file because `shape_files.name` can repeat in a conversation. Files named by a notice before this migration have no mark, so one can get one more notice.
- `holdTask` and `resumeTask` (`store/holds.ts`) move a task's `QUEUED` run that has not run to `HELD` and back (decision `2026-10-29-hold-a-queued-task.md`). `HELD` is non-terminal and derives the Blocked board status.
- Model catalogue storage, migration 0047 (generated; routing reads it): `account_models` (`store/account-models.ts`, keyed by account and model) holds what each account reports, with its own prices and a nullable `family`; `replaceAccountModels` replaces an account's rows and keeps `unusable` only while the `launch_id` and efforts are unchanged (a price change alone does not clear it). `role_settings` is unique per role and project, and per role with no project (two partial unique indexes, because SQLite treats NULLs as distinct); `patterns` keeps its scope's order in `position` (`store/model-settings.ts`, `setPatterns` replaces one scope). `model_profiles` gained nullable `maker`, `family`, `tier`, `status`, `input_price`, `output_price` and `release_date`, written by `upsertModelProfiles`, which also writes `enabled` (routing may pick the model) and leaves scores and the AA slug alone. The fetched catalogue document is the app setting `catalogue.document`. `replaceAccountModels` (which refuses a model named twice and answers whether the list changed) and `upsertModelProfiles` append their event only when something changed; the other writes (`markAccountModelUnusable`, `setRoleSetting`, `clearRoleSetting` for a row that existed, `setPatterns`) always emit `settings.changed`. `clearRoleSetting` returns a project's role to the global value. `setAppSetting` and `patchJudgeConfig` append no event.
- Task model setting, migration 0048 (generated): `tasks.model_setting`, the builder's own `ModelSetting` for one task; null is no override and Automatic is a setting. `patchTask` takes `modelSetting` (null clears it).

- Migration 0049 (`--custom`, authored once): renames the four Claude Code aliases stored in `model_profiles`, `workstreams` (the column and each step's `model` and `profileId`), `personas.model_pin` and `shapes.model` to canonical IDs, merges an alias profile into the canonical row reconcile already wrote (step counts add, scores come from the row that has them, the newer measurement when both do), turns Fable on, and removes `modelMap` and `aliases` from `accounts.settings`. `sessions.model` and `judge_calls.model` record history and stay as written; `account_models.model` never held an alias.
- Task thread, migration 0053 (generated; Workbench spec §11): `task_messages` (author `builder`, `agent` or `system`; kind `message`, `reply` or `notice`; `pushed_at` and `delivered_at`, null until a session is handed the message and a turn takes it) and `task_files` (a pasted picture: its message, name, media type, size, `sha256`, `stored_path`, `inline_sent`). `store/task-thread.ts`: `insertBuilderMessage` writes a builder message and its pictures in the caller's write and appends `task.message_added`; `listTaskThread` answers the thread oldest first, each message with its pictures; `getTaskFile` answers one picture's row with its stored path, which `TaskFileDto` leaves out. A message's id is `tmg_<uuid>`; the part after the underscore is the uuid it carries to a session (`idUuid`, read back with `idOfUuid`). Delivery (§6.3): `markTaskMessagesPushed` stamps `pushed_at` each time a message is handed to a session; `markTaskMessagesDelivered` sets `delivered_at` once, for the task's own messages only, and answers those it marked; `listUndeliveredTaskMessages` answers the pushed and not delivered, oldest first, with their pictures' rows; `markTaskFilesInline` marks the pictures sent as blocks and, for a fresh session, clears the task's others first, as `markShapeFilesInline` does. `deleteUnsentBuilderMessage` takes back a builder message no session was handed, with its pictures' rows, appending `task.changed`, and answers the stored paths no other row names (null, removing nothing, for one pushed, delivered or taken by a turn): a page of a pass that refused the message as it went in keeps nothing of it. `insertSystemNotice` writes 10db's own line (author `system`, kind `notice`) and appends `task.message_added`. `listTaskThreadRows`, `getTaskMessageRow` and `listTaskFileRows` answer rows with stored paths for the daemon. The marks append no event, as Plan's file marks don't. `turn_id` comes with `pass_turns`.
- Workbench passes, migration 0054 (generated; Workbench spec §5, §11): `passes` (state `OPEN`, `CLOSING`, `CLOSED`, `SETTLED`, `ABANDONING`, `ABANDONED`; `batch_id`, `page_cap`, `return_branch`, `start_sha`, `opened_at`; partial unique index `passes_one_open` on the first, second and fifth), `pass_dirt` (a record keyed by pass and path; `blob` null for a deleted file), `batches.pass_id` (unique when set) and `tasks.pass_id`. `store/passes.ts`: `insertPass` writes the pass, its batch `OPEN` through `insertBatch`'s `pass` input (`batch_id` is set in the same write, after the batch row exists), the dirt and each task's `pass_id`, and appends `pass.opened`; it refuses a task of another project or one a pass still holds, a second open pass and an unfinished shared batch. `findOpenPass` reads the open, closing or abandoning one; `passHoldingFolder` the oldest that is neither settled nor abandoned (W9); `passHoldingTask` the pass that still holds a task (`passHoldsTasks`: open, closing or abandoning), so a task of a closed, settled or abandoned pass is ordinary again. `insertWorkstream` refuses a held task a run outside its pass's batch. `countLanes` answers `byPass` for the lanes of held tasks and counts every other lane in `byProject`. `placeTaskByRule` moves a task's placement with the rule's reason, refused as the builder's own move is.
- Workbench turns and take-outs, migration 0055 (generated; Workbench spec §5.4, §6.2, §11, §12): `pass_turns` (a task's turns, numbered per task; `ended_at` and `ending` (`ready`, `stopped`, `failed`) written together, `settled_at` once the end is carried through, so start-up finishes a turn ended and not settled (`listTurnsEndedUnsettled`) by its `ending`; `kept_sha`, `kept_base_sha` and `shared_seq`; a partial unique index allows one turn per task with no `ended_at`), `pass_take_outs` (one per task and pass: `step`, the last finished, `-1` when written and `5` done; `tries`, the kept commit, `left` and `drops`), `task_messages.turn_id`, `tasks.kept_work_sha` and `kept_base_sha`, `passes.abandon_step` and `projects.app_url`. `store/pass-turns.ts`: `insertPassTurn` numbers the turn and marks the message that starts it; `endPassTurn` ends it and appends the agent's reply naming it in one write (`insertAgentReply`); `settlePassTurn` sets `ready_at` and appends `pass.page_ready` for a `ready` turn only; `clearPassTurnAnswered` takes back a turn's `answered_at` with the message that set it; `settleTurnsLeaving`, for a task leaving its pass, ends its open turn `stopped` and settles every turn not settled, none Ready; `latestPassTurn` reads the task's current run only (its latest workstream), so a turn of a run in a pass the task left is never this run's, while `openPassTurn` reads every run, since the index allows one open turn per task. `store/pass-take-outs.ts` keeps the take-out rows; a step is never recorded below the last. `leavePass` clears `tasks.pass_id`, so the pass no longer holds the task and its lane counts for the project; `setAbandonStep` records an Abandon's steps, its first moving the pass to `ABANDONING`; `abandonPassAndBatch` moves the pass and its batch to `ABANDONED` in one write, or neither; `passPageAreas` answers the areas that are pages in a pass.
- Workbench shared areas and the close, migration 0056 (generated; Workbench spec §5.3-§5.5, §7.2, §9.2, §11, §12): `pass_holds` (one per shared grant, keyed by its claim: the area, its number on the pass's chain, the record commit, `closed_at` and `empty`; unique per pass and number), `pass_hold_paths` (the record taken at the grant: path and blob, null for a deleted file), `pass_shared_changes` (one per chain commit, keyed by pass and number: `paths`, `blobs` by path, `dirty_kept`, `landed_sha`; a drop is a row of its own with `drop_of`, and the change it puts back gets `dropped_by`), `pass_sign_offs` (a sign-off waiting on an open hold, one per task), `passes.shared_landed`, `close_step`, `close_plan`, `stacked_on`, `closed_at`, `settled_at`, `reviewed_sha` and `notices` (the header's), and `batches.pr_draft`. `store/pass-shared.ts`: `insertHold` numbers the hold after every hold and drop of the pass in the grant's write (`maxGrantedSeq`), and the unique index refuses a second writer that numbered from a stale read; `upsertSharedChange` writes or replaces an open hold's change, `closeHold` closes it once; `insertDrop` appends a drop; `markLanded` moves `shared_landed` forward only. `store/pass-sign-offs.ts` keeps the waits. In `store/passes.ts`, `setClosePlan` moves an open pass to `CLOSING` with its plan and step 1; `setCloseStep`, `reopenClosingPass` and `closePass` write only while the pass is `CLOSING` and answer whether they did, so an Abandon that took the pass over stops a close at its next write; `settlePass` moves a `CLOSED` pass on; `getPassProgress`, `getPassPullRequest` and `getPassChecks` read what the Workbench shows. Every pass write appends `pass.changed`, and the chain's writes `pass.shared_changed`. `insertPass` makes its batch with `autoMerge` off, and `listWatchedPullRequests` follows a pass's batch with a pull request while it is `OPEN` or `FAILED`.
- `insertWorkstream` requires `first`, the model and effort of the plan's first step; there is no placeholder model. A test that has no plan passes any real model ID.
