# 02 Batch delivery

- **Status:** Locked
- **Scope:** How finished work leaves the machine: `local` delivery, and `pull_request` delivery with one branch and one pull request per batch.
- **Summary:** The design is `docs/superpowers/specs/2026-10-21-10db-batch-delivery-design.md`; its decisions and the plan's are rows 78–86 of `decisions.md`. Changes are new rows that name what they supersede. Worktree mode (**built**) is `docs/superpowers/specs/2026-10-27-10db-worktree-mode-design.md`, with its decisions in `decisions/2026-10-27-worktree-*.md`; the sections above describe shared mode, and the one below what differs.

## Where it lives

| Module                                         | Job                                                                                                                                                                                        |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `packages/db` `batches`                        | one row per batch; a partial unique index allows one unfinished shared batch (`CUTTING`, `OPEN`, `SHIPPING`, `FAILED`, `worktree_path` null) per project; worktree batches are not limited |
| `apps/daemon/src/delivery/`                    | starting (cut, join, dependency checks), shipping, the ship trigger, Ship anyway, Retry, Abandon, the launch rule, startup recovery, and worktree mode (`worktree-*.ts`, `checkout.ts`)    |
| `apps/daemon/src/git/`                         | `currentBranch`, `remoteUrl`, `fetch`, `switchNewBranch`, `switchBack`, `push`                                                                                                             |
| `apps/daemon/src/github/`                      | the `Gh` interface over the `gh` CLI                                                                                                                                                       |
| `apps/daemon/src/guard/`                       | agents never push in `pull_request` projects, and run only an allowlist of read-only `gh` commands                                                                                         |
| `apps/desktop/src/views/board/batch-strip.tsx` | the line above the board for a branch several tasks share; `batch-panel.tsx` is a task drawer's delivery section; Settings' General form and the new-project form hold the delivery fields |

Settings shows the base branch and the PR title prefix in either delivery, because it checks both fields whatever the delivery and an error must never be hidden; the new-project form shows them only for pull requests.

## Lifecycle

CUTTING → OPEN → SHIPPING → SHIPPED | CLOSED | FAILED; FAILED → SHIPPING | OPEN | ABANDONED; OPEN → ABANDONED. A refused or interrupted cut deletes its CUTTING row.

## Starting

- A start answers at once with what the daemon can check without git or the network: `400` for a batch start in a `local` project (a task start there runs as before) or an invalid body; `404` for an unknown project or task; `409` while the project's batch is `CUTTING` or `SHIPPING`, for a task that is not open, already running or parked in a human column, and for an unfinished dependency outside the batch. The parked check runs before any git work, so a refused start never leaves a fresh branch checked out. A start that passes answers `202` with a list of the batches it made or joined (`BatchStartResult`): one for the tasks that run in Your folder (`shared`), one per dependency group of the tasks that run in a separate copy (`worktree`) (`decisions/2026-10-27-batch-start-answers-an-array.md`).
- **A start follows each task's placement, not the project's** (`TaskDto.workspaceMode`; `projects.workspace_mode` is only the default a new task takes). `startBatch` checks every part first (each task is startable; no dependency joins a task in Your folder to one in a separate copy, which is refused as "Beta runs in a separate copy but needs Alpha, which runs in Your folder…", naming both tasks; the shared part is refused while the shared batch is `CUTTING` or `SHIPPING`, though a copy's batch never is; unfinished dependencies and landing per part), and only then writes, in one transaction: each task's placement, the shared batch, and every copy's batch with its workstreams. A refused start therefore leaves no batch. A fix task sent with `batchId` takes that batch's placement, written onto the task. A batch's kind is whether its `worktree_path` is set (no column), so the project's default can change while batches are unfinished without moving any of them; nothing reads the project's live setting once a batch exists. The shared cut's and switch back's lane check, and the seed copy, still read the project, not the checkout (`docs/superpowers/specs/2026-10-29-10db-task-placement-design.md`, P6 and §7, built next).
- **Start closes the window in which a placement can change** (task placement spec §5). A task's placement changes only while Start could start it, so the start makes the task look started in the same request. A new shared batch's `CUTTING` row and its tasks' `QUEUED` workstreams are inserted together, as a copy's are: the scheduler waits while the batch is not `OPEN`, the cut's lane check doesn't count `QUEUED`, and a refused cut or a restart mid-cut cancels them with the row (`deleteCuttingBatch`), so the tasks can start again. The cut's last write only records the branch and opens the batch. A join (a shared start into the `OPEN` batch, or a fix task sent with `batchId`) can't insert early, since its batch is open and the scheduler would launch the workstream before the join's checks finish. Instead the starter holds each pending join's task ids in memory from the request until the join writes or refuses; a second start of such a task answers `409` ("Beta is joining a batch…"), and so does a placement patch through the daemon's task service (`BatchStarter.refuseIfJoining`). Without this, a builder could move a `CUTTING` task to a copy and start it again, and the shared cut's last write would fail after the checkout had been switched.
- A task or batch title refuses control characters such as a newline when the task is created or edited and when a batch starts, because the title becomes the pull request's title and GitHub would refuse it only after the push.
- The git and `gh` checks run after the answer, in a background job, one at a time per queue: the project's single queue for the shared batch, and for a separate copy's batch its own cut and ship queues (below), so a copy never waits behind the shared batch. A new batch runs the cutting checks (no lane running in the project, a clean checkout, `origin`, a fetch of the base branch, `gh` installed and signed in, the GitHub repository, dependencies merged on the base) and then cuts `10db/<slug>-<8 hex>` from `origin/<base branch>`. A join checks the branch and the dependencies, and reopens a `FAILED` batch.
- Each background refusal is one inbox card whose `detail.taskIds` names the refused tasks. A join refused for its branch, an error or a shutdown also carries `detail.batchId` (one refused for unmerged dependencies does not). A refused new batch's `CUTTING` row is deleted and its workstreams cancelled. A new batch's tasks arrive as `workstream.created` events with its `batchId` when the start answers; a joined task's arrives when the join writes. The card's fold key is `start-refused:<sorted task ids>:<title>`, so starting the same tasks again into the same refusal reuses the card still open instead of adding another; the reuse rewrites the card's body and detail with the new refusal's (so it names the files in the way now), its `updatedAt` moves and an `inbox.changed` event goes out, and the Board reads that as the new refusal. Only a refused start's card asks for this (`refresh` on the flag); every other folded card's repeat is a silent no-op, since some are raised on every scheduler tick. The Board shows the refusal on the task's own card with a link to the Inbox, and "Starting…" until a run appears or the card changes; after 30 seconds with neither it says "No answer yet: check the Inbox" and Start can be pressed again.

## Shipping

- The ship trigger moves an `OPEN` batch to `SHIPPING` when its last member settles (`DONE` or `CANCELLED`); startup runs the same check. A member is a task's latest workstream in the batch.
- Ship anyway, on a failed member's card or in a task's drawer, ships a batch whose members are all `DONE`, `CANCELLED` or `FAILED`. While any member still runs, waits or is queued, it is refused with the unfinished work named, in an `OPEN` or a `FAILED` batch alike, and it never reopens a batch; a refusal on the card keeps the card open.
- Retry on a failed member's card runs that workstream again in its batch. Retry in a task's drawer acts on a `FAILED` batch: it ships settled work and otherwise reopens the batch (`FAILED → OPEN`) so the unfinished work runs and the batch ships itself.
- A project with no gate command ships without the gate step: each task was approved by the builder on its `check` card before it counted as `DONE` (`decisions/2026-10-28-optional-gate.md`). The PR body's "How it was checked" section then reads "No gate command: each task was approved in 10db." in place of the gate command block; the CI line stays.
- Abandon takes an `OPEN` or `FAILED` batch none of whose workstreams is running (in a lane, `TAKEN_OVER`, or `WAITING_HUMAN` with its session still live), cancels its unfinished members and raises a card naming the finished tasks and the local branch that holds their code. The branch is deleted if it never left its base; if it holds commits a second card names it and their count and offers Delete Branch or Keep (`decisions/2026-10-30-finished-tasks-leave-no-local-branch.md`). The drawer, the card menu and the line above the board hold Abandon back while a run is live and name it, so the refusal never surprises the builder.

## Switching the checkout back

The cut records where it found the checkout (`return_branch`, null when HEAD was detached, and `return_sha`), read under the lock it switches in. Once the batch is `SHIPPED`, `CLOSED` or `ABANDONED`, the project's queue switches the checkout back (`delivery/checkout-return.ts`, `Git.switchBack`): to the branch at its current tip, or detached at the commit. It does so only while no workstream in the project has work in hand (as Abandon counts it), HEAD still names the batch's branch, nothing is uncommitted (in the files or in the checkout's own index, which a daemon commit can leave behind when another git holds `index.lock`), the place still exists, no other worktree has the branch checked out or is rebasing or bisecting it, and nothing git doesn't track lies where the switch would write (`mergeIntoBranch`'s check). It uses `read-tree -m -u` as the cut did, and puts the batch's files back if HEAD can't then be moved. Otherwise the checkout stays where it is with one card per batch ("Your checkout stays on `<branch>`: …") saying why and, where git would accept it, the command to switch back; a checkout the builder moved off the branch raises no card, only a log line. The place is cleared once handled, so it is tried once (`decisions/2026-10-29-shared-checkout-switch-back.md`).

## Recovery

At startup, after workstream recovery and before the scheduler starts:

- Each `CUTTING` row is deleted, which emits `batch.updated` with `to: null`, with a "Batch not started" card. A cut stopped by a shutdown ends here too, because shutdown leaves its row for startup. The card carries `detail.batchId`, and its `detail.taskIds` names the row's tasks, read from its workstreams before the delete cancels and detaches them (and from a `cutting_tasks.<batch>` setting a daemon from before task placement left, which recovery then drops).
- An orphaned shipping gate is killed by its pid and start time.
- An `OPEN` or `SHIPPING` batch whose branch is not checked out fails with a wrong-branch card.
- A `SHIPPING` batch re-runs shipping from the first step, and an `OPEN` batch whose members all settled ships.
- A finished batch whose return place is still set (the daemon stopped between recording the end and the switch back) has its checkout switched back, or left with its card, as above, newest batch first.

## Worktree mode

**Built.** A `pull_request` project with `workspace_mode = worktree` gives each started task its own git worktree and branch, cut from `origin/<base branch>`, and ships it alone as its own pull request. The project's shared mode is unchanged. Decisions: `decisions/2026-10-27-worktree-mode-per-project.md` and its siblings named below.

- **The placement.** Each task stores where it runs (`tasks.workspace_mode`, `shared` or `worktree`); the project's `workspace_mode` is the default a new task takes, and `worktree` needs `pull_request` delivery. A start follows the tasks (see Starting), so one project holds one unfinished shared batch and any number of worktree batches at once. A batch is one task, or one dependency-linked group, with `batches.worktree_path` set; the unique index allows one unfinished shared batch beside any number of worktree batches. A start of several tasks in separate copies makes a batch per dependency group (`delivery/grouping.ts`); a task start never joins, and a fix task is added with `batchId` to an `OPEN` or `FAILED` batch and takes that batch's placement. Starting while another batch is `CUTTING` or `SHIPPING` is allowed. Every group's request-time checks pass before any group is inserted, and each group's `CUTTING` row and its `QUEUED` workstreams are inserted together, so a second start of the same task is refused while its cut runs.
- **Where worktrees live.** `<base>/<8 hex of the data dir's hash>/<project slug>-<6 hex>/<branch leaf>`, under `~/.10db/worktrees` or `TENDB_WORKTREE_ROOT` (`decisions/2026-10-27-worktree-root.md`). The root is refused when it overlaps a checkout, the data dir or the lane temp root, or lies under a file; the daemon then exits 4 with one line, and the desktop supervisor doesn't restart it (`decisions/2026-10-28-daemon-refused-config-exit.md`).
- **The cut** (`delivery/worktree-cut.ts`), each refusal deleting the `CUTTING` row and removing what was made: `origin` exists and its push URL matches the pin and names a GitHub repo; a fetch of the base branch; `gh` installed and signed in; dependencies merged on the base; the base tree uses no filters; nothing exists at the worktree path. Not checked: lanes running in the project, the main checkout's branch or cleanliness. Then the branch (`update-ref`), `worktree add --no-checkout --lock` (with `worktree.useRelativePaths=false`, so the gitfile is absolute whatever the builder's git config says), the pin, `read-tree -m -u`, the seed copy of ignored directories by clone (`worktree-seed.ts`), for a pnpm project the dependency install under the gate sandbox (`worktree-dependencies.ts`; a failed install refuses the cut with a card), and one transaction that sets `branch`, `base_sha` and `repo` and moves to `OPEN` (`decisions/2026-10-27-worktree-creation-and-pin.md`, `worktree-seed-by-clone.md`). Before each gate its branch takes its base as origin has it then, merged and never rebased (below).
- **`checkoutOf`.** `delivery/checkout.ts` answers where a workstream works: its batch's worktree, else the project's checkout. The launch rule holds work until the batch is `OPEN` with `branch` and `base_sha` set and the worktree exists, is pinned and is on the branch; a missing worktree is one folded card naming the path (`worktree-checkout-of.md`). Area claims and per-copy hazard claims (`harness`, `deps`) are scoped to the batch, whether the scheduler takes them at launch or an agent asks with `request_claim`, and the other hazards (`migrations`) to the project (`worktree-claims-scope.md`, `per-copy-hazards-and-waiting-claims.md`); `request_claim` waits for a held claim with a card naming the holder.
- **Two queues.** Per separate-copy batch kind, cuts, joins and reopens run one at a time in one queue (`<project>:cut`), ships and cleanup in another (`<project>:ship`), and lanes run in parallel (`worktree-delivery-queues.md`). `jobKey` (`delivery/jobs.ts`) takes the batch, not the project: a batch with no `worktree_path` is in the project's single queue (its cut switches the checkout a ship reads), so a project with a shared batch and copies runs both at once. The queue a batch used stays its own if the project's default placement changes. A finished copy's `worktree_path` is cleared, so the late deletion of its branch queues in the project's queue, after the removal has run.
- **The base before every gate.** A batch's gates run in turn (`decisions/2026-10-29-batch-gates-in-turn.md`). Each task's verify gate and the shipping gate, once they hold their gate slot, fetch the base branch, then merge `origin/<base>` into the batch's branch in its worktree: a fast-forward, or a merge commit with the branch as first parent, made with no hook, filter or merge driver, and never over an uncommitted change or anything git doesn't track at a path the base adds. The fetch and the install count in the slot, not in the gate's timeout. `base_sha` moves only forward to the merged base, and each task's start with it: to the base for a task that began at the batch's base, else to the merge of its start with the base, kept at `refs/10db/<level>/starts/<workstream id>`. The worktree installs again whenever its lockfile is not the one its packages were last installed from. A fetch failure, a conflict, files in the way or a failed install leave the branch as it is: the gate runs on it, and a note heads its evidence (so the fix session reads it) and the shipping gate's failure card. A conflict also raises one card per batch naming the files, GitHub's Update branch and a hook-free command to merge by hand, and files git doesn't track in the way raise one naming them, which the gate's note tells a fix session to leave; both go once the branch holds the base. A task's kept start goes when its batch's worktree does, and the startup sweep drops any left. In shared mode nothing is merged into the builder's checkout; the note says how many commits the branch lacks (`decisions/2026-10-29-gate-with-base.md`). A conflict in a drizzle `meta/_journal.json` whose branch migration takes a number the base already gives another makes that card "must regenerate migration …", with the steps: merge, take the base's migration directory whole, run drizzle-kit generate, commit.
- **The base before the migrations hazard.** `request_claim` granting `migrations`, and a run that starts holding it, first bring the base into a worktree batch's branch the same way, in the batch's gate turn and with no install (`delivery/migrations-base.ts`), so a migration the task generates is numbered after the base's latest. A branch that can't take it gives the hazard back: the call answers `granted: false` with the instruction, unrecorded, and the conflict (or files-in-the-way) card says the task generates no migration until it is resolved; the task's own uncommitted change in the way raises no card. The builder's own checkout is never merged into, and a failed fetch grants the hazard (`decisions/2026-10-30-migrations-hazard-takes-the-base-first.md`).
- **Ship and after ship.** The shipping steps run with the worktree as the checkout: step 0, the commit count, the gate and the PR template read it, and the push runs in the main checkout. The template is read from the shipped commit through git, and a link or a file over 64 KiB is no template, in both modes (`pr-template-from-commit.md`). `SHIPPED` and `CLOSED` remove the worktree after recording the state and clear `worktree_path`; `CLOSED` deletes its branch while the tip is still `base_sha`. That removal is `remove --force --force` with no check of its own for uncommitted changes: it relies on step 0's clean check, and a re-run by recovery does too. Every finished batch's worktree, and every orphan the sweep finds clean, is kept with a card when it holds git-ignored files outside a directory the ignore rules match and outside the seeded directories, other than Finder's `.DS_Store`, such as a hand-made `.env` (`decisions/2026-10-28-worktree-keeps-ignored-files.md`). Build output known by exact name does not count either: `*.tsbuildinfo` and `.eslintcache`. An uncommitted-changes card still lists them, since its removal command deletes them, and removing a worktree withdraws its kept cards (`decisions/2026-10-29-worktree-build-output-not-loose-work.md`).
- **Retry and Abandon.** Retry of a `FAILED` batch first makes its worktree whole (kept if present, pinned, on the branch and holding an `index`; otherwise rebuilt from the existing branch) in a cut-queue job, then reopens it; a worktree with uncommitted changes on another branch is never replaced, a card names it instead. Abandon removes a clean worktree and keeps one with uncommitted changes, with a card naming the path and the command that removes it from anywhere (`git -C <main checkout> worktree remove --force --force <path>`); one git won't trust is kept too, and its trust card explains.
- **Recovery and the sweep.** At startup a `CUTTING` worktree batch has its worktree removed if git lists it (an unlisted directory only when empty) before its row and pin are deleted; an `OPEN` or `SHIPPING` batch whose worktree is missing, unpinned or on another branch fails with a card naming the path; a finished batch whose `worktree_path` is still set has its removal re-run. The sweep runs in every `pull_request` project and touches only worktrees under this daemon's hashed level locked `10db bat_...` whose batch is gone or whose `worktree_path` is cleared or names another place. It removes a clean one, with its pin when no live worktree of the batch holds it, keeps one with uncommitted changes, git-ignored files 10db didn't seed other than build output, or that git can't read with a card naming it, and then prunes. A project or entry git refuses is logged and skipped, so startup goes on (`worktree-removal-and-sweep.md`). Then an `ABANDONED` batch whose worktree is gone but whose branch is still local has that branch settled as Abandon would: deleted at its base, else offered on one card, unless the builder already answered that card (`decisions/2026-10-30-finished-tasks-leave-no-local-branch.md`).

## Guard

- In a `pull_request` project an agent's `git push` is denied. In every project an agent runs only an allowlist of read-only `gh` commands, and `gh auth status --show-token` (or `-t`, alone or in a flag cluster) is denied in both delivery modes because it prints the token.
- The guard reads a command's literal words. A flag held in a shell variable passes (`T=-t; gh auth status $T`), as a force flag held in one passes the `git push` rule in a `local` project. The guard is defense in depth for a cooperative agent, not a sandbox.

## Invariants

- The batch row exists before any git side effect; the branch is checked before every launch and every ship.
- The daemon switches branches only when no lane runs in the project, to cut a batch's branch and to switch back when it ends; agents never do.
- The shipping gate shares the daemon's gate slots with every lane's verify gate (one at a time by default, `TENDB_GATE_SLOTS`): it waits for a slot, then its timeout starts (`decisions/2026-10-28-gate-slots.md`).
- Shipping steps (branch and clean check, commit count, the base, gate, push, find-or-create PR, record) are each safe to repeat; recovery re-runs them from the first.
- Every network call runs in the login environment with prompts off, a timeout and an abort signal: 2 minutes for a fetch or a `gh` call, and the gate's timeout (30 minutes by default) for the push, which runs the clone's pre-push hook. Fetch and push run in a process group of their own; a timeout or an abort kills the group, so the hook's children stop with git. A push stopped by its timeout fails the batch with a card that says the push or its pre-push hook ran past the limit. The shipping gate's group is killed the same way on its timeout, and by pid and start time at startup if a crash orphaned it.
- Every refusal the request can't answer is an inbox card that says what to fix, and nothing is pushed.

## Not covered

- A fork whose clone also has an `upstream` remote. `gh repo view` without `-R` picks the base repository by remote priority (`upstream`, then `github`, then `origin`), so the batch would record the parent repository while the push goes to `origin`. `docs/open-items.md` tracks it with the spec's §9 "Later" items.
