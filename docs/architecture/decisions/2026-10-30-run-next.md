# The builder can put a queued task first in line for the next free lane

- **Date:** 2026-10-30

## Decision

A started task waits for a lane in the order its workstream was created. Run Next
(`POST /tasks/:taskId/run-next`, `runNext` in `packages/db/src/store/workstreams.ts`) stamps the task's QUEUED
workstream with `workstreams.run_next_at` and answers the workstream and the titles of the task's dependencies
that are not done (`RunNextResult`). `queueOrder` (`packages/contracts/src/run-next.ts`) is the one order: stamped
workstreams first, the latest press leading, then the rest by creation time and id. The scheduler walks the
queued workstreams in that order, and the Board numbers each queued card's place in line with the same function.

The stamp is cleared when the workstream gets its lane, so a run that is queued again later (a usage pause that
ended, a retry) waits in the order it was started. Run Next on a task whose latest workstream isn't QUEUED is a
`ConflictError`. The Board offers it only for an open, unparked task whose run is queued.

A task whose dependencies aren't done keeps its stamp and takes no lane until they finish, as before; the others
launch meanwhile. The answer says so, and the Board tells the builder the task "will run once <dependencies> are
done, before the other queued tasks".

## Why

The order lives only in the scheduler's walk, so a single nullable timestamp on the row is enough: no queue table,
no renumbering, and two presses order themselves. Clearing it on launch keeps Run Next a statement about the next
lane, not a lasting priority. Caps, claims, account blocks and branch checks are unchanged: a pushed task still
waits for any of them, and the next task in line launches in its place.
