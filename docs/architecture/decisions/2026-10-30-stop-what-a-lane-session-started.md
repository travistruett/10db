# A lane session's processes are stopped when it ends, and after a daemon that died

- **Date:** 2026-10-30
- **Amends:** decision 132 (the gate kills its process group; lane commands had no equivalent)

## Decision

- **Watch the tree while the session runs.** `sandbox/lane-processes.ts` samples the process table (`ps -axo pid=,ppid=,pgid=,lstart=`, one reading shared by all sessions, every second) from the moment Claude Code reports its pid; the first reading is taken fresh, since a shared one may predate the session's process. It remembers every process under the session's pid, everything below those, and everyone in their process groups, by pid and start time. When the session's start time couldn't be read as it started (one failed `ps -o lstart= -p`, likeliest on an overloaded Mac), the watch still starts: it takes the start time from its own reading of the table, read fresh on each sample until one lists the pid. The session's process is the daemon's child and runs until the session ends, and nothing is read for it after the end, so the pid in that reading is its own. The runner logs a warning while no reading has listed it; if none ever does, the end rejects and that is logged too, so a session's leftovers are never left running without a word.
- **Name the jobs of commands that return at once by what they hold in the lane's own temp dir.** `pnpm dev &` or `(while :; do :; done) &` as its own call forks the job and its shell exits within milliseconds, before any sample, so the job is a child of launchd in a group nobody saw. Each sample (and the end) also takes every child of launchd started since the session's process began and not judged before, and reads its open paths once (`lsof -w -n -P -Fn -p …`: working directory, program, open files). One that holds a path in the session's own temp dir (`CLAUDE_CODE_TMPDIR`, by its name and its real path) is the session's, with its tree and group. That covers a job that works there, and a job with no redirection of its own, which inherits the command's stdout: Claude Code's per-command output file, which lives in that dir. Working in the checkout never makes a process the session's. In Your folder (shared) mode and for local delivery the checkout is the builder's own, where several lanes and the builder work at once, and a batch worktree is shared by the batch's lanes. A job found there may be another running lane's dev server or the builder's `nohup pnpm dev &`.
- **Stop it all when the session ends**, however it ends (finished, cancelled, handed off, the daemon stopping): in the runner's `finally`, after the Claude Code process is gone and before the temp dir is removed, `LaneSession.endProcesses()` reads the table again (and looks for new orphans once more), sends SIGTERM to each remembered process and its group, waits 1.5 s, sends SIGKILL to what is left and repeats up to four times for what forked meanwhile. A failure to read the table is logged and the session still ends, but its ledger is kept for the next start to act on.
- **Survive a daemon restart.** Each session keeps a ledger, `10db-proc-<daemon pid>-<hex>.json`, in the sandbox temp root, named for the daemon that runs the session as the daemon's mark (`10db-daemon-<pid>`) is. A lane's Bash can't write there, and the file-access judge refuses a file-tool write anywhere in the temp root but the session's own temp dir, with no card: a ledger the builder let a lane write would make the next start signal any process. At start, right after the temp root is claimed and before recovery and before any session or gate, `reapLaneProcessLedgers` stops what each ledger names and removes it, unless the ledger's owner is another daemon that still runs (its pid is alive and its mark is in the root): that daemon's session is live, and its ledger is left alone. A dead daemon's ledgers are reaped even while another daemon shares the root, so a second daemon on another data dir never keeps a restarted one's leftovers running. A ledger with this daemon's own pid is a dead one's that had the same pid, since no session has started yet. A machine whose table can't be read leaves the ledgers for the next start.
- **Never signal what is not the lane's.** A process is signalled only while its pid and start time match what was recorded (a recycled pid is left alone). Never launchd, the daemon, or the daemon's own process group, even if a session process shares it (that process is signalled by pid). The process environment is never read.
- **A command that starts an endless background loop raises a permission card.** `guard/background-loops.ts` reads a Bash command's quotes, comments and operators (and follows `sh -c` and `eval`, and skips wrappers with their options, `nice -n 19`, `env -i`, `caffeinate -i`, `stdbuf -oL`), in time linear in the command, as it runs on the daemon's only thread: a `while :`, `while true`, `until false`, `for ((;;))`, `yes`, `cat /dev/zero`, `dd` from `/dev/zero` with no count, or an interpreter one-liner that loops forever, with an `&` (or `coproc`) puts it in the background. So does the Bash tool's own `run_in_background` flag, which runs the whole call in the background (30 minutes by default, two hours at most), so such a loop anywhere in a call with the flag is asked about too. Any flag value but an absent or false one counts, so a spelling Claude Code reads as true is not missed. The broker asks about it like a hazard, but no stored rule answers it and its card offers only allow-once and deny, so no answer stores a rule that would let the next loop run unasked. The same loop in a foreground call, with no `&` and no flag, is not asked about: the lane waits for the call, which ends with the loop or at the tool's timeout.
- **A denial covers equivalents, and lasts the workstream.** The text a lane gets names the denied call and says an equivalent (another program, loop, script, wrapper, tool) is denied too, with the builder's note. Every later session of the workstream is told in its prompt (and after a compaction), from the denied permission cards in the database (`deniedPermissionsForWorkstream`, the newest 20, each clipped to 400 characters). No new table.

## Why

On 2026-10-29 a lane ran a command that started twelve `(while :; do :; done) &` loops, then 10db restarted for an app install before the command ended. The loops lost their parent, went to launchd and ran for ten hours at about 55% CPU each, which put the Mac at load 170 and made gates fail on timeouts. The gate already killed its process group; a lane's commands had nothing like it. The same lane had just been denied a `yes` loop, and the broker allowed the `while` form without a card.

- A walk down from the session's pid at the end finds nothing: orphans have launchd as their parent. So the tree is remembered while the parents are alive, and the process group (which outlives its leader) catches what forked after the last sample.
- Spawning Claude Code as a process group leader would put commands in one group only if Claude Code leaves them there; it does not promise that, and a changed spawn would change how a hard daemon kill ends the session. Sampling and the ledger don't depend on it.
- The ledger sits in the temp root, not in the lane's temp dir, because a lane could rewrite its own and make the next start signal anything.
- Reading each process's environment for the lane's `TMPDIR` would name every orphan, including a double-fork between samples, but a process environment holds the project's secrets and is read by nothing else in 10db. A process's open paths are not secret. The lane's temp dir is its own: no other lane and no builder process works there or holds its files, so a path there is lane-owned evidence. Only children of launchd started since the session began are read, each once, so the cost is one `lsof` when such a process appears.
- Naming a job by a working directory in the checkout was tried and rejected. A lane's job and another running lane's or the builder's look the same there. When one session ended it would have stopped another lane's live dev server, or the builder's own background job.
- The known gap: a job whose command returned at once, works in the checkout, and redirects its own output out of the temp dir (`pnpm dev > dev.log 2>&1 &`), so that it holds nothing in the temp dir. Also a process that within one sample leaves the session's tree, its groups and its temp dir (`cd / && setsid …`), or a job started in the last moment before a daemon dies hard, before any sample wrote it to the ledger. The permission card for an endless background loop says 10db tries to stop such things, not that it will.
- A ledger named for its daemon lets a start tell a dead daemon's leftovers from a live one's sessions without waiting for every other daemon to stop. Skipping the reap whenever another daemon was alive left a restarted daemon's loops running for as long as the other one lived.
- A call the Bash tool runs in the background doesn't block the lane, so it is the same load as an `&` with no `&` in its text: twelve `while :; do :; done` calls with the flag hold twelve cores for as long as their timeouts while the session goes on. It is also the obvious next try after a denied `(while :; do :; done) &`.
- A denial that lives in the session's tool result is gone with the session. The permission cards are already stored with their answer and note, so a query reads them back.
