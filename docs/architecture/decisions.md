## Repository governance

Decided in `docs/superpowers/specs/2026-10-14-10db-repo-governance-design.md` §2, which gives the reasons. The numbering is the spec's and independent of the decision log below.

| # | Decision | Enforced by |
|---|---|---|
| G1 | No contributor agreement; Apache-2.0 §5 covers contributions. | `CONTRIBUTING.md` |
| G2 | Conventional Commits with a fixed, required scope list. | `commitlint.config.js` on every commit; the `policy` job on the PR title |
| G3 | Squash merge only; the PR title becomes the commit on `main`. | `.github/repo-settings.json`, `.github/rulesets/main-protection.json` |
| G4 | Signed commits on `main`; GitHub signs squash merges. | `.github/rulesets/main-protection.json` |
| G5 | lefthook git hooks, installed by the root `prepare` script. | `lefthook.yml` |
| G6 | mise pins every non-npm tool with checksums and replaces `.node-version`; CI uses the same file. | `mise.toml`, `mise.lock` |
| G7 | Renovate for dependency updates, batched: one PR for every non-major update before 6am Monday (Pacific), lock file maintenance monthly, a major only after its box is ticked on the Dependency Dashboard, and a release used only once it is 3 days old. Security fixes skip the schedule. | `renovate.json`, `tests/repo/src/governance.test.ts` |
| G8 | One SemVer version for the repo, from `0.1.0`, released by release-please in manifest mode. | `release-please-config.json`, `.release-please-manifest.json` |
| G9 | macOS releases are Apple Silicon only, signed, notarized and stapled. | plan `05-release` |
| G10 | Rulesets and repo settings live as JSON and are applied by `make github-settings`. | `.github/rulesets/`, `.github/repo-settings.json`, `scripts/github-settings.mjs` |
| G11 | The pre-existing commits are reworded to Conventional Commits before the first push. | plan `04-go-public` |

How M0 implements them, where the spec leaves a choice:
- The commit scope is required (`scope-empty: never`), so every commit names its area.
- The pre-push hook refuses updating or deleting the remote `main`, but allows creating it, which is the new repository's first push.
- `main` has two rulesets, because a ruleset bypass skips every rule in that ruleset. `main-protection` has no bypass actors: PRs only, squash, linear history, signed commits, no force push or deletion, the five required checks and resolved conversations bind everyone, the admin included. `main-review` holds only the code-owner approval, and the repository admin can bypass it on a pull request, so Travis can merge his own PRs without a second reviewer but never before the checks pass.
- release-please's PR title is `chore(repo): release ${version}`, because its default scope `main` isn't on the list.

## Decision log

| # | Decision | Why |
|---|---|---|
| 1 | The first slice is the factory loop: board → batch → managed sessions → automatic handoff → inbox → verified done. | It removes most of the traced manual steps. |
| 2 | Clean handoff at a context threshold is the default. Compaction is only an emergency fallback, and is logged. | A fresh, curated context is cheaper per turn and leaves a structured record. Blocking compaction outright fails requests during context-limit recovery. |
| 3 | Managed headless sessions are the default. "Open in terminal" is an explicit, serialized takeover. | Structured events power the inbox, like the Codex app. A session is never driven two ways at once. |
| 4 | Claude first. The session interface is designed for several providers, and Codex is the next adapter. | Claude subscription use is documented as allowed. Codex's third-party terms are unknown and its app-server is experimental. |
| 5 | The runtime is the official TypeScript Claude Agent SDK, pointed at the user's installed `claude` binary. Raw `claude -p` stream-json is the fallback adapter. | Typed events, a permission callback, hooks as functions, resume by id, context usage. The least protocol code to own. |
| 6 | 10db's SQLite owns tasks, decisions, deviations, handoffs, proposals, sessions and events. Agents write only through MCP tools. Markdown is exported, never authoritative. | One writer per concept. gbrain's Markdown-plus-DB design was its largest source of drift bugs. |
| 7 | The harness is injected at launch: plugin dir, settings and per-session MCP config. Repos keep only `AGENTS.md`. | One version to maintain, nothing to copy between repos, and the same behavior on every machine. |
| 8 | Tauri 2 shell, a TypeScript daemon, one pnpm monorepo. | The builder's choice. TypeScript everywhere except a thin Rust shell. |
| 9 | No LangGraph or Pydantic AI. A hand-rolled state machine sits behind an interface. | Claude Code is the agent; 10db needs only a status workflow. A framework adds a second language and a second source of truth. |
| 10 | SQLite (WAL) via Drizzle, with FTS5 and no embeddings. | It is mature and can be inspected live with `sqlite3`. gbrain's PGlite record shows unclean-shutdown corruption, deadlocks and lock bugs. gbrain's own evals show vector search adds little over keyword search. |
| 11 | Picker: rules choose candidates, then a skippable PM-agent review, then the builder approves. | Rules are fast and predictable. Some judgment helps. |
| 12 | The pilot project first, then 10db manages its own build. | Real backlog and real pain first, then dogfooding. |
| 13 | One shared checkout per repo, enforced (§8). Worktrees come later, per task. | Worktrees duplicate Docker, databases and ports, and complicate QA. The real collisions were git and staging collisions, which serialized git fixes. Claims schedule work; they don't sandbox it. |
| 14 | Kanban board plus brainstorm. Brainstorm suggestions are pending proposals, never applied silently. | Planning in the same place. Proposals are the mechanism PDF intake reuses. |
| 15 | Personas, flows and per-project teams are configurable. Humans are team members, with routing rules. | Different projects need different spend and specialists, and questions route to the right human. |
| 16 | No named tiers. Each step is right-sized to the cheapest model and effort at or above its need, under the project's budget ceiling, escalating on failure. | This matches the model-and-effort mental model, and the frontier can be visualized later. |
| 17 | The knowledge layer has decisions, principles and facts with you, project or area scope. Agents only propose principles. Supersession is by a fixed key. Every write needs provenance. | Learned from an earlier private knowledge repo and gbrain. It stops repetition across projects. |
| 18 | Keep the Mac awake while lanes run. | It retires the `caffeinate` tab. |
| 19 | Apache-2.0. | Permissive, with an explicit patent grant and contribution terms. |
| 20 | Type-aware ESLint (typescript-eslint strict-type-checked), Prettier, the strictest TypeScript, enforced boundaries, knip, exact pins, and zod at every boundary. | The builder wants really robust, modern, idiomatic code, and type-aware rules catch daemon bugs. |
| 21 | TypeScript 7 (`tsc`) typechecks; the TypeScript 6.0 API is installed alongside under the `typescript` name (`npm:@typescript/typescript6`) for ESLint and knip. Drop the alias when typescript-eslint supports the TypeScript 7.1 API. | TypeScript 7 is much faster but ships no compiler API until 7.1; typescript-eslint requires `typescript` < 6.1. This is the side-by-side setup the TypeScript team recommends. |
| 22 | Node 26 (pinned 26.11.1) instead of Node 24. | Node 26 becomes LTS on 2026-10-28 and Node 24 enters maintenance on 2026-10-20; the builder prefers the most modern stable toolchain. |
| 23 | TanStack Router with code-based routes, not file-based generation. | No generated route tree to drift-check; four routes don't need a generator. |
| 24 | React Compiler through Babel (`@rolldown/plugin-babel`), not the Rust compiler in `@vitejs/plugin-react`. | The Rust React Compiler is marked experimental; the Babel one is stable. Revisit when the Rust one is stable. |
| 25 | Import boundaries are enforced with `no-restricted-imports` patterns, not `eslint-plugin-boundaries`: workspace packages through their entry point only (M0), and daemon modules through their `index.ts` only (M1a). | Workspace imports resolve through package exports, which the boundaries plugin can't see without an extra resolver; the daemon's modules are one flat level deep, so two path patterns express the rule exactly with no extra dependency. |
| 26 | `eslint-plugin-jsx-a11y` runs on ESLint 10 through `@eslint/compat`'s `fixupPluginRules`, with a pnpm peer-rule allowance. | Its last release declares ESLint ≤ 9; the shim restores the context APIs ESLint 10 removed. Revisit when it publishes ESLint 10 support. |
| 27 | Permission grants live in a `permission_rules` table (project or workstream scope, tool, optional command prefix). An allow (base, gate or stored rule) only covers a plain command segment: no redirection beyond `2>&1` or `>/dev/null`, no `NAME=value` prefix, no `$` or backtick, no command-carrying wrapper flags; anything else raises a card. "Always for this project" on a command with no safe prefix acts as allow-once. | Spec §7's "always for this project writes an allow rule" needs a home; a table is queryable and auditable, unlike settings JSON. A rule that matched a prefix of a compound or expanded command would approve more than the builder saw. |
| 28 | Flag, proposal and review cards close straight to RESOLVED when answered; only question and permission cards deliver to waiting sessions. In M1 a review card only acknowledges; reopening work from it arrives with flows in M2. | They have nothing to deliver; skipping DELIVERING keeps recovery's redelivery pass to cards that need it. |
| 29 | The workstream state machine lives in `@10db/contracts`, not the daemon. | The database layer enforces it on every transition and the UI can show which actions are allowed; both import the same table. |
| 30 | `commit` stamps a `10db-Op: <opId>` git trailer and checks for it before committing. | It makes a retried commit idempotent even when the daemon crashed between the git commit and recording the operation. |
| 31 | One shared daemon log (`logs/daemon.log`, rotated at startup past 10 MiB, 5 kept) with `workstreamId` on every runner line, instead of a file per workstream for now. | The Factory detail view (M2) is the first reader of per-workstream logs; filtering by field covers M1 debugging. |
| 32 | Hazard claims are exclusive per hazard name (two workstreams can't both hold `deps`), not one hazard workstream per repo. A hazard command matches on its words with flags and flag values dropped, so `pnpm -w add`, `pnpm --filter x add` and `pnpm i` need the `deps` claim too. Git is an allowlist (read-only verbs, branch listing, `push` with its own checks). The guard is defense in depth for a cooperative agent, not a sandbox. | The spec's "hazard work never runs in parallel" is met per hazard; a repo-wide hazard mutex would serialize unrelated migrations and dependency work. Revisit if real collisions say otherwise. A literal prefix match was trivially bypassed by a flag before the subcommand. Git through 10db's commit tool, claims and the watcher are the other layers. |
| 33 | `inbox.answer` applies what an answer implies in the answer's own transaction: permission rules for `allow_workstream` / `allow_project`, and a proposal's status and rationale. An `allow_once` that arrives after the workstream was parked becomes a one-time allowance for the identical call in the resumed session. | The asking session may have been parked before the builder answered, so the broker can't be the only place a choice takes effect. |
| 34 | Recovery signals a stored pid only while its OS start time (`ps -o lstart=`, recorded when the session or gate started) still matches; a running gate's process group is recorded on the workstream so recovery can kill it. | After a reboot a stored pid can belong to an unrelated process; a detached gate survives `kill -9` and would otherwise run twice in one checkout. The `started` session event is unchanged, because the daemon looks the start time up itself. |
| 35 | A clean stop writes `daemon.clean_shutdown` to `app_settings`; the next start passes it to recovery, which then keeps `recoveryAttempts` unchanged. A session that ends in `handoff` or `step_done` resets `recoveryAttempts` to 0. | Spec §5.4 counts failed attempts: quitting the app three times must not fail a long task, and the limit is about consecutive failures, not lifetime ones. |
| 36 | Claims are released when the workstream reaches DONE, CANCELLED or FAILED (including a recovery that fails it), never by lease expiry. `claims.lease_expires_at` follows the workstream lease for diagnostics. | Claims belong to the workstream, recovery re-queues the same holder, and every terminal transition releases them, so expiry would only add a race. Spec §8.1's "released when the lease expires" needs rewording to match (open item). |
| 37 | The daemon ships as the pinned Node binary itself (Tauri `externalBin`), plus `daemon.mjs`, migrations, the harness plugin and the `better-sqlite3` addon as resources, rather than a Node single-executable application. | Same size as a SEA, keeps ESM and top-level await, and loads the native addon with a plain `nativeBinding` path instead of SEA asset extraction. Spike 8 has the measurements. |
| 38 | The login-shell environment is captured at every daemon start and held only in memory, not captured once at onboarding and stored. | It routinely holds secrets (tokens, keys). Re-capturing per start also picks up PATH changes without a settings screen. |
| 39 | Managed sessions use `settingSources: ['project']` and `strictMcpConfig: true`, and the adapter registers the servers from the target repo's `.mcp.json` next to 10db's own `10db` server once the builder has approved each one (decisions 52 and 53). A repo server named `10db`, or any name starting with `10db` or containing `__`, is dropped, 10db's server keeps the name, and a flag card says so. | `user` would load the builder's own hooks and plugins (spec §3 excludes them), and `local` (`.claude/settings.local.json`) can switch billing to Bedrock. Strict MCP keeps the builder's user servers and claude.ai connectors out, while the repo stays the source of truth for the project's own tools. Registering the servers in code lets the daemon validate the file, gate each server and expand its variables itself (decisions 50, 52 and 53). `mcp__10db__*` is allowed without asking, so no repo server may produce a tool name under that prefix. |
| 40 | Auto-compaction stays enabled as the emergency fallback; 10db logs each `compact_boundary` as a deviation and re-injects the context pack. | Spec decision 2. Blocking compaction fails requests during context-limit recovery. |
| 41 | A rate-limit event with `isUsingOverage: true` is treated as a usage-limit pause, the same as `rejected`. | On a subscription, silently spending extra usage is a billing switch. The builder can resume deliberately; a setting to allow overage can come later. |
| 42 | The Tauri shell spawns and supervises the sidecar with `std::process::Command`, not `tauri-plugin-shell`. | Supervision needs the pid, SIGTERM and exit codes. The shell plugin adds a JS-visible capability surface 10db doesn't use. |
| 43 | The sidecar listens on port 0, and the shell and UI find it through `daemon.json` and `ui-token`. The CSP allows any loopback port. | There's no clash with a dev daemon on 4317, and a restarted sidecar is found again after a crash. |
| 44 | The gate runs in the session environment built for the project, not the daemon's own `process.env`. | A Bedrock or `TENDB_*` variable in the daemon's environment must not leak into a project's gate command. |
| 45 | The watcher never blocks; it flags writes `git status` still reports that fall outside every active claim, and writes inside a claim whose holders have no live session (attributed to the live workstream when there is exactly one). With several active workstreams in a project it names all of them as candidates. More than 50 ordinary strays in one batch fold into one bulk flag. Sensitive paths (`.git/config`, `.git/hooks/**`, `.git/info/**`, and `.claude/**`, `.codex/**`, `.env`, `.env.*`, `.mcp.json`, including moved-in directories and symlinks) are flagged even when git ignores or omits them, and always get their own card, never a place in a bulk card. At the end of a step it diffs `git status` against the claims of every unfinished workstream except one a human took over, plus the ending workstream's own; a write inside a waiting, paused or queued lane's claim is left to the real-time batch, which reports it as a write inside another workstream's claim. | FSEvents can't attribute a write to a process. The guard already blocks Edit and Write outside claims; the watcher catches Bash-made writes. A write that can change what runs, or hide later writes, must not be buried in a bulk card or dropped because git ignores the file. A lane that edited inside its own claim and then stopped to wait made that write itself, so another lane's step end must not be blamed for it, and the card would come back after every dismissal. |
| 46 | The event-stream WebSocket refuses upgrades whose `Origin` isn't an allowed UI origin, and the browser dev loop uses a random per-checkout token, never a committed one. | Browsers don't apply CORS to WebSockets and the stream takes its token in the query string, so a page on another origin could otherwise read every event from a known token. |
| 47 | A managed session's billing is checked against the project's billing mode (`SessionSpec.billingMode`), never against a mode inferred from its env. Before `claude` starts, the adapter refuses a session whose repo `.claude/settings.json` sets env names in the refused families or credential-helper keys (decision 54). The check then runs in three places: `accountInfo()` before the prompt is sent, `apiKeySource` at the first `init`, and every tool callback, which waits for both. The repo's settings file is re-checked after every tool call (`PostToolUse` and `PostToolUseFailure`) and on `ConfigChange`, and a change that adds a refused key, or makes the file unreadable or invalid, halts the session (`ConfigChange` acts only on `project_settings`). A subscription needs a first-party provider and a non-empty `subscriptionType`, whose value is never compared to a plan name; `apiKey` mode needs a first-party provider too. A failed check ends the session as `billing_refused`, which fails the workstream at once, with the refusal as its failure card; it is never retried as a crash. | A check after the prompt bills at least one request the wrong way. A retry meets the same credentials and settings, so it can only be refused again, up to the recovery limit. A check against the env itself can't catch a builder regression. The repo's committed settings can add an `env` block after the env was built, and a tool can rewrite that file mid-session. |
| 48 | The watcher keeps only paths `git status` still reports as changed when a batch runs, except sensitive paths (decision 45), which are flagged whether or not git reports them. Its `git status` runs with `-c core.fsmonitor=false`. | A committed file already went through the claim-checked `commit`, and its claim may be released within the batch window. The same check drops gitignored files and directories, with no separate `check-ignore` call. A repository's own config can name a `core.fsmonitor` program that git would run on every status. |
| 49 | A continuation session hands off at `max(handoffPct, first reading + 5)`, not at `handoffPct` alone. | A low threshold below a session's starting context would otherwise hand off every new session at once. |
| 50 | The daemon reads the repo's `.mcp.json` strictly. Each server is `{ type?: 'stdio', command, args?, env? }` or `{ type: 'http' \| 'sse', url, headers? }`, and any other field fails the file. The file must be a regular file under 256 KiB, server names match `^[A-Za-z0-9_-]{1,64}$`, URLs are http or https, and header names are HTTP tokens. The daemon expands `${VAR}` and `${VAR:-default}` itself, only for names the server's approval lists (decision 52); an expanded value may hold no `${`. An unreadable file or invalid JSON fails the session start with a folded flag card. An unapproved or unset variable fails that server only, with a flag card naming the server and the variable, and the session runs without it. | Claude Code merges its own environment into a stdio server's and may expand variables itself, so the daemon resolves every value and hands over plain strings. A silently shorter server list would look like a working session, so every left-out server is named. A field such as `headersHelper` runs a command, so it is refused rather than dropped. This replaces an earlier `${ANTHROPIC_*}` denylist, which missed the subscription token (`CLAUDE_CODE_OAUTH_TOKEN`) and AWS credentials. |
| 51 | Tools from repo-declared MCP servers get no allow rule from 10db. Each call goes through `canUseTool` and the permission broker, so it becomes a permission card unless a workstream or project rule already covers it. The repo's own committed `.claude/settings.json` permissions win: an allow rule there approves the call without a card, as infrastructure as code (the builder's choice, 2026-10-15; adding a project to 10db is the trust step). 10db's `PreToolUse` guard still runs on every call, so claims are enforced either way. | A repo can declare any server, and the builder decides what its tools may do, as for any other tool. Spike 4 confirms that `canUseTool` sees `mcp__<server>__<tool>` calls. |
| 52 | A repo `.mcp.json` server runs only after the builder approves it for the project, on an inbox card that shows the server's name, transport, the full launch line (declared env assignments with their unexpanded values, command, arguments) or the URL with header names and unexpanded values, and the names of the variables it reads, with credential-like names flagged. The card says when the env block replaces `PATH` or `HOME`, and renders every repo-controlled string through one set of unsafe characters (control, bidi, zero-width and line-separator characters, shown as `\u{…}`), shared by the two renderers `visible` and `word`. The approval is keyed by the SHA-256 of the server's normalized, unexpanded config, so any change asks again; a denial lasts until the config changes. An unapproved or denied server doesn't block the session: it starts without the server, and the prompt and the log name every server left out. An unapproved server's card stays open in the inbox; a denied server raises nothing on later sessions. | The stdio `command` is spawned and HTTP servers are contacted at session start, before any tool call, so `canUseTool` (decision 51) never sees them; a cloned third-party repo could otherwise run `npx -y <anything>` or send a header to any URL on the first session. Claude Code itself asks before using project-scope servers, and `strictMcpConfig` skips that prompt. A card that shows less than what runs, or lets a hostile string reshape itself, would turn the approval into a rubber stamp. Blocking the session on the card would stall every lane in the project on one unanswered card; a missing docs server rarely stops the work, and the note tells the agent to say so in its handoff if it does. Per-variable approval is left to M2. |
| 53 | An approved stdio server is launched as `/usr/bin/env -i PATH=… HOME=… <its declared env> <command> <args>`, never with an `env` block, so it gets PATH and HOME from the session environment plus what its approved config declares, and nothing else. HTTP and SSE headers carry approved variables only. The SDK receives no `mcpServers` in its query options: after the billing preflight and before the first prompt, the adapter registers 10db's server and the approved repo servers with `q.setMcpServers()` over the control channel. | Claude Code builds a stdio server's environment as its own environment plus the declared `env` (read from Claude Code 2.1.300's bundle; spike 4 measures it), and its own environment is the session's: the subscription token, an API key in `api_key` mode, AWS credentials in Bedrock mode. An `env` block can add but never remove. PATH and HOME are all `npx -y @mantine/mcp-server` needs to download, start and list its tools. `mcpServers` in the query options would put the whole MCP config on the `claude` command line (`--mcp-config`), readable by any local account: expanded header values, these arguments and 10db's per-session MCP token. The control channel keeps them off `claude`'s argv. An approved stdio server's expanded env values are still briefly on `/usr/bin/env`'s argv, until it execs the server. The billing preflight (decision 47) gates registration, since `setMcpServers` runs only after `accountInfo()` matches the billing mode, but the `init` `apiKeySource` check runs after the servers start, and no billing check says whether a server can be trusted; that is why the approval and the minimal env exist. The live acceptance run checks on this route that a repo MCP tool call reaches `canUseTool` as a permission card (`repo MCP tool gated`) and that a stdio server sees only PATH, HOME and npm's own keys (`repo MCP server env`). Header delivery on the route is covered only by 10db's own HTTP MCP server, whose Bearer header every task needs to complete; the run does not test a repo server's headers. |
| 54 | A session is refused, before `claude` starts, when the repo's committed `.claude/settings.json` sets an `env` name that starts with `ANTHROPIC_`, `CLAUDE_`, `AWS_`, `GOOGLE_`, `CLOUD_ML_`, `VERTEX_`, `NODE_`, `SSL_` or `OTEL_`, ends with `_PROXY`, or is `REQUESTS_CA_BUNDLE` or `CURL_CA_BUNDLE`, or sets a top-level `apiKeyHelper`, `proxyAuthHelper`, `awsCredentialExport`, `awsAuthRefresh`, `gcpAuthRefresh` or `otelHeadersHelper`, or sets a top-level `disableAllHooks`. Env names match case-insensitively and the top-level keys match exactly, and an unreadable or invalid settings file also refuses the session, as does one that is not a regular file (a symlink, FIFO or device) or is larger than 256 KiB, which is never read. The reason names the keys, never values. | Claude Code applies a project's `env` after 10db has built the session environment, so a committed file can redirect the endpoint, the credentials or the TLS trust root while every billing check passes. The families are matched whole, so a variable added in a later Claude Code release is covered too. `disableAllHooks` would turn off the guard and the billing re-check after each tool call. The file is read at every session start and after every tool call, so a FIFO or `/dev/stdin` would block the daemon and `/dev/zero` would exhaust its memory; a symlink is refused even to a regular file, because its target can sit outside the repo and change after the check. |
| 55 | The packaged sidecar is spawned with stdin piped and `TENDB_PARENT_STDIN=1`, so the daemon shuts down when its stdin reaches EOF, which happens when the shell dies however it dies. The supervisor strips the dev and test-only variables (`TENDB_DEV_UI_TOKEN`, `TENDB_FAKE_SCRIPTS`, `TENDB_LIVE_CLAUDE`, `TENDB_SQLITE_BINDING`) from the sidecar's environment. | Spec §3: Quit stops the work. A daemon the shell no longer supervises is an orphan that keeps sessions running with nobody watching, and a shell crash or SIGKILL runs no cleanup of its own. A fixed UI token, scripted sessions or a live-Claude run set in the shell's environment must not reach the packaged daemon. |
| 56 | A model profile is provider, model alias and effort, plus its AA slug. Its scores (Intelligence, Coding and Agentic Index), cost per task (USD) and output speed come from the builder's own AA sync (decision 65); the repo ships profile definitions and slugs only. A profile the builder edits by hand becomes `manual` and the sync leaves it alone until the builder hands it back. | AA is the builder's source of truth, and AA's terms forbid committing its data. Editing by hand stays possible for a model AA hasn't measured. |
| 57 | Each role compares the score that fits it: plan, plan review and review use the Intelligence Index, implement uses the Coding Index, QA uses the Agentic Index. The router takes `minimum = max(step need, rule floor, persona minimum score)` and picks the enabled, measured profile of the project's provider whose score for the role is at least the minimum and whose cost per task is within the project's budget ceiling: cheapest first, then fastest, then lowest score. If none is within the ceiling, it picks the cheapest that meets the minimum and marks the step over budget; starting a task with an over-budget step is refused with the steps named. If no profile is measured at all for that score (no AA key yet), the step runs on the project's model and effort, pinned, and says why. A persona's model pin overrides the router, budget included, and a pinned step never escalates. | Spec §5.2.3 and decision 16; the per-role scores are the builder's choice. Refusing to start is the visible failure: running a step below its need would hide the problem, and silently overspending breaks the ceiling. The unmeasured fallback keeps 10db usable before the builder adds a key. |
| 58 | A flow is an ordered list of steps, each with a role, a need, optional skip rules and an optional persona. The skip rules are `unless_risk` (skip unless the task has one of the tags) and `unless_criteria_over` (skip unless the task has more acceptance criteria than the count). A step's persona overrides the team's binding for its role, so a flow can run two different reviewers. Three flows are seeded: `quick` (implement), `standard` (implement, review) and `full` (plan, plan review, implement, review, QA). A project defaults to `standard`; a task can name its own flow. | Spec §4 "ordered steps by role with skip rules". Declarative rules keep the picker's judgment (M2b) separate from what the flow requires; persona-per-step makes teams scale past one persona per role. |
| 59 | A workstream's step plan is resolved when the task starts and stored on the workstream. Each step holds its role, persona, profile (model and effort), score kind, need, why the profile was chosen, status, attempts, result and when it started. Later edits to flows, bindings or profiles don't change a running workstream; a persona's instructions are read when each session starts, so a fix applies to the next session. A handoff belongs to the step it was written in: a later step never continues from an earlier step's handoff. | The plan is what the builder approved (the M2b approval sheet edits it before start); instructions are guidance and should pick up fixes. A reviewer told to "continue from the handoff" of an implementer would do the wrong job. |
| 60 | Only implement steps write. Plan, plan-review, review and QA sessions get no file-writing tools in their allow list, and the guard denies `Edit`, `Write`, `MultiEdit` and `NotebookEdit`.
