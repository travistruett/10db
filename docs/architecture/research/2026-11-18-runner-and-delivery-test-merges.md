# Runner and delivery tests: merges and removals

One pass over `apps/daemon/src/runner/runner.test.ts`, `apps/daemon/src/delivery/base-update.test.ts` and
`apps/daemon/src/delivery/ship.test.ts`. A test is merged only into one that boots the same lane or
repository in the same state, and the merged test keeps the union of the checks. Every row names the
test that still covers the behavior.

## Brief

- **What changes:** 52 tests fewer that each booted a whole lane (`createTestEngine`) or a git repository
  (`createDeliveryHarness`); nothing in production changes.
- **What it buys:** `runner.test.ts` runs 207 tests instead of 255 (326 and 278 with the 71 skipped
  sandbox tests); `ship.test.ts` and `base-update.test.ts` run 148 instead of 152.
- **What could go wrong:** a merged test passes for a reason its parts did not. Two merges were tried and
  undone for that reason (below); the rest passed unchanged on the first run.
- **Measured:** the Mac was at load average 20 to 28 for both runs, so seconds are not comparable between
  them: 717 s summed test time before (`runner.test.ts`), 231 s after. CI's per-file timing comment on the
  pull request is the number to read; this pass only claims the count of lane boots removed.
- **Needed from you:** nothing.

## Merges tried and undone

- `pins the branch at the first session` into `parks a long wait ... resumes with the answer`: with HEAD
  moved the lane stays QUEUED instead of reaching DONE, so the merged test failed for a reason the two did
  not have. Kept apart.
- `hands the builder's note to that implement session` into `fails after the fix limit ...`: a retry with a
  note leaves another next action than one without. Kept apart.
