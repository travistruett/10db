# Sessions M2: one kind of session, and the first change asks where

## Brief

**What changes for you.**
- Sessions loses its tab strip. The panel lists your sessions by project. The title row shows the session's
  title, a ⌄ switcher, a meta line ("on `main` · 2 files changed"), the agent, Changes, the next git step, the
  terminal button and ⋯.
- A session reads freely and holds nothing. The first time it goes to change files, a bar above the composer asks
  **Here, on `<branch>`** or **On a New Branch**. Here works in your checkout, as a chat does today. A new branch
  carries the same conversation into its own worktree, cut from the commit you're on.
- Once files have changed, the title row offers **Commit…**, then **Open Pull Request**, then **Merge** (or **Merge
  into `main`** on a local project).
- Changes opens as a drawer from the right (⌘⇧D).
- Gone from Sessions: Do It and its sheet and brief, task tabs, the pass of one in Sessions, Sign Off, Close
  Pass, Send Reading Only and the four-way held send. Old sealed chats still open, read-only, with a link to their
  task on the Board.

**What it buys.** Sessions works like Claude Code. 10db asks one question, and only when it matters.

**What could go wrong, and how we'd know.**
- *After the move, the agent edits your checkout through old paths.* The sandbox and the hook refuse it, naming
  the worktree's path. A seatbelt test and the live checks on each provider prove it.
- *A restart, Stop, Archive or a second click lands mid-move.* Each is a row in this plan's state table, tested on
  a real store and a real git repo.
- *A chat worktree is swept or left behind.* Each place that owns worktrees learns chat owners, and each gets a
  real-git test.
- *The bar never shows for a shell-first write.* The spike (Task 0) decides per provider. Where 10db can't see the
  refusal, the agent is told to make its first change with an edit.

**Calls you might disagree with.** The coordinator made the first six, and the plan writer made the rest.
1. A new branch starts from your checkout's `HEAD`, not from `main`.
2. Open Pull Request from `main` moves the commits to a new branch, then resets your local `main` to `origin/main`.
3. Merge into `main` on a local project needs a clean checkout on `main`.
4. Push, Open Pull Request and Merge in a reading session count as Here.
5. Archive keeps the branch.
6. A branch session isn't on the Board yet. That's a follow-up.
7. The Inbox card for the choice is an ordinary **flag card with two options**. The Inbox already draws and answers
   those, so M2 changes no Inbox file and stays clear of M3.
8. The turn is interrupted by 10db's own Stop, right after the denied call, on both providers. A guard-level
   interrupt flag isn't added.
9. A failed install during the move undoes the worktree and the branch and returns to the bar with the error. A
   lane would raise a card instead.
10. Both choices start the next turn with one short 10db message ("Carry on"). It shows as a system line, not as
    your words.
11. "You moved here before your last change" is said once, from memory. A restart between the move and the next
    turn drops that one line. The standing note about where the session works always survives.
12. The pull request's state is read on demand and kept for 2 minutes per branch (the watcher's interval). The
    desktop refetches while the session is shown. Nothing polls `gh` in the background.
13. Panel search matches session titles only.
14. A chat worktree's lock reason is `10db cht_<uuid>`, since a chat's id is `cht_…`. The spec wrote `chat_`.

**Migrations:** one. It adds `chats.work_place`, `worktree_path`, `branch` and `base_head`. Tasks change
`schema.ts` and regenerate the baseline locally so tests see the columns. The coordinator regenerates it once more

## Global constraints

- Code style and testing rules as in the repo. Use `as const` objects, not enums. Use branded ids, zod at every
  boundary, and no `as` casts outside a validated boundary.
- **Every change to `chats.work_place` is a compare-and-set** on the state it expects, in one transaction with
  its event (`ChatChanged`) and, where the table says so, its Inbox card.
- **The chat's root** is the checkout while it is reading, choosing or here, and the worktree on a branch. Every
  reader of "the checkout" in `chat/` resolves the root through one function, `chatRoot(chat, project)`. Nothing
  else picks a path.
- **Only `git/` makes and removes worktrees** (`git/AGENTS.md`). Chat code calls `Git.addWorktree` and
  `Git.removeWorktree`.
- **The chat row names the worktree before the worktree exists.** `addWorktree` sets the pin during the cut
  (`git.ts:3763`), and `pinOwner` finds the owner from the database. So the `choosing → moving` write records
  `worktree_path` first.
- **Provider parity:** see the table below. Nothing in the daemon branches on the provider, except where the spike
  says a provider can't report a shell refusal.
- **Words** are git's and GitHub's: branch, commit, pull request, merge, your checkout. Never use "Your folder",
  "hold", "pass of one" or "Separate copy" in anything new.
- No new dependencies.

## State and event table

This table covers every async flow that something else can interrupt. **Test** names the task whose test covers
the row. A "turn" is a chat turn. A "holder" is a Board task (lane) or a pass that holds your checkout.

|---|---|---|---|
| reading | an edit tool call (any agent, subagent too) | CAS → choosing, with the flag card in the same write. The call is denied with "Waiting for the builder to choose where this work happens", then `engine.stop` runs | 3 |
| reading | `make_branch`, `switch_branch`, `pull`, `commit_changes` | same as an edit | 3 |
| reading | a shell write the sandbox refused | per Task 0: same as an edit, or refused by the sandbox only | 3 |
| reading | `push_branch`, `open_pull_request`, `merge_pull_request` | CAS → here, no bar. The call runs only if this turn can hold the checkout; otherwise it's refused with the holder's words | 4 |
