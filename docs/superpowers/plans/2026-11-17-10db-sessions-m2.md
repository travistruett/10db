# Sessions M2: one kind of session, and the first change asks where

## Brief

**What changes for you.**
- Sessions loses its tab strip. The panel lists your sessions by project. The title row shows:
  - the session's title and a ⌄ switcher;
  - a meta line ("on `main` · 2 files changed");
  - the agent;
  - Changes, the next git step, the terminal button and ⋯.
- A session reads freely and holds nothing. The first time it goes to change files, a bar above the composer asks
  **Here, on `<branch>`** or **On a New Branch**.
  - Here works in your checkout, as a chat does today.
  - A new branch carries the same conversation into its own worktree, cut from the commit you're on.
- Once files have changed, the title row offers **Commit…**, then **Open Pull Request**, then **Merge**. On a
  local project the last step is **Merge into `main`**.
- Changes opens as a drawer from the right (⌘⇧D).
- **Gone from Sessions:** Do It and its sheet and brief, task tabs, the pass of one, Sign Off, Close Pass, Send
  Reading Only and the four-way held send. Old sealed chats still open, read-only, with a link to their task on the
  Board.

**What it buys.** Sessions works like Claude Code. 10db asks one question, and only when it matters.

**What could go wrong, and how we'd know.**
- *After the move, the agent edits your checkout through old paths.* The sandbox and the hook refuse it, naming
  the worktree's path. A seatbelt test and the live checks on each provider prove it.
- *A restart, Stop, Archive or a second click lands mid-move.* Each is a row in the state table, tested on a real
  store and a real git repo.
- *A chat worktree is swept while you still need it, or is left behind.* Every place that owns worktrees learns
  chat owners, and each gets a real-git test. The sweep never touches a branch with no commits of its own.
- *The bar never shows for a shell-first write.* The spike (Task 0) decides per provider. Where 10db can't see the
  refusal, the agent is told to make its first change with an edit.

**Calls you might disagree with.** The coordinator made the first six. The plan writer made the rest.
1. A new branch starts from your checkout's `HEAD`, not from `main`.
2. Open Pull Request from `main` moves the commits to a new branch, then resets your local `main` to `origin/main`.
3. Merge into `main` on a local project needs a clean checkout on `main`.
4. Push, Open Pull Request and Merge in a reading session count as Here, once the judge lets the call through.
5. Archive keeps the branch.
6. A branch session isn't on the Board yet. That's a follow-up.
7. The Inbox card for the choice is an ordinary **flag card with two options**, answered through the existing
   `onFlagAnswerInWrite` hook. M2 changes no Inbox view.
8. **The first change stops the turn**, right after the denied call's answer is sent, on both providers. You'll
   see "Stopped here." in the thread, and the "replied" notification fires, as it does for any stop.
9. A failed install during the move undoes the worktree and the branch, and returns you to the bar with the error.
   (A lane raises a card instead.)
10. Both choices start the next turn with one short 10db message, "Carry on". It shows as a system line.
11. "You moved here before your last change" is said once, from memory. A restart before the next turn drops that
    line, but the standing note about where the session works survives.
12. A pull request's state is read on demand and kept for 2 minutes per branch. 10db's own Open Pull Request and
    Merge clear it.
13. Panel search matches session titles only.
14. A chat worktree's lock reason is `10db cht_<uuid>`, since a chat's id is `cht_…`. The spec wrote `chat_`.
15. Archive sends the list of files it warned you about. If more have changed since, it refuses and warns again.

**Migrations:** one new generated file, `packages/db/drizzle/0093_*.sql`, from `pnpm --filter @10db/db generate`.
- It adds `chats.work_place`, `worktree_path`, `branch`, `base_head` and `work_asked_at`.
- Tasks may generate it locally to run their tests.
- After the final merge of `main`, the coordinator drops that one file and regenerates it. M3's columns, if any,
  go in the same file.
- Migrations are forward-only since v0.1.0, so nothing else under `drizzle/` changes.

**Needed from you:** nothing to start. The live checks (Task 15) need your ChatGPT sign-in and `aws sso login`.

## Global constraints

- Code style and testing rules as in the repo:
  - `as const` objects and branded ids;
  - zod at every boundary;
  - no `as` casts outside a validated boundary.
- **Every change to `chats.work_place` is a compare-and-set** on the state it expects. It goes in one transaction
  with its `ChatChanged` event and, where the table says so, its Inbox card.
- **The chat's root** comes from one function, `chatRoot(chat, project)`.
  - It's the checkout while reading, choosing, moving or here.
  - It's the worktree on a branch.
  - A branch with no worktree reads its checkout, read-only.

  Nothing else in `chat/` picks a path.
- **Only `git/` makes and removes worktrees** (`git/AGENTS.md`).
- **The chat row names a worktree before the worktree exists.** `Git.addWorktree` sets the pin during the cut, and
  `pinOwner` finds the pin's owner in the database. So:
  - every write that leads to a cut (the move, Reopen) records `worktree_path` first;
  - every cut is idempotent by path.
- **A turn takes the folder hold only on a Here session.** This applies to `turnStarting`, to `spec()`'s `writes`,
  to `ChatService`'s `mustWait`, and to the push, pull-request and merge tools.
- **Words are git's and GitHub's:** branch, commit, pull request, merge, your checkout. Never use "Your folder",
  "hold", "pass of one" or "Separate copy" in anything new.
- No new dependencies.
