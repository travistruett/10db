# Sessions M6: the folder hold, a chat that writes in Your folder, and Do it

## Brief

**What changes for you.** A chat changes your code the way Claude Code does in a terminal. It edits files in Your
folder and runs commands that write there. It branches, commits, pulls, pushes, and opens and merges pull requests
through 10db's git tools. When a task or pass holds Your folder, the chat warns you before your message runs, and
gives you a one-click way out:
- **Wait for It.** The message runs once the folder frees, ahead of any task that hasn't started yet.
- **Send Reading Only.** The turn runs as a chat does today: it reads, and runs judged commands such as
  `pnpm test` and `tsc` under a read-only sandbox.
- **File as Tasks.** M6b adds **Do It in a Separate Copy**.

Two chats can write at once, as two terminals can, and each says the other is there.

**What it buys.** You can do the quick fix, the package bump and the commit without leaving 10db, inside its
sandbox, judge and accounts.

**What could go wrong, and how we'd know.**
- **Two writers in one folder.** Real-git tests show that no chat edit lands while a task or pass holds the folder,
  and that 10db's own git work (a batch's branch cut, the switch back, opening a pass) never runs under a chat. An
  adversarial reviewer goes after `.git`, credentials, 10db's branches, forced pushes and unjudged pull requests or
  merges.
- **Holds can last days.** A task holds the folder from its start until it ships, through waiting on you and usage
  pauses. A pass holds it until its pull request merges. Every wait and refusal names the holder and says what it
  waits for ("until its pull request merges").
- **A chat waiting on your card keeps the folder** until you answer, or until the project's wait plus 5 minutes.
  Your-folder tasks wait meanwhile.
- **Your pre-commit hooks don't run** on a chat's commits. The tools say so, and a follow-up runs your checks.

**Refusals that became warnings:**
1. **A message while a task or pass holds the folder.** It warns first and offers the choices above.
2. **Two chats** (and, from M7, a chat in your terminal). Both write, and each is told about the other. Committing
   everything while the folder is shared warns rather than refuses.
3. **A pass that has closed and waits for its pull request.** A chat's edits now run. Only commits and branch moves
   wait for the merge.
4. **A folder with uncommitted changes** never refuses a chat or Do It.

**Stops that stay, and why.** They cover only 10db's own writers and the sandbox:
- **A chat's edits and writing commands while a task runs, or while a pass is open or closing.** That task's
  commit, or the pass's sign-off, would take the chat's edits as its own.
- **`make_branch`, `switch_branch`, `pull` and `commit_changes` while a closed pass waits.** Its merge moves your
  branch by compare-and-swap, which a commit or switch would break.
- **10db's own git work waits for a chat's turn.** A Your-folder task's start, a branch cut, the switch back and a
  pass's open each wait, naming the chat, so 10db never moves your branch under it.
- **Git writes typed in the chat's shell** go to the tools, because the kernel keeps `.git` closed.
- **Filters such as LFS.** `commit_changes`, `switch_branch` and `pull` refuse when `.gitattributes` asks for them:
  10db's git doesn't run filters.
- **10db's branches** (`10db/…`, batches, passes) are refused by every git tool.
- **No forced pushes.** `push_branch` has no force option. Pushing and opening a pull request are judged, and merging
  is limit 4.

**Calls you might disagree with:**
- **Two chats share the folder.** I recommend it.
- **A turn runs on a write profile only while it holds the folder.** When that changes between turns, the session
  reopens on the other profile, resuming the same agent session. That costs a few seconds.
- **Background jobs stop when a turn ends,** so a dev server started in a chat stops too. A running job can't keep
  the folder, or it would stall your tasks. There's a follow-up for this.
- **Docker follows the project's switch,** as for lanes.
- **Claude chats turn on file checkpointing now,** so rewind has history. Codex has no equivalent.
- **The plan is split.** M6a is the hold, the writes and the git tools. M6b (Do It, Changes, a pass of one) is
  planned once M6a merges. M7 needs only M6a.

**Needed from you:** nothing. Reply to approve.

## Design

### Holders and what excludes what

| Holder ↓ \ wants the folder → | lane's first start | 10db git work | chat_turn | takeover (M7) |
| --- | --- | --- | --- | --- |
| **lane** (counted, `folderLanes`) | shares (claims decide) | today's checks (`lanesInProjectCheckout`); a batch's own row never blocks its cut or switch back | reads only, or waits | refused |
| **pass**, open or closing | waits (W9) | refused (today) | reads only, or waits | refused |
| **pass**, closed and unsettled | waits (W9) | refused (today) | writes; the four folder git tools are refused "until its pull request merges" | the same limit |
| **10db git work** (memory: a branch cut, a switch back, a pass's open, each for its git calls) | waits | one at a time (the delivery queue) | reads only, or waits | refused |
| **chat_turn** (memory, per chat) | waits, naming it | waits, naming it | **shares, warned** | shares, warned |
| **a waiting chat** (memory) | **waits** (the builder is there) | runs | n/a | n/a |
| **takeover** (`taken_over` chats) | waits | waits | shares, warned | shares, warned |

- `folderLanes` covers the tasks whose run is in Your folder, from the `STARTING` write until the run lands or
  ends, between steps too. It also covers a shared batch from `CUTTING` until its switch back has run.
- Reasons per phase, which the words carry:
  - A running lane or an open pass would commit the chat's edits as its own.
  - A lane in `WAITING_HUMAN` or `PAUSED_LIMIT` still has uncommitted work in the folder.
  - A closed pass's settle moves the return branch by compare-and-swap, and refuses commits that are on neither the
    base nor the pushed branch (`pass-settle.ts`).
- `folder-hold/exclusion.ts` is this table as a pure function, with `holderWords`:
  - "the task ‘Bump vite’ and 2 more"
  - "the pass ‘Settings pass’ (until its pull request merges)"
  - "the chat ‘Retry login’"
  - "the chat ‘Retry login’ in your terminal"
  - "10db switching Your folder back to `main`"

### The module

`apps/daemon/src/folder-hold/` (new; `AGENTS.md` beside it). Every call is synchronous.

- **`blockers(projectId, asker)`** reads:
  - `passHoldingFolder`, with the pass's state
  - `folderLanes`
  - `taken_over` chats
  - the memory entries
- **`takeTurn(projectId, chatId)`** → `{ taken, sharedWith, limits }` or `{ blockers }`. A served reservation
  becomes the turn's hold.
- **`releaseTurn`** is idempotent. It serves waiters before it returns.
- **`reserveGit(projectId, what)` / `releaseGit`** are for 10db's git work. Each returns blockers or a token.
  Only a chat's turn, a takeover and other git work exclude it; lanes and passes keep today's checks
  (`lanesInProjectCheckout`, `passHoldingFolder`), and a shared batch's own `folderLanes` row never blocks its own cut
  or switch back. `releaseGit` serves waiters, and a cut or switch back that waited retries on `FolderHoldChanged`.
  A closed pass's settle (`moveCheckedOutBranch`), the Move card's answer and the folder and Abandon cards' switches
  take `reserveGit` around the move alone, and wait for a chat's turn, since a chat may edit then. Each wait stays
  in the project's delivery slot (it is not re-queued), puts a notice on the batch naming the holder, and says other
  delivery work for the project queues behind it. Recovery at startup never waits: a busy folder keeps the batch's
  place and queues the switch back.
- **`wait`, `cancelWait`.** Serving a waiter puts a *reservation* on it and calls `engine.releaseStarts(id)`, which
  now returns whether a turn began. `takeTurn` clears the chat's own wait. A waiter served with nothing queued is
  dropped. Waiters are served again on account changes and when the update hold lifts. If none began (the chat was retired, paused, or under the update hold), the
  reservation goes at once and the chat stays a waiter (a retired one is dropped).
  `takeTurn` clears the chat's own wait. A waiter served with nothing queued is dropped. Waiters are served again
  on account changes and when the update hold lifts, not only on workstream, batch, pass and conversation changes.
- It emits `FolderHoldChanged { projectId }` on every memory change.

### When a turn takes the hold, and on which profile

- **The engine calls `turnStarting(conv)`** (an `ExploreOwnerHooks` member; not `turns.beginTurn`). It does so only
  just before it reduces a `builder_message` from a state outside `BUSY`. That covers `queued`, a parked release,
  `RunQueue` with turn starters, and the waiter served.
- **It answers `{ writes }`.**
- **A session opened able to write stays warm after its turn,** as in Claude Code, and its next turn that holds
  the folder reuses it. Between turns it keeps no call: the chat's guard denies every call from it while the turn
  doesn't hold the folder, and from any session that is not the one the chat's hold now belongs to, so an older
  session's background agent is refused even when the chat's next turn holds. When the turn ends the owner stops
  what the session's commands left running (`endJobs`), so nothing it started outlives the turn.
- **A warm session opened with the other `writes`** is idle-closed first, so the turn starts cold. It resumes the
  agent session (Claude `resume`, Codex `thread/resume`) on the profile that `writes` picks:
  - writable checkout with `.git` denied while the turn holds the folder
  - Plan's read-only profile, with today's judged commands, while it doesn't
- **Chained turns inherit** the hold and the profile. `SendNow` only adds its marker and takes nothing.
- **The engine calls `onState(conv, state)` after every reduce,** a transition or not. Outside `BUSY`, the owner
  releases: jobs stop, then `releaseTurn`. So a reduce that starts no turn frees what `turnStarting` took.
- **Invariant (rung-1 table over `reduceExplore`):** an outcome whose effects begin a turn (`Start`, `Push`,
  `NextTurn`, `StartFreshFromDigest`) always lands in `BUSY`. No state outside `BUSY` ends with a holder.

**Races, designed once:**
1. **A chat's take and a lane's start.** Both are synchronous. The scheduler reads `blockers` again inside the
   `STARTING` write, and the lane holds from that write. `runner.launch`'s async preparation is covered.
2. **10db's git work.** `reserveGit` comes before any git call (`openPassBranch`, `switchNewBranch` in the cut,
   `returnCheckout`). A chat can't take the folder between the check and the move.
3. **Release, waiters and the scheduler.** Waiters are served inside the release or the bus handler, before any
   tick. A waiting chat blocks every lane's first start.
4. **A served waiter whose turn never starts.** Its reservation is dropped in the same call.
5. **Jobs before release.** A new turn of the same chat while the jobs stop cancels the pending release.
6. **A call allowed, then the hold lost.** It can't happen: a turn keeps its hold until it ends, and the stop grace
   kills the process before the release.
7. **A restart.** Recovery stores the partial turn, and the ledger reap stops the jobs.

### Git through the daemon (M6a)

These are tools on the chat's `/mcp` token. The daemon's git and `gh` run in Your folder:
- pinned, under `withRepoLock`
- hooks off (`DAEMON_GIT_CONFIG`), with no attributes and `GIT_OPTIONAL_LOCKS=0`
- config read the pinned, trusted way
- commits carry the builder's identity and signing config

Every tool refuses when HEAD, the target branch or a PR's head is `10db/…`, a batch's or a pass's branch.

| Tool | Does | Refuses |
| --- | --- | --- |
| `make_branch {name}` | `git switch -c <name>`, keeping the working tree (not `switchNewBranch`, which refuses dirt) | an invalid ref name; a name under `10db/` or starting with `-` or `+`; an existing name |
| `switch_branch {name}` | `git switch <name>`, without force, `submodule.recurse=false` | a conflicting change (in git's words); filters |
| `pull` | fetch the upstream (`branch.<x>.merge`), check it is an ancestor, then `moveCheckedOutBranch` | diverged; detached HEAD; an operation in progress; filters |
| `commit_changes {message, paths?}` | with paths: `git commit --only -F - -- <paths>`, so other staged files stay staged. Without: `git add -A`, then commit | no changes; paths outside the checkout or in `.git`; filters. Without paths while shared it commits and its result warns, naming the other holder |
| `push_branch` | `Git.push`, current branch, origin's pinned URL, fully qualified refspec | detached HEAD; no force |
| `open_pull_request {title, body, base?}` | `Gh.prCreate`, body in a temp file, `-R` pinned | a branch not pushed at HEAD |
| `merge_pull_request {number}` | `Gh.prMerge`, on the URL built from the pinned repo and the number (squash, as 10db merges) | a PR of another repo |

- **The first four** refuse unless the turn holds the folder (naming the holder), and refuse while a closed pass
  waits.
- **Push, open and merge** stay out of `allowedTools` and reach the judge. They get a bare allow from the hook only where
  10db's judge runs, and `ask` on Claude's auto mode and on the rules floor (LC2 showed auto mode approves all three
  unasked). The chat's trust policy names a push and a PR (sending data out) as
  judged, and a merge as limit 4.
