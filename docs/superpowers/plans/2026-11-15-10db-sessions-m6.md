# Sessions M6: the folder hold, a chat that writes in Your folder, and Do it

## Brief

**What changes for you.** A chat changes your code the way Claude Code does in a terminal. It edits files in Your
folder and runs commands that write there. It branches, commits, pulls, pushes, and opens and merges pull requests
through 10db's git tools. When a task or a pass is working in Your folder, the chat warns you before your message
runs. It gives you a one-click way out: **Wait for It**, **Send Reading Only** or **File as Tasks**. M6b adds
**Do It in a Separate Copy**. Two chats can write at once, as two terminals can, and each says the other is there.

**What it buys.** You can do the quick fix, the package bump and the commit without leaving 10db. The sandbox, the
judge and your accounts stay in charge.

**What could go wrong, and how we'd know.**
- **Two writers in one folder.** A chat's edit could land in a task's commit. Real-git tests show that no chat edit
  lands while a task or pass holds the folder, and that a task's kept work holds none of the chat's. An
  adversarial reviewer tries `.git`, credentials, force pushes and unjudged merges.
- **Your pre-commit hooks don't run** on a chat's commits (10db's git runs with hooks off). The tools and the
  prompt say so, and a follow-up runs your checks.
- **A forgotten holder** stalls work. Every wait and refusal names the holder. A chat's turn is held only in
  memory, so a restart frees it.

**Refusals that became warnings:**
1. **A message while a task or pass works in Your folder.** The outline ran the turn read-only without a word.
   Now you see the warning first and pick a way out.
2. **A chat's turn while another chat writes** (or, from M7, a chat in your terminal). The outline allowed one
   writer at a time. Now both write and are told about each other, since neither one lands work.
3. **A folder with uncommitted changes** never refuses a chat or Do It. This was already the spec, and it stays.

**Stops that stay, and why** (only 10db's own writers, or the sandbox's integrity):
- **A chat's edits, writing commands, and `make_branch`, `switch_branch`, `pull` and `commit_changes` while a task
  or pass holds the folder.** That task's commit, or the pass's sign-off, would take the chat's edits as its own.
- **A Your-folder task that would start during a chat's turn** waits, naming the chat, for the same reason.
- **Passes.** A pass, or Do It Here, doesn't open while a task, another pass or a chat's turn holds the folder.
  Do It Here also refuses while a merge, rebase or bisect is in progress, because the pass's branch needs a clean
  index.
- **Git writes typed in the chat's shell** go to the tools. The kernel keeps `.git` closed.
- **`commit_changes` on a project whose `.gitattributes` asks for filters** (such as LFS). 10db's git doesn't run
  filters, so it would commit raw blobs.
- **10db's own branches.** `make_branch` and `switch_branch` refuse `10db/…` branches, which passes and batches
  read.
- **Pushes and merges.** `push_branch` has no force option, and `merge_pull_request` is limit 4.

**Calls you might disagree with:**
- **Two chats share the folder.** Recommended: yes. The cost: one chat's commit could take in the other's edits, so
  `commit_changes` needs explicit paths while the folder is shared.
- **Background jobs stop when a turn ends** (spec call), so a dev server started in a chat stops too. A follow-up
  covers jobs that should outlive the turn.
- **No Docker socket in a chat** for now, since a container could write after the turn ends. There's a follow-up.
- **A waiting chat gets the folder before a queued task**, because you're there.
- **Claude chats turn on file checkpointing now**, so rewind has history when it lands. Codex has no equivalent.
- **Split:** M6a ships the hold, the writes and the git tools. M6b (Do It, the Changes panel, a pass of one) is
  planned once M6a merges. M7 needs only M6a.

**Needed from you:** nothing. Reply to approve.

## Design

### Holders and what excludes what

| Holder ↓ \ wants the folder → | lane | pass | chat_turn | takeover (M7) |
| --- | --- | --- | --- | --- |
| **lane** (counted: tasks in Your folder, first start → landed or ended) | shares (claims and hazards decide) | refused (today's `lanesInProjectCheckout` refusal) | reads only, or waits | refused |
| **pass** (one; `passHoldingFolder`: not `SETTLED`/`ABANDONED`) | waits (W9, today) | refused | reads only, or waits | refused |
| **chat_turn** (memory; per chat) | waits, naming the chat | refused, naming it | **shares, warned** | shares, warned |
| **takeover** (`taken_over` chats) | waits, naming it | refused, naming it | shares, warned | shares, warned |

`lane` and `pass` are **10db's writers**: 10db commits what is in the folder as their work. `chat_turn` and
`takeover` are **attended writers**: they commit only when asked, by paths, as a terminal does. The table is
`folder-hold/exclusion.ts`, a pure function with one test row per cell.

**Holder words** (one function, `holderWords`, used by every wait and refusal):
- "the task ‘Bump vite’", or "the task ‘Bump vite’ and 2 more"
- "the pass ‘Settings pass’"
- "the chat ‘Retry login’"
- "the chat ‘Retry login’ in your terminal"

### The module

`apps/daemon/src/folder-hold/` (new; `AGENTS.md` beside it):

- `blockers(projectId, asker)`: the holders that exclude `asker` (`{ kind, id }`), in start order. It reads
  `passHoldingFolder`, the new `folderLanes` (`@10db/db`), the chats whose conversation is `taken_over`, and the
  in-memory turns. It is synchronous, since SQLite reads are.
- `takeTurn(projectId, chatId)` → `{ taken: true, sharedWith }` or `{ taken: false, blockers }`. It is
  synchronous. A chat that already holds keeps the hold.
- `releaseTurn(projectId, chatId)`. Before it returns, it serves this project's waiters (below).
- `holdsTurn(projectId, chatId)`, which the guard reads per call.
- `wait(projectId, chatId)` and `cancelWait`: FIFO per project. On each bus event that can free the folder
  (workstream, batch, pass and conversation changes), and on `releaseTurn`, the first waiter with no blockers is
  given the hold synchronously, inside that call. Then `engine.releaseStarts(conversationId)` runs its parked turn.
- It emits `EventType.FolderHoldChanged` `{ projectId }` when a memory holder or waiter changes, for the desktop.

### State × event table

Columns: the folder free; held by lanes; by a pass; by another chat's turn or a takeover; by this chat. "Rel." means
the session's background jobs stop, then `releaseTurn`.

| Event | free | lanes | pass | other chat / takeover | this chat |
| --- | --- | --- | --- | --- | --- |
| A turn begins (`Start`, `Push`, `NextTurn`, `SendNow`, `RunQueue`); message sent `read_only` (the default) | taken | not taken; a notice: "This turn reads only: Your folder is in use by {holder}." | same as lanes | taken, shared; a notice: "Your folder is also in use by {holder}." | kept |

**Races, designed once:**
1. **A chat's take and a lane's start.** Both are synchronous. The scheduler reads `blockers` again inside the
   `state.write` that moves the run to `STARTING`, so nothing can come between the check and the hold.
2. **A chat's take and a pass opening.** `openPass` checks `blockers` inside its write, so a take during its git
   work refuses the write.
3. **A release and a waiting chat.** The waiter is served inside `releaseTurn` or the bus handler, before any
   scheduler tick runs.
4. **A chained turn.** The owner is never told the turn ended between two chained turns, so the hold stays.
5. **Jobs before release.** `release` awaits `endJobs()` while the chat still holds the folder. A new turn of the
   same chat during that wait cancels the pending release.
6. **A call allowed, then the hold lost.** It can't happen: a turn keeps its hold until it ends, and the stop
   grace kills the process before the release.
7. **A restart mid-turn.** Recovery stores the partial turn. The ledger reap stops its jobs. Lanes may start.

### Git through the daemon (M6a)

These are tools on the chat's `/mcp` token (`ChatToolName`). They run the daemon's resolved git and `gh` in Your
folder: pinned, hooks off (`DAEMON_GIT_CONFIG`), no attributes, `GIT_OPTIONAL_LOCKS=0`. Commits carry the builder's
identity and signing config, as in their terminal. Credentials never enter the sandbox.

| Tool | Does | Refuses |
| --- | --- | --- |
| `make_branch {name}` | `Git.switchNewBranch(repo, name, 'HEAD')` | a name that `check-ref-format` refuses, one under `10db/`, one that starts with `-` or `+`, an existing branch |
| `switch_branch {name}` | `git switch <name>` without force, `submodule.recurse=false` | a batch's or pass's branch; a change that conflicts (in git's words) |
| `pull` | `Git.fetch`, then a fast-forward of the current branch (`moveCheckedOutBranch`) | a diverged branch, a detached HEAD, a merge in progress |
| `commit_changes {message, paths?}` | `git add -- <paths>` (or `-A`), then `git commit -F -` in the real index | no changes; paths outside the checkout or in `.git`; filters (`Git.filtersIn`); no `paths` while the folder is shared |
| `push_branch` | `Git.push(repo, current, net)` to origin's pinned push URL, with a fully qualified refspec | detached HEAD; there is no force option |
| `open_pull_request {title, body, base?}` | `Gh.prCreate` with `-R` pinned, head = current | a branch not on origin at HEAD ("push_branch first") |
| `merge_pull_request {number}` | `Gh.prMerge` on this project's repo | a PR of another repo |

The first four also refuse unless `holdsTurn`, naming the blocker. `push_branch` and `merge_pull_request` stay out of
`allowedTools` and reach the judge: a bare allow from the hook where a judge runs (auto mode's classifier, or 10db's
judge through `judgeCall`), and `ask` on the rules floor. The chat's trust policy names a push as judged and a merge
as limit 4. Every other chat tool runs (`CHAT_TOOL_POLICY`).
