# apps/daemon/src/sessions

- Every sandboxed lane session runs in Claude Code's `auto` permission mode (`LANE_PERMISSION_MODE` in `sessions/claude-session.ts`), unless the app-wide setting `lane_auto_mode` (`permissions/lane-auto-mode.ts`; Settings, Lane permissions) is off: the runner reads it when each session starts and puts it on the spec (`lanePermissionMode`); the adapter's own option, which only the live test sets, wins. An unsandboxed lane always runs in `default`; the one unsandboxed session that may run in `auto` is a chat the builder turned Full access on for (`full-access.ts`, `fullAccessOptions`; `decisions/2026-11-24-a-chat-the-builder-turns-full-access-on-for-runs-as-claude-code-does.md`): its `fullAccess` exists only on `ExploreSessionSpec`, a Bedrock key keeps the scrub and `default`, and an API key is read by `apiKeyHelper`, never the env. Its settings billing check (`fullAccessSettingsBillingProblem`) reads the project's, local and user files, at start and on each `ConfigChange`. A Codex Full access thread sends `sandbox: 'danger-full-access'` on `thread/start` and `thread/resume` and `sandboxPolicy: { type: 'dangerFullAccess' }` on each `turn/start`, skips the lane-profile check and is still judged by 10db's judge; it does not start without one. A session in `auto` sets `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0` (Claude Code forces `default` while it is `1`); in `default` it stays `1`. Inline `autoMode` rules are the session's `TrustPolicy` (`trust/policy.ts`, built by the runner for a lane or pass and by Plan for its own) rendered by `sessions/claude-auto-mode.ts` (`$defaults` first in all four lists, or Claude Code's built-in rules are replaced; the limits soft where a person is in the session and hard where none is; the coordination lines hard everywhere; `classifyAllShell` on), and the exact gate command stays out of a sandboxed lane's allow list. Each call's judge is `judgeForCall` (`trust/call-judge.ts`) over the session's starting judge (`capabilities.judge`, which reads the model through `trust/auto-mode-models.ts`) and the `permission_mode` Claude Code reports with the call; the hook's asks and refusals that depend on the judge are `guard/judged-rules.ts`'s, and a Claude Code bump reviews `guard/reviewed-tools.ts` (a repo test fails until it does). A session on the `rules` floor says why in its thread (`trust/floor-notice.ts`). There is no environment switch.
- `main.ts` hands the daemon one routed adapter (`sessions/routed-adapter.ts`), a registry keyed by the harness a call names (`AccountAgent.harness`, from `harnessOf` in `@10db/contracts`, a table `HARNESSES_OF_KIND`; a new agent is one `Provider` value, one row and one adapter). Each adapter reports `capabilities` (`sessions/capabilities.ts`), and the daemon reads one where it once compared a provider (the runner's read-back reads `readBack`). Each adapter runs 10db's pinned copy of its CLI (`environment/pinned-tools.ts`, `startPinnedTools`: fetched into `<data dir>/tools`, checked against `agent-pins.ts`); while that copy is fetching or refused, every session on it ends at once with the status's reason, naming the tool. `codex-adapter.ts` probes a ChatGPT account over `codex app-server` (`initialize`, `account/read`, `account/rateLimits/read` for the workspace, `model/list`) with a 30 s deadline on the injected clock, always closes the child, and puts nothing the child printed in an error or a log. `codex-session.ts` starts a session (`startCodexSession`): it refuses a lane with no sandbox and any session with no `CODEX_HOME` (an explore conversation with no lane sandbox starts on `readOnlyPermissions`: the checkout read, no host, no env, and its hook refuses every command), pins the checkout untrusted (`CodexHome.prepare`) before the process starts, then runs the spec's start checks in order (account and workspace, the project layer off, the guard hook trusted and enabled at a reported `timeoutSec` no shorter than `CODEX_HOOK_TIMEOUT_SECONDS`, the `lane` profile and the requested model on the thread, a server error at `thread/start` or the first `turn/start` ending the session `model_refused` only when its message names the requested model ID), each call under a 60 s deadline on the injected clock, and sends the prompt only after all pass; a failure ends the session as `sandbox_refused` or `account_refused` with the child closed. The usage read, which names the workspace, is asked again after no answer or a server error, up to `USAGE_READ_TRIES` (3) times `USAGE_READ_RETRY_MS` (2 s) apart on the injected clock. An account that still can't be read waits for its sign-in (`missingAccountRefusal`, `account_refused`) only when `codexLoginStatus` says the home is signed out; otherwise the start ends `error`, its message naming the read, which the runner recovers from, so one slow or failing read never pauses the account. A usage read that names no workspace is refused as an identity mismatch with no seen identity. `codex-lane-config.ts` builds the per-session `thread/start` config: the `mcp_servers`, `permissions.lane` (`codex-lane-permissions.ts` translates the lane's `LaneSandboxSettings`: `:minimal` read for `denyRead: ['/']`, the checkout and `allowWrite` as write, the checkout's own `.agents` as write too when it is a real directory (not a link) and no `denyWrite` covers it, since Codex makes an existing `.agents` read-only in a writable root and Claude lanes write it (`.git`, `.codex` and `.aws` stay protected; Codex still can't create a missing `.agents`, as its protection covers absent paths, a parity gap with Claude, and its unlink deny on a writable root means a lane can't remove or rename `.agents` itself, though its contents are fine), other `denyRead` as deny, a `denyWrite` as read only under a writable path and no entry elsewhere, the stricter of two entries on one path, each entry under its real path so a link and its target are one entry (Codex repeats every read and deny entry in its temp-dir rules, and a list with every alias outgrows macOS's sandbox compiler: no command runs; entries are compared on real paths too, so a link carries no grant into a denied tree and a `denyWrite` link keeps an entry on its own path, `read` when its target is readable and `deny` otherwise), each listing pattern's dir as a `read` with a `deny` on every entry under it the Claude profile keeps closed (`listedDirEntries`: mise lists its `installs` dir on every command, and its shims failed `Operation not permitted` in every ChatGPT lane without it; links are skipped, as Codex would apply their entry to the target), `enabled: true` with `mode: 'full'` even for no hosts) and `shell_environment_policy` (`inherit: 'none'`, `set` is `LaneSandboxSpec.shellEnv`, the gate's recipe of the allowlisted session env, `TMPDIR` and the sandbox's variables). After `turn/start` the session reads notifications through `codex-mapping.ts` (`mapCodexNotification`, which updates a `CodexTurnState`; every handler parses with `safeParse` and logs only the method of a bad shape, never throws): `item/started`, `item/commandExecution/outputDelta` and `item/completed` are `tool_call`s (`codex-tool-calls.ts`: one per thread item, one edit per file of a patch, its output tail kept to 4,096 characters), `item/agentMessage/delta` and `item/reasoning/summaryTextDelta` are `text_delta` and `reasoning_delta`, a completed `agentMessage` is a `message` and text activity, `turn/plan/updated` is a `plan_update`, `thread/tokenUsage/updated` is context, and the session's tokens are the thread's latest `total` minus a baseline (the last `total` seen outside a turn before the first turn: 0 fresh, the replay on a resume), a `contextCompaction` item is `compacted` (Codex 0.154 sends no `thread/compacted`), a `send` made while the session starts waits for the first turn, `account/rateLimits/updated` is one `rate_limit` per window (`limitTypeOf`: 300 `five_hour`, 10080 `seven_day`, else `<n>_minutes`). A failed `turn/completed` ends the session on `usageLimitExceeded` (a `rejected` `rate_limit` with the last window's reset, else `account/rateLimits/read`, then `rate_limited`), on `unauthorized` (`account_refused`, signed out) and on a `badRequest` naming the requested model (`model_refused`); any other is a `turn_complete` with `result: 'error'`. After `started` the session lists its commands (`CODEX_COMMANDS`, `codex-commands.ts`); a `send` of `/compact` or `/review [instructions]` is its own call (`thread/compact/start`, `review/start` inline), sent once no turn runs and never steered, reported `consumed` once Codex answers it. Any other `send` is `turn/steer` during a turn and `turn/start` between turns, in order, each with the message's client uuid as `clientUserMessageId` and its pictures after the text as `localImage` items naming the stored file (`ShapeImage.path`; one with no file goes as an `image` of its bytes), the prompt's with the first turn; `interrupt` answers the messages not yet handed to Codex as `stillQueued`, waits (within `stopGraceMs`) for the turn a `turn/start` in flight begins, sends `turn/interrupt` and waits up to `stopGraceMs` for the turn's `turn/completed`, and no message is steered into a turn an interrupt is stopping; a turn not reported ended by then ends the session `error`, so what it held goes to the next one; `stop` sends `turn/interrupt`, waits `stopGraceMs` for it, ends the process and emits one `ended`. A child exit nobody asked for ends `error` with the end of its stderr in the message only. `context-event.ts` holds `contextEvent`, shared with the Claude adapter. `codexLoginStatus` (`codex-sign-in-check.ts`) is its `claudeAuthStatus`. The system check reports the pinned copy's status and the version it prints (`withAgentStatus`), and warns on any version but `CODEX_VERIFIED_ON`; a `codex` the builder installed is never looked for or run. The briefing follows the agent of the account each session runs on (`PromptInput.provider`, the harness of the account the runner reads before it builds the prompt, never `project.provider`): a Codex session is told to change files with `apply_patch`, to ask through `mcp__10db__ask_human`, that the Edit or Write tool means `apply_patch`, gets no auto-mode line, and its command-shape and edit lines name no "Allow Bash?" or permission card, which a Codex lane never gets (`CODEX_RULES`); its skills' bodies (`RunnerOptions.skillBody`, `readSkillBody` in `@10db/harness`) are in the prompt because it loads no plugin. Claude's briefing is unchanged. An explore conversation (Plan, a chat) opens the same `startCodexSession` as a lane: on its read-only lane sandbox, with `approvalPolicy: 'never'` and the guard socket answering each call through the spec's judge (`judgeCall`, else the `preToolUse` floor); its `developerInstructions` are the profile's `systemPrompt` and then the setup's instructions (`codexDeveloperInstructions`). Codex has no subagents (`capabilities.subagents` is false), so Plan there runs without its research and review agents and its header says so. The guard hook's `tool_use_id` is the item's id (live-checked), so `judgeHookCall` tells each refusal (`OnDenied`: the guard's and the broker's `10db` or `builder`, 10db's judge's `judge` with its `limit`; `soft` is false, since an attended limit is a card and never a deny) to the turn state (`CodexTurnState.denials`), and a declined item carries it (`withDenial`; a patch's per-file calls share the item's id before `:index`). Codex reports no item for a call its hook refused (live-checked, code mode), so the session also emits that call from the hook's own input (`codex-refused-calls.ts`: a command, a patch's files or an MCP tool, denied, under the item's id), and an item Codex does report replaces it. A refused call whose id starts `exec-` is read as a code-mode script's nested call: it gets `#<n>` (a per-session count, so a repeat stays apart) and the script as its `parentId`, and its title and refusal say so. That prefix is unverified: no recorded live check shows it, so check whether Codex reports an item for the script, and whether a call outside code mode ever carries it (it would show twice). A Claude lane records the same refusal through `preToolUseHook` (`JudgedHookAnswer`).
- `sessions/codex-generated/` holds the Codex app-server protocol as the pinned release generates it:
  `ts/`, the import closure of `ClientRequest`, `ServerRequest`, `ServerNotification` and the responses
  10db reads; `schema/` and `fixtures/`, the generated JSON schema and the sampled payloads
  (`scripts/codex-samples.ts`) of each type `codex-protocol.ts` reads; and a `STAMP` with the release and
  a sha256 of the rest. Only `pnpm --filter @10db/daemon generate:codex` (`scripts/codex-generate.ts`, on
  a Mac, through `ensureAgent`) writes it, replacing the whole folder; the `drift` script
  (`scripts/codex-stamp-check.ts`) checks only the `STAMP`, so CI never runs the darwin binary.
  `codex-protocol.ts` stays the runtime validator, and `codex-protocol.test.ts` holds it to the folder:
  each generated type is assignable to its schema's input, and each fixture passes the generated schema
  and the runtime one. A Codex pin bump fails `drift` until `generate:codex` is run and the folder
  committed.
- Only `sessions/claude-*.ts` import `@anthropic-ai/claude-agent-sdk`, and only `claude-adapter.ts` imports it at runtime (the others import types).
  `claude-session.ts` is the one Claude session core, with a lane and an explore (Plan) profile and the retry loop over
  its starts; `claude-query-options.ts` holds every SDK option that depends on the profile and the sandbox;
  `claude-session-hooks.ts` holds the billing-gated guard hook and the `canUseTool` bridge. Both profiles stream
  (`includePartialMessages`): `claude-stream.ts` turns the partial frames into `text_delta`, `reasoning_delta`
  and one `message` per text block (item id `<message id>:<block index>`), `claude-tool-calls.ts` turns each
  `tool_use` and its `tool_result` into one `ToolCallView` (`TodoWrite` is a `plan_update`), with a written file's
  previous text read in the PreToolUse hook (`before-text.ts`) and diffed by `hunks.ts`; every deny records who
  made it (`ToolDecision.by`, auto mode's through `judge-denial.ts`), and the session reports its commands after
  `started` (`supportedCommands`). The decision is
  `decisions/2026-11-12-agent-output-streams-as-live-frames.md`. The fake is
  `fake-script.ts` (the script book), `fake-session.ts` (one session core with a lane and an explore driver),
  `fake-plan-script.ts` (the e2e's Plan script), `fake-figma-fetch.ts` (the `fetch` that answers the Plan's Figma tools) and `fake-adapter.ts` (the adapter and its records).
  Tests inject a scripted `query`; only `claude-adapter.live.test.ts` runs real Claude Code, behind
  `TENDB_LIVE_CLAUDE=1`; `test/codex.live.test.ts` runs the real `codex` binary against a fake Responses server
  behind `TENDB_LIVE_CODEX=1`, in a checkout outside `/tmp`, and never in CI.
- Both adapters check a session's account with `sessions/account-check.ts` before the prompt and at the first `init`; a refusal ends the session as `account_refused`, which pauses the account, and a model mismatch fails the workstream. Logs never carry an email or organization.
- A managed session's MCP servers are 10db's own plus the repo's `.mcp.json` servers the builder approved
  for that exact config, resolved per session in `sessions/project-mcp.ts`. Claude Code never reads MCP
  config itself (`strictMcpConfig: true`). A repo stdio server reaches Claude Code only as its launch under srt
  (above); never hand it the session environment.
- `claude-connectors.ts` reads a plan account's claude.ai connectors with a probe of its own (`createConnectorDirectory`) and
  `claude-session.ts` relays them as `claudeai-proxy` entries under `strictMcpConfig`, which stays on; the probe, its
  refusals and the switch are `docs/architecture/decisions/2026-11-14-claude-ai-connectors-are-relayed-under-strict-mcp-config.md`.
  A keyed Claude session deletes its account folder's `mcp-needs-auth-cache.json` unread before it registers servers,
  and takes no connector. `codex-mcp-sign-in.ts` signs a server in with Codex's own login on an ephemeral thread and
  reads `mcpAuthStatus` (`codex-mcp-auth.ts`) on the same home sessions use; it opens only plain https pages and keeps
  no token (`docs/architecture/decisions/2026-11-14-mcp-sign-ins-stay-in-each-agents-own-store.md`). A session that
  finds a server signed out says where to sign in (`mcpSignInWhere`).
- `takeoverCommand` and `takeoverNotes` on `AgentAdapter` are pure: Claude's (`claude-takeover.ts`, `--setting-sources ''`, `apiKeyHelper` or the scrubbed Bedrock key, `markOnboarded` for the account's first-run marks) and Codex's (`codex-takeover.ts`, Codex's own defaults except the billing line, the sign-in store and the `untrusted` pin; header tokens through `env_http_headers` from a sealed file). `takeover-servers.ts` maps the servers each agent takes and names what it leaves out. A change to a row is a change to a test table, never a flag only a test reads.
- `codex-complete.ts` holds `completeWithCodex`, an ephemeral, tool-locked one-shot turn for the stakeholder answer writer only: `CodexAdapter.complete` still rejects with `CODEX_NO_QUESTIONS`, which pass review, area naming and hazard assessment rely on. It starts its own `codex app-server` in the caller's empty folder (checkout pinned untrusted, `noToolPermissions`: the base grant and the empty folder read, no network; approval `never`, web search off, no MCP servers), checks the account as `probeAccount` does and trusts the guard hook as a session does. The lock has two layers: the hook's socket is its own and refuses every call (a call it was asked about fails the question, even refused), and the item stream is the backstop for tools the hook can't see (a `webSearch` item, for one): the first item that is not an `agentMessage`, `reasoning` or `userMessage` item interrupts the turn and fails the question, and the process always ends. Codex reports no item for a call its hook refused, so only the hook layer sees a command or a patch; `test/codex.live.test.ts` proves each layer red on its own. An approval request is answered with an error by `createCodexRpc`, which declines it.
- A lane's Codex reaches 10db's MCP tools only through code mode, which hands the script the tool's content as data, so
  an MCP tool result's image never reaches the model as a picture (`test/codex.live.test.ts`, "reports whether an MCP tool
  result image reaches the model", on the Mac): the lane browser's prompt tells a Codex session to open a screenshot's
  path with `view_image` (`briefing/prompts.ts`).
