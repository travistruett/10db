# apps/daemon/src/shape

- `shape/` runs a Shape conversation (spec `docs/superpowers/specs/2026-11-02-10db-brainstorm-chat-design.md`, decision `decisions/2026-11-02-shape-session-and-convert.md`). A conversation's session opens through `AgentAdapter.open` with the explore profile (`sessions/claude-session.ts`), not the lane profile: it loads no settings or plugins and has no lane, claim or area (`decisions/2026-11-05-plan-runs-commands-and-project-tools-through-the-lane-broker.md`). The chat's `prepare` (`ChatHooksDeps.prepare` in `chat/hooks.ts`, built by `daemon/shape-session-tools.ts`, present only with a lane sandbox) gives each session a read-only lane sandbox (`forSession({ readOnly: true })`: the whole checkout in `denyWrite`), the project's approved MCP servers (`inbox/project-mcp-reader.ts` with no workstream) and the lanes' permission broker owned by the conversation (`shapeId`, no workstream, project rules only, `commandsAsk`: every command that reaches it is carded); `release` withdraws its cards, stops what its commands left running (the adapter spawns Plan's Claude Code itself and reports its pid, which `trackProcesses` watches, as a lane's) and disposes the sandbox when the session ends. The servers are read from the launcher's `projectEnv()`, never the session's env; a remote one on a private host (`privateHostProblem`) is left out; a session whose servers' AWS credentials expire within five minutes is closed before the next turn, which resumes it with fresh ones; an unreadable `.mcp.json` or an unbuildable sandbox gives a session with less, named in its first message. `confinement.ts` (`judgeShapeCall`, the PreToolUse hook): a Read, Grep or Glob only on real paths under the checkout or the conversation's files directory (refused, never asked); `Bash` from the session or a `code-researcher` judged by `judgePreToolUse` with no areas, hazards or claims, a read-only command settled and any other `ask`, with background jobs, `nohup`, `setsid`, `disown`, `run_in_background` and `dangerouslyDisableSandbox` refused; a project MCP tool (a repo's approved server, the builder's own or a claude.ai connector) from the session a bare allow on 10db's judge and on Claude's auto mode, so the judge or classifier reads the call as for a lane's, `ask` on the rules floor, and refused from any agent (`decisions/2026-11-21-a-conversations-mcp-calls-go-to-its-judge.md`); `Agent` only for the three reviewers, the researcher and the code researcher, always in the foreground (`run_in_background: false` through `updatedInput`), with `model` one the account offers (`ShapeAccess.agentModels`); a Shape tool by who is calling (`agent_id`). Without `prepare` the session has no `Bash` and no project server, and the hook refuses both. A call the session makes is the adapter's own `tool_call` item, a refused one `denied` with the guard's reason (sessions M4b call 14); the hook writes only Plan's read-budget lines. A plan's session is its chat's: the chat's hooks (`chat/hooks.ts`) own the conversation and compose `plan-parts.ts` (`createPlanParts`, built by `service.ts` as `planParts`): Plan's prompt (`shapeSystemPrompt`, appended after the chat's, once the chat has a plan; `PLANNING_STUB` before) and `tendb-*` agents (from every session's start, plan or not; none without subagents, no researcher without the web), the opening lines (New Plan's line, the catch-up), the digest of the plan's rows after the chat's, what each turn's message is preceded by (`intake`: the builder's edits, dropped files and mis-sized tasks), the read budget of the pictures the session Reads (after the chat's verdict), `keepsResume`, and the checks at a turn's end (a rehearsal that didn't read every task). `service.ts` answers a press's turn through the engine (`rehearse`) and builds an engine of its own only when none is given (tests). A builder's message is the chat's (`POST /chats/:id/messages`); Plan has no message or stop route of its own, and no Propose press: the agent files rows as things are decided. `validate.ts` is pure (every error at once), `rounds.ts` reconciles a `propose_plan` draft with the rows (pins kept, dropped keys refused), `convert.ts` writes goals, loose tasks, additions, changes, removals and decisions in the caller's one transaction and starts nothing (a draft whose `external` issue is already a task of the project is skipped: no task and no `shape_links` row, so Undo Accept leaves the card, and the key stands for that card to the drafts that wait on it), and `undo.ts` is Remove Draft Goal, Undo Accept, Withdraw Decision and Withdraw Principle. Undo Accept (`POST /shapes/:id/accepts/:acceptId/undo`) reads only the Accept's record (its proposals by `accept_id`, their links, its landing groups), runs in the caller's one write, and refuses before writing when the Accept is undone or not the plan's latest, when any task it would remove has any workstream row (it never cancels a run), or when a goal of it holds a live task it did not make; a decision superseded or a principle replaced since, a change or removal of a Board task, and a landing group holding a task it didn't make are left and counted as `kept`, by the one reading (`acceptReach`) that `ShapeViewDto.lastAccept` shares. A change to the confinement must keep the live test (`test/shape-session.live.test.ts`, `TENDB_LIVE_CLAUDE=1`, never in `make gate`) passing; re-run it after each Claude Code or SDK upgrade. `mcp/server.ts` (`/mcp`) gives every chat's session the chat's tools and Plan's together, plan or not, and a session with neither a workstream nor a chat 401. Plan's handlers (`shape/tools.ts`) read the chat's plan (`planOfChat`) at each call: `propose_plan` makes it (`ensurePlanOfChat`, in the round's one write, rolled back with a refused first round) and, on a pass, answers the planning rules the session is owed (`owedRules`, `ChatLive.planRules`) as `rules`; `note_heard` with no plan answers and writes nothing, the two searches write no line, and `attach`, `write_spec`, `report_finding`, `resolve_finding` and `see_screen` are refused with `NO_PLAN_YET`. Plan's agents are named `tendb-scope`, `tendb-engineering`, `tendb-rehearsal`, `tendb-researcher` and `tendb-code-researcher` (`PLAN_REVIEWERS`, `PLAN_RESEARCHER`, `PLAN_CODE_RESEARCHER`); `judgePlanTool` stamps the stored reviewer by dropping the prefix, which is bookkeeping, not a limit. `propose_plan` has no Propose gate and no imported-plan refusal: an imported row carries `PIN_IMPORTED`, which rounds keep as a whole and a re-import may replace, and Unpin or Restore clears. `view.ts` is the read model the screen renders (`GET /shapes/:id`: the transcript, every proposal with its typed body and what Convert made of it, the latest `note_heard` items as `heard`, and where the session is as `turn`); the service announces `shape.changed` when a turn starts and ends, since `turn` is in no row. A plan is made by `POST /chats` with `plan: true` (New Plan), `POST /chats/:chatId/plan` (Show Plan), a passing `propose_plan`, `start_shape` and `POST /projects/:id/plans/import`; the first, `start_shape` and import make a session with its plan. The routes (`GET /projects/:id/shapes`, `/shapes/:id/{rehearse,model,convert,resume,files,export,record}`, `/goals/:id/remove-draft`, `/shapes/:id/decisions/:id/withdraw`) are served by `daemon/shape-services.ts`; Convert (the panel's Accept) answers 400 `{errors}` for a refusal and never waits on or stops a running turn. Accept and Start is `convert` with `start: true`: `daemon/shape-services.ts` then starts the tasks the Accept made (its `acceptId`'s proposals' links) that are ready, through `startTasks` (wired in `daemon/start.ts` to `settleSizing`, then `startBatch` in pull-request delivery or `startTask` one by one locally), and answers `start` with what started, what stayed on the Board and why, and `refused` for any error after the Accept, which stands. `start-counts.ts` (`startCounts`, pure) is the one rule for who starts (a task waiting on unfinished work outside the start, on a task that runs in another place, or on another task in the start in local delivery stays; at most 50), shared by the start and by `GET /shapes/:id/start-counts`, which `buildStartCounts` (`preview.ts`) answers from the preview's lane simulation over the ticked rows. `startDaemon` makes the service with the project's account and the `plan` role's model (`launch`), and closes it, and the engine, before the runner stops; the engine recovers each explore conversation before the API serves. A daemon on the fake adapter run from `main.ts` answers a Shape conversation with `scriptedShapeBehaviour` (`sessions/fake-plan-script.ts`): it echoes what it heard with `note_heard`, and on a message containing "propose" states one goal with two tasks, two loose tasks and a decision, in the project's first area. A message containing "linear" proposes one loose task linked to the Linear issue AMP-1 (`external`), for the e2e's import flow.
- Shape ceremony, review and rehearsal (slice 4, spec §7, `decisions/2026-11-02-shape-ceremony-review-and-rehearsal.md`): `shape/ceremony.ts` is the rule (loose L, goal XL, more than 5 tasks, a one-way path force `spec`; the builder pins `direct`; the content hash ignores `ceremony`, so pinning it neither re-rehearses nor answers a question). One-way paths are the app setting `shape.oneWayPaths.<projectId>` (`GET/PUT /projects/:id/one-way-paths`); a task is one-way when its area or hazard holds a tracked file (`git ls-files`, cached 30 s) matching a glob. `review.ts` holds `write_spec`, `report_finding` and `resolve_finding`; the reviewer (scope, engineering, rehearsal) is never read from tool input: the PreToolUse hook in `confinement.ts` stamps `reviewer` from the subagent's `agent_type` through `updatedInput`, and `report_finding` with none is refused, so only a subagent can report. A rehearsal's mark is written on a `final` report (a none, or the last question). `service.rehearse` queues a rehearsal turn (a `rehearse` note kind, which Jev's Propose counting ignores) for tasks with no mark at their current hash, and `POST /shapes/:id/findings/:fid/dismiss` is the builder's dismissal; a builder edit answers that task's rehearsal questions. Convert never waits on a finding or question; it warns. `GET /shape-measures` also carries the question-card rates.
- Shape preview, attachments and reopening (slice 5, spec §10.2, §10.3, §12): `shape/preview.ts` (`buildPreview`, carried in `ShapeViewDto.preview`) reads and never writes. The project's running and queued work comes first (a held run, or a task no longer open, holds no lane), each for what is left of its estimate: the hours a conversation derived for it, else the project's median lane time per finished task (the M bucket while none has finished), less its lane time so far, floored at zero. The draft's pending tasks follow, additions included, with their derived hours. `preview-schedule.ts` (`simulateFactory`) is pure: running work keeps its lane, even past a `maxLanes` lowered since; queued work goes next, then the draft, longest chain first; a task starts once its dependencies have ended, a lane is free and no running task claims one of its areas. The critical path runs back from the last task to end through what let each one start, and a clash is an area two tasks claim with nothing ordering them (two pieces of existing work never clash). The end estimate adds the project's median non-lane time per finished task for each draft task on the critical path. `attach.ts` is the session's `attach` tool: a Mermaid diagram, a Vega-Lite chart (`ChartSpec` refuses a `url`, `href`, `src`, `srcset` or `background` key anywhere and requires `data.values`) or an HTML mockup, on a proposal key (a goal's task keys included) or on a goal or task this conversation converted. Each call adds a `shape_attachments` row; the view carries them as `attachments` and leaves out a stored body that no longer parses, and the desktop renders them inert (`apps/desktop/AGENTS.md`). `GET /goals/:id/shape` and `GET /tasks/:id/shape` answer which conversation made a goal or task (`shape_links`), or null, for the drawers' Open conversation. `POST /shapes/:id/resume { event }` (`service.resume`, for the engine's Re-plan in Shape cards) records the event as a note a proposal may cite and queues it for the next turn with each converted row's current state (`converted-state.ts`: a task's status, "not started", or "started" with its run's state, as in "started (queued)"); it starts no turn, and a fresh session's digest carries the same lines. Re-planning is `propose_plan`'s `additions`, `changes` and `removals`; validation allows a change or removal only for a task that has not started, and a successful round moves a converted conversation back to `proposed`.
- The builder's cut (`milestone-cut.ts`, decision `decisions/2026-11-14-convert-shows-the-builders-cut-of-a-plan-with-many-milestones.md`): a milestone is a goal proposal. `judgeMilestones` is pure; `convertProposals` takes the request's `cut` and refuses a Convert of a goal while more than five goals are pending and any has no mark, adds `needed` goals to the selection, drops `cut` ones as Drop does (their outline stays as a rejected row) and leaves `later` ones pending. A Plan of more than five goals converts a goal with no `needed` mark only once every goal before it is cut, converting in the same call, or has all its tasks done or removed. No stored state: `pending` and `rejected` are the marks. The Convert modal shows the list before any task is made.
- Review turns (`review-turn.ts`, `service.review`/`rehearse`, `policy.ts` `reviewNote`/`rehearseNote`): Review ▾ is two presses, each a `shape_event` turn starter carrying `prompt` (Claude: Agent calls to the `tendb-*` reviewers) and `promptInSession` (a session with no subagents reads each row itself and says it ran without separate reviewers); `chat/hooks.ts` sends the one that fits (`deliverable`) and, for a session with no subagents, sets the live `ShapeReviewTurn` (`ChatLive.review`, cleared at the turn's end). `judgePlanTool` lets that session's own `report_finding` through only while the turn is live; the MCP handler (`tools.ts`) then stamps the reviewer from the review (`stampReview`: Check for Questions reports as the rehearsal, a Plan review as the `scope` or `engineering` lens it names), since a Codex hook cannot rewrite a call. A session with subagents has no live review, so its rule is unchanged (only `tendb-*` subagents, stamped by the hook). `POST /shapes/:id/review` is Plan review (answers like rehearse; `tasks` counts the goals and loose tasks), `POST /shapes/:id/attachments/:attachmentId/approval { approved }` approves a mock-up (`shape_attachments.approved_at`; the session is told on its next turn); `ShapeAttachmentDto.approved` carries it, and an approved mock-up converted to a task is in that task's lane brief (`ContextPack.mockups`, `plan-record/approved-mockups.ts`) and its drawer's Plan context (`TaskPlanContextDto.mockups`, read as they stand now).
- Dropped files (`dropped-files.ts`, `POST /shapes/:id/files`, which is async): the daemon decides what a file is from its bytes (`conversation/file-kind.ts`) after the size and count check (the count is checked again inside the insert's write), and a kept file's extension always agrees with its bytes (an image or PDF under its real extension, text named like one with `.txt` appended; the row keeps the dropped name). `start_shape`'s inline files take any safe text name and refuse an image or PDF extension. A docx or pptx is kept as `<name>.md` and a PDF's text is read after the upload has answered (the service's `pdfReading` set tells the intake line it is still running, and a Codex intake that finds no text and no read starts one again, once per run, `pdfTextComing`; at most two extraction workers run at once; nothing is written once the service closes or the folder is gone) and goes in `text/<stored>.txt` beside the files (a path `storeFile` never produces); both are extracted in a worker thread killed at 30 s (`conversation/extraction.ts`, built as `extract-worker.mjs` beside `daemon.mjs`). `intake` takes the session's provider (`chat/hooks.ts` `providerKnown`): Claude reads a PDF itself, scans included; a Codex session's `[file]` line for a PDF names the text file, since Codex can't read a PDF, says 10db is still reading it, or says the PDF has no text 10db could read.
- Design review (`design-review.ts`, `service.designReview`, `policy.ts` `designReviewNote`, `POST /shapes/:id/design-review`): a third review beside Plan review and Check for Questions, with `ShapeReviewer.Design`, `ShapeEventKind.DesignReview`, `ReviewTurnKind.DesignReview` (`stampReview` reports as `design`), `tendb-design` in `PLAN_REVIEWERS` and `SHAPE_AGENTS`. For each pending task with a mock-up (approved, else newest) and a page area, the service draws the mock-up and shoots the routes once for all tasks, writes one `design_checks` row per task, copies the PNGs into the plan's folder (`<plan folder>/design/<sha>.png`, which the session and reviewers already read), and only then queues the note, which lists the paths, the checkout's root `DESIGN.md` and what is missing. The press answers after the pictures; the desktop says "Taking pictures" meanwhile. `nothing` when no task has both. Codex (no subagents) reads the same paths with `view_image` and reports `reviewer: "design"`. A lane's `check_design` (`mcp/design-check-tool.ts`) is offered only with an approved mock-up and answers the PNGs as image blocks, since a lane reads nothing under the data directory.
