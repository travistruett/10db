# apps/daemon/src/verify

- Gates are limited machine-wide (`verify/gate-slots.ts`, `decisions/2026-10-28-gate-slots.md`): `startDaemon` wraps the one gate runner with `limitGates` over a single `createGateSlots(limits.gateSlots)` (default 1, `TENDB_GATE_SLOTS`), so a lane's verify gate and a batch's ship gate share it. Waiters are served in the order they asked, except that a `GatePriority.Advice` runner (the Workbench turn check) waits behind every gate that decides. The gate's timeout starts when it gets a slot. A gate that waits calls `GateRequest.onWaiting`, and `GateRequest.beforeStart` runs once it holds its slot, before its sandbox or command (a false answer is an abort); a new place that starts a gate goes through that same runner, never a second one.
- A project gate that fails because its environment is not ready is held, not failed (`daemon/gate-hold.ts`, `holdStaleGates`, wrapped around the limited task and ship runners so a waiting gate holds no slot). `gateHoldReason` (`gate-hold-rule.ts`) reads the last three lines of a failed gate's tail, only for a failure faster than `HOLD_MAX_DURATION_MS`, for a `10db-hold: <what to do>` line, or the phrase "start make watch" that Ampsio's gate prints. The gate runs again every `GATE_HOLD_RETRY_MS` (the gate's own failing precondition is the check, and it fails fast), one project status card (`inbox/gate-hold-card.ts`) says what to start and closes when the last held gate of the project gets through, a stop ends the wait (the result comes back aborted), and after `GATE_HOLD_MAX_MS` the real failure stands. Any other failure, a timeout and a stop are never held.
- `GateRunner.run` takes an optional `copyId`; `withCopyId` applies it last, so the gate and a copy's teardown see `TENDB_COPY_ID` only from the copy's journal and never from the project's env. A gate of a copy batch without its id doesn't run.
