# apps/daemon/src/hazards

- A hazard is held per copy or per project (`HazardDef.scope`, read with `hazardScope`; a stored hazard with no scope takes its stock namesake's, else `project`; `decisions/2026-10-29-per-copy-hazards-and-waiting-claims.md`). `harness` (`AGENTS.md`, `.claude/**`, `.codex/**`) and `deps` (manifests and lockfiles, install commands) are per copy: scoped like an area, to the batch with a worktree, else to the project (a shared checkout is one copy), so tasks in separate worktrees hold them at once. `migrations`, and any hazard the builder adds, are per project. Every claimer passes `copyHazardNames(project)` to `acquireClaims` as `copyHazards` (the scheduler and `request_claim`), and the watcher's `perCopyClaims` treats a per-copy hazard like an area. `request_claim` waits (`mcp/claim-wait.ts`): `ClaimWaits`, one per MCP handler (`createMcpHandler`), runs one wait per claim of a workstream, which every call for that claim joins. A wait shows a `Notice` (key `claim-wait:<kind>:<name>`, `workstreams.notice`) on the waiting task's card and drawer that names the holder's task, and raises no Inbox card (it asks the builder nothing; `decisions/2026-10-31-notices-not-cards.md`); it polls every `claimPollMs` (default 2 s), takes the claim once it frees and clears the notice, and ends with an error when the session's signal aborts. A call waits at most `claimWaitSliceMs` (default `CLAIM_WAIT_SLICE_MS`, 4 min, under the session's tool timeout) and then answers `granted: false, waiting: true` unrecorded, so the agent calls again with the same opId. `granted: false, waiting: false` with a "Claim deadlock" card means the holder waits, through the live waits in `ClaimWaits` (not the cards, which the builder can dismiss), for a claim the asker holds; it is checked at the start and on every holder change. Startup clears every workstream's notice, and withdraws the wait cards (`detail.waitingFor`) an earlier build left (`withdrawStaleClaimWaits`). `patchProject` refuses to change the scope of a hazard a running task holds. The wait does not use the `WaitObserver`: a human-wait timeout would park a session no answer resumes, so the workstream stays `RUNNING`.
- `hazards/` reads a project's hazards from its repository (`decisions/2026-11-08-hazards-are-read-from-the-repository-and-additions-apply.md`). `readRepoText` lists HEAD's tracked files through `Git.survey` and reads a short list of instruction, make, compose, manifest and doc files through `Git.fileAt` (object store, no link followed, size- and line-capped); `assessmentPrompt` gives them to the injected `AreaNamer` (the area namer's model, no tool) as numbered lines of data; `checkAssessment` keeps only what passes in code (a command of plain words that is no check and not the gate, whose cited line names its last word; a glob that matches a tracked file and not most of them). `HazardAssessor.assess` applies the additions in one write (`applyHazardAdditions` in `@10db/db`, recorded in the app setting `hazard-assessment:<project id>`) and sets the project's one removal card (`hazard-removals:<project id>`, `inbox/hazard-card.ts`; its answer is applied in the answer's own transaction); a removal is never applied by a look. An entry 10db added that the builder took out (Undo, an agreed removal, by hand in Settings, or with the hazard it made) is recorded as declined (`reconcileHazardAssessment` at the start of each look) and never proposed or added again; a hazard is made only from a glob the batch really adds. The project's gate, precheck and changed-check commands are checks, never hazard commands. A model that is absent, slow (`ASSESS_MS`) or unusable changes nothing. `subscribeHazardAssessment` schedules a look (`SCHEDULE_MS` later, bursts joined) on `ProjectCreated` and on a `CommitRecorded` whose paths include a manifest, lockfile, makefile, compose file or `AGENTS.md`. It imports `git`, `folders` (the reply parser), `guard` (`classifyPath`, to match globs as a hazard does), `inbox` and `@10db/db`, and types only from `events` and `log`.
