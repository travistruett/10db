# apps/daemon/src/load

- `load/` is the load guard (`decisions/2026-10-30-hold-work-while-the-mac-is-overloaded.md`): `guard.ts` declares an overload (load above 4× the cores for 5 minutes, ending below 2×) and holds waiters, `culprits.ts` reads `ps` and `lsof` and says which gate or lane each busy process belongs to, `monitor.ts` raises, rewords and withdraws the one `machine-overloaded` card. While it is on, the scheduler's `held` launches nothing, the runner's `hold` starts no session or task gate, and `limitGates`' `hold` starts no shipping gate; each hold is an `untilClear(signal)` that a stop ends, with a sync `holding()`. A task's gate waits in the runner, not in `limitGates`, before it takes its batch's turn or a slot, and looks again in its `beforeStart` once it has them, because a gate parked inside the turn keeps a sibling's gate, an install and a migrations claim waiting behind it (`decisions/2026-11-03-app-follows-main-by-itself.md`). The runner records each lane session's temp dir (`laneTempDirs`) so an orphan is named by it. A failed ship gate's card says so through `ShipperDeps.load`. Tests inject `read` and `processes` (`DaemonOptions.load`), never real load. Never read another process's environment.
