# apps/daemon/src/thread

- `thread/` keeps a task's thread (Workbench spec `docs/superpowers/specs/2026-11-09-10db-workbench-design.md` §4.3, §11, §12, §13): `GET /tasks/:taskId/thread` lists it oldest first, `POST /tasks/:taskId/thread` takes a builder's message as a multipart form (a `text` part, a `picture` part per picture; up to 10 pictures and 40 MB together, each at most Plan's 20 MB) and `GET /tasks/:taskId/thread/pictures/:fileId` serves a picture to its own task only. A picture is a PNG, JPEG or WebP by its name's extension (a name of at most 255 characters), and its bytes must agree (`screens/file-check.ts`, the check Plan's dropped files use too); it is kept at `<data dir>/tasks/<task id>/files/<sha256>.<ext>`, mode 0600, written under a temporary name and renamed, and its row is written after every picture of the message is on disk, in one write with the message (`insertBuilderMessage`). A write that fails removes the pictures that call wrote, never one an earlier message holds; a picture whose file is gone answers 404. `thread/session-text.ts` is how the thread reads to a lane session: `builderMessageText` (a message under its id, each picture attached or named by its stored path) and `buildThreadDigest` (the brief, then the builder's messages and the agent's replies before the message a fresh session acts on, from the latest handoff on, each picture named by its path, never resent; the files each turn changed join it once turns are rows).
