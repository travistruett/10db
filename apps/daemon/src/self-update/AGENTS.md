# apps/daemon/src/self-update

- `self-update/` makes the installed app follow `main` (`decisions/2026-11-03-app-follows-main-by-itself.md`). `createSelfUpdate` polls once a minute, asks `githubHeadOfMain` and `githubMainIsAhead` for main's head and whether it is ahead of the running commit, and only then stages a build (`install-app.sh --stage --running`: the newest finished build, as `make install-app` picks it, never an older one) and, when `midSessionWork` (`countMidSession` plus `DeliveryJobs.pending()` plus `ShapeService.turnsInProgress()`, a shaping turn running or queued) is 0, holds the scheduler back (`pause` is `stop()` then `await idle()`, because a tick can be inside `branchSnapshot`; `Scheduler.stop()` also keeps that tick from launching), looks again, and starts `install-app.sh --apply --quit-first --relaunch` detached. From the pause on, every way out but the install starting resumes the scheduler (`install` and `notStarted`): a throw is a failed `start-install` with its card, never a scheduler left stopped. What it follows is fixed when the app is built: `scripts/build.ts` writes `GITHUB_REPOSITORY` and `GITHUB_SHA` to `build-info.json` (`readBuildInfo`); no project, checkout, origin or `app_settings` value names the repository. The only setting is the app-wide `self_update.enabled` (on until the builder turns it off), served at `/settings/self-update`. Shutdown calls `SelfUpdate.stop()` first, so a check under way cannot start the scheduler again, and awaits it beside the delivery jobs. The install script runs outside any sandbox: `script-installer.ts` starts it with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `TENDB_INSTALL_GH` set to the gh `resolveGh` found, `GH_REPO` set to the pinned repository and the login environment minus `PATH`, `BASH_ENV`, `ENV`, `DYLD_*`, `LD_*` and `TENDB_INSTALL_*`; the script runs gh only as `$TENDB_INSTALL_GH`. A new call in the script goes through those rules, never a `PATH` lookup and never an input from a checkout. A shaping turn is no lane, so the status names it: `midSession.shapes` lists `ShapeService.runningTurns()` (the turns `turnsInProgress` counts, less those a hold parked), Settings and the factory note say which conversation the drain waits for, and when only such turns have held a drain for `SHAPE_HOLD_ALERT_MS` (5 minutes) `createSelfUpdate` holds a status line (`status/`, shown after 2 more minutes) naming them, and raises no card; the line and Settings give the same way out (`SHAPE_HOLD_WAY_OUT`: Stop, and the switch or a quit for a session that ignores the interrupt). The line lifts when a lane also holds the drain, the drain ends, or the install can start, and `settle` resolves a `self-update-shape-turn` card an earlier version left open. Tests wait on conditions (the head-check counter, the inbox, `Scheduler.idle()`), never on a sleep; the real scheduler is used where a lane must not start (`scheduler/scheduler.test.ts`).
- A failed update's card offers Try Again (`createSelfUpdateCardAnswers`, wired through the inbox's `onFlagAnswer`): the same `retry()` the Settings switch makes, then a `tick()` at once. An install already running, or a shaping hold, is as for an automatic one: the check returns at once and the running install's outcome words the card again (`refresh`). The card closes on `update_installed` with the commit it was raised for: `SelfUpdate.closeInstalled()` runs at start, after `settle`, and closes each such card whose commit is the running one or that GitHub says the running commit is ahead of; a card GitHub cannot compare, or one ahead of the running commit (a rollback put an older build back), stays open.
- The stage picks only a main commit whose `ci.yml` push run succeeded (`decisions/2026-11-24-the-app-updates-only-to-a-commit-with-green-ci.md`), so a red head leaves the app on its build and `headOf` may be ahead of what stages.
- A failed-update card whose commit GitHub cannot compare to the running one stays open: it is neither closed as installed nor treated as ahead. The builder dismisses it or answers Try Again.
- Merges come in one install (`decisions/2026-11-25-self-updates-install-in-windows.md`): with work running, the drain starts only once the builder's wait limit has run from staging and `UPDATE_WINDOW_MS` (90 minutes) has run from the last install (`self_update.installed_at`, written by `settle` when the install took) or from the last drain released at its cap. Until then the update waits with nothing held, and a status line (`update-wait`) says until when. Install Now skips the window. A drain that a running gate has held for `DRAIN_HOLD_CAP_MS` (30 minutes) is released: work goes on and the next drain waits a window. With nothing running the update installs at once. The constants and `drainNotBefore` live in `update-window.ts`; the log says each wait's length (`waitedMs`, `drainedMs`, `heldMs`).
- Past `DRAIN_LIMIT_MS` the install goes over lanes and sessions but never over a running gate (`deps.gates()`, the lanes' and batches' `gate_pid`): a restart kills the gate and its suite starts from zero. `gateHoldsInstall` keeps the install waiting until the gate ends, or `GATE_WAIT_MAX_MS` (the gate timeout's cap) past the limit, and holds a status line naming the task or batch; the drain still holds every new gate and ship meanwhile.
