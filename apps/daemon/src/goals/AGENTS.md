# apps/daemon/src/goals

- `goals/` adopts a goal brief (`decisions/2026-11-01-adopt-a-goal-from-a-brief.md`): `brief.ts` is pure (front matter, `yaml`, `GoalBrief`, then the rules that need the project, every error with a plain-words path), `adopt.ts` reads a `path` or `text`, answers a refusal, a dry run's preview or the goal `insertGoal` wrote in one transaction. The brief is import only: nothing is written into the repository, and the original file text is not kept a second time, only the rows it produced.
- A goal's digest and list are computed in `@10db/db` (`store/goal-digest.ts`, from existing rows; no goal state is stored in phase 1) and served by `api/app.ts`: `GET /goals/:goalId/digest` answers `GoalDigestDto` and is the one read that advances the goal's `goal_views` mark (a visit within 30 minutes keeps its window); `GET /projects/:projectId/goals` answers `GoalListDto` (each goal's digest and new-item count, plus Ungrouped; a Workbench page that is Ready, `pass_review`, counts as running in neither) and never advances a mark, so a list refetch can't close a window the builder hasn't looked at. The status rule is `docs/superpowers/specs/2026-10-29-10db-goals-design.md` §8 and `DESIGN.md`; this module computes it, the desktop only paints it. `GET /projects/:projectId/candidates` takes an optional `goalId` for the goal-scoped Start Ready Tasks. A goal's task can be started by hand and runs as it would alone, behind the same dependency refusal; a finished goal's leftover tasks stay on the Board until the builder removes them (`decisions/2026-11-02-goals-and-the-brief.md`).
