# apps/daemon/src/runner

- A project with no gate command waits on the builder instead of a gate (`decisions/2026-10-28-optional-gate.md`). `runner/builder-check.ts` raises the one live `check` card (`raiseBuilderCheck`, refreshing a card that shows an older head; `liveCheckCard`) and `waitsForCheck` tells the state; the runner parks the workstream `WAITING_HUMAN` with `builder_review`, claims held. `runner/check-answer.ts` (`applyCheckAnswer`) turns the builder's answer into `Runner.approveCheck` or `Runner.sendBack`, inside the write that resolves the card; `RunnerNotStartedError` (409) refuses an answer given before the runner exists. `runner/fix-evidence.ts` (`outstandingFixEvidence`) names the failure a fresh session still has to fix: the latest gate failure, or the builder's note until a step that started later has acted on it. `GET /workstreams/:id/changes` is `delivery/workstream-changes.ts`: it reads through `Git.diffSince` (plumbing `diff-tree`, 512 KiB of diff text at most) at the head of the card the workstream points at, else the checkout's head, and answers 409 for a finished batch with no worktree path.
- A project may set `changedCheckCommand` (`decisions/2026-10-30-changed-packages-check-per-step.md`): the runner's verify step runs it in place of `gateCommand` (the evidence records the command that ran), the shipper's gate before the push always runs `gateCommand`, and with no `gateCommand` the builder checks as ever. `permissions/rules.ts` lets an edit step run it without a card, beside the gate. For this repository it is `make check-changed` (`scripts/check-changed.mjs`).
- A builder message reaches a lane session as the `feedback` next action (Workbench spec §6.3; `runner/next-action.ts`, `runner/lane-messages.ts`, `runner/thread-pictures.ts`). With a provider session the runner resumes it and the prompt ends with the message; with none (never recorded, a resume that crashed, another account) a fresh session starts from the handoff, the thread's digest and then the message, and once that session has started the thread gets the system notice "Started a fresh session" (`FRESH_SESSION_NOTICE`). A page of an open pass whose open turn a restart cut short gets "Resumed after 10db restarted" once, in the recovery write that queues it again (never while the pass is closing or abandoning) (`recovery/recover.ts`, spec §4.3). Each message is pushed under a client uuid, as the prompt's `promptUuid` or through `SessionHandle.send(text, images, uuid)`, and marked pushed: its first push goes under the UUID of its row's id (`idUuid`), and any later one (a resumed conversation, a push again after an interrupt) under a uuid of its own, which `LaneMessages` maps back to the message, because Claude Code runs no turn for a message under a uuid its transcript already holds: it acknowledges and drops it (the live test saw a resumed session sent its first prompt's uuid again start no turn). Every message text names its id and says a repeated id is one message. It is delivered only when a turn lists its uuid, which the adapter reports as the `consumed` event and `LaneMessages.consumed` marks: the turn's first assistant message stamps `user_message_uuids` for what its prompt brought (the one `user_message_uuid` from an older producer), and a message folded into the running turn between tool rounds is stamped on no later assistant message, only on the turn's result, which lists every message the turn consumed and comes before `turn_complete` (seen live on the pinned 2.1.302; the fake does the same). An echo of the message is never evidence. Once the message a session was started for is taken, its next action becomes a plain fresh one, so a crash resumes without sending it again. Messages are written to the task's implementer, so only an implement step's sessions are handed them: each such session start pushes again every message an earlier session was handed and no turn took, and each such session end turns its next action into `feedback` for the oldest one (`withUndelivered`), a `feedback` keeping the message it was started for (through a usage pause or an account hold too, `keepingFeedback`); a step that ends with one untaken runs again with it as after a crash, counted toward the recovery limit, rather than going on to verify. `SessionHandle.interrupt()` answers Claude Code's receipt, `{ stillQueued }`, or null with none (a Claude Code without `interrupt_receipt_v1`; the pinned 2.1.302 advertises it); a Codex session answers the messages it has not handed to Codex yet, 10db's own queue; `LaneMessages.interrupt` leaves a message the receipt names undelivered and pushes again every other one not taken (`pushedAgainAfter`), every one with no receipt; one whose `consumed` event the runner has not yet read is pushed again too, which at-least-once delivery allows. A picture goes as an image block while it fits the account's limits and what the thread's budget has left, counted as Plan counts a conversation (`blockPictures`, `threadInlineBytes` over `task_files.inline_sent`, which a fresh session's start clears), else as its path; one the session already holds as a block goes by its path when its message is pushed again. The lane reads its task's pictures: the guard's `ownSession.filesDir` lets Read (only) open them and settles that call, and `LaneSessionInput.taskFiles`, once the task has a picture, makes them `allowed` to the file tools' judge and replaces Claude Code's own deny of the data directory with a deny of every entry beside the way down to them, read at the session's start (`sandbox/beside-the-way.ts`; its rules take no exception): an entry made later, another task's new folder among it, is refused by the guard and the judge alone; the commands' profile still denies all of it. A push's uuid is kept on the row (`markTaskMessagePushedUnder`, `task_messages.push_uuids`) in the write that stamps it pushed, before the session can hand it on. Codex takes the same messages and pictures (decision `2026-11-11-a-pass-runs-on-the-projects-account-claude-or-codex.md`): a message goes under its uuid as `clientUserMessageId`, the thread records it as the `clientId` of the `userMessage` item a turn takes it in, and `mapCodexNotification` reports it `consumed` once a model item (`MODEL_ITEMS`) follows it in the turn or the turn completes, never on the record alone, which comes before the model answers. A Codex turn that ends (failed, or interrupted by the guard) without taking a message it was handed reports it on `turn_complete` as `dropped`, except a turn the handle's own `interrupt` stopped; for a page the runner hands it back (`LaneMessages.handBack`, `markTaskMessagesHandedBack`: no longer pushed, uuids kept, never taken back as unsent) and fails the turn with Retry Turn; a message pushed again after it went under a uuid gets a fresh one. A Codex lane can open no stored picture by its path (the guard refuses `view_image`, the sandbox the data directory), so it is sent every picture as its file on every push (`readsPictureFiles`), whatever the budget. Before a lane resumes a Codex thread while the task has a message pushed under a uuid and not delivered (after a restart or a stop), `readBackThread` (`runner/read-back.ts`) reads the thread back through `AgentAdapter.readClientUuids` (`sessions/codex-thread-read.ts`: a short-lived app-server, `initialize` then `thread/turns/list` newest first, `TURNS_PER_PAGE` a page and at most `THREAD_READ_PAGES` pages, full items, 60 s on the injected clock, the lane's stop signal, the child always closed; it looks only for the in-doubt uuids and stops once all are found or a turn that ended before the oldest was written is passed; the same rule per turn; an unknown turn status is not completed). `markTaskMessagesTakenUnder` delivers what it took, and a `feedback` whose message was taken resumes the thread as `resume` (`TURN_CUT_SHORT`), in the same write. A thread Codex says no user message has reached took nothing; any other that can't be read (`ConversationUnreadError`) gives way to a fresh session (`nextActionOnAnotherAccount`), kept with the notice `THREAD_UNREAD_NOTICE` in one write: the messages go again under fresh uuids, at least once. A stop during the read ends the launch as stopped, deciding nothing. Claude Code's adapter refuses the read, and a resumed Claude session is pushed the message again.
- A pass page's turns (Workbench spec §6; `decisions/2026-11-09-a-pass-task-session-stays-open-between-turns.md`, `decisions/2026-11-09-a-ready-page-is-a-new-check-item-each-time.md`): for a lane of a task a pass holds, `turn_complete` records no step and never verifies; `runner/pass-turn.ts`'s `endTurnSteps` ends every turn (`ready`, `stopped`, `failed`) in one order: its end and reply in one write, `keepTurnWork`, then a write that settles it; a Ready turn raises a new `check` item (`runner/pass-check.ts`) and parks on `pass_review`, the session kept warm until `RunnerLimits.warmIdleMs` or a yield (`scheduler/warm-yield.ts`) closes it. A message is handed in by `Runner.deliverMessage` after `foldHandEdits`; a session that opens a turn (a warm session closed, a Stop, a restart, the first turn) folds them too before its session row opens the turn, the message it starts from leading with the agent's note. A message to a warm session with no turn open while Your folder is off the pass's branch is held: the session closes and the message waits untaken, queued with the pass's folder card. A message the hand-over refuses (`ConflictError`: the page left or began leaving its pass) is taken back from the thread (`thread/service.ts`), unless a session was handed it. `Runner.stopPassLane` ends a turn `stopped` and raises nothing; a pass lane never goes `FAILED` (a "Turn failed" flag with Retry Turn, refused unless the pass is `OPEN` and the page has no unfinished take-out). The launch rule (`scheduler/pass-launch.ts`) keys on rows: an untaken builder message or an open turn, never while a take-out row is unfinished, the pass is not open or the folder is off its branch; the tick raises the pass's folder card once for a page it holds for the folder and withdraws it once its read shows the pass's branch (`folderSeenOn`), reading the folder of a pass whose card is open though no page is queued. Routes: `POST /tasks/:taskId/stop`, `/thread/redo`, `GET /passes/:passId`.
- The check after each Workbench turn (Workbench spec §8.1, W16, D19; `decisions/2026-11-10-the-per-turn-check-is-advice-in-the-one-gate-slot.md`, `decisions/2026-11-10-a-failed-check-a-broken-preview-and-a-review-finding-are-offered-never-sent.md`) is `runner/turn-checks.ts`. `pass.page_ready` (the runner's Ready, or recovery's finish of an ended turn) asks for it; it runs the project's `changedCheckCommand` only (none: nothing runs, and Start Pass's `no_changed_check` lack says so) in Your folder through `shipGate` (the shared gate slots, held by the load guard), with the project's id, env and rules, timeout `TURN_CHECK_TIMEOUT_MS` (10 min) or the gate's when shorter, logging to `<dataDir>/logs/gate/pass-<passId>-check-<ms>.log`. `runner/turn-check-queue.ts` is its pure per-pass queue: one check running, one waiting, a later Ready joining the waiting one; a run's end, however it went (a run that threw included), starts what waits. A pass marks the run's turns `passed`, clears the header's `turn-check` notice and takes back every unsent check offer on the pass's pages; a failure takes those back too, marks the turns `failed`, sets a sendable `turn_check` header notice and offers a thread notice (`runner/check-targets.ts`, pure: each changed path the last 64 KB of output names whole, a sentence's full stop after it allowed, goes to the one page still held and not signed off that holds it; with none named, to the run's tasks still held, not signed off and not working again); a timeout, exit 126, a refused Docker or a run that threw is a header notice that offers nothing, its turns left `none`. Every result is written in one write only while the pass is `OPEN`. The running check's group is `passes.check_pid` (recorded once `identifyProcess` answers, cleared after that recording lands), named by the load monitor as "the Workbench check of pass …". `startTurnChecks` runs before `recoverOnStartup`: it stops and clears every recorded check pid first, then subscribes, so recovery's Readys are asked for and never run beside a left check; no check runs until its `begin`, which start-up calls once `recoverBatches` has stopped the left ship and pass gates. A run records its pid only while not stopped and clears it only while the pass still names its own, and the recording is caught as it is made. With one slot a 10-minute check can hold it ahead of a ship gate. A pass leaving `OPEN` (`pass.changed`) stops its check, and the close's and Abandon's `stopPassChecks` is `withTurnChecks(passPullRequests, turnChecks)`: the pull request's checks, then the turn check, each waited for. Shutdown stops them all before the gate slots close.
- Launching a model (built): `Launcher.session(account, model, accountModels)` launches the account row's `launchId` for the canonical model, or the canonical ID when the account lists none, and throws `ModelNotLaunchableError` for a tier name. The launcher sets no variable that names a model (no `ANTHROPIC_DEFAULT_*`); `session-env.ts` still strips them from the login env. `modelMatches` compares the reported model with the launched ID up to a trailing `[1m]`, which a subscription's `init.model` drops. `runner/resolve-step.ts` (`resolveStep`) runs at every session start: a planned model the account offers (at the step's effort, not marked unusable) is kept; otherwise (a project moved, the list changed, the model was refused, or the step names a tier) the step's `setting` is applied again through `chooseModel`, the reason says why, and `resolvedStep` saves the result on the workstream (its `model`, `effort` and the step). A step that resolves to nothing keeps its planned model and setting, and holds the account with `AccountProblem.NoUsableModel` (one refusal card, no restart loop), unless no model profile of the account's provider exists at all: that is a catalogue not yet read, not the account's fault, so the step goes back to the queue (`awaiting_profiles`) and `ModelListWait` (`accounts/model-list-wait.ts`) holds that account's queued work out of the scheduler until profiles are rebuilt or 5 minutes pass, logs the first hold of an account, and keeps one self-clearing card ("<account> is waiting for its model list") open until the account has profiles. The holds are in memory, but the cards are stored: a new `ModelListWait` takes on the open ones an earlier daemon left, with no hold, so the rebuild at start closes those of an account that has profiles. `rebuildProfiles` in `daemon/start.ts` is the one place profiles are written and holds released; it runs from a fetch, an account-list read, the held catalogue at start and when an account is created (`onCreated`), the last two with no network. That pause needs the builder's Resume: it does not lift when the account's model list changes. A session that ends `model_refused` (Claude Code's `model_not_found` at the first assistant message, since `init.model` echoes any ID, or an `invalid_request` or `unknown` error at the conversation's first reply, before a tool ran, whose text names the launched model ID as a whole token and says the model is not found or not accessible, or says, after the model's ID or the word model in the same clause (within 160 characters, so a long text reads in linear time), that it is not supported or not available, which is how a Bedrock validation error names a model, also behind Claude Code's `API Error: 400` and inside a JSON body; a config error that puts the phrase first ("thinking.budget is not supported for model X") never counts, while one that names the model first ("Tool use with model X is not supported") still does, until the account's list changes: `isModelRefusal` in `sessions/account-check.ts`, applied by `refusesModel` in the Claude lane and the Plan session alike; a resumed Plan conversation is never at its first reply; a `server_error`, overload, rate limit or any error that merely quotes the ID is not a refusal; Codex's refusal naming the model) marks the model unusable on that account with `markAccountModelUnusable`, raises one `<account> cannot run <model>` card, and the lane starts over on the next model of the refused model's tier (whatever the step's setting, which it keeps; the reason reads "the refused model's tier (<tier>)", and a step chosen again for another cause names its source as the task, a pattern or a role while one still gives its setting, else "its planned setting (<setting>)", through `ChooseInput.plannedSetting` and `startOverTier`); a lane retries whenever choosing again, with the model now unusable (another lane may have marked it first), gives another model, and fails with the card only when it would pick the refused model again, so nothing can loop; a Plan session that ends `model_refused` marks its model too; Codex counts a refusal only when the error names the model and says it does not exist or is unknown; an account with no row for the model records nothing, so the task fails with that card instead of asking again. The area namer asks for `ModelTier.Efficient` on the default account. A Plan conversation picks any model the account lists (`ShapeModel`, `ShapeModelsDto.offered` carries each model's tier); its agents take Claude Code's aliases only on a subscription or an API key (`shape/agent-models.ts`), and on Bedrock, a gateway and ChatGPT run on the session's model, which the prompt (`shapeSystemPrompt`) says.
- Process per rigor (built; `decisions/2026-11-13-each-rigor-sets-its-review-rounds-and-fix.md`, plan `docs/superpowers/plans/2026-11-13-process-per-rigor.md`). A rigor's row (`rowProcess` in `routing/playbook.ts`, project → global → default per field) gives `reviewRounds`, `fixBy` and `approvesPlan`, read live where they apply. **Rounds:** a reviewer's rejection (Review, QA, Plan Review) is at its limit when `atRoundLimit(step.sentBack, rounds)`; below it the work goes back without touching `attempt`, at it the work ships with a follow-up (`limit-ship.ts`) or fails for a `failsAtLimit` kind. Gate failures, uncommitted ends, merge sends and the builder's send-backs keep `attempt` against `FIX_ATTEMPT_LIMIT`. Each reviewing step carries `reviewRounds` for the card. **Resumed fix:** a step records the provider session that last ran it (`WorkstreamStep.providerSessionId`, written in the session-start write from a fresh read); on a send-back whose row says `resumed` and whose target has a session, `revise` carries that `providerSessionId`, the step keeps its model (no escalation) and the prompt carries the rejection's findings. A resumed revise that crashed, whose session ran on another account, or whose model the account no longer gives the step runs fresh, one profile up, once (`withFreshFixEscalated`, `fixFresh`), and the reason names the cause. **Re-plan at every step end:** `withCurrentPlan` re-reads the task, kinds, playbook and the leased account inside the write that ends a step and replaces the pending steps after the current one (`team/replan-steps.ts`: steps that ran are kept, so a pending `revise.reviewStep` keeps its reviewer); the move (next step, done, park) is chosen from the re-planned steps in that write (`finishApproved`, the gate pass, `finishWithoutGate`). A rigor change therefore applies from the next step boundary. A workstream whose steps were not planned from a rigor (a merge-resolution run, a CI fix) is never re-planned. **Light's safety net:** when Build passes with no Review after it, `reviewForcedAfter` reads the change (`forced-review.ts`, numstat with a byte cap; a binary file, a big diff, a hazard, manifest, lockfile, migration, CI or agent-instruction path, an `alwaysReviewed` kind, or an unreadable diff) and the write inserts a Review planned like a kind's added step, its reason "review added: …". **Plan approval:** when the step being entered is Build, a Plan ran before it and the row says `approvesPlan`, the write parks the workstream `WAITING_HUMAN` on one `plan` Inbox card (`runner/plan-approval.ts`, next action `plan_approval`, no lease, claims kept). Approve (`plan-answer.ts` through `inbox/service.ts`) re-plans and starts Build with `attempt` 0; Send Back needs a note, records builder evidence and reruns Plan as a `fix` (counting `attempt`). Recovery keeps exactly one live card.
