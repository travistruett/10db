# apps/daemon/src/delivery

- `delivery/` owns batches: a start answers at once and cuts or joins in a background job (`jobs.ts`: one queue per project in shared mode; in worktree mode two, `cut` for cuts, joins and reopens and `ship` for ships and cleanup, each one job at a time); git and gh refusals are flag cards (`cards.ts`) that name their tasks in `detail.taskIds`, except the card for a `CUTTING` row startup deletes, which has only `detail.batchId`. A failed batch member's card offers Retry, Ship anyway, Ship without it and Later (`batch-card.ts`), acted on through the inbox's `onFlagAnswer`; its options say Ship anyway puts the failed run's commits in the pull request. Ship without it (`Shipper.shipWithout`, `leaveOut` in `ship.ts`, `decisions/2026-11-03-ship-without-it-leaves-out-every-failed-task.md`) reverts the commits of every failed member (the shas of the `commit` tool ops of all its task's runs in the batch still on the branch) with `Git.revertCommits` as one commit, `revert: leave out "<task>", ...`, in the ship queue before the batch moves to SHIPPING, closes the other runs' failed cards, and puts a `left-out` notice (`LEFT_OUT_NOTICE_KEY`, kept through a restart, cleared by Retry) on each failed run, which the drawer shows and the pull request body names under Not done; only a `FAILED` run counts as left out, and one no longer holds its batch's ship trigger. A revert that conflicts, would bring conflict markers back or meets uncommitted changes writes nothing, ships nothing and raises a card naming the files (`leftOutCards`) with the failed card's choices, so Ship without it can be answered again. A lane's first launch in a worktree batch calls `BaseUpdates.atLaunch` (the runner's `baseFirst`), so its copy holds the base as it is now: a fast-forward when the copy has no commits, 10db's base merge when it has, and a `base-fetch` notice with the lane started on the copy as it is when the fetch fails (`decisions/2026-11-02-a-lane-starts-on-the-base-as-it-is-now.md`). `recoverBatches` runs at startup after `recoverOnStartup`; `subscribeShipTrigger` follows `workstream.changed`. `pr-watch.ts` (`createPrWatch`, `subscribePrWatch`) reads every followed SHIPPED batch's pull request every 2 minutes on the injected clock, once at start and when a batch becomes SHIPPED (`DaemonOptions.prWatchIntervalMs` overrides the interval); it runs outside `jobs.ts`, one gh call at a time, and records the status on the batch (`recordPullRequestStatus`) in the same write as the `prCards` its change raises (failing checks, closed, one `pr-watch-gh` card), only on a stored transition, rewriting an open failing-checks or gh card when what it says changes (`raiseIn`, `rewriteIn` and `withdrawIn` in `context.ts`, over the inbox's `flagCard`, `rewordCard` and `withdrawCard`). A failure of gh itself (signed out, not installed, a timeout, `unreachable`) ends a round; any other leaves only its own pull request unknown, and the next round starts after the pull request that ended the last (`decisions/2026-10-29-pull-request-watch.md`). The scheduler imports only `batchLaunchVerdict`, `LaunchVerdict` and `claimScopeOf`, and the composition root passes `flagWrongBranch` to it as `onWrongBranch` and the missing-worktree card as `onWorktreeMissing`; the runner and workstream recovery import `batchCardFields` for the failed card. Worktree mode (`workspace_mode = worktree`, `pull_request` delivery) gives each batch a git worktree under the worktree root (`daemon/worktree-root.ts`: `TENDB_WORKTREE_ROOT`, an absolute path, or `~/.10db/worktrees`, plus a level hashed from the data dir). `checkout.ts` has `checkoutOf` (a workstream's checkout: its batch's `worktree_path`, else `project.repoPath`), `claimScopeOf` (the batch a worktree batch's area claims and per-copy hazard claims are scoped to, for the scheduler and MCP `request_claim` alike; the other hazards stay project-wide) and the list of checkouts the sandboxes deny; every consumer of a workstream's checkout asks it. `worktree-cut.ts` cuts (branch, worktree, pin, seed), `worktree-seed.ts` clones ignored directories, `worktree-repair.ts` makes a worktree whole for Retry and reopen, `worktree-cleanup.ts` retires one after SHIPPED, CLOSED or ABANDONED (an ABANDONED one never with uncommitted changes; SHIPPED and CLOSED rely on ship step 0's clean check; none while it holds git-ignored files outside matched directories and the seed, which keeps it with a card), `worktree-sweep.ts` removes orphans at startup (only entries under this daemon's level locked `10db bat_...`, keeping one with uncommitted changes, git-ignored files 10db didn't seed, or that git can't read, with a card); both count no build output as such a file, a fixed list by exact name in `build-output.ts` (`*.tsbuildinfo`, `.eslintcache`; `decisions/2026-10-29-worktree-build-output-not-loose-work.md`), list every ignored file outside the seed, build output included, on an uncommitted-changes card, and withdraw a worktree's kept cards (`keptWorktreeKey`) once they remove it, the kept-worktree cards name `worktreeRemovalCommand` (`git -C <main checkout> worktree remove --force --force <path>`), and `recover.ts` recovers worktree batches at startup. In shared mode the cut records where it found the checkout (`batches.return_branch`, `return_sha`), and `checkout-return.ts` (`returnCheckout`) switches it back after SHIPPED, CLOSED or ABANDONED, in the project's queue, only while no work runs in the project (as Abandon counts it) and it is clean, still on the batch's branch, its index matching HEAD, free of untracked files where the switch writes (`untrackedInTheWay`) and its branch not out, rebased or bisected in another worktree, else leaves it with a card (none when the builder moved it); recovery switches back finished batches whose place is still set, newest first (`decisions/2026-10-29-shared-checkout-switch-back.md`). The PR template is read from the shipped commit through `Git.fileAt` (`pr-template.ts`), never from the checkout. With no project prefix the PR title is `<type>(<scope>): <subject>` (`pr-text.ts`): `fix` when every finished task's title opens with fix, the one scope `.10db/pr-scopes.json` at the batch's base gives every file committed since it, none on a git failure (`pr-scopes.ts`, `Git.filesChangedBetween`), and none when they span several (`decisions/2026-10-28-pr-title-from-the-work.md`). Before every gate of a batch, a task's verify gate and the shipping gate alike, `base-update.ts` (`createBaseUpdates(ctx).beforeGate`) runs as the gate's `beforeStart`, once it holds its slot, inside `BaseUpdates.gate`, which runs a batch's gates in turn (the runner and the shipper share the daemon's one instance; `decisions/2026-10-29-batch-gates-in-turn.md`). It fetches the base once in the project's checkout. In worktree mode it merges `origin/<base>` into the batch's branch (`Git.mergeIntoBranch` with `resolve: { generated }`, never a rebase). A conflict where each side only added lines at the same place is settled by keeping both (`git/conflict-text.ts`), and a conflict in `packages/contracts/generated/` or `packages/db/drizzle/` takes the base's directory, but only where `generatedIn` (`worktree-generated.ts`) finds the package that makes it (`@10db/contracts`, `@10db/db`, with a `generate` script) in the manifest at both the branch and the base; in any other project those paths are plain files. After the install, `ctx.generators` (`createWorktreeGenerators`, `pnpm --filter <pkg> --fail-if-no-match generate` under the gate's sandbox) regenerates them in a worktree with no uncommitted change, and the base update commits what changed there; a failed run's files are put back with `Git.restoreDirs`. Neither raises a card, and a note heading the gate's evidence names the files (`decisions/2026-10-30-a-batch-settles-its-own-conflicts-with-main.md`). The branch's own migrations are carried over after the base's (`migration-carry.ts`): one `generate --name` or `generate --custom --name` per migration in journal order (with two or more generated migrations each but the last runs on a schema file written from its own snapshot merged by key with the base's, `snapshot-schema.ts`, so each stays a step; `packages/db/src/schema.ts` is replaced between runs and put back whatever happens), a custom one's SQL copied back as bytes, the journal checked before anything is committed, and any that changed number listed on the `migrations-renumbered` notice (one line per original tag, a later renumbering from the same tag replacing it), whose body the runner puts in every later session's brief. A pull request's catch-up writes that notice only once its merge is pushed (the `merged` answer carries `renumbered`; `ship.ts` keeps it), so a rewound catch-up leaves it as it was. A `.sql` the branch added that the merge dropped and the journal at HEAD lacks, whatever kept it from being made again, is an `uncarried` answer: no gate runs, it goes on the `migrations-uncarried` notice (also in the brief), and `standing` answers `uncarried` at every later gate until the journal holds it, then clears the notice and the card. The runner counts that as a failed gate, the shipper fails the batch (`shipCards.migrationsLost`), a ship with no gate asks with `standingOnly`, and a catch-up keeps no notice, pushes nothing and puts the merge back (`decisions/2026-11-04-a-base-merge-carries-a-batchs-migrations-over.md`). Asked by a task's verify gate (`BeforeGateOptions.inSession`, the runner's) or by the shipping gate (the shipper's), a conflict where every file left is a text file both sides changed the same lines of is committed with git's markers in it instead (`resolve.leaveMarkers`, `marked`): the merge commit has the base as second parent, `Git.keepNote` keeps what is left at `refs/10db/<level>/merges/<batch id>` (`start-refs.ts` `mergeRef`; retirement and the sweep delete it), `beforeGate` answers `conflicted` with no gate run and an info `base-conflict` notice, and the runner queues the task's workstream again with `nextAction: { kind: 'merge', base, paths }` (`sendToMerge`, counted in `attempt`, with one session of headroom past the fix limit: a step that used all its fix attempts still gets one merge session, and the send after that fails, worded "still in" for markers a session already saw and "a new merge" for markers the gate's own new base merge just made, `fresh` on the `conflicted` answer), no card. A merge session that ends with uncommitted changes in its claims goes back through `sendBackUncommitted` on the same count, and its failure counts the fix attempts and merge sessions the step used. The session resolves the markers, commits through the commit tool, and asks the builder with `ask_human` only for a resolution that changes what a side does. The next gate answers `conflicted` while `Git.conflictMarkers` finds markers at HEAD; once none is left it drops the note, installs, regenerates the generated directories the merge took (they waited for the resolved sources) and answers `merged` (`decisions/2026-11-01-a-session-resolves-the-conflicts-of-the-base-merge.md`). The shipping gate runs no gate on a `conflicted` answer, whether it made the merge or found an earlier gate's markers: `ship.ts` `sendToMerge` moves the batch SHIPPING → FAILED → OPEN in one write, opens the batch's last finished task again (`setTaskStatus`) and gives it a new workstream of one implement step (its last one, reset) with `nextAction: { kind: 'merge', base, paths }` and no card, and asks for a tick; the batch ships itself when that task is done. When no task can take it (none finished, the task closed, no implement step) the batch fails with one `base_conflict` card naming the files and why (`shipCards.baseConflict`, `BatchFailure.BaseConflict`) (`decisions/2026-11-01-the-shipping-gate-sends-its-last-task-to-merge.md`). Any other conflict is the batch's `base-conflict` notice (below) with each file's reason, and with the renumber steps when a migration's number collides, read from every conflicted path (`conflicted`), settled ones included; a regeneration that fails, can't run (a failed install, uncommitted changes), changes nothing in a directory, or drops a branch's `.sql` migration is one `base-regenerate` card. Asked for the migrations hazard (`forMigrations`), a generated directory's conflict stays a conflict (`generatedHeld`): no generator runs while the task's session works. The merge moves `base_sha` only forward and each member's `base_head` with it (to the base, or, for a member that started later, to the merge of its start with the base, `Git.mergedCommit` at `refs/10db/<level>/starts/<workstream id>`, which `start-refs.ts` names under this daemon's worktree-root level, so another daemon on the same repository keeps its own, and which retirement and the startup sweep delete), and installs again whenever the lockfile blob at HEAD isn't the one last installed (`installed-lockfile.ts`: `worktree_lockfile.<batch id>`, recorded by the cut, a Retry's rebuild and the gate, deleted with the worktree). In shared mode it never writes the builder's checkout, only counts the commits the branch lacks. Nothing it meets fails a gate or throws: a fetch failure, a conflict, files in the way, a refusal or a failed install leaves the branch as it is, and `gateNote` heads the gate's evidence and the shipping gate's failure card with why; a conflict is a `Notice` on the batch (`baseNotices.conflict`, key `base-conflict`), and so are files git doesn't track in the way (`baseNotices.kept`, key `base-kept`; the note tells a fix session to leave them), in `batches.notices`, which every task of the batch shows on its card and drawer (`notices.ts`). Neither raises an Inbox card: they ask the builder nothing, and a gate that meets the same cause again writes nothing (`setBatchNotice` compares), so no gate raises or rewrites anything twice (`decisions/2026-10-31-notices-not-cards.md`). Both are cleared once the branch holds the base; retiring the worktree clears them too, except that a conflict that stood when the batch shipped becomes "Pull request conflicts with <base>" until the pull request merges or closes. A pull request that can't merge by itself (the repository's auto-merge setting is off, GitHub refused auto-merge or the immediate merge) is a `pull-request-merge` notice the same way (`mergeNotices`). A gate waiting for its batch's turn stops as soon as its signal aborts. The runner gets it as its required `baseUpdates` option; the shipper makes its own, and a project with no gate merges nothing (`decisions/2026-10-29-gate-with-base.md`). Decisions: `docs/architecture/decisions/2026-10-27-worktree-*.md`. Tests wait on `Scheduler.idle()` and the delivery jobs' `idle()`.
- At start `moveRetiredLandings` (`delivery/retired-landings.ts`, `decisions/2026-11-03-a-task-on-a-retired-branch-takes-the-default-landing.md`) moves an open task whose landing names a branch origin lacks, with no unfinished batch based on it, to the project's default landing (`resetTaskLanding`, which skips `patchTask`'s started check) and raises one card listing the tasks; an origin it can't ask moves nothing. It runs beside the start and shutdown aborts and awaits it.
- A copy's installed packages are checked, not trusted (`delivery/install-health.ts`, `decisions/2026-11-03-a-broken-install-is-not-a-failed-gate.md`): `checkInstall` resolves every direct dependency the lockfile names for each workspace package, and `WorktreeDependencies.refresh` removes a broken root `node_modules` before the sandboxed install (which rebuilds from nothing or from a clone, not from another pnpm's tree). The base update's install runs at every gate for a copy that was installed, and, when they still don't resolve, removes `node_modules` and installs once more by itself (a batch notice `install-repaired` says when, `decisions/2026-11-03-a-broken-install-repairs-itself-once.md`); it answers `install_broken` (no gate; the runner fails the task as `install_broken` with no attempt counted) only when that second install is broken too. A lane adds a dependency with the `install_dependencies` tool (`delivery/dependency-change.ts`, `decisions/2026-11-03-a-lane-installs-through-the-daemon.md`): exact versions only, `--no-frozen-lockfile` under the gate sandbox in the batch's gate turn, never `pnpm add` by hand.
- A check that fails only in tests is rerun once on just the failing files (`delivery/flaky-tests.ts`, `decisions/2026-11-03-a-check-that-fails-only-in-flaky-tests-is-rerun-once.md`): `rerunFlaky` reads the failing vitest tests from the logs the output names (`make gate`, `make check-changed` and `make precheck` all print `FAILED <step>: <command> (log .gate/<step>.log)` lines), runs `pnpm exec vitest run <files>` through the same gate runner (the runner's verify step and the shipper's check before the push both call it), and answers `flaky` only when the rerun passes. A flaky pass continues the step with no attempt counted and no card; the runner's gate evidence and the shipper's `gate-flaky` notice name each test and its first failure, and `fileFlakyTests` files one Icebox task per test file (`Fix flaky test file <file>`), adding a later flake to the open one. A rerun that fails is the failure it was.
- A Workbench pass (Workbench spec §5, §7.3; `decisions/2026-11-09-a-pass-has-a-batch-of-its-own-kind.md`, `decisions/2026-11-09-a-page-file-is-the-pages-alone-in-a-pass.md`) is opened by `openPass` (`delivery/pass-open.ts`; `POST /projects/:projectId/passes`): in the project's delivery queue it refuses what the database already refuses before queueing, then `Git.openPassBranch` records the folder's dirt (`pass_dirt`, content at `refs/10db/passes/<pass id>/dirt`) and makes `10db/<slug>-<6 hex>` at HEAD writing no file, and one write makes the pass, its `OPEN` batch (`batches.pass_id`), a `QUEUED` workstream per task on the project's implement step alone (a pass is reviewed once, at its pull request) and its page claims through `acquireClaims` (a page held elsewhere is a `claim-wait` notice naming the holder); a failed write takes the branch back (`Git.undoPassBranch`). Once the pass is written, still in its job, each task with saved work (`tasks.kept_work_sha`) is put back through the injected `PassOpenDeps.putBack` (`putBackKeptWork`, wired in `daemon/start.ts`), so `delivery` never imports `pass`; a put-back that fails is logged and the pass stays open. Opening also refuses a merge, cherry-pick, revert, rebase or `git am` in progress, and a HEAD on a batch's branch or a `10db/` branch no task names (an abandoned pass's branch excepted, spec §5.4), checked in the write so the branch is taken back; nested repositories are left out of the dirt and its commit, and every refusal rejects `openPass`'s promise. The dirt commit's trailers name the pass's branch and the return branch, and start-up (`delivery/pass-recover.ts`, step 0 of `recoverBatches`) takes back a pass the daemon stopped opening before its row was written while nothing was built on it, else raises one card naming the branch. A pass holds its tasks while it is `OPEN`, `CLOSING` or `ABANDONING` (`passHoldsTasks`, `passHoldingTask`): `insertWorkstream` gives such a task a run only in its pass's batch, the starter refuses it, and the scheduler never launches it; a task of a closed, settled or abandoned pass is ordinary again, whatever `tasks.pass_id` says. A task the pass holds is In progress on the Board unless its run is paused by a usage limit or held (`deriveBoardStatus`'s `inPass`; `decisions/2026-11-10-a-pass-page-is-the-workbenchs-everywhere-else.md`), since the Workbench, not the Inbox, is where its Ready, question or failure is acted on. A take-out and an Abandon end a task's pass membership (`leavePass`); a close will. `checkBatch` never ships a pass batch, `ship`/`shipWithout`/`abandon` refuse one and start-up's batch recovery skips one, all keyed on `pass_id`, never on the batch's state. `countLanes` counts a pass task's lane for `byPass`, not `byProject`, and the scheduler asks `roomForLane` (`scheduler/lane-room.ts`: daemon cap, account limit, then the pass's page cap or the project's `maxLanes`). While `passHoldingFolder` finds a pass that is neither `SETTLED` nor `ABANDONED` (W9), the starter sends a Your-folder task the builder did not place to a copy (`placeTaskByRule` with `proposePlacement`'s `passHoldsFolder` reason), `prepareShared` refuses the rest, and the scheduler leaves a queued folder workstream with the `workbench-pass` notice, written over no other notice and taken down once the run no longer waits for a pass. The guard's `GuardInput.inPass` is `{ pages }`, the areas that are pages in the pass (`passPageAreas`: every page area, and each area with no role a task of the pass holds, spec §7.1): it denies a write to a file under one the lane does not hold, before a held hazard or shared area allows it. The runner's two judge calls and the pass lane's commit tool pass it. `pass/` is the pass's own module; `passView` (`pass/view.ts`) builds what the Workbench reads of a pass from its rows: a page per task in it, with its run, its latest turn and a failed turn's flag, and the timing of every turn of the pass.
- A pass's pull request and what follows its close (Workbench spec §5.3, §5.5, §8.3, D19, D21, D22, D24) live in `delivery/`. `pass-pr.ts` (`createPassPullRequests`, `GET`/`POST /passes/:passId/pull-request`) offers Open Pull Request once the pass's branch holds a commit past its start, with `origin` and `gh`; in the project's delivery key it pushes the pass's branch (`pushBranch`, out of `ship.ts`) and opens a draft (`prCreate({ draft })`, base `passPrBase`: the stacked-on pass's branch while its pull request is open), or pushes to the one it has and rewrites its body (`Gh.prEditBody`, `passPrBody` in `pr-text.ts`: a line per signed-off page and how it was checked). It is also `PassShipDeps` (`gatePassTip`, `pushPassBranch`, `ensurePassPr`, `stopPassChecks`, `openFollowOnPr`), the seam slice 7a's close is injected with; `openFollowOnPr` (call 6) takes the fetched base in by `Git.mergeKeepingTree` when its tree is the pushed tip's, forgets the merged pull request before it pushes (so a restart between them still opens one), pushes and opens a ready one against the base; `ensurePassPr` reads a recorded pull request's live state first and, when GitHub merged it before the watch read it, does the same rather than edit or ready it. After the push, outside the key, `pass-checks.ts` runs the gate and the one review under one abort per pass (`stopPassChecks` raises it; daemon shutdown stops them all). `scratch-gate.ts` gates the pushed commit where copies are allowed (`delivery: pull_request`) in a worktree of it on `10db/gate-<6 hex>`, locked `10db <batch id>`, never seeded from the folder, installed, run by the extracted `runGate` (the shipping gate's slot, its pid on the batch row, held back by `holdShips`) and removed with its branch in `finally`; start-up's batch recovery reaps the gate pid of an open or failed pass batch, its sweep removes a scratch worktree a crash left, and `removeScratchLeftovers` deletes the branches before stray branches are listed. A failed gate is the `gate` header notice (sendable) and a body line; the batch does not move. A push or create that failed is the `pr-open` notice, a gate or review that could not run the `gate` or `review` notice, and the job reads the pass again before the pull request and before the checks, which start nothing for a pass no longer open. A folder-only project's draft says its gate has not run, and a body written before this daemon has run or started a gate of the pass (after a restart) says the gate's result is unknown, never that it is running. `pass-review.ts` (D21) reads the diff once, from the tip the last review read (`passes.reviewed_sha`) else from the base, with the project's review step's model and effort (`CompletionSpec.effort`, `timeoutMs` 10 min; the default stays 2 min) and `passReviewPrompt`; each finding is a thread notice on the page whose area holds its file (`findingTargets`), else a header notice (a review of a newer tip clears the last one's header findings first; one that reads on at the same tip keeps them and adds each new finding once, numbered past them), a page's thread gets a finding it already holds only once, and a tip read already is not reviewed again unless a cut review left files unread. A review reads at most 400 kB: the new commits first (`Git.diffSince` with `paths.except` the unread files), then, with what room is left, the unread files from where they were left (`paths.only`; a path filter picks files from the whole change's counts and reads them in turns of literal pathspecs, so no command line grows with it); what it did not read whole is kept by pass (`review-left.ts`: app setting `pass_review_left.<pass id>`, deleted by `subscribePassSettles` once the pass settles or is abandoned), and Open Pull Request reviews the same tip again while any is left. A file longer than a review reads is read as far as it goes when nothing else fits, and named. Until all of it is read the `review-cut` notice and a body line say so. A notice offered with Send to Agent keeps its text beside the thread (`@10db/db`'s `offerToAgent`/`offeredText`: app setting `send_to_agent.<message id>`), and the thread reads it as `TaskMessageDto.sendable`, the desktop's cue for the button; `POST /tasks/:taskId/thread/:messageId/send-to-agent` sends that text, or a sendable header notice's of the task's pass, as the builder's message, and refuses (409) one that offers nothing; a thread notice is sent once: the send takes its offer (`takeOffer`), put back if the send fails, so it reads not sendable after. `pass-watch.ts` is the pull request watch's branch for a pass's batch while the pass holds its tasks, and on a `local` project always: it stores the read, keeps one `checks` header notice of failing checks, forgets a pull request closed unmerged while the pass is open (`forgetPassPullRequest`) with a `pr-closed` notice instead of the closed card, and starts no fix, catch-up, merge, rerun or card. The merged-branch sweep (`removeMergedBranches`) keeps a pass's branch until the pass settles. `pass-settle.ts` (D22) raises one Move card (`pass-move:<pass>`) when a pass closes unsettled (`subscribePassSettles` on `pass.closed`); after each read of a closed pass's pull request, in the project's queue, a merge whose base tree is the pass's tip moves the return branch to the base by `Git.moveBranchCas` (only while it is at the tip, HEAD names it and `Git.branchInUseElsewhere` finds it nowhere else) and settles the pass, and drift, a CI fix or a close unmerged reword the card; Move (`answerPassMoveCard`) is `Git.moveCheckedOutBranch`, refused while an uncommitted change lies where it writes or the branch holds a commit on neither the base nor the pushed branch; a dismissed card is raised again only with news; `resumePassSettles` looks at each closed pass at start-up. `pass-stack.ts` (D24): `openPass` stacks a new pass on the project's newest closed, unsettled one in its write (`stackOn`), and on a `local` project, where every pass settles at its close, on the newest settled one while its record pull request is open and the new pass's start holds that pass's tip (`stackTarget`, read before the write), so `passPrBase` gives that pass's branch; `followLocalRecord`, after each read of the settled pass's pull request (the watch queues that look only for a settled pass; `resumePassSettles` also queues it at start-up for each settled `local` pass whose record merged or closed under a pass stacked on it), retargets the later pull request once the record merges and offers Retarget when it closes unmerged; a pass that stacks on one whose merge was read already has that merge followed at once; `stackedAbove` finds the stacked pass while it is open, closing or closed, whose Move card waits withdrawn and comes back if the stacked pass is abandoned at its start; when the lower pass merges the stacked one is retargeted (`prEditBase`, each step checked first) and, with the base's tree the lower pass's tip or the tip it pushed (pages signed off after its last push ride the stacked pass), takes the base by `Git.mergeKeepingTree` (one merge commit whose tree is its own, pushed if the branch was), the lower pass settling last (a closed stacked pass's return branch follows the merge by compare-and-swap, from the merge's first parent on a rerun after a crash, and not while another pass is stacked on that one, whose close moves it from its start); closed unmerged, the stacked pass gets a `stack_unmerged` notice and a Retarget card. Each time the closed pass is looked at again (a read of its pull request, start-up), the base the stacked pull request has on GitHub decides: the project's base (by 10db or by hand) clears both, a Retarget answered that did not go through (a failed edit, a restart) is carried out at that look, and a failed read counts as not retargeted, so the card is still offered. While a pass is closed, W9's notice reads `PASS_PR_WAIT_LINE`. A run of a task with saved Workbench work (`kept-work-start.ts`, call 33) never launches before the work is back in its checkout: the scheduler asks `createKeptWorkGate` (its required `keptWork` option) last, just before the claim, of a run every other check would launch now and whose claims are free (`claimConflict`), and the gate queues one put-back through `DeliveryContext.putBack` (the pass module's `putBackKeptWork`) and says no until it has run; a run of a batch not open, of a pass, or held by W9 passes.
