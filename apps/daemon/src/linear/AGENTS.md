# apps/daemon/src/linear

- `import.ts` (`createLinearImport`) is From Linear (a named Linear project is drafted as one goal of its issues): `POST /projects/:id/integrations/linear/import` opens a Plan session on the project's account whose brief names no team or workspace ("Import Linear issues as tasks. Ask me which issues…"). A project is not linked to a Linear team: it uses its account's Linear sign-in (`docs/architecture/decisions/2026-11-22-linear-needs-no-link.md`). It refuses only on a definite `LinearVia.None` for the account (the row's hint); an unchecked account goes ahead. `GET /projects/:id/integrations` carries `linear: { on, note, blockedBy }` and `PUT` on the same path writes `linear-reporter.<projectId>` (off drops the project's pending rows). A part 2 `linear.<projectId>` value is left unread.
- `reporter-comment.ts` (pure) is the comment 10db writes for an owed update: `cleanBody` (which also removes, in code, internal ids, step indexes and home-folder paths from the agent's words, keeping a path's last part), `plainFact` (the same removals for facts shown to the agent), `footerOf` (`10db · <event> · attempt <n>`, no row id: the dedupe is the row's `dedupeKey`, never the footer), `commentText` and `parseWrittenLines` (the agent's closing `<post id>: <comment id>` or `<post id>: failed: <words>` lines). The agent hands over a body only (`report_linear_post`: a `postId` and a `body`, or `nothingToReport`); `reportPost` in `reporter.ts` refuses a body under `MIN_BODY_CHARS`, withholds one that matches a secret pattern (naming it itself), then writes it. `reporter-writer.ts` is 10db's own write: when one of the account's `mcp.linear.app` entries carries an `Authorization` header (`authorizedLinearServer`), `begin` gets a `LinearCommentWriter` (`createLinearCommentWriter`: Linear's `save_comment` over MCP HTTP with those headers), the run is `direct`, `reportPost` records the row (`recorded`, no id yet) and then writes, adds Linear's id (`attachLinearCommentId`) or, only when Linear certainly wrote nothing (`LinearWriteError.refused`: an error answer, or a connection that failed before the send), reopens the row with a try spent (`reopenLinearPost`); a timeout or a connection dropped after the send leaves it recorded with the reason (`noteLinearPostError`), since Linear may have taken it. The agent writes no comment at all (the guard refuses `save_comment`). An account whose Linear is an OAuth sign-in its agent holds (a Codex login, a claude.ai connector) has no header 10db can present, so the agent carries the call: `reportPost` stages `commentText` on the run (`ReporterRun.comments`) and answers the `save_comment` arguments first in its `next`, the guard lets one `save_comment` through per staged comment with Linear's id and exactly that text, `verdict` records the row before it allows the write, and the settle adds the id from the closing message or keeps a `failed:` line's words on the still-recorded row (the agent can't tell a refusal from a write Linear took without answering, so it reopens nothing). Either way a retry or restart never writes a comment twice, and a comment with no id stays recorded without one. `decisions/2026-11-25-the-daemon-authors-the-reporters-linear-comment.md`.
- `reporter-guard.ts` is the Linear reporter's rule, pure: `judgeReporterCall` allows its 10db tool (`report_linear_post`), `ToolSearch`, an exact list of Linear reads, two Linear writes on the linked issue's own id and the one upload request 10db named: `save_comment` with the text 10db built (every string through `scanSecrets`; a refusal says which part of the call was wrong) and `save_issue` with only `id` and `state`, where the state is one `report_linear_post` picked this run (any state when the project's note steers status). A `prepare_file_upload` passes only when its `filename`, `contentType` and `size` are exactly an entry of `ReporterRun.uploads` (the one file `report_linear_post` named for an owed update) not yet asked, with no other key; `verdict` marks it asked, so it is made once. It denies everything else, links and every other upload included (`prepare_attachment_upload`, `create_attachment`, `create_attachment_from_upload`, a second or changed request); it never goes to a judge. `runToolNames` lists the run's tools in full for its first message. Linear's tools are known by their server's prefix (`linearToolPrefixes`): `mcp__claude_ai_Linear__` for the claude.ai connector and `mcp__<server>__` (`mcpToolPrefix`) for each `mcp.linear.app` entry. Codex names a server's tool `mcp__<server>__<tool>` too (its hook name is split on `__` in `sessions/codex-refused-calls.ts`, and `test/codex.live.test.ts` calls `mcp__10db__commit`), so the same prefix applies; no signed-in Codex was checked.
- `reporter-events.ts` turns bus events into owed updates (`linear_posts` rows): `subscribeLinearEvents` reads what an event doesn't carry, `linearRowOf` (pure) maps it to rows with a dedupe key, and one `state.write` enqueues them for tasks with a Linear issue (`task-link.ts`, `linearLinkOf`: the task's own `external`, or, for the follow-up Run these now made (or a follow-up of one), the link of the task its chain started from, since one issue has one live linked task, and none once that task is cancelled; the guard and the brief read the same link, and the brief tells the reporter the follow-up reports for that task and lists that task's recorded rows with its own) in a project where `reporterBlockedBy` is null (`linear-reporter.<projectId>` on, Your MCP servers on). A run's start and end keys carry the number of Ended rows the workstream already has, so a re-entry dedupes and a Retry posts. `waiting` keys the same way (one per workstream per phase, not per Inbox item) and a `verdict` has one key per workstream and phase (a plan review makes no row: the one verdict comment tells it, since the brief reads every verdict the run has), so each phase of a run (start, review verdict, end, landing) is at most one comment. The landing is `pr_merged`; a batch that only ships with a pull request makes no row (`PrOpened` stays in the enum for rows already written), and the end's comment names the open pull request and what waits on it. A batch that ships as a local copy (no pull request) queues `landed` per Done run instead (key `landed:<batch>`), with the base branch, the commit the copy promoted onto it (`getLocalCopy(...).candidate`) and `localCopy` true in its detail. A new row is due `REPORT_DELAY_MS` out, never later: it does not wait behind another row's backoff. `reporter-settings.ts` reads the setting: absent is on, a value not the shape is off.
- `reporter.ts` (`createLinearReporter`) is the run. One timer per task, armed at its earliest pending `due_at` (`start` arms from the store, `poke` re-arms); a pickup drops the project's pending rows when `reporterBlockedBy` says so. Before any hold, it withholds each due row that `nothingToReport` (`reporter-needs.ts`, pure: a PR update with no `prUrl`, a `landed` with no base or commit) says lacks what its post needs, with the pattern `LinearWithheldPattern.NothingToReport` and already dismissed. No session starts for it, it is never held for a sign-in, and the card doesn't count it. The pickup then holds the due rows when `checkSaysSignedOut` (a checked `LinearVia.None`, or `signedIn: false`, which `daemon/linear-sign-ins.ts` gives only when every Linear server of a Codex account reads not signed in; a status that couldn't be read is null) or on an account a run found signed out less than `HOLD_RETRY_MS` ago, unless the check now says signed in (an unchecked or unread row goes ahead), and otherwise posts the starter into the task's Reporter conversation (`reporter-conversation.ts`, one per task, owner id the TaskId) and queues it. The session's `spec` (`reporter-owner.ts`) calls `begin`, which takes every row due now (stamping the session) and opens the in-memory `ReporterRun` the guard, and `report_linear_post` answer from, by session id; a session id with no run is refused. A run settles once, from `onTurnEnded`, from `onState` when the conversation leaves a turn without a turn end (not `IdleWarm`), or from the 15-minute deadline (which stops the conversation first). Taken rows the run wrote no comment for and still pending are, for a completed turn of a run the agent wrote for, held when its agent said `Linear: not signed in` (`SIGNED_OUT_LINE` in `reporter-comment.ts`, which the brief asks for when Linear answers that it is not signed in); otherwise `reachOutcome` (`reporter-reach.ts`, pure) decides from the run's and the conversation's earlier tool calls (the newest 200 items, split at the run's `afterSeq`, a call on Linear by `mcp__<mcpToolPrefix(server)>__`; earlier calls count only since `accountRunStart`, where the unbroken run of the conversation's newest sessions on the run's account began, so another account's answers before a move say nothing) and the sign-in row the trigger read: held only on evidence (a Linear call refused for its sign-in, a check that says signed out, no Linear server, or nothing showing Linear ever answered), failed with `noLinearCall`'s reason when the check says signed in or Linear answered earlier in the conversation (the account is not taken as signed out), and otherwise failed one by one with `5 min x 2^tries` (6 h cap), the end's words or "the session ended without recording". A `direct` run (10db writes for it) shows nothing about the agent's sign-in, so its open rows only fail. A row fails for good at `MAX_TRIES` (5), except a `verdict` or `ended` row (`LASTING`), which is retried at the cap until it posts or the builder dismisses it. A `save_comment` the guard withholds for a secret withholds only the post it carried (`judgeReporterCall`'s `withheld`), in `verdict`. 10db's own write turned away for its sign-in holds too (`LinearWriteError.signedOut`: `UnauthorizedError`, or HTTP 401 or 403), through `reopenLinearPost` with no `maxTries`. An allowed Linear call forgets the account's signed-out note (`decisions/2026-11-25-a-linear-update-holds-only-on-sign-in-evidence.md`). A hold (`holdLinearPosts`; a held row is pending with tries 0 and a `lastError`) spends no try. Its reason is `signInNeeded` (`sign-in-needed.ts`: the account's label and how its harness signs in to Linear), it is due again in `HOLD_RETRY_MS` (30 min), and the account counts as signed out in memory until then. `wake(projectId)` makes the project's held rows due now, forgets its account's signed-out note and refreshes the card. A move wakes the project, as does a Retry on the card, (`onMoved` in `daemon/start.ts`), as do an `mcp_sign_in.changed` to signed in for its account (`subscribeLinearEvents`) and `setSettings` with Linear on, which is how Connect Linear lands (`decisions/2026-11-25-linear-updates-hold-on-the-projects-own-account.md`). The conversation is retired and the task re-armed on a zero-delay clock timer, off the engine's effect chain. `stop` cancels timers and leaves every row as it is. The Reporter conversation is left out of `ExploreEngine.busy()` and the warm cap.
- The reporter's session is the smallest 10db opens: `ToolSearch` only, no agents, plugins, setup or project servers, the account's `mcp.linear.app` entries (and the claude.ai connectors on a plan whose Linear is one or unread), Codex web search off, a read-only lane sandbox (`createReporterPreparer` in `daemon/shape-session-tools.ts`), the Efficient tier at low effort (`daemon/reporter-launch.ts`), and `preToolUse` = `reporter.verdict` (an allowed call is a settled allow). Each run is a fresh session (`keepsResume` is false), so a posting run after a snapshot has its own writes and report tool; its first message names its tools in full (`runToolNames`, from the guard's own lists) and says to search for one by that name when it isn't listed.
- `reporter-brief.ts` is the reporter's first message: `readReporterFacts` reads, once and from the store only, the task (title, criteria), its link (key, Linear id and url, never a workspace or team), the project's note, the rows owed (the agent writes their bodies; 10db adds the footer; each names its default status move) and the rows already recorded, the PR url, whether 10db writes the comments itself (`direct`, which picks the brief's hand-over rules), and per run the implementation report, every verdict, the open findings (the latest rejection of each review step, parsed with `parseFindings`), the evidence and commits, and what was not verified (skips, denied permissions, "No gate ran"). Report and finding text is cut at 4,000 characters and says how much. `reporterBrief` (pure) renders them with the numbered rules: plain words for a partner who did not watch the run, what each kind of update says (started, blocked and on whom, review found, how it ended and what landed or where it landed, what waits on someone), the status rules (give `report_linear_post` the issue's statuses, make the `save_issue` its `next` lists), and one landed commit fact (the last commit's short id) instead of a claim-by-claim mapping. Facts reach the agent through `plainFact`, so no id or home path is shown to it, except the owed post ids it hands back.
- `reporter-status.ts` (pure) decides the default status moves, by type and position with the name only a tie-break: `statusAimOf` maps `run_started` to the team's first started status (only from a triage, backlog or unstarted type) and `pr_opened` and `landed` to the review-like started status (the started status after the first, the earliest whose name says review, only when it sits after the issue's current status); every other event moves nothing, and no row is queued for a pull request that is only opened, so a `landed` row is the one that reaches the review-like aim. `pickStatusMove` applies it to a team's statuses and never moves backwards, to a completed or canceled type, or over a status the builder set since 10db's last set (`lastSet`). With no positions (Linear's MCP server lists none, in no fixed order) the names place the started statuses: the one that says progress is the first (else the only one that doesn't say review; several such are a guess, so nothing moves) and the one that says review the review-like one; a type past started, or one 10db doesn't know (`duplicate`), is never moved to or from. The pick is the daemon's and rides on the comment (`decisions/2026-11-26-the-linear-status-move-rides-on-the-reporters-comment.md`): the daemon has no Linear client for every account, so the session reads the issue's status and its team's (`get_issue`, `list_issue_statuses`) and hands them to `report_linear_post` as `status` (`current` by name, `statuses` as Linear lists them); an update with a default move and no steering note is refused without them. `statusMoveOf` in `reporter.ts` runs `pickStatusMove` (`lastSet` is `lastStatusSet` of the task chain's recorded rows, read from the store, not from the agent) and the answer's `next` lists the Linear writes left in order: the staged `save_comment` (when the agent carries the write), then `save_issue` with `id` and the picked `state`. A run moves the issue to one status, its furthest: the session reads the issue once, so a later update of the same run is measured from the run's own pick (`Flight.runPick`, `pickStatusMove`'s `runPick`), not from the `current` it carries, and only the first pick asks whether the builder moved the issue. So a run that owes a start and a landing ends at the review status, and one that reports the landing first picks nothing for the start. `ReporterRun.pickedStatuses` holds the newest pick alone; with no steering note (`noteSteers`, the project's note is not empty) the guard refuses any other `save_issue` `state`, an earlier pick of the run included. The agent does not report the status, and an allowed call is not a set one: when the run settles, `settleStatuses` reads the run's tool calls from the conversation (`appliedStatuses`: a `save_issue` on a Linear server that came back done, its `state` read from the view's arguments, on Claude and Codex alike) and records each as the `statusSet` of the rows it was picked for (`attachLinearStatusSet`). A `save_issue` that failed, or a run that died before its settle, records none, so the next update moves the issue rather than reading its status as the builder's. A steering note lifts the check and the agent follows the note. The brief puts each owed update's aim in words (`STATUS_AIM_TEXT`). A daemon that later reads Linear itself replaces the session's two reads and calls `pickStatusMove` directly.
- The reporter's agent never sees or sends a picture: `upload_linear_picture` and `reporter.uploadPicture` are refused, and 10db sends every file itself. `reporter-pictures.ts` is the daemon's own upload (`decisions/2026-11-25-the-daemon-uploads-a-tasks-pictures-to-linear-and-says-why-it-has-none.md`): `picturesFor`, called from `reportPost`, adds to an `ended` comment (a `pr_merged` or `landed` one when no earlier row shows pictures: the row's `attachmentUrl` is the record; a local copy's landing is the exception, spared only by an earlier landing that showed pictures, since the before its `ended` comment showed must not hide the after taken once it landed) the task's before and after pairs from `picturePlan`, at most six, uploaded one at a time through `LinearCommentWriter.preparePicture` (Linear's `prepare_file_upload`) and a PUT only to an https `storage.googleapis.com/linear-uploads…` URL signed by Linear's `linear-server@linear-1` account, each signing parameter once, Linear's signed headers unchanged, 30 s, no redirects. A task with none says so once, on its first `ended` comment (a local copy's landing one), with the reason from `deps.picturesOutlook` (`Pictures.outlook`: `none`, `wait`, `later` or `skipped`; a `none` carries a `why` when the task has no after, which a landing says and an `ended` comment does not). A landing that can show a before but has no after says so after its pictures (`PicturesToShow.note`, `AgentUpload.note`). `pickup` does not run due `ended`, `pr_merged` or `landed` rows while the outlook is `wait` (a capture of the after is queued or running): it looks again every `PICTURES_POLL_MS` for at most `PICTURES_WAIT_MS` and spends no try, then the comment goes out saying the pictures were still being taken. A batch that ships as a local copy makes a `landed` row per Done run so its after has a comment to ride in; its `ended` comment says the pictures follow. `picturesToShow` decides what a comment shows (the pictures, or the words for none); `picturesFor` uploads them for a run with a writer. An account with no sign-in 10db can present (`writer` null: a Codex login, a claude.ai connector) gets the same pictures through its agent's sign-in (`reporter-agent-upload.ts`, `decisions/2026-11-26-the-agent-asks-linear-for-the-upload-address-and-the-daemon-sends-the-picture.md`): `reportPost` opens an `AgentUpload` for the update (`Flight.uploads`) and answers a `next` of `prepare_file_upload` for one named file (its name, `image/png`, its exact byte size; `nameNextPicture`) and then `report_linear_post` with the post id alone. The session's result hooks (`reporter-owner.ts`: `postToolUse`, `toolFailed`) reach `reporter.toolResult`, which hands Linear's answer for that file to `takeUploadResult`: it parses it (`parsePreparedPicture`), checks the address and PUTs the bytes at once (`sendPicture`). The call back closes the step (`closeUploadStep`: it waits for the send, and gives a request or result not yet seen `RESULT_WAIT_MS`, since an agent may make both calls at once) and names the next file; a failure names no more. With none left, `uploadAnswer` builds the comment with the pictures that reached Linear (`picturesText`), stages it and answers `save_comment` and the status move; the row's `attachmentUrl` is recorded with the comment in `verdict` (`Flight.attachments`). A repeated call back answers the staged comment again and sends nothing twice. The words 10db adds never name a pull request, and nothing in them stops the comment going out.
- `reporter-inbox.ts` keeps the project's one Inbox card, "Linear Updates Need You" (`refreshReporterCard`, fold key `linear-reporter:<projectId>`): counts of held, waiting, failed and withheld rows, then the latest reason (with any row held, the held row's, which names the account that needs a Linear sign-in and how, since `linearPostProblems` sorts held rows first), and one line per row (task, issue, event, attempt, state, post id; ten at most), withdrawn when none are left. The reporter refreshes it after every settle, drop and settings change; its options are `ReporterChoice` Retry and Dismiss, and answering it goes through `onFlagAnswerInWrite` in `daemon/start.ts` (`answerReporterCard`). Retry (`retryLinearPosts`) makes the project's failed, undismissed rows pending with no try spent and its rows waiting on a retry due now, then wakes the reporter (`lateLinearReporter` in `start.ts`). Dismiss (`dismissLinearPosts`) marks the failed and withheld rows dismissed and turns the rows waiting on a retry into failed and dismissed ones; held rows are left to their sign-in (`decisions/2026-11-25-a-runs-last-linear-updates-never-expire.md`). The decision record is `docs/architecture/decisions/2026-11-22-the-linear-reporter-is-10dbs-own-errand-with-its-own-guard.md`.
- `snapshot.ts` and `LinearReporter.snapshot` read a linked task's issue for its lane: before each fresh build attempt (`runner.ts`, `action.kind === 'start'`, a step that writes) the runner awaits `snapshot(taskId)`, which runs the reporter's own session in a read-only mode (the same Reporter conversation, `ReporterRun.readOnly`: only `get_issue` and `list_comments` on the account's Linear servers, no 10db tool, no write, at most `SNAPSHOT_MAX_READS` reads, a 3-minute deadline) with `snapshotBrief` as its first message; the answer is the session's last message, read back from the conversation (cut at 12,000 characters, fenced as data by `snapshotSection`). It is the lane's brief, not a tool, so Claude and Codex lanes get it alike. A project with Linear off, an account with no Linear, a run in flight for the task, a timeout or an empty answer gives `{ kind: 'missing', reason }`, and the brief says the issue could not be read and why; the lane always starts. The guard can't know a relation's id ahead of the read, so a snapshot run's reads are bounded by count and tool, not by id.
- `lane-reads.ts` (pure; never imports `daemon/`) is a lane's own Linear reads: `laneLinearPrefixes` names the session's Linear tool prefixes (the claude.ai connector on a plan that loads connectors, and each of the builder's `mcp.linear.app` remotes by its `claudeName` on Claude, its plan name on Codex), less any prefix another server of the session holds (`otherServers`: the project's servers and the builder's stdio ones, plus the builder's remotes on another host), so a repo server named `claude_ai_Linear` never has its calls settled; and `isLaneLinearRead` is true only for a `LANE_LINEAR_READS` tool on one of them with a record input of at most 2,000 characters and no `secretIn` hit. The runner passes the result to the guard as `linearRead`, which settles the call (`decisions/2026-11-25-a-lanes-linear-reads-run-settled.md`). It also holds `isLinearServer`, which `daemon/` imports from here.
