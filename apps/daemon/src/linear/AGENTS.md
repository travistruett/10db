# apps/daemon/src/linear

- `import.ts` (`createLinearImport`) is From Linear (a named Linear project is drafted as one goal of its issues): `POST /projects/:id/integrations/linear/import` opens a Plan session on the project's account whose brief names no team or workspace ("Import Linear issues as tasks. Ask me which issues…"). A project is not linked to a Linear team: it uses its account's Linear sign-in (`docs/architecture/decisions/2026-11-22-linear-needs-no-link.md`). It refuses only on a definite `LinearVia.None` for the account (the row's hint); an unchecked account goes ahead. `GET /projects/:id/integrations` carries `linear: { on, note, blockedBy }` and `PUT` on the same path writes `linear-reporter.<projectId>` (off drops the project's pending rows). A part 2 `linear.<projectId>` value is left unread.
- `reporter-guard.ts` is the Linear reporter's rule, pure: `judgeReporterCall` allows its report tool, `ToolSearch`, an exact list of Linear reads and a few Linear writes on the linked issue's own id (exact key lists, one `10db` link for the PR, every string through `scanSecrets`), plus `prepare_file_upload` and `upload_linear_picture` for the run's offered pictures, and denies everything else; it never goes to a judge. Linear's tools are known by their server's prefix (`linearToolPrefixes`): `mcp__claude_ai_Linear__` for the claude.ai connector and `mcp__<server>__` (`mcpToolPrefix`) for each `mcp.linear.app` entry. Codex names a server's tool `mcp__<server>__<tool>` too (its hook name is split on `__` in `sessions/codex-refused-calls.ts`, and `test/codex.live.test.ts` calls `mcp__10db__commit`), so the same prefix applies; no signed-in Codex was checked.
- `reporter-events.ts` turns bus events into owed updates (`linear_posts` rows): `subscribeLinearEvents` reads what an event doesn't carry, `linearRowOf` (pure) maps it to rows with a dedupe key, and one `state.write` enqueues them for tasks with a Linear issue (`task-link.ts`, `linearLinkOf`: the task's own `external`, or, for the follow-up Run these now made (or a follow-up of one), the link of the task its chain started from, since one issue has one live linked task, and none once that task is cancelled; the guard and the brief read the same link, and the brief tells the reporter the follow-up reports for that task and lists that task's recorded rows with its own) in a project where `reporterBlockedBy` is null (`linear-reporter.<projectId>` on, Your MCP servers on). A run's start and end keys carry the number of Ended rows the workstream already has, so a re-entry dedupes and a Retry posts. A new row is due `REPORT_DELAY_MS` out, or later when the task has a pending row on backoff. `reporter-settings.ts` reads the setting: absent is on, a value not the shape is off.
- `reporter.ts` (`createLinearReporter`) is the run. One timer per task, armed at its earliest pending `due_at` (`start` arms from the store, `poke` re-arms); a pickup drops the project's pending rows when `reporterBlockedBy` says so, holds the due rows when `checkSaysSignedOut` (a checked `LinearVia.None`, or `signedIn: false`) or on an account a run found signed out less than `HOLD_RETRY_MS` ago (an unchecked row goes ahead), and otherwise posts the starter into the task's Reporter conversation (`reporter-conversation.ts`, one per task, owner id the TaskId) and queues it. The session's `spec` (`reporter-owner.ts`) calls `begin`, which takes every row due now (stamping the session) and opens the in-memory `ReporterRun` the guard, and `report_linear_post` answer from, by session id; a session id with no run is refused. A run settles once, from `onTurnEnded`, from `onState` when the conversation leaves a turn without a turn end (not `IdleWarm`), or from the 15-minute deadline (which stops the conversation first): taken rows still pending are withheld with the guard's first pattern; else, for a completed turn, `reachOutcome` (`reporter-reach.ts`, pure) decides from the run's and the conversation's earlier tool calls (the newest 200 items, split at the run's `afterSeq`, a call on Linear by `mcp__<mcpToolPrefix(server)>__`) and the sign-in row the trigger read: held only on evidence (a Linear call refused for its sign-in, a check that says signed out, no Linear server, or nothing showing Linear ever answered), failed with `noLinearCall`'s reason when the check says signed in or Linear answered earlier in the conversation (the account is not taken as signed out), and otherwise failed one by one with `5 min x 2^tries` (6 h cap, `MAX_TRIES` 5), the end's words or "the session ended without recording". A `failed` report from a run that reached no Linear follows the same rule, its reason kept. An allowed Linear call forgets the account's signed-out note (`decisions/2026-11-25-a-linear-update-holds-only-on-sign-in-evidence.md`). A hold (`holdLinearPosts`; a held row is pending with tries 0 and a `lastError`) spends no try. Its reason is `signInNeeded` (`sign-in-needed.ts`: the account's label and how its harness signs in to Linear), it is due again in `HOLD_RETRY_MS` (30 min), and the account counts as signed out in memory until then. `wake(projectId)` makes the project's held rows due now and forgets its account's signed-out note. A move wakes the project (`onMoved` in `daemon/start.ts`), as do an `mcp_sign_in.changed` to signed in for its account (`subscribeLinearEvents`) and `setSettings` with Linear on, which is how Connect Linear lands (`decisions/2026-11-25-linear-updates-hold-on-the-projects-own-account.md`). The conversation is retired and the task re-armed on a zero-delay clock timer, off the engine's effect chain. `stop` cancels timers and leaves every row as it is. The Reporter conversation is left out of `ExploreEngine.busy()` and the warm cap.
- The reporter's session is the smallest 10db opens: `ToolSearch` only, no agents, plugins, setup or project servers, the account's `mcp.linear.app` entries (and the claude.ai connectors on a plan whose Linear is one or unread), Codex web search off, a read-only lane sandbox (`createReporterPreparer` in `daemon/shape-session-tools.ts`), the Efficient tier at low effort (`daemon/reporter-launch.ts`), and `preToolUse` = `reporter.verdict` (an allowed call is a settled allow). Each run is a fresh session (`keepsResume` is false), so a posting run after a snapshot has its own writes and report tool; its first message names its tools in full (`runToolNames`, from the guard's own lists) and says to search for one by that name when it isn't listed.
- `reporter-brief.ts` is the reporter's first message: `readReporterFacts` reads, once and from the store only, the task (title, criteria), its link (key, Linear id and url, never a workspace or team), the project's note, the rows owed (each with the exact footer its comment ends with, `footerOf`, which retry deduplication reads back) and the rows already recorded, the PR url, and per run the implementation report, every verdict, the open findings (the latest rejection of each review step, parsed with `parseFindings`), the evidence and commits, and what was not verified (skips, denied permissions, "No gate ran"). Report and finding text is cut at 4,000 characters and says how much. `reporterBrief` (pure) renders them with the numbered rules (a start post is run facts only; a verdict or end post maps each claim to a listed commit and ends with the deferrals), and the pictures the run may post.
- `reporter-pictures.ts` puts a finished task's before and after pictures into its `ended` comment, with no setting of its own: the Linear reporter's switch covers it. `reporterPictures` picks the pairs the pull request and Slack show (`picturePlan`, at most `MAX_LINEAR_PICTURES`), only for a run that owes an `ended` update; `begin` puts them on the `ReporterRun`, and the brief lists them by id, file name and exact size. Per picture the agent calls Linear's `prepare_file_upload`, then 10db's `upload_linear_picture`, and puts the returned markdown in the comment. The session has no network of its own, so the daemon sends the bytes (`uploadPicture`): only a picture the run was offered, only to a URL `isLinearUploadUrl` accepts (https, `storage.googleapis.com/linear-uploads…`, signed by Linear's `linear-server@linear-1` account, which storage checks), with Linear's signed headers sent unchanged, a 30 s timeout and no redirects. The guard allows `prepare_file_upload` only for a PNG in a run with pictures, and `upload_linear_picture` only for an offered id. The signed URL lasts 60 s, so the brief has the agent finish one picture before preparing the next; a picture that fails twice is left out and the comment points at the pull request. Codex reaches the same tools through its `mcp.linear.app` entry.
- `reporter-inbox.ts` keeps the project's one Inbox card, "Linear Updates Need You" (`refreshReporterCard`, fold key `linear-reporter:<projectId>`): counts of held, waiting, failed and withheld rows, then the latest reason (with any row held, the held row's, which names the account that needs a Linear sign-in and how, since `linearPostProblems` sorts held rows first), and one line per row (task, issue, event, attempt, state, post id; ten at most), withdrawn when none are left. The reporter refreshes it after every settle, drop and settings change; answering it goes through `onFlagAnswerInWrite` in `daemon/start.ts` (`dismissReporterPosts`), which marks the project's failed and withheld rows dismissed. The decision record is `docs/architecture/decisions/2026-11-22-the-linear-reporter-is-10dbs-own-errand-with-its-own-guard.md`.
- `snapshot.ts` and `LinearReporter.snapshot` read a linked task's issue for its lane: before each fresh build attempt (`runner.ts`, `action.kind === 'start'`, a step that writes) the runner awaits `snapshot(taskId)`, which runs the reporter's own session in a read-only mode (the same Reporter conversation, `ReporterRun.readOnly`: only `get_issue` and `list_comments` on the account's Linear servers, no 10db tool, no write, at most `SNAPSHOT_MAX_READS` reads, a 3-minute deadline) with `snapshotBrief` as its first message; the answer is the session's last message, read back from the conversation (cut at 12,000 characters, fenced as data by `snapshotSection`). It is the lane's brief, not a tool, so Claude and Codex lanes get it alike. A project with Linear off, an account with no Linear, a run in flight for the task, a timeout or an empty answer gives `{ kind: 'missing', reason }`, and the brief says the issue could not be read and why; the lane always starts. The guard can't know a relation's id ahead of the read, so a snapshot run's reads are bounded by count and tool, not by id.
- `lane-reads.ts` (pure; never imports `daemon/`) is a lane's own Linear reads: `laneLinearPrefixes` names the session's Linear tool prefixes (the claude.ai connector on a plan that loads connectors, and each of the builder's `mcp.linear.app` remotes by its `claudeName` on Claude, its plan name on Codex), less any prefix another server of the session holds (`otherServers`: the project's servers and the builder's stdio ones, plus the builder's remotes on another host), so a repo server named `claude_ai_Linear` never has its calls settled; and `isLaneLinearRead` is true only for a `LANE_LINEAR_READS` tool on one of them with a record input of at most 2,000 characters and no `secretIn` hit. The runner passes the result to the guard as `linearRead`, which settles the call (`decisions/2026-11-25-a-lanes-linear-reads-run-settled.md`). It also holds `isLinearServer`, which `daemon/` imports from here.
