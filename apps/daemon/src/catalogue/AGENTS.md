# apps/daemon/src/catalogue

- `catalogue/` owns the model catalogue (`source.ts` parses models.dev, `tiers.ts` derives the four rungs, Efficient, Balanced, Capable and Frontier, from each model's share of its maker's top output price: `decisions/2026-11-13-models-are-ranked-in-four-rungs.md`) and what is built from it. `join.ts` joins an ID an account reports to the maker's own entry (exact, then the canonical ID of a Bedrock-style one, then normalised; never fuzzy). `account-offer.ts` turns an account's list into `account_models` rows, adding per family the newest `amazon-bedrock` model under the account's own region prefix, because Claude Code's Bedrock list understates what runs. `profiles.ts` (`reconcileProfiles`) writes `model_profiles` rows for every model and effort an account offers, idempotently, keeping scores and step counts and writing `enabled` from the model's status (on only for a Current model, so a superseded, retired or unknown one is never chosen automatically). `account-lists.ts` stores a list only after the caller's account check passed: a signed-out process still answers `supportedModels()`. The one refresh path is `CatalogueSync` plus its `afterSync` (`accounts/list-refresh.ts` probes every account, then profiles are rebuilt); `RunningDaemon.refreshModels()` joins a run in flight and does nothing with `catalogueSync` off. `runnability` (`join.ts`) says whether a runtime can run a model, apart from the join: a model of another maker, or one whose maker the catalogue cannot name, is refused on a Claude Code kind, gets no profile, and is the Not runnable status a Models row derives from it (nothing is persisted for it). Only the maker's own entries are ranked and priced, and an account's assumed offer is unranked while another account of the maker has a real list. A list is also read when a sign-in finishes and, at most daily, when a session is about to start on the account (`accounts/list-refresh.ts`). The module imports no model ID or price: the only names are the runtime-to-maker table in `join.ts`. `model-rows.ts` (`buildModelRows`, pure) makes the Models page's rows: one per canonical model, merging every effort's profile and every account offering it, with `efforts` (one per profile, strongest Intelligence first) and scores and cost from the first; a profile with no status that no account offers (a seeded alias) is not listed; a model only an account with no list yet offers, where another account of its maker has a real list, is Unknown (unconfirmed); one an account lists that its runtime cannot run has no profile and is Not runnable. `GET /models` (with `?account=<id>`, a model that account offers lists the efforts it offers, each priced on it by `routing/cost-on-account.ts`, the router's own rule; an unknown or archived account is a 404), `GET /models/picks?account=<id>&rigor=<rigor>` (the cells of that rigor, Standard when left out; `routing/role-picks.ts`: `chooseModel`'s Automatic choice per role at the cell's need (`ROLE_NEED` for a role the rigor does not run) on that account, with the role's default persona, no project settings, kinds or ceiling; an unknown or archived account is a 404), `/models/offers` (each account's launch ID and own price), `/models/status` and `POST /models/refresh` (a forced `refreshModels`, which joins a run in flight) are served by `daemon/services.ts`; none is a screen read.
- The release snapshot (built): `scripts/release/fetch-catalogue.mjs`, run by `scripts/release/build-macos.sh` before `tauri build`, writes models.dev's document cut to the four providers `CATALOGUE_PROVIDERS` names (every other provider kept by name only, so `makerOf` gives a Bedrock model the same maker as from a fetch) to `dist/release/catalogue-snapshot.json` and names it in `TENDB_RELEASE_CATALOGUE_SNAPSHOT` (not the runtime's `TENDB_CATALOGUE_SNAPSHOT`, so a developer's setting never reaches a bundle), and fails the build on a failed or malformed fetch. The daemon's bundle step (`scripts/build.ts`) removes any `catalogue-snapshot.json` an earlier build left beside the bundle and copies in only the one that variable names, so only a release build carries one and it is always its own (not committed; `resources/` is ignored). `catalogue/snapshot.ts` (`readCatalogueSnapshot`) reads it through `parseCatalogue` and answers null for an absent or malformed file; `main.ts` passes the file beside the bundle as `catalogueSnapshot`, so a source run, which has none, starts from the stored copy. A stored fetch always wins over the snapshot. An account's `settings.tierOverrides` reach `chooseModel` through `routingInputs`, with the account's list, so an override its list lacks or has marked unusable is skipped. `tests/repo/src/model-names.test.ts` fails when non-test source names a model, apart from an allowlist that gives a reason for each entry.
- OpenRouter's numbers on a row: `openrouter-join.ts` places an OpenRouter id (`maker/model`, a dated permaslug, never a `~` router) on a catalogue model through `joinModel` of the maker's provider, exact, canonical or normalised, never fuzzy; `groupMeasuresByModel` groups the stored `openrouter_measures` by the model they join to and drops the rest. `model-facts.ts` is the merge rule, one figure at a time with its source: a score is AA's for that effort, else AA's as OpenRouter relays it on the Max effort alone; cost per task is AA's alone; speed is OpenRouter's p50 on the account's provider (`speedProviderFor`), else the median of fresh providers that have one, else AA's, and a row older than `SPEED_STALE_MS` or without a throughput is skipped. `buildModelRows` ranks efforts on AA's own score so OpenRouter's never moves a row's headline, reads the row's Coding and Agentic from the Max effort, and takes OpenRouter's numbers only when `services.ts` passes them (an OpenRouter account is picked for decisions). Routing reads none of it.
