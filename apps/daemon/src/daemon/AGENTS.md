# apps/daemon/src/daemon

- The instance lock (`instance-lock.ts`, `decisions/2026-11-25-a-silent-daemon-is-killed-and-replaced.md`) is async and judges the holder by its `ps` state and `/health`, not by `kill(pid, 0)` alone: a zombie or exiting holder is taken over, and a holder silent on `/health` for 10 s is SIGKILLed only when `daemon.json` names its pid and `ps` shows it started no later than `startedAt`. A `ps` that can't run means "unknown", so the holder keeps the lock and nothing is killed; never turn that into "dead". Its regression test needs the setuid `ps` and skips with `SANDBOXED`, so only CI and an unsandboxed run show it.

- The Workbench setup's settings (`decisions/2026-11-10-workbench-setup-suggests-settings-from-origins-base.md`): `daemon/suggest-settings.ts` (`suggestSettings`) reads every file from origin's base commit, found once by the exact name `refs/remotes/origin/<base>` (`originBaseCommit`, `Git.remoteTrackingCommit`; never a guessed ref name, which a lane-made branch or tag can answer), never HEAD, which a local-delivery project's lanes write; with no such ref it reads HEAD, suggests no dev login, and suggests Docker only from the builder's own commands. The detectors are pure in `folders/` (`detect-app-address.ts`, `detect-dev-login.ts`, `detect-changed-check.ts`); the live look (`daemon/listening-ports.ts`, lsof, 3 s) and the probe (`daemon/loopback-probe.ts`, one GET, 1 s, no redirect, only `localhost`, `127.0.0.1`, `[::1]`) come in through `DaemonOptions` (`listeners`, `probe`), so a daemon test owns no port. The dev login is the one model question (`askWithin`, `NAMING_MS`), and `devLoginAnswer` keeps only its exact argv shapes with arguments the repository's scripts pass (`devLoginWords`). Allow Docker follows the gate command, a saved turn check, or the scripts at origin a suggested check runs, never 10db's own check text nor the model-written dev login. Setup never pushes and shows no branch note (`decisions/2026-11-24-suggestions-open-from-add-areas-menu-and-drop-the-branch-note.md`).
- Page labels for projects that had pages before labels existed: `daemon/page-label-guess.ts`. At start, before the API serves, `seedPendingPageLabels` lists every project there is under the app setting `workbench.page_labels_pending`. It does this once; the list only shrinks after, so a project added later is never guessed. `guessPendingPageLabels` then runs beside the start and is aborted at shutdown. For each listed project it runs the Workbench setup's read (`proposeSetupAreas`, HEAD's object store only). It gives each page with no label the label the setup guessed for the page of the same name (`folders/guessed-labels.ts`, pure), and takes the project off the list. A label the builder set is never replaced. A builder's save of a project's areas (`services.patchProject`, which Settings and the setup's Apply both call) takes the project off the list. The guess writes only if the project is still listed inside its write, so areas saved during the read stand. A repository it can't read is logged and stays listed.
- `connect-service.ts` (`createServiceConnector`, `POST /settings/connect/:service`) sets a service up for a project's account in one call. `CONNECTABLE_SERVICES` is the table (server name and address; Linear and Figma, whose `whenWorks` is a no-op since it has no per-project switch); the route accepts only its keys. A server at the entry's host counts when the account can sign in to it (`harnessReadsServer`: every session gets the approved servers of every source, so a Codex account counts any; Claude Code's `/mcp` signs in only `~/.claude.json` and plugins, so a Claude account adds one there when only Codex's file has it; `linear-sign-ins.ts` and `figma-sign-ins.ts` use the same rule). Connect then takes the server a session loads under that name (`ProjectMcpServers.loaded`, from the plan) and approves and signs in that key, refusing with the other entry's source when a different server holds the name. With none at the entry's host, an installed plugin that has one but is off for the project (`ProjectMcpServers.offPluginServers`) makes it refuse and name Settings › Trust, so a second server is never added beside the plugin's; otherwise it adds one with the pinned CLI (Codex `mcp add <name> --url`, Claude Code `mcp add --transport http --scope user`), never overwriting a different server of that name. `codex mcp add --url` otherwise starts an OAuth login in the builder's own Codex and opens their browser, so its env sends proxy traffic to a refused port: the entry is written and the CLI exits at once, and the account's sign-in (`McpSignIns.start`) is the only one started. It approves the server through Trust's Approve, only one at a table entry's host; a `Changed` config is approved again, since pressing Connect is the review. It then re-reads the server on the project's effective switches and throws a ConflictError naming the switch when sessions would not load it (Your MCP Servers off, the server's switch off, or `enabled = false`). A Claude Code account is told to finish with `/mcp`; a Codex account's `whenWorks` follow-on (Linear: the project's Linear switch on) runs at once when signed in, or on `mcp_sign_in.changed` for a connect still waiting (kept in memory only; a failed sign-in, or the project's Linear switched off, drops it through `forget`). Each step that already holds is skipped. The CLI's result is parsed with zod.
- Separate copies in the services: a start routes by the task's placement (`workspaceMode: worktree` in a local project goes through `starter.startTask` and is cut a batch, as a pull-request task is), a placement change to a copy is refused with `COPY_NEEDS_REVIEW` when the resolved process runs no review, and the landing, its journal and retirement are `delivery/copy-landing.ts`, `copy-retire.ts` and `copy-teardown-run.ts` (see `docs/architecture/02-batch-delivery.md`).
