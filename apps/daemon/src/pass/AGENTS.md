# apps/daemon/src/pass

- `pass/` keeps a pass's work in Your folder (Workbench spec §5.4, §6.4, §9.1, §12; `decisions/2026-11-09-a-turns-work-is-kept-at-a-ref.md`, `decisions/2026-11-09-hand-edits-ride-the-owning-task.md`, `decisions/2026-11-09-a-taken-out-tasks-workstream-is-cancelled.md`, `decisions/2026-11-09-abandon-pass-puts-unsigned-pages-back.md`). `kept-work.ts`: `keepTurnWork` keeps the task's page files at `refs/10db/passes/<pass>/<task>` through `Git.keepWork` (unsigned, compare-and-swap, a trailer per turn; refused with `PassFolderOffBranchError` while HEAD is off the pass's branch); a page file is one `pageMatcher` gives the task, as the judge reads a pass (a path in any page of the pass is that page's holder's alone; a hazard counts only outside the pass's pages); `keepNamedPaths` keeps the page paths of a pass lane's commit tool and refuses one outside the task's page (`keepCommitToolPaths` sends a shared file under a held area to its hold first); neither moves the branch. The git primitives check only the parts on the way to a path, so a link is kept as a link and a path beyond a link or file is gone, and a put-back leaves a directory in the way. `hand-edits.ts` folds the builder's edits into the task's kept work. `take-out.ts` is the take-out's six recorded steps (`pass_take_outs`; a page Add Page put back is taken out again on a fresh row, `decisions/2026-11-10-a-page-taken-out-again-starts-a-fresh-take-out.md`), as a delivery-key job (`takeOut`, `POST /passes/:passId/tasks/:taskId/take-out`) or for a caller holding the key (`takeOutSteps`); step 5 cancels the run from any unfinished state, ends and settles every turn of the task (`settleTurnsLeaving`) and moves the work to `refs/10db/kept/<task>`, made on any saved work still recorded rather than over it. A take-out asked for alone that fails before step 4 deletes its row, so the page takes messages again; inside an Abandon or a close, Your folder off the pass's branch keeps the last kept commit, writes no file in step 4 and lets go of the page's open holds (`letGoHold`), so an Abandon always finishes and leaves no hold open. Step 4 tells the folder's watcher which files it wrote (`TakeOutDeps.wrote`, `Watcher.daemonWrote`), which cards none of them while they are unchanged since. `put-back.ts` brings saved work back when a pass opens, recording what did not go back. `abandon.ts` is Abandon Pass's eight recorded steps (`passes.abandon_step`, `POST /passes/:passId/abandon`), step 4 dropping each unlanded shared change, newest first, steps 2 and 6 kept for ships and sign-off; its card names left files, read from the take-out rows on a refused Move too, and offers Move to the return branch; an abandoned pass withdraws its folder card. `folder.ts` raises the pass's one folder card when HEAD is off its branch, never repointing it; `cards.ts` answers both cards through the built switch. `resume.ts` (`resumePassWork`, after `recoverOnStartup`, its stop the runner's `stopPassLane`) keeps and releases each shared hold a stop left open and remakes a lost hold ref, raises the folder card, puts back saved work a restart cut short, and goes on with unfinished take-outs and Abandons. The watcher leaves a pass's page writes to the fold (`watcher/pass-writes.ts`): no foreign-claim or stray card inside a claim the pass holds; a write outside every claim is carded only while a lane of the pass works, at its session end with its turn open, or just after its turn; a warm session closing between turns cards nothing. A path the pass's open recorded as dirt (`pass_dirt`) that still holds the content the database recorded for it and the mode the dirt commit (`refs/10db/passes/<pass>/dirt`) gives it (`Git.hashOnDisk` against the row and `Git.blobsAt`; `accountedAt`; a ref moved since accounts for nothing new) is no write made in the pass and is never carded as one, nor is a shared file that still holds the content and mode of the newest change on the pass's shared chain that sets it (its row's blob, its chain commit's mode) while that change has neither landed nor been dropped (either ends what the pass accounts for at its paths, the dirt included; a drop accounts for what it put back) (a turn's end keeps its hold's change and releases the claim in one write, and the file stays changed in the folder until it lands; a drop counts as the newest change of what it put back); edited, made executable or swapped for a link since, either is judged as any write, and a read git can't answer cards it. The folder is read for this only while a lane of the pass works, the only time such a write is carded. Sensitive paths keep their own rule.
- The Workbench's routes over a pass (Workbench spec §4.2, §4.3, §11): `GET /passes?live=true` (`pass/live.ts`) is every pass that still holds Your folder, each as `passView` reads it. `GET /projects/:projectId/pass-start` (`pass/start-preview.ts`, reads only) is Start Pass's preview: each page area with its route, its last commit (`Git.lastChangedAt`), its changed files in the folder (a file under a page is the page's) and the task holding it (`folderAreaHolder`), the other changed files counted, what the project lacks (`docker_off` by the auto switch's own reading of `origin/<base>`, `gateCallsDocker` in `daemon/docker-need.ts`; `ahead_of_base`; `no_app_url`) and the first refusal as a code (`no_page_area`, `pass_open`, `unfinished_batch`, `lanes_in_folder`, then of the folder `operation_in_progress` (`Git.operationInProgress`, the check `openPassBranch` makes), `detached_head`, `return_branch` (`returnBranchProblem`)) with words; the open refuses again whatever changed since. `PassOpenRequest.pages` makes a task per page, "<Page>: UI work" with no brief, in Your folder, one of `goalId`'s tasks when named (`insertPassPageTask`), in `openPass`'s own write before the pass, so a refusal there leaves none; a new page is sent the builder's first message only when there is one. Add Page, `POST /passes/:passId/pages` (`pass/join.ts`), is its own job under the delivery key: in one write the pages' new tasks and the open tasks named join (`joinPass` in the db), each gets its run in the pass's batch and claims its pages as opening does (`startPassTasks`, shared with `openPass` with `refusePassTask`, `newPageTasks` and `writePageTasks`); a joining task's saved work is then put back, and only after that is a `firstMessage`, when there is one, written, so no page starts on a folder half put back. It refuses a folder off the pass's branch, where a put-back would write into another branch's files, a pass not open or full and a task that can't join (409), and a page it holds or overlaps (400). `PATCH /passes/:passId` renames the pass and its batch (`renamePass`), never its branch. `POST /projects/:projectId/workbench-setup` (`folders/workbench-setup.ts`, `decisions/2026-11-10-the-workbench-setup-rebuilds-the-areas-for-one-apply.md`) answers `WorkbenchSetupDto`: the areas rebuilt (see `folders/`), with `settings` and `branch` for the setup's other sections. `GET /goals/:goalId/pass-pages` (`pass/goal-pages.ts`) classifies the paths of each commit the goal's tasks' lanes recorded. `DELETE /tasks/:taskId/kept-work` (`pass/discard.ts`, a delivery-key job) forgets a task's saved work and then deletes `refs/10db/kept/<task>`; 409 while a pass holds the task. For a lane of a pass task with an open turn, each `session.activity` row is `SessionActivityData`: the tool and its target (`toolCallActivity` in `sessions/tool-target.ts` over each call's first `tool_call`, which both mappings and the fake emit) and the turn with the files it has written so far (at most `MAX_FILES_TOUCHED`, 200), read back from the turn's newest row (`turnFilesSoFar`, so a handoff's fresh session goes on with the count) and joined with what the call wrote (`runner/turn-files.ts`); `passView` fills a working turn's `activity` from that row (`latestTurnActivity`, the run's sessions newest first, on the events index). `GET /tasks/:taskId/turns` (`pass/turns.ts`) lists the task's turns with the page files (`pageMatcher`) each kept commit changed against the run's kept commit before it, each pair read once (`createTurnFiles`), since another page can land on the branch between two turns, then the shared files each of the turn's own holds (granted to its run from the turn's start up to but not at its end, `pass/turn-holds.ts`, so a hold granted at a boundary is the next turn's alone) kept, read from the hold record's parent to its change's chain commit; `GET /pass-turns/:turnId/activity` is the turn's log; `POST /tasks/:taskId/turns/:turnId/opened` notes `opened_at` once, for a Ready turn not yet answered. `renamePass` emits `batch.updated` with `pass.changed`. A screen's token reads none of these GETs: only the Workbench draws a pass, and the preview, the goal's pages and the turns read git.
- Sign-off and close of a pass (Workbench spec §5.4, §9.2, §12; `decisions/2026-11-09-sign-off-lands-one-commit-after-the-session-ends.md`, `decisions/2026-11-09-close-pass-shows-its-lists-and-stops-agents-only-on-confirm.md`, `decisions/2026-11-09-a-close-fast-forwards-the-folders-branch.md`, `decisions/2026-11-09-abandon-takes-over-a-closing-pass.md`). `pass/sign-off.ts` is Sign Off (`POST`/`DELETE /passes/:passId/tasks/:taskId/sign-off`, and the Ready `check` item's Sign Off through `applyCheckAnswer`'s `StartSignOff`): a delivery-key job that stops the page's session, waits on a `pass_sign_offs` row for another page's open hold it needs (taken up again by the hold's `pass.changed`, start-up, or its rerun; ended by a message to the page, its take-out, an Abandon, Close Pass and DELETE), then folds hand edits, lands the chain's prefix the page needs (`landSharedChanges`) and the page's files as one commit (`Git.landPaths`, whose `indexStale` the thread reports), and in one write takes the run to DONE by `signOffPath`'s edges. A page sign-off's write is refused when a message came to the page as it landed (the run no longer Ready, or a message no turn took): its commits stay on the branch and the next sign-off lands what the turn adds. Starting a Sign Off closes the page's Ready item with its Sign Off, so the view reads `signing_off` (`signingOff`) and a second Sign Off is refused as not Ready; start-up queues again a sign-off a restart cut short in flight (`resumeSignOffWaits`). A message that came as step 0 stopped the session lands nothing. A Sign Off that does not land (its job failed, its wait was cancelled, it was refused, or the pass stopped being open as it landed) says why on the thread and opens the page's Ready item again, and a landing whose compare-and-swap a hand-typed git raced lands once more from the new tip (`landOnBranch`), the trust card raised only when that retry races too (`Git.landPaths`' `willRetry`). `mcp/claim-wait.ts` answers at once a lane's `request_claim` for a claim of a page whose sign-off waits on that lane's hold. `pass/close-lists.ts` and `pass/unowned.ts` are `GET /passes/:passId/close` (stops nothing; token leaves out who is working); `pass/close.ts` is `POST` (checks the choices against the lists and the pages, `checkCloseRequest` and `closePages`: a Drop of a change a page set to Sign Off Now needs is refused, naming the page; stops the agents, compares the token, checks the request again on the pages the stop left, writes the plan and ends every waiting sign-off, opening its page's Ready item again (`endSignOffWaits`)) and the close job's steps 2-8 by `passes.close_step`, each write only while CLOSING, with 7b's ship injected as `CloseShip` from `daemon/start.ts`; it waits with the folder card while Your folder is off the pass's branch, before it lands (step 2), before its take-outs (step 4) and before the folder's gate and the fast-forward; a failed gate reopens the pass (`SHIPPING → FAILED → OPEN`, one card, no Retry, and a red `gate` header notice with the log's tail, whether it ran in a scratch copy or in the folder; a folder gate's is written by the close in its reopen's write, only when the pass did reopen, and names the pages the close took out, if any), its landed mark moved back before a change chosen Drop that no take-out dropped yet (`rewindSharedLanded`); `createPassCloses().resume()` goes on with each CLOSING pass at start-up, and `POST` on a CLOSING pass whose job stopped on an error (its `close` header notice), or `POST /passes/:passId/close/continue` (Continue Close, no body, 202; 409 unless closing), goes on from its recorded step on the plan it has; a run asked for while the job runs runs once more after it ends, while the pass is closing. The `close` notice (kind `close`) is only ever a stopped close: a pull request the close pushed but could not make ready (`close-pr-ready`) and a follow-on pull request that did not open (`follow-on`) are `pr_not_opened` notices, so neither offers Continue Close nor stops the header's progress line. The notice is a plain sentence naming what the close was doing, with the message of a domain error or of a typed git error (`PassFolderOffBranchError` with how to switch back, `GitNetworkError`, `GitTrustError`), and for any other error (SQLite's, a library's) only a pointer to the log; it comes down each time the job runs again. From step 7 the notice offers no Abandon, which is refused then. Inside the job a `PassFolderOffBranchError` waits with the folder card and goes on, a hold that cannot be kept is let go (`keepOrLetGo`), and a gate stopped by anything but an Abandon stops the close with the notice (`CloseGateStoppedError`). `closePages` refuses Sign Off Now for a page with no run or a FAILED, CANCELLED or TAKEN_OVER one. `pass/fast-forward.ts` is D8; the merge command its card offers names each branch as one shell word (`pass/paste-command.ts`). Abandon (`startAbandon`) writes step 1 outside the key, aborts the pull request's checks and the close's job, then queues; it skips signed-off pages.
- A pass's own exits besides Close Pass (`pass/`). `move-copy.ts` (§8.4): `request_claim` for `migrations` or `deps` from a pass lane is refused, recorded under its opId, where the project allows copies (`delivery: pull_request`; a page's launch claims only its pass's areas), with one flag card per task (`pass-move-copy:<task>`, `PassMoveToCopyDetail`, Move to a Separate Copy / Not Now) and one thread line when it is raised; after Not Now in the pass no card is raised again and the agent is told the builder chose Not Now; Move takes the task out (`takeOut`, alone), places it in a copy (`touches <hazard>`) and starts it there (`MoveToCopyDeps.startInCopy`, the starter in `daemon/start.ts`), where the kept-work gate puts its work back; with no copies the hazard is granted and the thread says the page may be slow. `merged-open.ts` (call 6; `decisions/2026-11-10-a-pass-whose-pull-request-merges-while-open-closes-itself.md`): `subscribeMergedPasses` follows the watch's `batch.updated`, and an open pass whose pull request reads merged closes through `createPassCloses().closeMerged` from a plan whose token is `merged-while-open` (every unfinished page taken out, nothing signed off or placed), which `closeSteps` runs with no gate and, at step 6, `followOnPush` (with unfinished pages nothing; else the pages signed off after the last push go to `openFollowOnPr`); after the job, outside the key, `carryOver` opens the follow-on pass for the taken-out pages with the merged pass's page cap (`CloseDeps.openFollowOn`, `openPass`, so it stacks and puts their work back; when none opens, the card names the branch and the commits not pushed) and raises the `pass_follow_on` card (`pass-follow-on:<pass>`), which also marks the carry-over done; `resume()` closes a merged open pass and carries over one the restart cut short. Close Pass on a merged pass is refused (409) and starts this close. `reopen.ts` (§6.1): `runner.deliverMessage` hands a message to a signed-off page (its run DONE, its pass open) to `reopenSignedOffPage`, which in one write makes a new run of the task in the pass's batch on the implement step (`delivery`'s `passPlan`), queued with `feedback` for the message in a fresh session, and opens the task again; the scheduler claims the page or makes it wait, and the sign-off's per-run opId lands a second commit.
