# apps/daemon/src/plan-record

- `plan-record/` keeps a Plan's whole record and gets it to the lanes (decision `decisions/2026-11-12-a-plan-keeps-its-whole-record-locally.md`); `shape/service.ts` is untouched by it. `sections.ts` indexes a document's ATX headings of levels 1 to 4 outside fences into GitHub slugs (`Task <n>` is `task-<n>`; a leading byte order mark never hides the first heading; a slug is cut by code point to leave room for its `-<n>` under `SECTION_SLUG_MAX_LENGTH`; a section ends at the next heading of its level or higher, or at the next task heading), and `anchors.ts` (`locateAnchor`) finds an excerpt (one final newline aside) at its line (current), within 200 lines (moved) or nowhere (changed); both are pure. `read-bundle.ts` reads a bundle file (absolute) and its body files (relative, at or under the bundle's folder by real path), neither at or under the data dir, the worktree root or a sandbox root (`forbidden-places.ts`, which export uses too), each opened once with `O_NOFOLLOW` and `O_NONBLOCK` and refused when it has another hard link, is no longer at its real path once open, or changes size while read, 16 MiB in all, fatal UTF-8 with the BOM kept; a lone surrogate anywhere in a bundle's text is refused by `PlanBundle`, and `inlineBundle` refuses a `bodyPath` without a file. `validate-bundle.ts` is pure and answers every issue at once (a new revision numbered below a stored one is refused), `lookup.ts` reads what an earlier import stored (`loadStoredRecord`) and the record for export, and `import.ts` (`planImportChanges`, pure, and `importBundle`, in the caller's transaction) writes one Plan or updates it by bundle id: new revision numbers, entry versions, dropped entries superseded, pending unpinned proposals replaced, and after Convert `change:<taskId>` and additions: a converted task is compared with what the Plan's proposals last stated for it (`task-statement.ts`), never with the board, the statement is brought up to the bundle, a change still pending keeps what it carried, and what a change can't carry (headline, why, size, dependencies) is named once in what was left alone. `revisions.ts` (`appendRevision`) is the one way a document, an app spec (`write_spec`) or an eval (Convert) gains a revision, and `backfill.ts` gives the ones kept before revisions their revision 1 at start. The import doors are `POST /projects/:projectId/plans/import` and the builder MCP's `import_plan` (19 tools), one service in `daemon/plan-record-services.ts`; on an imported Plan the session's `propose_plan`, `write_spec` and `resolve_finding` are refused (`shape/tools.ts`). `export.ts` (`POST /shapes/:shapeId/export`) writes `export-layout.ts`'s Markdown into a new, empty or own marked folder (`.10db-plan-export`, written first, so a retry of an export that failed part-way is accepted), refusing a registered checkout, the worktree root, the data dir, a sandbox root and any git work tree, each read through links and for paths not made yet, and a folder that can't be resolved; each file is written under a fresh `O_EXCL | O_NOFOLLOW` name and renamed over its place, so a planted link, hard link or FIFO is replaced, and a file system error is refused naming the file. Convert writes `task_context` for each task with a `planRef` (a change of cites alone keeps the stored pin), keeps a decision with `lasting: false` out of Knowledge and refuses one that supersedes, and refuses a cite of a decision proposal that was dropped or replaced. `plan-context.ts` (`buildPlanContext`) builds the brief's Plan block: the section and shared sections whole, then the cited decisions, names, facts and experiments, open imported findings on the section and intent within `PLAN_CONTEXT_BUDGET_TOKENS` (6,000), the rest named; a cited fact a re-import superseded, or a decision dropped or replaced, carries `dropped` and its line says so, and a superseded fact's anchors are never checked; `plan-lines.ts` writes each item's line, which both the budget and `briefing/plan-context-text.ts` (`renderPlanContext`) use. An anchor reads only this workstream's checks at the base it reads (the runner's first pack passes the base it read, since the row has none yet) for the fact's current version. `anchor-check.ts` (`checkTaskAnchors`) runs in the runner right after the base is read and before the stop and account-move re-checks, through the daemon's git (`fileAt`, 4 MiB cap), once per workstream, base and fact version; a git error or an oversized file is `unchecked` with a note, a URL is never fetched, and a throw is logged and never stops the session. The runner keeps the rendered block in `task_context.packed_text` in the write that emits `context.packed` (`recordPlanPacked`). The lane tools `get_plan_section`, `get_plan_entry` and `find_plan_entries` (`mcp/plan-tools.ts`) are read-only and find their Plan by the task's pin, else its own or its goal's `shape_links` row, never by key across Plans; `get_plan_entry` also reads an imported finding by its key, search reads an entry's string values (never its field names) and findings' text, and a section hit names the revision it read. `record-read.ts` answers the Record view's reads (`GET /shapes/:shapeId/record`, `/shapes/:shapeId/record/:list`, `/shapes/:shapeId/documents/:documentId/revisions/:number` and `GET /tasks/:taskId/plan-context`, each a database read the dev UI may make and a screen may not): every list is filtered, sorted and paged here (25, 50 or 100 rows), a document is read by its attachment id, since a goal's spec and its eval share a key, a superseded proposal is left out unless its state is asked for, an entry and a task's Plan context show only the checks of each entry's current version (each check names its `entryVersion`), and a task's Plan context is the block stored when its lane was packed, never one built now.
