# apps/daemon/src/sandbox

- `sandbox/` opens a session's setup read-only (`setup-reads.ts`: `setupReadRefusal` judges each real path,
  `collapseReads` keeps the profile small; `setup-dir.ts`: `keepSetup` and `createSetupDir`, one
  `10db-setup-<hex>` dir per session in the files root, removed with its sandbox and swept by `stale-files.ts`, as is
  a pass's `10db-read-<hex>` dir (`secret-reads.ts`), where the broker writes a copy of a checkout secret the
  builder allowed a Read of, since Claude Code's deny rule on the secret stays;
  `plugin-wrapper.ts`: a wrapper per plugin linking `skills`, `agents` and `commands` by folded name and
  re-emitting `hooks/hooks.json` with each command started in the wrapper, never MCP or LSP servers). Every `.env*` file and folder in an opened read, and what a link in a `.env*` folder
  leads to, is denied to the kernel, Claude Code's rules and the file-access judge. Only the lane profile gets
  setup reads, never a gate's or a repo MCP server's. `test/setup-reads.seatbelt.test.ts` holds it against the
  kernel.
- `sandbox/` owns the lane and gate sandbox: the settings profile Claude Code's Bash sandbox runs under (`buildLaneProfile`, validated by `LaneSandboxSettingsSchema`, whose field names match the SDK's `SandboxSettings`), the protected reads, the toolchain reads, the env-name allowlist, each lane's short temp directory and the package caches inside it, and its read-only `CLAUDE_ENV_FILE` (`env-file.ts`), which exports every variable the sandbox sets for lane commands (the package caches, the mise variables, `xcrun_db`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_OPTIONAL_LOCKS=0`, an empty `XDG_CONFIG_HOME` in the temp dir, `TENDB_SANDBOX=1`; `CARGO_HOME`'s `bin` is a link to `~/.cargo/bin` so mise finds its rustup-linked rust) before each command, single-quoted, because Claude Code strips variables that point a tool at its config, `GIT_CONFIG_GLOBAL` and `CARGO_HOME` among them, from a sandboxed command's env. A new variable for sandboxed commands goes in `prepareCommandEnv` (`command-env.ts`), which feeds a lane's session env and its file, and a gate's env. A lane's session env, which Claude Code and its own git run with outside the sandbox, holds no variable whose value is the temp dir or a path in it (`withoutTempDirPaths`, applied by `forSession`), except `CLAUDE_CODE_TMPDIR`: a lane writes there, and a tool outside the sandbox that followed the variable would run what it wrote (mise's `[env] _.source`, xcrun's cache file, `XDG_CONFIG_HOME`, cargo's `rustc-wrapper`). The file and a gate's inner env carry them all; `LaneSession.commandEnv` is the full set, and `lane-sandbox.test.ts` and the live test fail on a path in the session env. Toolchain reads that only list a dir (mise's `installs` and its tool dirs) are `toolchainAccess`'s `listings`, two exact-match patterns per dir (`listingGrant`, `childListingGrant`), the only patterns the profile holds; never open a dir whole and deny secrets inside it. It imports no SDK and only `guard` (for the file system's case fold); callers pass paths in. Every real lane and gate runs under it, with no switch. `startDaemon`'s `sandbox` option is required and builds both; `createRunner`'s `laneSandbox` and `createGateRunner`'s `sandbox` are required too. `daemonOptionsFromEnv` gives `{}` unless the sessions are fake (`TENDB_FAKE_SCRIPTS`, development and e2e only), where it gives `null` and the gate runs unsandboxed, and tests pass `null` explicitly. With no sandbox, the daemon's git counts no temp root as lane-writable. The Claude adapter refuses a session whose spec has no sandbox unless it was built with `allowUnsandboxed: true`, which only tests that script the SDK set. Package caches, cargo's `CARGO_HOME` included, are per lane, in `<temp dir>/cache`: a cache can hold code a later install or build runs, so no two lanes share one. The sandbox adds no unsandboxed process that acts on lane-writable input (a manifest, a lockfile, `PATH`, config in the checkout), so nothing is prefetched. Approved repo stdio MCP servers run under srt too (below). `projectAccess` (`project-access.ts`) reads what both sandboxes are built from: the checkout's real path and `.env*` files, the protected reads, the toolchain, the stored hosts and read paths, and the git state of every registered checkout. mise's system config (`/etc/mise`) is denied and `MISE_SYSTEM_DIR` points at the lane's own mise dir. `forSession` takes every project's checkout (`checkouts`), whose PATH entries are dropped. mise's config dir is never opened: each lane gets its own global mise config (`mise-config.ts`). Each project's `sandboxLoopback` (Settings › General, "Let lane commands use localhost"), read before each session and passed to `forSession` with the project, lets its commands bind and connect on localhost. Under the sandbox the broker (`inbox/permission-broker.ts`) allows a Bash call without a card unless it is a hazard or something unread could make it one (`guard/unread-commands.ts`: an unnamed program, an unread script, an uncertain structure, or an unread argument that could select a hazard form of a program that has one; an unread argument to any other program is allowed), denies an unlisted `SandboxNetworkAccess` host at once with one card per host per session, and judges Read, Grep, Glob and the edit tools on real paths (protected paths are refused with no card, but in a pass (`LaneSessionInput.attended`) a Read of one of the checkout's own `.env*` files is carded instead: `FileAccessContext.secretsOnCard`, with a Claude Code ask rule in place of its deny rule, while the kernel and every search still deny it, and so is a read under the worktrees folder outside the session's own copy, `outside-copy`, with a message naming the copy; that check comes before the read list, so a stored Read rule doesn't open such a path: decision `2026-11-03-a-path-outside-the-lanes-copy-is-refused-not-carded.md`); a Read of a file directly in the session's own Claude Code task output directory (`<own temp dir>/claude-<uid>/<slug of the checkout>/<provider session id>/tasks/`, derived exactly, `isOwnTaskOutput` in `sandbox/file-access.ts`) is allowed with no card, and another session's, a lookalike under another uid or slug and a link out of it still ask (decision `2026-11-01-lane-reads-its-own-task-output.md`). A `Monitor` call is judged as a Bash command (its command runs inside the sandbox) and carded only for a hazard, an endless loop or an input key beyond command, description and timeout_ms (decisions `2026-10-30-lane-monitor-of-its-own-task-output.md` and `2026-10-31-lane-monitor-names-its-output-file-in-a-variable.md` are superseded). A Grep, Glob or LS of a directory that holds a protected path is refused too, so a data dir or account config dir inside the checkout makes every Grep, Glob or LS of the checkout root refused. The sandbox's own env sets `GIT_CONFIG_GLOBAL=/dev/null`, the one exception to keeping git config variables. A change here must keep the live test (`test/lane-sandbox.live.test.ts`, `TENDB_LIVE_CLAUDE=1`, never in `make gate`) passing, and re-run it after each Claude Code or SDK upgrade. The checkout's git dir, its common dir and `<checkout>/.git` (file or directory, wherever the git dir lies) are `denyWrite` in the profile, and so are every other registered checkout's (from `checkouts`, through `gitDirs`); every other registered checkout that isn't this one's ancestor is `denyWrite` as a whole (`otherCheckouts`), for lanes and gates, so a project nested in this checkout stays read-only too and `git/`'s exemption for a registered checkout's `.git` holds: only the daemon writes git state, and the lane env sets `GIT_OPTIONAL_LOCKS=0` so its read-only git works. The guard refuses `git push` for every lane.
- **Docker** (`projects.sandbox_docker`, "Allow Docker"; decision `2026-11-08-a-project-turns-docker-on-for-its-gate-and-lanes.md`): off, a gate's `docker` is a shim that refuses (`DOCKER_REFUSAL`, exit 125) and a lane has no engine socket. On, `dockerAccess` (`sandbox/docker-access.ts`) gives the gate and lane profiles the engine sockets (`dockerSockets`, which Codex's lane takes as `unix_sockets` too), the CLI's exact reads and the `DOCKER_HOST`, `DOCKER_CONTEXT` and `COMPOSE_*` names, and the gate has no shim. Docker reaches the whole host, so the switch is the builder's. `daemon/auto-docker.ts` wraps the shared gate runner: it gives every project's gate the switch as stored, turns it on (and says so in one Inbox card, `inbox/docker-card.ts`) only when the gate command or its Makefile target calls docker in `origin/<base>`'s commit (`daemon/docker-need.ts`, never the working tree or the local base branch, where a local-delivery project's lanes commit), and never when `sandbox_docker_opt_out` says the builder turned it off. A gate that fails on a refused `docker` turns nothing on and is not rerun: it leaves one Inbox card (`raiseDockerMayBeNeededNote`) that the project may need Docker, with the Settings switch and the answers Turn Docker on and Keep it off (which records the opt-out, as Settings does); once one was answered, no later refusal raises another. What reads lane-writable input to decide must not turn on a capability from it.
- The gate runs under srt (`gate-sandbox.ts`, decision 132): `createGateSandbox(...).forRun` builds the lane profile with `buildLaneProfile` (the checkout and the run's own temp dir writable, srt's `/tmp/claude` closed, the project's hosts with `strictAllowlist`, loopback from the project's switch), writes srt's settings to a sealed file (`sealed-file.ts`) and returns what to spawn: node running srt's command line (`resolveSandboxRuntime` in `paths.ts`: a bundle runs only its own `srt.mjs` and fails to start without it, never searching `node_modules`; source runs use the dependency), one srt process per run. `forRun` refuses (`SandboxProfileError`) an srt or node that lies, as written or through a link, at or under a registered checkout or a root lanes write, since both run outside the sandbox; so a daemon run from source can't gate a project whose checkout holds that source. The gate's env is the lanes' allowlist of the project env plus `prepareCommandEnv`'s, set inside the sandbox by `/usr/bin/env`; srt's host sees only a system `PATH`, `HOME` and `CLAUDE_CODE_TMPDIR`. A `docker` that refuses leads its `PATH` (`DOCKER_REFUSAL`). `verify/gate-runner.ts` runs what the sandbox returns in its own process group, kills that group when srt closes so nothing the gate left running outlives its verdict, and awaits its `dispose()`, which removes the temp dir off the event loop; a refused profile is a failed gate (exit 126) with its reason. srt exits 0 when its own child dies by SIGTERM or SIGINT, so the command runs under a shell that traps both and exits 143 or 130; never `exec` the command as srt's child. `test/gate-sandbox.seatbelt.test.ts` and `test/gate-toolchains.seatbelt.test.ts` (mise's installs, a rustup-linked rust, Apple's xcrun shims) run the real srt on macOS in `make gate`, skipped on Linux and inside a sandbox; daemon tests that start a sandboxed daemon pass `FAKE_SRT` (`test/fake-srt.ts`) as its runtime. `scripts/sandboxed-gate.ts` runs a project's gate command under the sandbox by hand. A gate run with `packageInstall` (only `delivery/worktree-dependencies.ts` asks) also gets pnpm's lock directory in the system temp dir open (`sandbox/pnpm-lock-dir.ts`: made private, refused if it is a link or open to others, swept of non-files afterwards, and walked only once renamed into the lane temp root, on the system data volume and closed to every sandbox, never at its own path, which every ChatGPT lane can write; a rename that fails walks nothing, the moved tree is removed by `find` and `rm -rf`, which never follow a link, after only its directories' modes, user flags and ACLs are opened, so no file's metadata changes, a second link's included, and each sweep first removes every moved tree left in that root), and runs no repository code: the worktree install passes `--ignore-scripts --ignore-pnpmfile`. A change here must keep that test and 10db's own gate under `scripts/sandboxed-gate.ts --loopback --host index.crates.io --host static.crates.io` passing. Run the script from a checkout other than the one it gates (it refuses an srt that lies in the gated checkout), and `knip.json` names the lefthook config file, so knip reads no `.git/hooks` of the main checkout from a linked worktree.
- Approved repo stdio MCP servers run under srt (`mcp-sandbox.ts`, decision 133): `LaneSandbox.forSession` takes the session's expanded stdio servers (`mcpServers`) and returns each as a `SandboxedMcpServer` on `LaneSession.mcpServers`, whose launch is a private field read through `launch()` and whose constructor takes a key only `mcp-sandbox.ts` holds; `SessionSpec.projectMcpServers` requires one for stdio, so an unsandboxed server or a copy of a sandboxed one doesn't typecheck, and `toSdkMcpServer` reads it by `instanceof`. A server whose sandbox can't be built (`SandboxProfileError`, such as an approved value with a control character) goes on `LaneSession.mcpFailures`, which the runner flags and names in the prompt; the session starts. `createLaneSandbox` takes the same `runtime` as the gate. Claude Code runs `/usr/bin/env -i` with a system `PATH`, `HOME` and srt's temp variable, then node and srt; inside, `/usr/bin/env -i` keeps only srt's proxy variables, by name, and `/bin/sh -c` sources the server's env from a sealed file and execs the command as srt's child. No approved value is on a command line: `readRepoMcp` ignores, with a warning card, a stdio server whose command or args hold `${`. Its profile is the lane profile with only its own temp dir writable (not the checkout) and the Mach service `com.apple.SystemConfiguration.configd` open beside FSEvents (an HTTP client such as uv's reads the system proxy settings through it, and panics without), the hosts its approval names and no others (`.10db/mcp-hosts.json`, read by `sessions/mcp-hosts-file.ts` and part of the config hash) and never loopback, whatever the project's switch; its env is the lanes' allowlist, `prepareCommandEnv`'s, `NODE_USE_ENV_PROXY=1`, `TMPDIR`, and `PATH`, `HOME` and its approved variables. A server whose declared env sets `AWS_PROFILE` to a literal never gets the profile or `~/.aws`, whose SSO token reaches every role the builder holds: `withAwsCredentials` (`sessions/project-mcp.ts`) swaps the profile for that one role's short-lived credentials, which `environment/aws-credentials.ts` exports with the AWS CLI outside the sandbox (`inbox/project-mcp-reader.ts` runs the step; an export that fails is a flag telling the builder to run `aws sso login --profile <profile>`). The sandbox's package caches include uv's (`UV_CACHE_DIR`, `UV_TOOL_DIR`, `UV_PYTHON_INSTALL_DIR`), so `uvx` works there on the system Pythons. srt runs with `SRT_DEBUG=1` and a sealed preload (`-r`, `mcp-refusals.ts`) that keeps its debug log off stderr and writes each host its proxy refused to a per-server log, both in the files root beside the server's other files; the daemon polls that log through the `Clock` and warns `{ server, host }` (`REFUSED_MESSAGE`), so a refused host shows in the daemon log with the server's name (`decisions/2026-11-06-a-refused-mcp-host-is-logged-and-a-changed-approval-names-its-new-hosts.md`). An approval card for a changed config names the hosts it adds and drops against the latest approval of the server (`earlierMcpApproval`). Each server's temp dir and files go with the lane session's `dispose()`. 10db makes nothing in the system temp dirs (`SYSTEM_TEMP_ROOTS`: `/private/tmp` and `/private/var/tmp`), which Codex's base policy opens to every ChatGPT lane, but pnpm's lock directory (the gate's, above), which a package-install gate opens and which is walked only after it is moved into the lane temp root (`temp-dir.ts`). The temp dirs of Claude lanes, gates and MCP servers go in `laneTempRoot()` (`/Users/Shared/10db-<uid>`, short enough for the socket path limit; each temp dir is named by six random characters, so Claude Code's own dir in it, `claudeCodeTmpPath`, fits `MAX_SANDBOX_TMP_BYTES`, and a longer one is refused, since Claude Code would fall back to the shared `/tmp/claude-<uid>` without a word), a ChatGPT lane's in `codexLaneTempRoot` (`~/.10db/lanes`, the runner's `codexLaneTempRoot`, passed as `LaneSessionInput.tempRoot` with `provider`; only a Codex session's temp dir has no length limit), and sealed files, env files, MCP servers' refusal logs and process ledgers in `sandboxFilesRoot` (`~/.10db/run`, `ProjectAccessDeps.filesRoot`). Every profile, a lane's, a gate's and an MCP server's, denies all three roots (`ProjectAccess.sandboxRoots`, `LaneProfileInput.sandboxRoots`) but for its own temp dir and own files there (`ownFiles`: a lane's or a server's env file), and leaves out every readable entry that is or holds a root, a built-in `SYSTEM_READS` one such as `/tmp` on Linux included (srt would close the own files under it too; `readListOverSandboxRoots`, and `forSession` logs each such entry once per session, naming it); a profile whose checkout or extra write is or holds a root is refused (`SandboxProfileError`), so a project that holds `~/.10db` runs no lane. `startDaemon` builds both sandboxes through `sandboxesFor` (`daemon/sandbox-roots.ts`, which `scripts/sandboxed-gate.ts` and the live tests use too, through `openSandboxRoots` and `sandboxDepsOf`). At start, before any session or gate, it makes each root with `ensurePrivateRoot` (mode 0700, its real path; a link, a non-directory or another user's directory is refused, and then every lane session and gate is refused with the reason and no root is claimed), writes `.metadata_never_index` in each (`keepSpotlightOut`, as `git/`'s worktree root does; no sweep or claim matches that name), asks Time Machine to skip each (`keepRootsOutOfBackups` with `tmutilExclusion`, `tmutil addexclusion`, off the event loop and never waited on; a root it could not exclude is logged, `stop()` ends what still runs, and `DaemonOptions.sandbox.backups` replaces it in tests), and calls `claimSandboxRoots` (`stale-files.ts`): in each root it removes this user's lane temp dirs and sealed files by their exact names, never following a link, unless a live daemon's `10db-daemon-<pid>` mark is there, then marks the root until `stop()`. After the ledger reap, before any session or gate, `sweepSystemTempFiles` unlinks 10db's sealed files and ledgers from the system temp dirs, never reading one (a ChatGPT lane can read and write there); once it listens, `sweepSystemTempDirs` removes its lane temp dirs there (`10db-` and six characters, the name they had there) off the event loop, testing each name before it looks at the entry, and `stop()` aborts it between entries and waits for it. Neither marks anything there, and a mark there counts only while its pid's command line, read from `ps -axo pid=,command=`, names `daemon.mjs` or `src/main.ts`: a mark naming any other running process keeps nothing, and when `ps` can't be read every live mark counts. The pnpm lock directory's sweep is async and tells `GateSandboxDeps.log` (required; the daemon and the script pass theirs) what it can't remove in the lane temp root instead of refusing the run. The file tools treat every sandbox root (`laneTempRoot`, the Codex lanes root, the system temp dirs and the files root), all but the session's own temp dir, as a protected read and refuse writes there (`FileAccessContext.sandboxTemp`); so does a Shape session (`ShapeAccess.sandboxRoots`). The Codex lanes root and the system temp dirs (`codexLaneTempRoot`, `laneWritableRoots`) count as the temp root does for PATH entries and srt, and the daemon's git, project registration and the worktree root treat every lane-written root as lane-writable. With no lane sandbox the runner leaves stdio servers out and names them in the prompt. `test/mcp-sandbox.seatbelt.test.ts` runs a probe server under the real srt on macOS, in `make gate` and CI's macOS job.
- A lane session's commands end with the session (`decisions/2026-10-30-stop-what-a-lane-session-started.md`). `sandbox/lane-processes.ts` samples the process table (`process-table.ts`, `ps -axo pid=,ppid=,pgid=,lstart=`; a reading shared among sessions) from the pid Claude Code reports (the first reading fresh, never the shared one), remembers what runs under it and in its process groups by pid and start time, plus each child of launchd started since the session began that holds a path in the session's own temp dir, its working directory or an open file such as Claude Code's per-command output file (`lsof`, read once per process): the job of a command that returned at once (`pnpm dev &`). Working in the checkout alone never makes a process the session's: other lanes and the builder run jobs there. It writes all this to a ledger, `10db-proc-<daemon pid>-<hex>.json`, in the files root (Bash can't write there and the file-access judge refuses file-tool writes outside the session's own temp dir; `claimSandboxRoots` leaves it), with the daemon's own process group (`daemonGroup`), each time by renaming a whole new file over it (`<ledger>.<hex>.tmp`, which is never read as a ledger and which a reap removes once its daemon is gone). A failed `lsof` keeps what the tree and the groups gave, and each kind of watch failure (the ledger write, `ps`, `lsof`) is logged once per session (`LaneSandboxDeps.log`). The ledger is removed at `dispose()` only when `endProcesses` stopped everything; otherwise the daemon's `createLedgerSweep` tries again every 30 s until a round can read the machine, and the next start stops whatever is still left. A round reaps every ledger but a running session's (held from `forSession` to `dispose()`) and another running daemon's; the start's own reap hands its failures to the same sweep, which `stop()` ends. The runner calls `LaneSession.trackProcesses` at `started` with the pid and the start time `identifyProcess` read, or none when that `ps` failed: the watch then reads the process itself, from a fresh table on each sample until one lists the pid, the runner logs a warning while it is not watched, and `endProcesses` rejects (logged too) if no reading ever listed it. It calls `endProcesses` in its `finally`, after the Claude Code process is gone and before `dispose()`: SIGTERM to each remembered process and its group, SIGKILL after 1.5 s to what is left. `startDaemon` calls `reapLaneProcessLedgers` right after the claim, before recovery and any session, and stops every ledger's processes but those of another daemon that still runs (its pid alive and its mark in the root), even when one shares the root. It never follows or signals the group of the daemon that kept a ledger, which Claude Code was spawned into and the daemon was started in (a terminal's job, the app's): a process there is signalled by pid alone, and a ledger with no group recorded has no group signalled. Never signal launchd, the daemon, its process group, the group of a ledger's daemon, or a pid whose start time changed; never read a process's environment. `guard/background-loops.ts` (`startsEndlessBackgroundLoop`) makes the broker ask before a Bash command puts something endless in the background (`while :`, `yes`, `cat /dev/zero` with an `&`, or anywhere in a call with the Bash tool's own `run_in_background` flag, any value but an absent or false one). No stored rule answers that card, and it offers only allow-once and deny, so it stores none. A denial's text covers equivalents (`denialMessage`), and `deniedPermissionsForWorkstream` (`@10db/db`) gives the next sessions of the workstream the same denials and notes in their prompt (`PromptInput.denials`), less any denied read outside the lane's copy (`denialsForLane`). `answeredCardsForTask` (`@10db/db`) gives a review step the cards the builder already answered on its task (`PromptInput.answeredCards`), and the runner sends them again after a compaction, so a reviewer checks a decision against them instead of asking again; other steps aren't shown them. Tests inject the table and the signals (`sandbox.processes`); `sandbox/lane-processes.system.test.ts` uses the real ones and skips where `ps` can't run.
