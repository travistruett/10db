# apps/daemon

The 10db daemon: the only database writer. It serves the UI over loopback HTTP and WebSocket,
serves agents over MCP, and runs Claude Code sessions and, for a `codex_signin` account, Codex sessions through
`codex app-server` (`sessions/codex-*.ts`).

- `src/env.ts` is the only module that parses or validates environment variables; `src/main.ts`
  hands it `process.env`. Every variable is in `.env.example` with a comment. Errors name variables
  and problems, never values. `main.ts` exits 4 with one line on an `EnvError` or a `WorktreeRootError`,
  and the desktop supervisor stops instead of restarting into the same refusal.
- `TENDB_BENCHMARKS=off` keeps a daemon from reading the Artificial Analysis key and from calling AA
  (`aaKeyReaderFromEnv`: the sync records `no_key`). Only the installed app's daemon syncs; the e2e web
  server, the live acceptance daemon and `scripts/dev.sh` set it, and `tests/repo/src/benchmarks-off.test.ts`
  checks they do. A new launcher of a throwaway daemon sets it too.
- `TENDB_CATALOGUE=off` keeps a daemon from fetching the model catalogue from models.dev
  (`catalogueSync` in `daemonOptionsFromEnv`); the stored copy and the release snapshot are still read. It also turns
  off the account-list refresh that follows each fetch, so a daemon test never spawns a probe.
  The e2e web server, the live acceptance daemon and every daemon test that spawns the entry with its own
  environment (`test/crash-recovery.test.ts`, `parent-death`, `bundle`, `refused-config`) set it, and
  `tests/repo/src/benchmarks-off.test.ts` checks they do. `scripts/dev.sh` leaves it on, so `pnpm dev` sees
  real data; the fetch is one daily GET with no key. A new launcher of a throwaway daemon sets it too.
  `DaemonOptions.catalogueSync` is off unless given, so an in-process test harness never reaches the network.
- `TENDB_CATALOGUE_SNAPSHOT` (an absolute path; `catalogueSnapshotFromEnv`) names the catalogue file read when none is
  stored, instead of the one beside the bundle. `startDaemon` rebuilds the model profiles from the catalogue it holds
  (stored, else snapshot) before it returns, whatever `catalogueSync` says, so a daemon that never fetches still plans
  and launches on real models. Every launcher that sets `TENDB_CATALOGUE=off` also sets this to
  `test/fixtures/catalogue.json`, and `tests/repo/src/benchmarks-off.test.ts` checks it.
- `TENDB_JUDGE=off` keeps a daemon from reading the OpenRouter key and from calling OpenRouter (`judgeOff` in
  `daemonOptionsFromEnv`; every decision then keeps today's rule). Only the installed app's daemon asks models;
  the e2e web server, the live acceptance daemon and `scripts/dev.sh` set it, and
  `tests/repo/src/benchmarks-off.test.ts` checks they do. A new launcher of a throwaway daemon sets it too.
- `src/api/` is typechecked by the desktop app too (it imports `AppType`). Code there must not import
  `node:*` modules or `@10db/db`; receive services through the `ApiServices` interface (passed in `ApiDeps`).
- The package entry (`src/index.ts`) exports types only.
- Listen on `127.0.0.1` only.
- Browser origins: only the Tauri webview's are built in. `TENDB_DEV_UI_ORIGIN` opts one loopback http origin in
  (`decisions/2026-10-29-dev-ui-over-the-factory.md`); a launcher of a daemon a browser UI talks to sets it.
- `pnpm --filter @10db/daemon build [outDir]` bundles everything into `dist/daemon.mjs`, bundles srt's
  command line (`@anthropic-ai/sandbox-runtime`) into `srt.mjs`, copies srt's Java proxy agent to
  `vendor/java-proxy-agent/srt-proxy-agent.jar`, where srt looks before it runs `npm root -g` unsandboxed from
  the gate's checkout, and copies migrations (`drizzle/`) and the
  SQLite addon (`better_sqlite3.node`) beside it. Nothing stays external: the Tauri sidecar runs the bundle
  from a directory with no node_modules.
  `better-sqlite3` is still a daemon dependency: the build copies its addon, and
  `test/crash-recovery.test.ts` opens the database with it directly.
- `pnpm --filter @10db/daemon dev` runs from source with tsx and loads `apps/daemon/.env` when it
  exists. Copy `.env.example` to `.env` to override a variable; `.env` is git-ignored.

## Modules

`src/<module>/` directories are flat; each exports its public surface from `index.ts`, and other
modules import only that (ESLint enforces it). Dependencies point one way:

`clock`, `log`, `events`, `judge`, `guard`, `permissions`, `sandbox`, `git`, `github`, `verify`, `routing`, `picker`, `folders`, `placement`, `knowledge` → `sessions`, `inbox`, `briefing`, `team` →
`delivery`, `accounts` → `mcp` → `screens` → `shape` → `runner` → `watcher`, `scheduler`, `recovery`, `backups`, `benchmarks`, `self-update` → `daemon` (composition root) → `main.ts`.
`api` depends only on `@10db/contracts` and its own `ApiServices` interface; the composition root
implements it and hands it to `createApp` in `ApiDeps`.

Time comes from an injected `Clock`; never call `Date.now()` or `setTimeout` directly in logic.

The fake adapter (`sessions/fake-adapter.ts`) is the test boundary for Claude Code; daemon tests never call the real CLI.

- **The security rule.** No process outside a sandbox acts on lane-writable input (a file in a checkout, a
  `PATH` entry or tool variable that names one, a lockfile). Remove a capability rather than check for its
  misuse. Never deny individual secrets inside an otherwise open tree: open only what is needed.
- `sandbox/` owns the lane and gate sandbox: the settings profile Claude Code's Bash sandbox runs under (`buildLaneProfile`, validated by `LaneSandboxSettingsSchema`, whose field names match the SDK's `SandboxSettings`), the protected reads, the toolchain reads, the env-name allowlist, each lane's short temp directory and the package caches inside it, and its read-only `CLAUDE_ENV_FILE` (`env-file.ts`), which exports every variable the sandbox sets for lane commands (the package caches, the mise variables, `xcrun_db`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_OPTIONAL_LOCKS=0`, an empty `XDG_CONFIG_HOME` in the temp dir, `TENDB_SANDBOX=1`; `CARGO_HOME`'s `bin` is a link to `~/.cargo/bin` so mise finds its rustup-linked rust) before each command, single-quoted, because Claude Code strips variables that point a tool at its config, `GIT_CONFIG_GLOBAL` and `CARGO_HOME` among them, from a sandboxed command's env. A new variable for sandboxed commands goes in `prepareCommandEnv` (`command-env.ts`), which feeds a lane's session env and its file, and a gate's env. A lane's session env, which Claude Code and its own git run with outside the sandbox, holds no variable whose value is the temp dir or a path in it (`withoutTempDirPaths`, applied by `forSession`), except `CLAUDE_CODE_TMPDIR`: a lane writes there, and a tool outside the sandbox that followed the variable would run what it wrote (mise's `[env] _.source`, xcrun's cache file, `XDG_CONFIG_HOME`, cargo's `rustc-wrapper`). The file and a gate's inner env carry them all; `LaneSession.commandEnv` is the full set, and `lane-sandbox.test.ts` and the live test fail on a path in the session env. Toolchain reads that only list a dir (mise's `installs` and its tool dirs) are `toolchainAccess`'s `listings`, two exact-match patterns per dir (`listingGrant`, `childListingGrant`), the only patterns the profile holds; never open a dir whole and deny secrets inside it. It imports no SDK and only `guard` (for the file system's case fold); callers pass paths in. Every real lane and gate runs under it, with no switch. `startDaemon`'s `sandbox` option is required and builds both; `createRunner`'s `laneSandbox` and `createGateRunner`'s `sandbox` are required too. `daemonOptionsFromEnv` gives `{}` unless the sessions are fake (`TENDB_FAKE_SCRIPTS`, development and e2e only), where it gives `null` and the gate runs unsandboxed, and tests pass `null` explicitly. With no sandbox, the daemon's git counts no temp root as lane-writable. The Claude adapter refuses a session whose spec has no sandbox unless it was built with `allowUnsandboxed: true`, which only tests that script the SDK set. Package caches, cargo's `CARGO_HOME` included, are per lane, in `<temp dir>/cache`: a cache can hold code a later install or build runs, so no two lanes share one. The sandbox adds no unsandboxed process that acts on lane-writable input (a manifest, a lockfile, `PATH`, config in the checkout), so nothing is prefetched. Approved repo stdio MCP servers run under srt too (below). `projectAccess` (`project-access.ts`) reads what both sandboxes are built from: the checkout's real path and `.env*` files, the protected reads, the toolchain, the stored hosts and read paths, and the git state of every registered checkout. mise's system config (`/etc/mise`) is denied and `MISE_SYSTEM_DIR` points at the lane's own mise dir. `forSession` takes every project's checkout (`checkouts`), whose PATH entries are dropped. mise's config dir is never opened: each lane gets its own global mise config (`mise-config.ts`). Each project's `sandboxLoopback` (Settings › General, "Let lane commands use localhost"), read before each session and passed to `forSession` with the project, lets its commands bind and connect on localhost. Under the sandbox the broker (`inbox/permission-broker.ts`) allows a Bash call without a card unless it is a hazard or something unread could make it one (`guard/unread-commands.ts`: an unnamed program, an unread script, an uncertain structure, or an unread argument that could select a hazard form of a program that has one; an unread argument to any other program is allowed), denies an unlisted `SandboxNetworkAccess` host at once with one card per host per session, and judges Read, Grep, Glob and the edit tools on real paths (protected paths are refused with no card, and so is a read under the worktrees folder outside the session's own copy, `outside-copy`, with a message naming the copy; that check comes before the read list, so a stored Read rule doesn't open such a path: decision `2026-11-03-a-path-outside-the-lanes-copy-is-refused-not-carded.md`); a Read of a file directly in the session's own Claude Code task output directory (`<own temp dir>/claude-<uid>/<slug of the checkout>/<provider session id>/tasks/`, derived exactly, `isOwnTaskOutput` in `sandbox/file-access.ts`) is allowed with no card, and another session's, a lookalike under another uid or slug and a link out of it still ask (decision `2026-11-01-lane-reads-its-own-task-output.md`). A `Monitor` call is judged as a Bash command (its command runs inside the sandbox) and carded only for a hazard, an endless loop or an input key beyond command, description and timeout_ms (decisions `2026-10-30-lane-monitor-of-its-own-task-output.md` and `2026-10-31-lane-monitor-names-its-output-file-in-a-variable.md` are superseded). A Grep, Glob or LS of a directory that holds a protected path is refused too, so a data dir or account config dir inside the checkout makes every Grep, Glob or LS of the checkout root refused. The sandbox's own env sets `GIT_CONFIG_GLOBAL=/dev/null`, the one exception to keeping git config variables. A change here must keep the live test (`test/lane-sandbox.live.test.ts`, `TENDB_LIVE_CLAUDE=1`, never in `make gate`) passing, and re-run it after each Claude Code or SDK upgrade. The checkout's git dir, its common dir and `<checkout>/.git` (file or directory, wherever the git dir lies) are `denyWrite` in the profile, and so are every other registered checkout's (from `checkouts`, through `gitDirs`); every other registered checkout that isn't this one's ancestor is `denyWrite` as a whole (`otherCheckouts`), for lanes and gates, so a project nested in this checkout stays read-only too and `git/`'s exemption for a registered checkout's `.git` holds: only the daemon writes git state, and the lane env sets `GIT_OPTIONAL_LOCKS=0` so its read-only git works. The guard refuses `git push` for every lane.
- The gate runs under srt (`gate-sandbox.ts`, decision 132): `createGateSandbox(...).forRun` builds the lane profile with `buildLaneProfile` (the checkout and the run's own temp dir writable, srt's `/tmp/claude` closed, the project's hosts with `strictAllowlist`, loopback from the project's switch), writes srt's settings to a sealed file (`sealed-file.ts`) and returns what to spawn: node running srt's command line (`resolveSandboxRuntime` in `paths.ts`: a bundle runs only its own `srt.mjs` and fails to start without it, never searching `node_modules`; source runs use the dependency), one srt process per run. `forRun` refuses (`SandboxProfileError`) an srt or node that lies, as written or through a link, at or under a registered checkout or a root lanes write, since both run outside the sandbox; so a daemon run from source can't gate a project whose checkout holds that source. The gate's env is the lanes' allowlist of the project env plus `prepareCommandEnv`'s, set inside the sandbox by `/usr/bin/env`; srt's host sees only a system `PATH`, `HOME` and `CLAUDE_CODE_TMPDIR`. A `docker` that refuses leads its `PATH` (`DOCKER_REFUSAL`). `verify/gate-runner.ts` runs what the sandbox returns in its own process group, kills that group when srt closes so nothing the gate left running outlives its verdict, and awaits its `dispose()`, which removes the temp dir off the event loop; a refused profile is a failed gate (exit 126) with its reason. srt exits 0 when its own child dies by SIGTERM or SIGINT, so the command runs under a shell that traps both and exits 143 or 130; never `exec` the command as srt's child. `test/gate-sandbox.seatbelt.test.ts` and `test/gate-toolchains.seatbelt.test.ts` (mise's installs, a rustup-linked rust, Apple's xcrun shims) run the real srt on macOS in `make gate`, skipped on Linux and inside a sandbox; daemon tests that start a sandboxed daemon pass `FAKE_SRT` (`test/fake-srt.ts`) as its runtime. `scripts/sandboxed-gate.ts` runs a project's gate command under the sandbox by hand. A gate run with `packageInstall` (only `delivery/worktree-dependencies.ts` asks) also gets pnpm's lock directory in the system temp dir open (`sandbox/pnpm-lock-dir.ts`: made private, refused if it is a link or open to others, swept of non-files afterwards, and walked only once renamed into the lane temp root, on the system data volume and closed to every sandbox, never at its own path, which every ChatGPT lane can write; a rename that fails walks nothing, the moved tree is removed by `find` and `rm -rf`, which never follow a link, after only its directories' modes, user flags and ACLs are opened, so no file's metadata changes, a second link's included, and each sweep first removes every moved tree left in that root), and runs no repository code: the worktree install passes `--ignore-scripts --ignore-pnpmfile`. A change here must keep that test and 10db's own gate under `scripts/sandboxed-gate.ts --loopback --host index.crates.io --host static.crates.io` passing. Run the script from a checkout other than the one it gates (it refuses an srt that lies in the gated checkout), and `knip.json` names the lefthook config file, so knip reads no `.git/hooks` of the main checkout from a linked worktree.
- Approved repo stdio MCP servers run under srt (`mcp-sandbox.ts`, decision 133): `LaneSandbox.forSession` takes the session's expanded stdio servers (`mcpServers`) and returns each as a `SandboxedMcpServer` on `LaneSession.mcpServers`, whose launch is a private field read through `launch()` and whose constructor takes a key only `mcp-sandbox.ts` holds; `SessionSpec.projectMcpServers` requires one for stdio, so an unsandboxed server or a copy of a sandboxed one doesn't typecheck, and `toSdkMcpServer` reads it by `instanceof`. A server whose sandbox can't be built (`SandboxProfileError`, such as an approved value with a control character) goes on `LaneSession.mcpFailures`, which the runner flags and names in the prompt; the session starts. `createLaneSandbox` takes the same `runtime` as the gate. Claude Code runs `/usr/bin/env -i` with a system `PATH`, `HOME` and srt's temp variable, then node and srt; inside, `/usr/bin/env -i` keeps only srt's proxy variables, by name, and `/bin/sh -c` sources the server's env from a sealed file and execs the command as srt's child. No approved value is on a command line: `readRepoMcp` ignores, with a warning card, a stdio server whose command or args hold `${`. Its profile is the lane profile with only its own temp dir writable (not the checkout) and the Mach service `com.apple.SystemConfiguration.configd` open beside FSEvents (an HTTP client such as uv's reads the system proxy settings through it, and panics without), the hosts its approval names and no others (`.10db/mcp-hosts.json`, read by `sessions/mcp-hosts-file.ts` and part of the config hash) and never loopback, whatever the project's switch; its env is the lanes' allowlist, `prepareCommandEnv`'s, `NODE_USE_ENV_PROXY=1`, `TMPDIR`, and `PATH`, `HOME` and its approved variables. A server whose declared env sets `AWS_PROFILE` to a literal never gets the profile or `~/.aws`, whose SSO token reaches every role the builder holds: `withAwsCredentials` (`sessions/project-mcp.ts`) swaps the profile for that one role's short-lived credentials, which `environment/aws-credentials.ts` exports with the AWS CLI outside the sandbox (`inbox/project-mcp-reader.ts` runs the step; an export that fails is a flag telling the builder to run `aws sso login --profile <profile>`). The sandbox's package caches include uv's (`UV_CACHE_DIR`, `UV_TOOL_DIR`, `UV_PYTHON_INSTALL_DIR`), so `uvx` works there on the system Pythons. srt runs with `SRT_DEBUG=1` and a sealed preload (`-r`, `mcp-refusals.ts`) that keeps its debug log off stderr and writes each host its proxy refused to a per-server log, both in the files root beside the server's other files; the daemon polls that log through the `Clock` and warns `{ server, host }` (`REFUSED_MESSAGE`), so a refused host shows in the daemon log with the server's name (`decisions/2026-11-06-a-refused-mcp-host-is-logged-and-a-changed-approval-names-its-new-hosts.md`). An approval card for a changed config names the hosts it adds and drops against the latest approval of the server (`earlierMcpApproval`). Each server's temp dir and files go with the lane session's `dispose()`. 10db makes nothing in the system temp dirs (`SYSTEM_TEMP_ROOTS`: `/private/tmp` and `/private/var/tmp`), which Codex's base policy opens to every ChatGPT lane, but pnpm's lock directory (the gate's, above), which a package-install gate opens and which is walked only after it is moved into the lane temp root (`temp-dir.ts`). The temp dirs of Claude lanes, gates and MCP servers go in `laneTempRoot()` (`/Users/Shared/10db-<uid>`, short enough for the socket path limit; each temp dir is named by six random characters, so Claude Code's own dir in it, `claudeCodeTmpPath`, fits `MAX_SANDBOX_TMP_BYTES`, and a longer one is refused, since Claude Code would fall back to the shared `/tmp/claude-<uid>` without a word), a ChatGPT lane's in `codexLaneTempRoot` (`~/.10db/lanes`, the runner's `codexLaneTempRoot`, passed as `LaneSessionInput.tempRoot` with `provider`; only a Codex session's temp dir has no length limit), and sealed files, env files, MCP servers' refusal logs and process ledgers in `sandboxFilesRoot` (`~/.10db/run`, `ProjectAccessDeps.filesRoot`). Every profile, a lane's, a gate's and an MCP server's, denies all three roots (`ProjectAccess.sandboxRoots`, `LaneProfileInput.sandboxRoots`) but for its own temp dir and own files there (`ownFiles`: a lane's or a server's env file), and leaves out every readable entry that is or holds a root, a built-in `SYSTEM_READS` one such as `/tmp` on Linux included (srt would close the own files under it too; `readListOverSandboxRoots`, and `forSession` logs each such entry once per session, naming it); a profile whose checkout or extra write is or holds a root is refused (`SandboxProfileError`), so a project that holds `~/.10db` runs no lane. `startDaemon` builds both sandboxes through `sandboxesFor` (`daemon/sandbox-roots.ts`, which `scripts/sandboxed-gate.ts` and the live tests use too, through `openSandboxRoots` and `sandboxDepsOf`). At start, before any session or gate, it makes each root with `ensurePrivateRoot` (mode 0700, its real path; a link, a non-directory or another user's directory is refused, and then every lane session and gate is refused with the reason and no root is claimed), writes `.metadata_never_index` in each (`keepSpotlightOut`, as `git/`'s worktree root does; no sweep or claim matches that name), asks Time Machine to skip each (`keepRootsOutOfBackups` with `tmutilExclusion`, `tmutil addexclusion`, off the event loop and never waited on; a root it could not exclude is logged, `stop()` ends what still runs, and `DaemonOptions.sandbox.backups` replaces it in tests), and calls `claimSandboxRoots` (`stale-files.ts`): in each root it removes this user's lane temp dirs and sealed files by their exact names, never following a link, unless a live daemon's `10db-daemon-<pid>` mark is there, then marks the root until `stop()`. After the ledger reap, before any session or gate, `sweepSystemTempFiles` unlinks 10db's sealed files and ledgers from the system temp dirs, never reading one (a ChatGPT lane can read and write there); once it listens, `sweepSystemTempDirs` removes its lane temp dirs there (`10db-` and six characters, the name they had there) off the event loop, testing each name before it looks at the entry, and `stop()` aborts it between entries and waits for it. Neither marks anything there, and a mark there counts only while its pid's command line, read from `ps -axo pid=,command=`, names `daemon.mjs` or `src/main.ts`: a mark naming any other running process keeps nothing, and when `ps` can't be read every live mark counts. The pnpm lock directory's sweep is async and tells `GateSandboxDeps.log` (required; the daemon and the script pass theirs) what it can't remove in the lane temp root instead of refusing the run. The file tools treat every sandbox root (`laneTempRoot`, the Codex lanes root, the system temp dirs and the files root), all but the session's own temp dir, as a protected read and refuse writes there (`FileAccessContext.sandboxTemp`); so does a Shape session (`ShapeAccess.sandboxRoots`). The Codex lanes root and the system temp dirs (`codexLaneTempRoot`, `laneWritableRoots`) count as the temp root does for PATH entries and srt, and the daemon's git, project registration and the worktree root treat every lane-written root as lane-writable. With no lane sandbox the runner leaves stdio servers out and names them in the prompt. `test/mcp-sandbox.seatbelt.test.ts` runs a probe server under the real srt on macOS, in `make gate` and CI's macOS job.
- A lane session's commands end with the session (`decisions/2026-10-30-stop-what-a-lane-session-started.md`). `sandbox/lane-processes.ts` samples the process table (`process-table.ts`, `ps -axo pid=,ppid=,pgid=,lstart=`; a reading shared among sessions) from the pid Claude Code reports (the first reading fresh, never the shared one), remembers what runs under it and in its process groups by pid and start time, plus each child of launchd started since the session began that holds a path in the session's own temp dir, its working directory or an open file such as Claude Code's per-command output file (`lsof`, read once per process): the job of a command that returned at once (`pnpm dev &`). Working in the checkout alone never makes a process the session's: other lanes and the builder run jobs there. It writes all this to a ledger, `10db-proc-<daemon pid>-<hex>.json`, in the files root (Bash can't write there and the file-access judge refuses file-tool writes outside the session's own temp dir; `claimSandboxRoots` leaves it), with the daemon's own process group (`daemonGroup`), each time by renaming a whole new file over it (`<ledger>.<hex>.tmp`, which is never read as a ledger and which a reap removes once its daemon is gone). A failed `lsof` keeps what the tree and the groups gave, and each kind of watch failure (the ledger write, `ps`, `lsof`) is logged once per session (`LaneSandboxDeps.log`). The ledger is removed at `dispose()` only when `endProcesses` stopped everything; otherwise the daemon's `createLedgerSweep` tries again every 30 s until a round can read the machine, and the next start stops whatever is still left. A round reaps every ledger but a running session's (held from `forSession` to `dispose()`) and another running daemon's; the start's own reap hands its failures to the same sweep, which `stop()` ends. The runner calls `LaneSession.trackProcesses` at `started` with the pid and the start time `identifyProcess` read, or none when that `ps` failed: the watch then reads the process itself, from a fresh table on each sample until one lists the pid, the runner logs a warning while it is not watched, and `endProcesses` rejects (logged too) if no reading ever listed it. It calls `endProcesses` in its `finally`, after the Claude Code process is gone and before `dispose()`: SIGTERM to each remembered process and its group, SIGKILL after 1.5 s to what is left. `startDaemon` calls `reapLaneProcessLedgers` right after the claim, before recovery and any session, and stops every ledger's processes but those of another daemon that still runs (its pid alive and its mark in the root), even when one shares the root. It never follows or signals the group of the daemon that kept a ledger, which Claude Code was spawned into and the daemon was started in (a terminal's job, the app's): a process there is signalled by pid alone, and a ledger with no group recorded has no group signalled. Never signal launchd, the daemon, its process group, the group of a ledger's daemon, or a pid whose start time changed; never read a process's environment. `guard/background-loops.ts` (`startsEndlessBackgroundLoop`) makes the broker ask before a Bash command puts something endless in the background (`while :`, `yes`, `cat /dev/zero` with an `&`, or anywhere in a call with the Bash tool's own `run_in_background` flag, any value but an absent or false one). No stored rule answers that card, and it offers only allow-once and deny, so it stores none. A denial's text covers equivalents (`denialMessage`), and `deniedPermissionsForWorkstream` (`@10db/db`) gives the next sessions of the workstream the same denials and notes in their prompt (`PromptInput.denials`), less any denied read outside the lane's copy (`denialsForLane`). `answeredCardsForTask` (`@10db/db`) gives a review step the cards the builder already answered on its task (`PromptInput.answeredCards`), and the runner sends them again after a compaction, so a reviewer checks a decision against them instead of asking again; other steps aren't shown them. Tests inject the table and the signals (`sandbox.processes`); `sandbox/lane-processes.system.test.ts` uses the real ones and skips where `ps` can't run.
- A test that needs what no sandbox gives (a setuid `ps`, a short path under the shared `/tmp`, the builder's real home, Seatbelt itself) skips with `SANDBOXED` from `test/fixtures.ts` (`TENDB_SANDBOX=1`) and says why; CI and an unsandboxed `make gate` still run it. A test that starts a daemon process passes it the test's own `TMPDIR` and `GIT_CONFIG_GLOBAL=/dev/null`.
- `createTempRepo` copies a template repository that `test/repo-template.global.ts` builds once per test run with `buildRepoTemplate` and removes after it: a copy is a few file writes, where building a repository takes nine git calls. A change to what every test repository holds (its config, its first commit) goes in `buildRepoTemplate`.
- `routing/` is pure: flows, floors, the per-role AA score (a role compares its own unless some costed profile in the pool that has an Intelligence score lacks it, then all on Intelligence), the router, escalation and step plans over rows its caller passes in. `choose-model.ts` (`chooseModel`) is the one place that picks a step's model and effort: persona pin, task setting, pattern (project's first), role setting (project's first), then Automatic, with tiers and prices from the profiles (`decisions/2026-11-07-one-function-chooses-a-steps-model.md`). `offeredProfiles(profiles, accountModels, provider)` narrows the profiles to the account's list; routing names no model, so a model is reached only through its tier, its price or a setting. `retryStep` tries a retry-only pattern before `escalateStep`. A step with nothing routable holds a tier name as its `model`, no `profileId` and the setting that decided: the launcher must never launch it.

- `delivery/` owns batches: a start answers at once and cuts or joins in a background job (`jobs.ts`: one queue per project in shared mode; in worktree mode two, `cut` for cuts, joins and reopens and `ship` for ships and cleanup, each one job at a time); git and gh refusals are flag cards (`cards.ts`) that name their tasks in `detail.taskIds`, except the card for a `CUTTING` row startup deletes, which has only `detail.batchId`. A failed batch member's card offers Retry, Ship anyway, Ship without it and Later (`batch-card.ts`), acted on through the inbox's `onFlagAnswer`; its options say Ship anyway puts the failed run's commits in the pull request. Ship without it (`Shipper.shipWithout`, `leaveOut` in `ship.ts`, `decisions/2026-11-03-ship-without-it-leaves-out-every-failed-task.md`) reverts the commits of every failed member (the shas of the `commit` tool ops of all its task's runs in the batch still on the branch) with `Git.revertCommits` as one commit, `revert: leave out "<task>", ...`, in the ship queue before the batch moves to SHIPPING, closes the other runs' failed cards, and puts a `left-out` notice (`LEFT_OUT_NOTICE_KEY`, kept through a restart, cleared by Retry) on each failed run, which the drawer shows and the pull request body names under Not done; only a `FAILED` run counts as left out, and one no longer holds its batch's ship trigger. A revert that conflicts, would bring conflict markers back or meets uncommitted changes writes nothing, ships nothing and raises a card naming the files (`leftOutCards`) with the failed card's choices, so Ship without it can be answered again. A lane's first launch in a worktree batch calls `BaseUpdates.atLaunch` (the runner's `baseFirst`), so its copy holds the base as it is now: a fast-forward when the copy has no commits, 10db's base merge when it has, and a `base-fetch` notice with the lane started on the copy as it is when the fetch fails (`decisions/2026-11-02-a-lane-starts-on-the-base-as-it-is-now.md`). `recoverBatches` runs at startup after `recoverOnStartup`; `subscribeShipTrigger` follows `workstream.changed`. `pr-watch.ts` (`createPrWatch`, `subscribePrWatch`) reads every followed SHIPPED batch's pull request every 2 minutes on the injected clock, once at start and when a batch becomes SHIPPED (`DaemonOptions.prWatchIntervalMs` overrides the interval); it runs outside `jobs.ts`, one gh call at a time, and records the status on the batch (`recordPullRequestStatus`) in the same write as the `prCards` its change raises (failing checks, closed, one `pr-watch-gh` card), only on a stored transition, rewriting an open failing-checks or gh card when what it says changes (`raiseIn`, `rewriteIn` and `withdrawIn` in `context.ts`, over the inbox's `flagCard`, `rewordCard` and `withdrawCard`). A failure of gh itself (signed out, not installed, a timeout, `unreachable`) ends a round; any other leaves only its own pull request unknown, and the next round starts after the pull request that ended the last (`decisions/2026-10-29-pull-request-watch.md`). The scheduler imports only `batchLaunchVerdict`, `LaunchVerdict` and `claimScopeOf`, and the composition root passes `flagWrongBranch` to it as `onWrongBranch` and the missing-worktree card as `onWorktreeMissing`; the runner and workstream recovery import `batchCardFields` for the failed card. Worktree mode (`workspace_mode = worktree`, `pull_request` delivery) gives each batch a git worktree under the worktree root (`daemon/worktree-root.ts`: `TENDB_WORKTREE_ROOT`, an absolute path, or `~/.10db/worktrees`, plus a level hashed from the data dir). `checkout.ts` has `checkoutOf` (a workstream's checkout: its batch's `worktree_path`, else `project.repoPath`), `claimScopeOf` (the batch a worktree batch's area claims and per-copy hazard claims are scoped to, for the scheduler and MCP `request_claim` alike; the other hazards stay project-wide) and the list of checkouts the sandboxes deny; every consumer of a workstream's checkout asks it. `worktree-cut.ts` cuts (branch, worktree, pin, seed), `worktree-seed.ts` clones ignored directories, `worktree-repair.ts` makes a worktree whole for Retry and reopen, `worktree-cleanup.ts` retires one after SHIPPED, CLOSED or ABANDONED (an ABANDONED one never with uncommitted changes; SHIPPED and CLOSED rely on ship step 0's clean check; none while it holds git-ignored files outside matched directories and the seed, which keeps it with a card), `worktree-sweep.ts` removes orphans at startup (only entries under this daemon's level locked `10db bat_...`, keeping one with uncommitted changes, git-ignored files 10db didn't seed, or that git can't read, with a card); both count no build output as such a file, a fixed list by exact name in `build-output.ts` (`*.tsbuildinfo`, `.eslintcache`; `decisions/2026-10-29-worktree-build-output-not-loose-work.md`), list every ignored file outside the seed, build output included, on an uncommitted-changes card, and withdraw a worktree's kept cards (`keptWorktreeKey`) once they remove it, the kept-worktree cards name `worktreeRemovalCommand` (`git -C <main checkout> worktree remove --force --force <path>`), and `recover.ts` recovers worktree batches at startup. In shared mode the cut records where it found the checkout (`batches.return_branch`, `return_sha`), and `checkout-return.ts` (`returnCheckout`) switches it back after SHIPPED, CLOSED or ABANDONED, in the project's queue, only while no work runs in the project (as Abandon counts it) and it is clean, still on the batch's branch, its index matching HEAD, free of untracked files where the switch writes (`untrackedInTheWay`) and its branch not out, rebased or bisected in another worktree, else leaves it with a card (none when the builder moved it); recovery switches back finished batches whose place is still set, newest first (`decisions/2026-10-29-shared-checkout-switch-back.md`). The PR template is read from the shipped commit through `Git.fileAt` (`pr-template.ts`), never from the checkout. With no project prefix the PR title is `<type>(<scope>): <subject>` (`pr-text.ts`): `fix` when every finished task's title opens with fix, the one scope `.10db/pr-scopes.json` at the batch's base gives every file committed since it, none on a git failure (`pr-scopes.ts`, `Git.filesChangedBetween`), and none when they span several (`decisions/2026-10-28-pr-title-from-the-work.md`). It fetches the base once in the project's checkout. In worktree mode it merges `origin/<base>` into the batch's branch (`Git.mergeIntoBranch` with `resolve: { generated }`, never a rebase). A conflict where each side only added lines at the same place is settled by keeping both (`git/conflict-text.ts`), and a conflict in `packages/contracts/generated/` or `packages/db/drizzle/` takes the base's directory, but only where `generatedIn` (`worktree-generated.ts`) finds the package that makes it (`@10db/contracts`, `@10db/db`, with a `generate` script) in the manifest at both the branch and the base; in any other project those paths are plain files. After the install, `ctx.generators` (`createWorktreeGenerators`, `pnpm --filter <pkg> --fail-if-no-match generate` under the gate's sandbox) regenerates them in a worktree with no uncommitted change, and the base update commits what changed there; a failed run's files are put back with `Git.restoreDirs`. Neither raises a card, and a note heading the gate's evidence names the files (`decisions/2026-10-30-a-batch-settles-its-own-conflicts-with-main.md`). The branch's own migrations are carried over after the base's (`migration-carry.ts`): one `generate --name` or `generate --custom --name` per migration in journal order (with two or more generated migrations each but the last runs on a schema file written from its own snapshot merged by key with the base's, `snapshot-schema.ts`, so each stays a step; `packages/db/src/schema.ts` is replaced between runs and put back whatever happens), a custom one's SQL copied back as bytes, the journal checked before anything is committed, and any that changed number listed on the `migrations-renumbered` notice (one line per original tag, a later renumbering from the same tag replacing it), whose body the runner puts in every later session's brief. A pull request's catch-up writes that notice only once its merge is pushed (the `merged` answer carries `renumbered`; `ship.ts` keeps it), so a rewound catch-up leaves it as it was. A `.sql` the branch added that the merge dropped and the journal at HEAD lacks, whatever kept it from being made again, is an `uncarried` answer: no gate runs, it goes on the `migrations-uncarried` notice (also in the brief), and `standing` answers `uncarried` at every later gate until the journal holds it, then clears the notice and the card. The runner counts that as a failed gate, the shipper fails the batch (`shipCards.migrationsLost`), a ship with no gate asks with `standingOnly`, and a catch-up keeps no notice, pushes nothing and puts the merge back (`decisions/2026-11-04-a-base-merge-carries-a-batchs-migrations-over.md`). Asked by a task's verify gate (`BeforeGateOptions.inSession`, the runner's) or by the shipping gate (the shipper's), a conflict where every file left is a text file both sides changed the same lines of is committed with git's markers in it instead (`resolve.leaveMarkers`, `marked`): the merge commit has the base as second parent, `Git.keepNote` keeps what is left at `refs/10db/<level>/merges/<batch id>` (`start-refs.ts` `mergeRef`; retirement and the sweep delete it), `beforeGate` answers `conflicted` with no gate run and an info `base-conflict` notice, and the runner queues the task's workstream again with `nextAction: { kind: 'merge', base, paths }` (`sendToMerge`, counted in `attempt`, with one session of headroom past the fix limit: a step that used all its fix attempts still gets one merge session, and the send after that fails, worded "still in" for markers a session already saw and "a new merge" for markers the gate's own new base merge just made, `fresh` on the `conflicted` answer), no card. A merge session that ends with uncommitted changes in its claims goes back through `sendBackUncommitted` on the same count, and its failure counts the fix attempts and merge sessions the step used. The session resolves the markers, commits through the commit tool, and asks the builder with `ask_human` only for a resolution that changes what a side does. The next gate answers `conflicted` while `Git.conflictMarkers` finds markers at HEAD; once none is left it drops the note, installs, regenerates the generated directories the merge took (they waited for the resolved sources) and answers `merged` (`decisions/2026-11-01-a-session-resolves-the-conflicts-of-the-base-merge.md`). The shipping gate runs no gate on a `conflicted` answer, whether it made the merge or found an earlier gate's markers: `ship.ts` `sendToMerge` moves the batch SHIPPING → FAILED → OPEN in one write, opens the batch's last finished task again (`setTaskStatus`) and gives it a new workstream of one implement step (its last one, reset) with `nextAction: { kind: 'merge', base, paths }` and no card, and asks for a tick; the batch ships itself when that task is done. When no task can take it (none finished, the task closed, no implement step) the batch fails with one `base_conflict` card naming the files and why (`shipCards.baseConflict`, `BatchFailure.BaseConflict`) (`decisions/2026-11-01-the-shipping-gate-sends-its-last-task-to-merge.md`). Any other conflict is the batch's `base-conflict` notice (below) with each file's reason, and with the renumber steps when a migration's number collides, read from every conflicted path (`conflicted`), settled ones included; a regeneration that fails, can't run (a failed install, uncommitted changes), changes nothing in a directory, or drops a branch's `.sql` migration is one `base-regenerate` card. Asked for the migrations hazard (`forMigrations`), a generated directory's conflict stays a conflict (`generatedHeld`): no generator runs while the task's session works. - The watcher flags a write to a sensitive path (`watcher/strays.ts`: agent and tool config, `.env` files, `.git` hooks, info and config) even when git ignores it, and even inside a claim that covers it. In a batch's copy, a sensitive path that holds only what 10db's own base merge or fast-forward brought in is not flagged (an `apps/daemon/.env.example` in a merge was the one file of 321 that carded, because sensitive paths skipped the "git still reports it as changed" test every other merged file passed): a file git reports as unchanged whose HEAD blob is the one the incoming base holds (`refs/remotes/origin/<base>`, which base-update merges from, or the batch's recorded `baseSha`), or a directory that holds files and only such files. The list applies in every `.claude/` folder of a lane's copy, not only the top-level one (a command run in `.claude/hooks` leaves `.claude/hooks/.claude/.cc-writes`): an entry matches as the whole tail of a path, so `x/.cc-writes` and `.cc-writesx` stay flagged, and a real file beside it (`.claude/hooks/.claude/settings.json`) still cards. A path joins it only if Claude Code writes it unasked and never reads it back as config or instructions; settings, hooks, agents and skills under `.claude/` stay flagged.
