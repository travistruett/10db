# apps/daemon

The 10db daemon: the only database writer. It serves the UI over loopback HTTP and WebSocket,
serves agents over MCP, and runs Claude Code sessions.

- `src/env.ts` is the only module that parses or validates environment variables; `src/main.ts`
  hands it `process.env`. Every variable is in `.env.example` with a comment. Errors name variables
  and problems, never values. `main.ts` exits 4 with one line on an `EnvError` or a `WorktreeRootError`,
  and the desktop supervisor stops instead of restarting into the same refusal.
- `TENDB_BENCHMARKS=off` keeps a daemon from reading the Artificial Analysis key and from calling AA
  (`aaKeyReaderFromEnv`: the sync records `no_key`). Only the installed app's daemon syncs; the e2e web
  server, the live acceptance daemon and `scripts/dev.sh` set it, and `tests/repo/src/benchmarks-off.test.ts`
  checks they do. A new launcher of a throwaway daemon sets it too.
- `src/api/` is typechecked by the desktop app too (it imports `AppType`). Code there must not import
  `node:*` modules or `@10db/db`; receive services through the `ApiServices` interface (passed in `ApiDeps`).
- The package entry (`src/index.ts`) exports types only.
- Listen on `127.0.0.1` only.
- `pnpm --filter @10db/daemon build [outDir]` bundles everything into `dist/daemon.mjs`, bundles srt's
  command line (`@anthropic-ai/sandbox-runtime`) into `srt.mjs`, copies srt's Java proxy agent to
  `vendor/java-proxy-agent/srt-proxy-agent.jar`, where srt looks before it runs `npm root -g` unsandboxed from
  the gate's checkout, and copies migrations (`drizzle/`) and the
  SQLite addon (`better_sqlite3.node`) beside it. Nothing stays external: the Tauri sidecar runs the bundle
  from a directory with no node_modules.
  `better-sqlite3` is still a daemon dependency: the build copies its addon, and
  `test/crash-recovery.test.ts` opens the database with it directly.
- `pnpm --filter @10db/daemon dev` runs from source with tsx and loads `apps/daemon/.env` when it
  exists. Copy `.env.example` to `.env` to override a variable; `.env` is git-ignored.

## Modules

`src/<module>/` directories are flat; each exports its public surface from `index.ts`, and other
modules import only that (ESLint enforces it). Dependencies point one way:

`clock`, `log`, `events`, `guard`, `permissions`, `sandbox`, `git`, `github`, `verify`, `routing`, `picker`, `folders` → `sessions`, `inbox`, `briefing`, `team` →
`delivery`, `accounts` → `mcp` → `runner` → `watcher`, `scheduler`, `recovery`, `backups`, `benchmarks` → `daemon` (composition root) → `main.ts`.
`api` depends only on `@10db/contracts` and its own `ApiServices` interface; the composition root
implements it and hands it to `createApp` in `ApiDeps`.

Time comes from an injected `Clock`; never call `Date.now()` or `setTimeout` directly in logic.

The fake adapter (`sessions/fake-adapter.ts`) is the test boundary for Claude Code; daemon tests never call the real CLI.

- **The security rule.** No process outside a sandbox acts on lane-writable input (a file in a checkout, a
  `PATH` entry or tool variable that names one, a lockfile). Remove a capability rather than check for its
  misuse. Never deny individual secrets inside an otherwise open tree: open only what is needed.
- `sandbox/` owns the lane and gate sandbox: the settings profile Claude Code's Bash sandbox runs under (`buildLaneProfile`, validated by `LaneSandboxSettingsSchema`, whose field names match the SDK's `SandboxSettings`), the protected reads, the toolchain reads, the env-name allowlist, each lane's short temp directory and the package caches inside it, and its read-only `CLAUDE_ENV_FILE` (`env-file.ts`), which exports every variable the sandbox sets for lane commands (the package caches, the mise variables, `xcrun_db`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_OPTIONAL_LOCKS=0`, an empty `XDG_CONFIG_HOME` in the temp dir, `TENDB_SANDBOX=1`; `CARGO_HOME`'s `bin` is a link to `~/.cargo/bin` so mise finds its rustup-linked rust) before each command, single-quoted, because Claude Code strips variables that point a tool at its config, `GIT_CONFIG_GLOBAL` and `CARGO_HOME` among them, from a sandboxed command's env. A new variable for sandboxed commands goes in `prepareCommandEnv` (`command-env.ts`), which feeds a lane's session env and its file, and a gate's env. A lane's session env, which Claude Code and its own git run with outside the sandbox, holds no variable whose value is the temp dir or a path in it (`withoutTempDirPaths`, applied by `forSession`), except `CLAUDE_CODE_TMPDIR`: a lane writes there, and a tool outside the sandbox that followed the variable would run what it wrote (mise's `[env] _.source`, xcrun's cache file, `XDG_CONFIG_HOME`, cargo's `rustc-wrapper`). The file and a gate's inner env carry them all; `LaneSession.commandEnv` is the full set, and `lane-sandbox.test.ts` and the live test fail on a path in the session env. Toolchain reads that only list a dir (mise's `installs` and its tool dirs) are `toolchainAccess`'s `listings`, two exact-match patterns per dir (`listingGrant`, `childListingGrant`), the only patterns the profile holds; never open a dir whole and deny secrets inside it. It imports no SDK and only `guard` (for the file system's case fold); callers pass paths in. Every real lane and gate runs under it, with no switch. `startDaemon`'s `sandbox` option is required and builds both; `createRunner`'s `laneSandbox` and `createGateRunner`'s `sandbox` are required too. `daemonOptionsFromEnv` gives `{}` unless the sessions are fake (`TENDB_FAKE_SCRIPTS`, development and e2e only), where it gives `null` and the gate runs unsandboxed, and tests pass `null` explicitly. With no sandbox, the daemon's git counts no temp root as lane-writable. The Claude adapter refuses a session whose spec has no sandbox unless it was built with `allowUnsandboxed: true`, which only tests that script the SDK set. Package caches, cargo's `CARGO_HOME` included, are per lane, in `<temp dir>/cache`: a cache can hold code a later install or build runs, so no two lanes share one. The sandbox adds no unsandboxed process that acts on lane-writable input (a manifest, a lockfile, `PATH`, config in the checkout), so nothing is prefetched. Approved repo stdio MCP servers run under srt too (below). `projectAccess` (`project-access.ts`) reads what both sandboxes are built from: the checkout's real path and `.env*` files, the protected reads, the toolchain, the stored hosts and read paths, and the git state of every registered checkout. mise's system config (`/etc/mise`) is denied and `MISE_SYSTEM_DIR` points at the lane's own mise dir. `forSession` takes every project's checkout (`checkouts`), whose PATH entries are dropped. mise's config dir is never opened: each lane gets its own global mise config (`mise-config.ts`). Each project's `sandboxLoopback` (Settings › General, "Let lane commands use localhost"), read before each session and passed to `forSession` with the project, lets its commands bind and connect on localhost. Under the sandbox the broker (`inbox/permission-broker.ts`) allows a Bash call without a card unless it is a hazard or something unread could make it one (`guard/unread-commands.ts`: an unnamed program, an unread script, an uncertain structure, or an unread argument that could select a hazard form of a program that has one; an unread argument to any other program is allowed), denies an unlisted `SandboxNetworkAccess` host at once with one card per host per session, and judges Read, Grep, Glob and the edit tools on real paths (protected paths are refused with no card). A Grep, Glob or LS of a directory that holds a protected path is refused too, so a data dir or account config dir inside the checkout makes every Grep, Glob or LS of the checkout root refused. The sandbox's own env sets `GIT_CONFIG_GLOBAL=/dev/null`, the one exception to keeping git config variables. A change here must keep the live test (`test/lane-sandbox.live.test.ts`, `TENDB_LIVE_CLAUDE=1`, never in `make gate`) passing, and re-run it after each Claude Code or SDK upgrade. The checkout's git dir, its common dir and `<checkout>/.git` (file or directory, wherever the git dir lies) are `denyWrite` in the profile, and so are every other registered checkout's (from `checkouts`, through `gitDirs`); every other registered checkout that isn't this one's ancestor is `denyWrite` as a whole (`otherCheckouts`), for lanes and gates, so a project nested in this checkout stays read-only too and `git/`'s exemption for a registered checkout's `.git` holds: only the daemon writes git state, and the lane env sets `GIT_OPTIONAL_LOCKS=0` so its read-only git works. The guard refuses `git push` for every lane.
- The gate runs under srt (`gate-sandbox.ts`, decision 132): `createGateSandbox(...).forRun` builds the lane profile with `buildLaneProfile` (the checkout and the run's own temp dir writable, srt's `/tmp/claude` closed, the project's hosts with `strictAllowlist`, loopback from the project's switch), writes srt's settings to a sealed file (`sealed-file.ts`) and returns what to spawn: node running srt's command line (`resolveSandboxRuntime` in `paths.ts`: a bundle runs only its own `srt.mjs` and fails to start without it, never searching `node_modules`; source runs use the dependency), one srt process per run. `forRun` refuses (`SandboxProfileError`) an srt or node that lies, as written or through a link, at or under a registered checkout or the temp root, since both run outside the sandbox; so a daemon run from source can't gate a project whose checkout holds that source. The gate's env is the lanes' allowlist of the project env plus `prepareCommandEnv`'s, set inside the sandbox by `/usr/bin/env`; srt's host sees only a system `PATH`, `HOME` and `CLAUDE_CODE_TMPDIR`. A `docker` that refuses leads its `PATH` (`DOCKER_REFUSAL`). `verify/gate-runner.ts` runs what the sandbox returns in its own process group, kills that group when srt closes so nothing the gate left running outlives its verdict, and awaits its `dispose()`, which removes the temp dir off the event loop; a refused profile is a failed gate (exit 126) with its reason. srt exits 0 when its own child dies by SIGTERM or SIGINT, so the command runs under a shell that traps both and exits 143 or 130; never `exec` the command as srt's child. `test/gate-sandbox.seatbelt.test.ts` and `test/gate-toolchains.seatbelt.test.ts` (mise's installs, a rustup-linked rust, Apple's xcrun shims) run the real srt on macOS in `make gate`, skipped on Linux and inside a sandbox; daemon tests that start a sandboxed daemon pass `FAKE_SRT` (`test/fake-srt.ts`) as its runtime. `scripts/sandboxed-gate.ts` runs a project's gate command under the sandbox by hand. A change here must keep that test and 10db's own gate under `scripts/sandboxed-gate.ts --loopback --host index.crates.io --host static.crates.io` passing. Run the script from a checkout other than the one it gates (it refuses an srt that lies in the gated checkout), and gate a plain clone: in a linked worktree knip can't read the main checkout's `.git/hooks` and reports exports unused.
- Approved repo stdio MCP servers run under srt (`mcp-sandbox.ts`, decision 133): `LaneSandbox.forSession` takes the session's expanded stdio servers (`mcpServers`) and returns each as a `SandboxedMcpServer` on `LaneSession.mcpServers`, whose launch is a private field read through `launch()` and whose constructor takes a key only `mcp-sandbox.ts` holds; `SessionSpec.projectMcpServers` requires one for stdio, so an unsandboxed server or a copy of a sandboxed one doesn't typecheck, and `toSdkMcpServer` reads it by `instanceof`. A server whose sandbox can't be built (`SandboxProfileError`, such as an approved value with a control character) goes on `LaneSession.mcpFailures`, which the runner flags and names in the prompt; the session starts. `createLaneSandbox` takes the same `runtime` as the gate. Claude Code runs `/usr/bin/env -i` with a system `PATH`, `HOME` and srt's temp variable, then node and srt; inside, `/usr/bin/env -i` keeps only srt's proxy variables, by name, and `/bin/sh -c` sources the server's env from a sealed file and execs the command as srt's child. No approved value is on a command line: `readRepoMcp` ignores, with a warning card, a stdio server whose command or args hold `${`. Its profile is the lane profile with only its own temp dir writable (not the checkout), the hosts its approval names and no others (`.10db/mcp-hosts.json`, read by `sessions/mcp-hosts-file.ts` and part of the config hash) and never loopback, whatever the project's switch; its env is the lanes' allowlist, `prepareCommandEnv`'s, `NODE_USE_ENV_PROXY=1`, `TMPDIR`, and `PATH`, `HOME` and its approved variables. Each server's temp dir and files go with the lane session's `dispose()`. At start, before any session or gate, `startDaemon` calls `claimSandboxTempRoot` (`stale-files.ts`): it removes this user's lane temp dirs and sealed files by their exact names, never following a link, unless a live daemon's `10db-daemon-<pid>` mark is there, then marks the root until `stop()`. The file tools treat the temp root, all but the session's own temp dir, as a protected read (`FileAccessContext.sandboxTemp`). With no lane sandbox the runner leaves stdio servers out and names them in the prompt. `test/mcp-sandbox.seatbelt.test.ts` runs a probe server under the real srt on macOS, in `make gate` and CI's macOS job.
- A test that needs what no sandbox gives (a setuid `ps`, a short path under the shared `/tmp`, the builder's real home, Seatbelt itself) skips with `SANDBOXED` from `test/fixtures.ts` (`TENDB_SANDBOX=1`) and says why; CI and an unsandboxed `make gate` still run it. A test that starts a daemon process passes it the test's own `TMPDIR` and `GIT_CONFIG_GLOBAL=/dev/null`.
- `createTempRepo` copies a template repository that `test/repo-template.global.ts` builds once per test run with `buildRepoTemplate` and removes after it: a copy is a few file writes, where building a repository takes nine git calls. A change to what every test repository holds (its config, its first commit) goes in `buildRepoTemplate`.
- `routing/` is pure: flows, floors, the per-role AA score (a role compares its own unless some enabled, costed profile that has an Intelligence score lacks it, then all on Intelligence), the router, escalation and step plans over rows its caller passes in. A step with no score to compare on runs on its role default (`role-defaults.ts`, decision `2026-10-28-routing-role-defaults.md`): the strongest Claude Code model the account offers for plan, plan review and review, a balanced one for implement, a fast one for QA, by each model's tier in `catalogue.ts`; it escalates up the same ladder. Each step's reason starts `by score:` or `by role default:`. Routing never reads the project's `model` and `effort`. It imports `@10db/contracts` only. Its tests use the invented catalogue in `test-catalogue.ts`, never AA's numbers.
- `picker/` is pure like `routing/`: the spec §5.2.1 rules over rows its caller passes in, planned tasks only. `team/candidates.ts` gathers the rows and adds each candidate's claims and step plan; `GET /projects/:projectId/candidates` serves the result. It models no batch: a batch is the delivery spec's entity.
- `folders/` holds gate detection (`gateCandidates`, spec §9.2, pure over files its caller has read) and `inspectFolder` (spec §9.1, `POST /folders/inspect`). Inspection reads the folder and writes nothing: git answers through `Git.inspect` on the unpinned, observed path, which never calls `pinned()` or `onRefused`, so a refusal is an `unreadable` answer and never an Inbox card; `Makefile` and `package.json` are read after an `lstat`, a link or a file over 256 KiB counting as absent. It imports `git`, `github` and `@10db/contracts` only; `daemon/` wires it and `api` reaches it through `ApiServices`.
- `team/` seeds the team configuration at start and turns a task into its stored step plan. Read the step a workstream is on with `currentStep` from `@10db/contracts`. Daemon tests get an invented measured catalogue from `test/catalogue.ts`.
- `benchmarks/` syncs Artificial Analysis's free model list with the builder's own key, read from the Keychain (service `10db`, account `artificial-analysis-api-key`). AA data stays on the machine: never in logs, fixtures, docs or the repo, and every view of it shows AA's attribution. Tests use invented numbers and an injected `fetch`.
- `github/` is the only module that runs `gh`, and `git/` the only one that runs `git`; both use `execFile` or `spawn` with argument arrays, never a shell. Network calls (fetch, push, every `gh` call) take a `NetworkCall` built from `environment/buildNetworkEnv`, a timeout and an abort signal, with prompts off. A push gets `pushTimeoutMs`, since it uploads every commit of the batch; fetch and `gh` get `networkTimeoutMs`. Fetch and push run detached in their own process group, and a timeout or abort kills the group. Delivery tests fake `gh` with `test/fake-gh.ts`; real git runs against a local bare `origin` (`createTempRepoWithOrigin`).
- `accounts/` owns account pauses (`account_pause.<id>`; usage limit, monthly cap, refused), the monthly cap in local time on the injected clock, readiness and the preparer, staggered subscription starts, the account cards and the account service. The scheduler and the runner ask `AccountRuntime.blocked` before every session start; a cap or refusal pause lets running sessions finish and a usage limit stops them. `limits.ts` acts on a session's usage report: past a project's threshold its lanes hand off and it moves to its usable fallback (ready, not paused, capped when metered), or the builder is asked; at the hard limit a project with a fallback moves at once. Only projects with work in flight move or are asked.
- `accounts/` also moves projects between accounts. `PATCH /projects/:id` and the cards go through `AccountMoves.move` (`moves.ts`), which remembers a move off a usage-limited account; `move-back.ts` asks to move back when that limit resets; `usage-reports.ts` keeps each account's latest report in memory. `Runner.handOff` asks a project's lanes on an account to hand off in the account's own words (`HANDOFF_NUDGE_ACCOUNT`). The runner reads the project's account before each session and never resumes a conversation that ran on another account: `runner/next-action.ts` starts the lane fresh from its handoff.
- `delivery/` owns batches: a start answers at once and cuts or joins in a background job (`jobs.ts`: one queue per project in shared mode; in worktree mode two, `cut` for cuts, joins and reopens and `ship` for ships and cleanup, each one job at a time); git and gh refusals are flag cards (`cards.ts`) that name their tasks in `detail.taskIds`, except the card for a `CUTTING` row startup deletes, which has only `detail.batchId`. A failed batch member's card offers Retry and Ship anyway (`batch-card.ts`), acted on through the inbox's `onFlagAnswer`. `recoverBatches` runs at startup after `recoverOnStartup`; `subscribeShipTrigger` follows `workstream.changed`. The scheduler imports only `batchLaunchVerdict`, `LaunchVerdict` and `claimScopeOf`, and the composition root passes `flagWrongBranch` to it as `onWrongBranch` and the missing-worktree card as `onWorktreeMissing`; the runner and workstream recovery import `batchCardFields` for the failed card. Worktree mode (`workspace_mode = worktree`, `pull_request` delivery) gives each batch a git worktree under the worktree root (`daemon/worktree-root.ts`: `TENDB_WORKTREE_ROOT`, an absolute path, or `~/.10db/worktrees`, plus a level hashed from the data dir). `checkout.ts` has `checkoutOf` (a workstream's checkout: its batch's `worktree_path`, else `project.repoPath`), `claimScopeOf` (the batch a worktree batch's area claims are scoped to, for the scheduler and MCP `request_claim` alike; hazards stay project-wide) and the list of checkouts the sandboxes deny; every consumer of a workstream's checkout asks it. `worktree-cut.ts` cuts (branch, worktree, pin, seed), `worktree-seed.ts` clones ignored directories, `worktree-repair.ts` makes a worktree whole for Retry and reopen, `worktree-cleanup.ts` retires one after SHIPPED, CLOSED or ABANDONED (an ABANDONED one never with uncommitted changes; SHIPPED and CLOSED rely on ship step 0's clean check; none while it holds git-ignored files outside matched directories and the seed, which keeps it with a card), `worktree-sweep.ts` removes orphans at startup (only entries under this daemon's level locked `10db bat_...`, keeping one with uncommitted changes, git-ignored files 10db didn't seed, or that git can't read, with a card), the kept-worktree cards name `worktreeRemovalCommand` (`git -C <main checkout> worktree remove --force --force <path>`), and `recover.ts` recovers worktree batches at startup. The PR template is read from the shipped commit through `Git.fileAt` (`pr-template.ts`), never from the checkout. With no project prefix the PR title is `<type>(<scope>): <subject>` (`pr-text.ts`): `fix` when every finished task's title opens with fix, the one scope `.10db/pr-scopes.json` at the batch's base gives every file committed since it, none on a git failure (`pr-scopes.ts`, `Git.filesChangedBetween`), and none when they span several (`decisions/2026-10-28-pr-title-from-the-work.md`). Decisions: `docs/architecture/decisions/2026-10-27-worktree-*.md`. Tests wait on `Scheduler.idle()` and the delivery jobs' `idle()`.
- `environment/` owns the login env (memory only), the Keychain, the launcher and the system check. `GET /system` answers from the services' last probe (tool versions and `gh api user`'s login, `ToolCheck.signedIn`); `?recheck=1` probes again, and nothing else does. Nothing else reads the login env, and only `launch.ts` names account variables (`CLAUDE_CONFIG_DIR`, `ANTHROPIC_API_KEY`, …); other modules use `SECRET_VARIABLES`, `signInCommand` and `Launcher.loginConfigDir()`. Never write the login env or a secret to disk, the database or logs.
- The guard's protected paths (`guard/account-rules.ts`) are the data directory and the default account's sign-in; `startDaemon` builds them once and passes them to the runner and the MCP handler.
- Every lane session runs in Claude Code's `default` permission mode, set in the Claude adapter; nothing chooses another, so hazards and new hosts reach the broker.
- Only `sessions/claude-*.ts` import `@anthropic-ai/claude-agent-sdk`, and only `claude-adapter.ts` imports it at runtime (the others import types).
  Tests inject a scripted `query`; only `claude-adapter.live.test.ts` runs real Claude Code, behind
  `TENDB_LIVE_CLAUDE=1`.
- A session runs in its launch env (the project env plus its account's variables); the gate and the shipping gate get the lanes' allowlist of the project env (the login env with every billing switch stripped), inside their sandbox, and the repo's stdio MCP servers get `PATH`, `HOME` and their approved variables from it, plus the lanes' allowlist inside their sandbox. Nothing from the daemon's own `process.env` reaches a project's commands.
- Both adapters check a session's account with `sessions/account-check.ts` before the prompt and at the first `init`; a refusal ends the session as `account_refused`, which pauses the account, and a model mismatch fails the workstream. Logs never carry an email or organization.
- The variables that point git at a repository (`GIT_REPO_ENV_VARS` in `git/`: `GIT_DIR` and the
  rest of `git rev-parse --local-env-vars` except the config ones) are dropped wherever the daemon
  starts a process that may run git: `git/`'s own calls (fetch and push take theirs off the
  `NetworkCall` env), every `gh` call (gh runs in an empty dir with `-R`), the login shell capture,
  and the launcher's env (sessions and the gate). A daemon started from a git hook still acts on the
  repository it names. Git config variables (`GIT_CONFIG_COUNT` with its `KEY_n`/`VALUE_n`,
  `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG`) are kept: they name no repository, and a builder's
  profile may set them on purpose.
- `git/`'s own calls also set `GIT_OPTIONAL_LOCKS=0`, so a read such as `status` never refreshes
  the index under `index.lock`. With the lock held, a lane's commit running at the same moment
  fails with "index.lock: File exists".
- The daemon's git runs nothing from the checkout (lane sandbox spec D13, decision 129). Every call in
  `git/git.ts` reads no attributes (`GIT_ATTR_SOURCE` at the empty tree, `core.attributesFile=/dev/null`) and
  passes `NO_ATTRIBUTES` and `DAEMON_GIT_CONFIG` through `run.ts` (every `GIT_*` dropped but the config-file
  selectors, a 60 s timeout) or `network.ts`; `gh` gets the hook and fsmonitor config through
  `GIT_CONFIG_COUNT` (`withDaemonGitConfig`). `startDaemon` resolves one git from the fixed prefixes `/opt/homebrew/bin`, `/usr/local/bin` and `/usr/bin` (never a `PATH`, which can lead with a lane-writable dir) with a behaviour probe, keeps the path it found it at (Homebrew's prefix link, which outlives a `brew upgrade` and its cleanup, where the Cellar path it points to doesn't), and refuses to start when none passes (`version.ts`, prefixes in `install-prefixes.ts`). gh comes from the same prefixes in the same order (`github/resolve-gh.ts`), resolved at start; every gh call runs that path with the resolved git's directory first on its `PATH`, and a missing gh fails each call as not installed. `DEVELOPER_DIR`, `SDKROOT` and `TOOLCHAINS`, which steer Xcode's `/usr/bin/git` shim per spawn, are dropped from every git call, the probe's included, and from gh (`XCODE_SELECTORS` in `run.ts`). `startDaemon` hands the resolved git and gh to the system check (`ResolvedTools`), which reports those; claude and docker come from the prefixes, then their own install dirs in home (`findClaude`: `~/.local/bin`, `~/.claude/local`; docker: `~/.docker/bin`), never the login `PATH`. `runGit` requires `bin`, so every call runs that git, and once a checkout is pinned, with `GIT_DIR` and `GIT_WORK_TREE` set to the pin, which `pinned()` reads once per operation and passes down. The
  daemon never reads or writes a worktree file itself: `changedPaths` is `status --ignore-submodules=all` on a
  private index, `commit` is `git add -A` on a private `GIT_INDEX_FILE` ending in
  `update-ref --no-deref <branch> <new> <old>`, and a batch's branch is checked out with `read-tree -m -u`;
  HEAD is never moved by a commit. A non-empty `info/attributes` in the git dirs is refused. A
  checkout's pin (git dir and common dir by device and inode, origin's URLs) is recorded at project
  registration and kept in `app_settings` (`daemon/checkout-pins.ts`, keyed by real path); a mismatch, a
  changed origin or a non-empty alternates file is a `GitTrustError`. Its card carries the state it found,
  and only the card's Trust answer re-pins, through `git.retrust(repo, candidate)`, which pins exactly that
  state and refuses anew if the checkout changed since, or with a card offering nothing if a git dir in it lies
  inside any registered checkout or a lane temp root; the same check runs when a checkout is first pinned. A dir at or
  under a registered checkout's own `.git` directory is exempt (its lane profile denies it), and a re-trust checks only
  dirs that differ from the current pin. `commit` and `switchNewBranch` read the pin inside the checkout's lock. A batch start reads origin's push URL through
  `pinnedPushUrl`, which checks it against the pin, so an origin added or changed since registration raises the
  Origin card. A commit's branch is the batch's or `workstreams.branch`, pinned at the first
  session, never HEAD. Fetch and push name the pinned URLs, in the form `git/remote-url.ts` parses (a URL with
  userinfo or anything that doesn't parse cleanly is refused), refuse a local origin inside any registered
  checkout (`checkouts`) or a lane temp root (`laneRoots`), read as written or through a link, and check the
  local-config allowlist (`git/config-trust.ts`) as defense in depth. A config file counts as lane-writable when it lies in
  the git dirs, any registered checkout or a lane temp root, read as written or through a link (`laneWritableRoots`),
  so a global include into another project's checkout is refused and its programs are never used. They read config with the login env
  (`NetworkCall.env`) and re-emit the builder's credential helpers through `GIT_CONFIG_COUNT`, after an empty
  helper that resets the list. Every refusal reaches `onRefused` (`daemon/git-refusal.ts`),
  which raises one card per checkout, cause and found state. A new git call goes through `git()` in
  `git.ts`, so it reads no attributes; only `check-attr` for the filter refusal reads them, which runs nothing,
  with the same git and pinned git dir.
- `git/` also makes and removes worktrees (worktree mode): `addWorktree` (`update-ref`, `worktree add --no-checkout
--lock --reason '10db <batch id>'`, the pin, `read-tree -m -u`), `removeWorktree` (only a directory under the
  worktree root, locked with a `10db ` reason and listed by git; otherwise `WorktreeNotOursError`),
  `listWorktrees`, `worktreeChanges` (an orphan's uncommitted changes, only for a locked, listed entry whose git dir is a direct child of the pinned common dir's `worktrees` and whose `commondir` names it), `worktreeIgnoredFiles` (its git-ignored files outside directories the ignore rules match, under the same checks; a refusal of a listed, locked entry's git dir is marked `unreadable`), `pruneWorktrees`, `deleteBranchIfAt` and `fileAt` (a file of a commit, through `ls-tree`). `path-entries.ts` holds `existsAsEntry` and `comparablePath`, and `checkout-pin.ts` the worktree pin key (`worktreePinKey`), for every module that needs them. A
  worktree's pin is made at creation, copies the main pin's URLs and is keyed by batch (`checkout_pin.<batch id>`);
  `createGit({ worktreeRoot })` refuses a path at or under the root with no pin as `GitTrustFailure.Unpinned`, and
  `projectAt` resolves a worktree path to its project so refusals raise the project's cards.
- Gates are limited machine-wide (`verify/gate-slots.ts`, `decisions/2026-10-28-gate-slots.md`): `startDaemon` wraps the one gate runner with `limitGates` over a single `createGateSlots(limits.gateSlots)` (default 1, `TENDB_GATE_SLOTS`), so a lane's verify gate and a batch's ship gate share it. The gate's timeout starts when it gets a slot. A gate that waits calls `GateRequest.onWaiting`; a new place that starts a gate goes through that same runner, never a second one.
- `keep-awake/` and `watcher/` follow lanes through `workstream.*` events, wired in `daemon/start.ts`.
- A managed session's MCP servers are 10db's own plus the repo's `.mcp.json` servers the builder approved
  for that exact config, resolved per session in `sessions/project-mcp.ts`. Claude Code never reads MCP
  config itself (`strictMcpConfig: true`). A repo stdio server reaches Claude Code only as its launch under srt
  (above); never hand it the session environment.
