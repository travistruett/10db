# apps/desktop/src/views/knowledge

- Knowledge (`views/knowledge/`, `daemon/knowledge-queries.ts`) is the nav item between Inbox and Settings and follows the project switcher. It shows the recorded decisions and principles of that project, which are not Settings › Decisions (10db's own judgement settings; that section links here and the view says so). Two tabs, Principles (with the number of pending proposals) and Decisions (`decisions/2026-11-08-knowledge-is-two-tabs-with-shelves.md`). The tab row holds New Principle or New Decision on its right. The filters live in the table's headers: the first column's filter holds the shelf (`knowledge-shelf.ts`: Pending n, Current and Past for principles; Current and Past for decisions) and the search, and the Scope column's filter the scope (Any Scope, All Projects, This Project and each area but one that covers the whole repository, `knowledge-areas.ts`, read Only in <area>); search and scope stay when the tab changes. A slim yellow banner with Review says when proposals wait while another shelf shows, and a dimmed line with Show Current says when a list shows Pending or Past. The table stays drawn when it is empty, saying so in its body, so its filters stay in reach; a filter popover stays open while the list it narrows changes (`hideDetached: false`). Current and Past read `GET /projects/:id/knowledge` a page at a time, with `kind` (`principle`, or the kinds the Type filter picks; `decision`), `shelf` (`current` or `past`: superseded, retired and withdrawn), `q` (debounced), `scope`, `area`, `sort`, `dir`, `page` and `pageSize`: the daemon narrows, sorts, pages and counts, and the browser never does (`decisions/2026-11-08-knowledge-lists-are-paged-where-they-are-read.md`). The table shows `mantine-datatable`'s pager (25, 50 or 100 a page, `1–25 of 30`, its buttons named Page n, Next page and so on) and goes back to the first page when a filter, the search, the shelf, the sort or the page size changes (`usePaging` in `shell/table-pager.ts`); the last page stays up while the next loads. Pending reads `GET /projects/:id/proposals`, keeps the principle proposals (every other proposal is answered in the Inbox) and applies search and scope in the browser (`matchesSearch` in `@10db/contracts`, the daemon's rule: every word typed starts a word of the record, and text with no word, such as "-", is no search). Each list is a `mantine-datatable` table (`knowledge-table.tsx`): columns resize, the Columns menu in the table's corner hides and shows them (the per-header hide button is hidden by `knowledge-table.css`), and the layout is kept per list in local storage; a column the stored layout doesn't know yet shows. Type, Scope, Date and State sort, and Type has a column filter; both go to the daemon. Principles ask for policies first unless a search is typed, when the best match leads. A row shows its words, its type as a coloured badge (the kinds read Rule, Preference and Background in the UI for `policy`, `heuristic` and `belief`; orange, blue, gray), scope (All Projects, This Project or Only in <area>) and a short date with the full one as its title; State only under Past. The topic key is not shown. Clicking a row, or its words (a button named "Where … came from" for the keyboard), opens `ProvenanceDrawer` (`GET /decisions|principles/:id/provenance`): the source in the builder's words (`knowledge-labels.ts` `sourceLabel`: Inbox answer, Agent, Plan conversation when a builder source's ref names a `shapeId`, Claude Code for `claude_code` or `builder_mcp`, the tool's own name otherwise, else The app), who and when, its quote, any retire or withdrawal with its reason, and what it replaced or what replaced it (each a button named by the record's words, `supersedesText` and `supersededByText`, that opens that record). The row's “⋯” menu, named by the record's words, never opens the row. A damaged search index (`search.available` false) is a dimmed line, not "no match". `decision`, `principle` and `proposal` events invalidate `knowledge`, `proposals` and `provenance` (`INVALIDATIONS`), so a record written by an Inbox answer, a lane or the API appears in the open view; proposal text is plain text. Writing from the view (`record-actions.tsx`, the dialogs beside it, the mutations in `knowledge-queries.ts`, which refetch the three lists, provenance and the Inbox when they settle): New Principle and New Decision write a record at You, This project or one area (`POST /projects/:id/principles|decisions`; the principle form never asks for a topic key, which a new principle takes from its statement (`topicKeyFrom`), and offers the type as three cards under "How agents use it", each saying what it does to an agent (`PRINCIPLE_KIND_DESCRIPTIONS`); because the key decides what a principle replaces, New Principle and Accept first ask the daemon by a dry run (`usePrincipleReplacePreview`), and a save that would replace a current principle names it and waits for Replace; `target-select.tsx` `placeOf` turns the choice into the routes' `scope` and `area`). A row's “⋯” menu has Edit on a current record (`POST /decisions|principles/:id/supersede`, the routes' explicit link: the form opens with its text and scope, saving writes a successor and the old one moves to Past as Superseded; a principle keeps its topic key, and a 409 for a key already current at that scope shows the daemon's message, which names the principle), and Remove on a current or superseded one (`remove-dialog.tsx`). On a current principle Remove first asks why: It no longer applies retires it, It was recorded by mistake withdraws it; a decision or an older version is withdrawn. It asks for a reason (`reason-dialog.tsx`) and says the record leaves briefings and search and stays under Past with it. Only the newest record of a chain can be withdrawn: on an older version the dialog follows its provenance to the newest (`useNewestVersion`), names it, and offers Remove Newest Version. Accept on a pending principle proposal opens the principle dialog filled from it (statement, kind and scope can change; the proposal's key is kept; `POST /proposals/:id/accept`); Reject takes an optional note; either closes the matching Inbox card, and a 409 shows the daemon's own message. A proposal that is not a principle's is decided in the Inbox. A dialog is mounted by the control that opens it, so it always starts from the record or empty. Every refusal shows the daemon's message in full in the dialog's footer (`FormModal` never clamps an error: one that doesn't fit beside the actions takes its own line above them; `e2e/loop.spec.ts` checks it isn't clipped, which jsdom can't see).
