# Settings › Trust

Notes for the Trust pages: the app-wide page and the project's. Their code is `views/settings/trust-section.tsx`,
`trust-rows.ts`, `project-trust-section.tsx`, `your-mcp-servers.tsx`, `mcp-server-row.tsx`, `daemon/trust-queries.ts`
and the files in this folder.

- Settings › Trust (`views/settings/trust-section.tsx`, `trust-rows.ts`, `daemon/trust-queries.ts`) switches what comes along into every session through `/settings/trust`: one `Switch` per row of `TRUST_ROWS` (one per `TRUST_SWITCH_KEYS`, each with its note per agent and "Applies from the next session."), then Claude Code's installed plugins with their versions, a plugin off in Claude Code saying so until the builder switches it here, then a read-only Judge list: one row per account with the model a new task gets there, what judges its calls (`JUDGE_LABELS`), and the daemon's `why` for a rules row. A project's Trust (`project-trust-section.tsx`, `/projects/:id/trust`) gives each row and plugin Default / On / Off (Default removes the override). Under each switch row sit the items it brings from the daemon's preview (`trust/preview-items.ts`, `trust/switch-items.tsx`: each item carries the switch that brought it, folded past 5 with a Show control); left-out items with an expected reason (a duplicate name, 10db's own skill) fold into one quiet line "n more left out as expected · Show" after the switches, and items no switch owns sit in an Other group. Then Repo MCP Servers (`trust/repo-mcp-servers.tsx`, below), Production (`trust/production-systems.tsx`: the old Live Systems; the `/projects/:id/live-systems` route and setting keep their name) and Allowed in This Project. Production is a `TagsInput` that sends each change at once and shows a refusal under the input, keeping the saved list; under it "10db found these in the repo" lists `GET /projects/:id/live-systems/proposals` (`trust/propose-production.ts` in the daemon: vercel.json aliases, `*PROD*` names and production URLs in `.env*.example`, prod compose images, production workflow urls, prod AWS and GCP profiles, each with its file and line, read from `origin/<base>` else HEAD) with an Add that writes through the same save; nothing is added without a click. The copy says lanes may read these places and 10db's judge refuses any write to them, not that the sandbox blocks them.
- Standing Approvals (`standing-approvals.tsx`, in the project's Trust above Allowed in This Project, `GET /projects/:id/precedents`): `active` and `paused` rows with the kind, its scope (`PRECEDENT_SCOPE_LABELS`), uses and last use, the examples as text, the last 5 calls it allowed (folded) and Remove (`PATCH` `revoked`), with the note that a running auto mode session keeps the line until it next starts; under them Not Routine lists `declined` and `revoked` rows, each with Approve (`PATCH` `active`). While no account runs decisions (`GET /judge`: none picked, or the judge off) it says "Standing approvals need a Decisions account" with a link to Settings › Decisions, and still lists any row so Remove works. Settings › Decisions' recent calls read a `crosses_limit` row with a `precedentId` as "Allowed as routine" (`decision-numbers.ts`).
- Repo MCP Servers (`trust/repo-mcp-servers.tsx`, `GET|PUT /projects/:id/repo-mcp-servers`): one row per `.mcp.json` server with its transport, a state badge (On approved, Off denied, Waiting for none) and a switch. Reading raises no card (`POST …/mcp-servers/review` does, so the desktop never calls it). Turning On opens a `ConfirmModal` with the approval card's own text for the current config (`body`) and sends `{ configHash, verdict }`; Off sends a denial at once. The daemon refuses a hash that is no longer current (409, "the config changed; look again"), answers the server's open Inbox card through `InboxService` when there is one, and otherwise records the verdict itself with no source card. An unreadable `.mcp.json` shows its error text in the card.
- Settings › Trust's Your MCP servers (`your-mcp-servers.tsx`) draws one `McpServerRow` (`mcp-server-row.tsx`) per server: a chevron, the name and its source on one line, then a "Needs Sign-in" badge (red when one failed), the state badge and Approve or the switch on the right; the server's `reason` shows in red under it. The name opens the row: what it runs and every config fact one monospace line each (env, "Signs in with OAuth: …" and the `authServerMetadataUrl`/`xaa` keys Codex sessions don't use, headers, cwd, tool filters), then a small table of each Codex account's sign-in from `GET /settings/trust/mcp-sign-ins` (`useMcpSignIns`): Signed in; Not signed in, Failed (the message in red) or Couldn't read whether it's signed in, each with Sign In; Signing in in your browser…, with Open Page Again, and each default-folder Claude plan account's "Signs in through your own Claude Code (/mcp)". Both buttons post `{ accountId, key }` (`useStartMcpSignIn`), and an `mcp_sign_in.changed` event refetches the rows. A Claude plan account in its own folder gets one terminal entry at the foot of the card (the command with a Copy button, then "Then run /mcp and sign in.").
