# apps/desktop/src/views/inbox

- The Inbox (`views/inbox/`) shows every project's cards, each naming its project (`shell/project-label.tsx`), narrowed by its own Project filter (`?project=`, `shell/project-filter.tsx`, shared with Factory); the Open count follows the filter, while the sidebar badge counts every project, and 10db's own cards show under any filter. It shows one row per card, except that identical dismissable flags (same project, title and body, no options) share a row with a count, and a Workbench pass's Ready pages (`check` cards whose detail is a `PassCheckDetail`) share one row per pass, "Workbench: n pages ready" with Open Workbench (Enter on the selected row too), which selects the pass's project and opens the Workbench, and each page's title, which opens that page there, with its Sign Off (`pass-ready-row.tsx`, the same sign-off route as the page's composer), which offers neither Approve nor Send Back (`inbox-rows.ts`); a failed turn's flag keeps its own row. A collapsed flag shows its body's first line and a Dismiss. Every other card a pass raises is drawn by its title, body and options; `pass-card-extras.tsx` (an exhaustive switch over `PassCardDetail`'s kinds) adds what the builder acts on outside 10db: a branch the close could not move shows its merge command with Copy command, and a follow-on card links the pull request the later sign-offs went to. Its keys are in `use-inbox-keys.ts` and the list the ? button opens is in `inbox-shortcuts.tsx`; change both together.
- Nothing from the system check goes above a view; it is sorted by what the builder can do (`views/inbox/system-cards.ts`, `decisions/2026-11-08-the-inbox-holds-what-needs-the-builder.md`). What needs the builder (a missing required tool, a refused pinned copy with Fetch It Again, an unreadable login shell, a refused Artificial Analysis key) is a 10db card at the top of the Inbox's Open view (`system-card-list.tsx`): it counts in Open n, the sidebar badge and the menu bar (`inbox-count.ts`), is never answered or resolved, and leaves once a check no longer finds it. A copy being downloaded is a dimmed line in the header (`shell/agent-download-status.tsx`). The release each copy runs, a newer release and a version warning are told in Settings › Updates (`views/settings/agent-copies-section.tsx`), which says there is nothing to do. `useSystemCheck` never asks in a screen's frame, whose token may not read `/system`.
- `InboxView` draws the Inbox header once, for both Open and Resolved: the title, an `Open n / Resolved` `SegmentedControl` beside it, and an always-rendered xs subtle `?` button on the right. Never draw a header inside a view, or switching moves it. The ? key still works only on Open.
- A `check` card in the Inbox (`views/inbox/`) is the builder's check of finished work in a project with no gate command (`decisions/2026-10-28-optional-gate.md`): it loads the task's changes from `GET /workstreams/:id/changes` and answers Approve, or Send Back with a required note. The board shows the waiting task as Blocked.
- The Inbox keys (`use-inbox-keys.ts`) ignore anything inside `data-inbox-keys-ignore`, and a check card is answered with its own buttons, never the digits or Enter.
- Knowledge on Inbox cards (`views/inbox/`): a principle proposal card (`isPrincipleCard`: a proposal whose detail has a `principleId`) shows its verdicts in words (`PRINCIPLE_VERDICT_LABELS`: This project, All my projects, This area (name), Reject) and the principle's kind as a badge; the kind and area come from `GET /projects/:id/proposals` (`principle-card.ts`), so the area choice reads plain "This area" until that loads. The daemon still gets the stable value (`accept_area`). A question card shows `RecordDecision` above the note: a checkbox, checked for product, design and engineering (`defaultRecording`, the daemon's own default) and a scope select (This project, All my projects, Area: name). A question's answer always carries `record` (`null` when unchecked, so nothing is recorded); every other kind and the Park the task choice send none, and the control goes while Park the task is chosen. The record choice lives in the card's draft like the note, and digit keys and Enter keep working until a field has focus. An answered question whose note said always or never has `detail.proposedPrinciples` (`CARD_PROPOSED_PRINCIPLES`, written by the daemon in the answer's transaction); the Resolved view then says a principle was proposed and links to `/knowledge?principle=<id>` after selecting the card's project (one link per principle; several read Open principle 1, 2…). `ProjectKnowledge` opens that principle in `ProvenanceDrawer`, which works in any state and names it by the provenance's `text`, on the Principles tab under Pending while its state is proposed, Past once it no longer applies, and Current otherwise; closing the drawer drops the id from the URL. A resolved card says its answer through `optionLabel` (the area verdict reads plain "This area", the proposal no longer being pending), and a choice no option matches reads as stored.
