# apps/desktop/src/views/board

- The task drawer is mounted through `project-task-drawer.tsx` (`ProjectTaskDrawer`), which reads the task, its run and batch, the columns and the project's settings from the project's own queries, so the Board and Factory (over its page, `?task=` on `/factory`) open the same drawer; `onOpenBoard` adds Open on Board to its top edge for a view that is not the Board.
- The board (`views/board/`) has human columns (parked tasks, never started) left of the derived system columns. `drop-rules.ts` holds the drag rules and the card menu's equivalent moves; both call `POST /tasks/:taskId/move` or `POST /tasks/:taskId/start`. jsdom can't drive dnd-kit's sensors (no layout), so `e2e/loop.spec.ts` drives a keyboard drag in WebKit. The whole card is the drag handle and the one `role="button"` (click or Enter opens `TaskDrawer`, Space picks it up); its menu and a shipped card's pull request link are siblings laid over it, because a button can't hold another control; Enter opens the drawer only when no drag is under way.
- A Workbench pass's page on the Board (`board/pass-page.ts`, `decisions/2026-11-10-a-pass-page-is-the-workbenchs-everywhere-else.md`): a task its pass holds is In progress unless its run is paused by a usage limit or held (the daemon's `boardStatus`), its card says Workbench in place of Shared branch (`batchTaskCount` counts a pass's batch as one) and, while it waits on the builder, "Waiting on you in the Workbench"; a page whose run is queued is in no line, since it starts a turn only when the builder writes to it: its card says "In the UI Workbench · runs when you write to it there" and its drawer says the same in place of the QUEUED badge (`PASS_PAGE_QUEUED`), with no place in line and no Run Next (which the daemon refuses for a page its pass holds), and `queuePlaces` leaves it out of every other task's place; its drawer names the pass's branch with Open Workbench and no batch action (`BatchPanel`), and neither its drawer nor its menu offers Abandon (which the daemon refuses for a pass's batch), Hold or Cancel Run: a page leaves its pass by Take Out. A task taken out keeps its last run in the pass's batch; `boardRun` shows it as a task with no run, so it shares no branch and its drawer offers nothing of the pass's.
- The board's batch sheet (`views/board/batch/`) starts work as the project's delivery mode and current batch allow: in a pull-request project one `POST /projects/:id/batches` (it starts, joins or reopens the batch), in a local one a `POST /tasks/:id/start` per task. Where a task runs is its own (`TaskDto.workspaceMode`: Your folder or Separate copy, with `placementReason`); the project's `workspaceMode` is only the default for new tasks, and `isolate` lists the areas and hazards proposed a separate copy. The sheet (`sheet-mode.ts`) follows the ticked tasks: all in separate copies is `worktrees` (one batch per task or per dependency-linked group, never held by the shared batch), a mix follows the shared batch (`currentBatch`) for the Your folder tasks and adds the copies to the same request. A batch is a separate copy when its `worktreePath` is set, and its "Add a Fix Task" (in the task drawer's `BatchPanel`) posts the batch id to join that batch.
- Placement (`board/placement.ts`): the card's badge (`placement-badge.tsx`, reason as tooltip), the drawer's badge and control, and the sheet's control (`placement-choice.tsx`) show only while `placementOpen` (the task is open and its latest run is not active; a parked task counts). The control is hidden for a local-delivery project unless it has `localCopies` on (then the task drawer offers Separate copy for one task; the batch sheet stays pull-request only) and patches `workspaceMode` alone the moment it is chosen; the daemon's refusal is shown beside it. Settings › General names the project's mode "Default for New Tasks" (changeable with work in flight) and edits `isolate`.
- A task's state is said once, on its card (`task-state.ts`: one plain line and a DESIGN.md color; the card's border and dot take the color, a card waiting on the builder gets a 2 px yellow border). The branch, pull request, why a ship failed (with the gate log), Retry, Ship anyway, Add a fix task and Abandon live in the task drawer (`batch-panel.tsx`); the card menu has Retry and Abandon too. Cancel Run (`task-cancel.ts`: an open task whose latest run is not terminal or held) is in both the card menu and the drawer, labelled Cancel Run because the drawer's form already has a Cancel; it asks `cancel-run-modal.tsx`'s confirm, which `BoardColumns` holds, and posts `useCancelWorkstream`. Factory has no Cancel: the refusals ("<task> is running: cancel it first.") point to the card and drawer. There is nothing above the columns for a shared branch, and the card doesn't say it either: the drawer's shared-branch section (`BatchPanel`) holds Abandon with `abandonNote`'s explanation as text under the button. The task drawer is `min(640px, 50vw)` wide (a side panel: the Board stays visible) and is built as in the readable-board spec §6: a header (the title, with the why under it when there is one), **one status line** (`StatusLine`), the notices and alerts, then three tabs, Overview (the default), Reviews (with a count of rounds) and Edit. The status line carries the run's state (or the column's name once the run has finished), the CI phrase (`ciStatus`, which drops the "Pull request open" that `ciLine` says on the card), the Pull request and CI job links, and the run actions (Retry, Start over, Cancel Run, Close task, Start, Remove, Run Next, Hold); there is no column badge and no separate links row. Overview holds What it promises (the criteria), Waits on (one task a line), Delivery (`BatchPanel`: branch, ship failure, Abandon; its pull request link is the status line's), the plan, the implementation report (`task-report.tsx`: what the build session wrote last, kept by the daemon as the implement step's `report` since an implement step records no result; for a task that changed nothing it is the only account of the work, and its own label keeps it apart from a reviewer's result), the latest review (a link to Reviews; each round there names its phase, `roundPhase`) and the task ID. Edit holds the form (Title, Why, Areas, Description, Acceptance criteria, Kinds, Rigor, Effort, landing, placement; Kinds is a multi-select of the builder's kinds in `task-fields.tsx`, an agent's kind staying its own; Rigor starts at the project's default and disables each rigor below the highest `minimumRigor` of the task's kinds, naming that kind (`rigor-options.ts`); Effort is Automatic or one effort every step of the task runs at) and the sticky Cancel / Save Changes bar, which is on Edit alone; the tabs share one component's state, so an edit survives a switch, and closing the drawer with an unsaved edit from any tab still asks to discard. Batch history is not on the Board: a goal's task list in Factory shows each task's pull request on its row (see the Factory bullet below). The app shell's main area is a flex column, and the Board takes the height it is given (never a fixed viewport height); when the columns' minimum exceeds it, the page scrolls. Each card's menu keeps its own Start. A card is what, why and where it stands: its indicator row holds only the goal, CI failed, Waits On and Cancelled (`indicatorsOf` in `task-card.tsx`); rigor, kinds, CI passed, a shared branch and the Workbench are the drawer's, and a done card keeps the plain border.
- The task drawer's pictures (`task-pictures.tsx`) pair each route's before and after; a `lane` screen (taken by a lane's own browser) is never an "after" but sits in a "Lane Screenshots" group under the pairs, oldest first, each with its note (the URL when there is none) and its URL; the section shows when there is a pair or a lane screen.
- Goals on the Board (`goal-line.tsx`, `daemon/goal-queries.ts`): the Board has no goal strips and no goal drawer; goal detail lives in Factory. A goal is never a card. Choosing a goal in the header's Goal select (`All Goals` is its first option, so keyboard users can clear it; a `?goal=` link chooses one too) shows a `GoalLine` beside it: the status dot from `goal-status.ts`, "Idle · 4 in review · 1 ready" (in review from the digest's progress, ready counted from the goal's Ready tasks, zero counts left out), **Start Ready** (disabled with none ready; opens a second `BatchSheet` with `goal` set, which sends `goalId` to `GET /projects/:id/candidates`) and **Open in Factory ›** (navigates to `/factory?goal=<id>`). With All goals nothing shows. The list comes from `GET /projects/:id/goals`, which never advances a goal's view mark; the Board never calls the digest route. Cards carry the goal's title (`goalTitle`, left off while a goal is chosen), and the select filters the columns only: the peers map and the header's own Start Ready Tasks count ignore it.
- In review (`BoardStatus.InReview`) holds finished tasks whose pull request is open; the daemon derives it from `BatchDto.pr`, and a merge moves the task to Done (`decisions/2026-10-30-done-means-merged.md`). `task-state.ts` (`pullRequestState`) says the checks on the card; a pull request closed without merging puts the task in Blocked, where the card menu and the drawer offer Reopen (`POST /tasks/:id/reopen`) and Close. In review and Blocked cards can't be dragged or dropped on.
- Hold (`task-hold.ts`, `POST /tasks/:taskId/hold`): a started task whose run is queued and has not run has Hold in its card menu and drawer; the run becomes `HELD`, sits in Blocked as "Held: not in the queue" and keeps its worktree. Every other live run shows Hold disabled with why ("It is running: cancel it first."; a reason never names the task, since the menu and the drawer already show whose it is): the card menu writes it in the item, the drawer puts it in the disabled button's tooltip and writes no sentence under the buttons. A held task's menu and drawer offer Start (`POST /tasks/:taskId/start` queues the same run again) and Remove (`POST /tasks/:taskId/remove`, which deletes its worktree and branch when nothing else is in its batch); a task with nothing left in it (`task-spent.ts`: open, in no pass, no saved work, its run cancelled, as an abandoned pass leaves one) offers Remove too, and the daemon refuses it, saying why, when an earlier run of it neither failed nor was cancelled or an open task waits on it (one whose earlier run failed is retired as Close retires it, keeping its runs and branch); `decisions/2026-10-29-hold-a-queued-task.md`.
- Goals in the UI: the status look (dot color and label) is one table, `board/goal-status.ts`, shared by the Board's goal line and Factory's rows, and the colors are DESIGN.md's (Shipping blue, Not started gray, green only once merged). The daemon computes the status, progress and digest; the desktop never derives a goal's status from tasks. The goal list `factory/goal-list.tsx`, the Board's goal line `board/goal-line.tsx`, and the queries `daemon/goal-queries.ts`. Design: `docs/superpowers/specs/2026-10-29-10db-goals-design.md`; decision `decisions/2026-11-02-goals-and-the-brief.md`.
- A task with a Linear link has a **Linear** tab in its drawer (`linear-tab.tsx`, from `GET /tasks/:taskId/linear-posts`, refetched on `linear_post.changed`): the issue's link and the reporter's updates newest first with their state. A follow-up of a linked task (Run these now) shows its source's issue, named as such, with only the updates made for the follow-up itself; the daemon says which issue (`linearLinkOf`) in the same response. The card's Linear id link is laid over the card's bottom, a sibling of its button like the Inbox link, never inside it.
- **For You** (`task-for-you.tsx`, `daemon/watchpoint-queries.ts`) is the first item of the task drawer's Overview. It fetches `GET /workstreams/:id/watchpoint-hits` for the drawer's latest run, as `TaskSkips` does, refetches on `evidence.recorded` (`INVALIDATIONS`), and returns null when the newest watchpoint reading has no hits. A reading with `skipped` says "Couldn't read this run's changes." One Accordion fold per watchpoint (open for ask and hold, closed for show) holds "You asked: <guidance>" and, per file, the Agent and Reviewer notes and its kept hunks through `HunkDiff` over `parseChanges(patch)`; the hunks come from the stored row, so a Done task still shows them. "Open the whole diff" (a modal over `ChangesPanel`) shows only while `canOpenDiff`.
- The drawer's Skipped While Nobody Was Watching (`task-skips.tsx`) offers Run These Now once the run has ended and
  it skipped a call a follow-up can run approved (`POST /workstreams/:id/skips/run`): a finished task's skip card
  closes, so the drawer is where those calls are run from. Each earlier run of the task that skipped something has a
  section of its own, newest first, with its own Run These Now, since a folded failed card speaks only for the newest. A refusal (a follow-up exists, the run is retried) shows
  under the heading.
- Eval markers (`eval-marker.tsx`): a card shows one plain text line per eval suite the task's change touched
  ("<suite> · not run", then passing, failing, regressed or "the eval itself changed"), from
  `GET /projects/:id/eval-markers`; the drawer's Evals block, after For You, shows the results before and after and the
  suite's live command, from `GET /tasks/:id/eval-coverage`. Both follow evidence events and refetch on focus.
