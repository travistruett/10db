# apps/desktop

The 10db window: React 19 + Mantine 9 UI built by Vite, inside a Tauri 2 shell (`src-tauri/`).
The UI never touches the database; it talks to the daemon over loopback HTTP and WebSocket.

- Daemon calls go through `src/daemon/client.ts` (Hono typed client over `AppType`). Never
  hand-write a fetch to the daemon. Parse every response with its `@10db/contracts` schema via `readJson`.
- The UI gets its daemon connection from `DaemonProvider` (Tauri `daemon_connection`, or
  `VITE_DAEMON_URL`/`VITE_DAEMON_TOKEN` in the browser); it also polls `/health` and owns the connecting,
  reconnecting and version-mismatch states. Use `useDaemon()` and the hooks in `src/daemon/queries.ts`.
- One event stream (`useEventStream`) invalidates queries by entity type (`INVALIDATIONS`). Don't poll lists.
- `pnpm dev` (`scripts/dev.sh`) shares one random token, kept in `.dev/ui-token`, between the daemon and Vite.
- MSW 3 intercepts jsdom's `WebSocket` as is; no extra environment option is needed.
- Hooks, query keys and fixtures are scoped per backend entity (`daemon/<entity>-queries.ts`, `test/<entity>-fixtures.ts`), accounts first. An account secret is sent by `daemon/account-secret.ts`, never through TanStack Query, and never kept in UI state.
- Server state lives in TanStack Query; routes are code-based TanStack Router in `src/router.tsx`.
- Mantine components and theme tokens only; see `DESIGN.md`. Use the Mantine MCP server for
  component docs (pinned to our Mantine version).
- Dark by default; every view must work in light mode too.
- The React Compiler is on; don't hand-write `useMemo`/`useCallback` for render performance.
- Tests: Testing Library + MSW. Hit the daemon URL through MSW, never a real daemon.
- Rust in `src-tauri/`: `cargo fmt`, `cargo clippy -- -D warnings` with pedantic lints.
- The app icon's source is `app-icon.svg` ("10" in Geist Bold, "db" in Geist Light, outlined to paths).
  `src-tauri/icons/` is generated from it with `pnpm --filter @10db/desktop tauri icon app-icon.svg`;
  never edit those files by hand.
- The menu-bar icon is `tray-icon.svg`, the same wordmark in black with no tile. It ships as a template
  image, which macOS tints to match the menu bar. `src-tauri/tray-icon.png` is generated from it with
  `pnpm --filter @10db/desktop exec tsx scripts/render-tray-icon.ts`; never edit the PNG by hand.
- The window has no title bar (`titleBarStyle: Overlay`): the traffic lights sit over the header's left
  end, `trafficLightPosition` centres them on its 48 px height, and elements marked
  `data-tauri-drag-region` move the window. The native window's theme follows the app's color scheme
  (`setWindowTheme`), not the system's.
- `pnpm --filter @10db/desktop dev:shell` runs the Tauri shell against the daemon and Vite server that
  `pnpm dev` already runs. It sets `TENDB_EXTERNAL_DAEMON=1`, which makes the shell skip its sidecar.
  Run `pnpm --filter @10db/desktop sidecar` once first: `tauri-build` checks the sidecar files exist.
  `src-tauri/tauri.dev.conf.json` (passed by `dev:shell` only, never by a release build) gives that shell its own
  identifier (`app.10db.desktop.dev`) and product name ("10db Dev"), so it runs beside the installed release app
  instead of being folded into it by the single-instance plugin. `dev:shell` also defaults `TENDB_DATA_DIR` to the
  checkout's `.dev/data`, so the dev window never reads the release app's `~/Library/Application Support/10db`.
  The data directory comes from `TENDB_DATA_DIR`, not from the identifier. `tests/repo` fails if the two configs
  share an identifier or product name.
- Factory and preview: the installed release app is the factory; it manages the 10db repo and runs its tasks.
  `pnpm dev` (its own `.dev/data`) with `dev:shell` or http://localhost:1420 is the preview: it renders the
  checkout with live reload and never runs tasks. While a task holds the checkout (Your folder / shared mode),
  don't hand-edit it; work in a worktree under `../10db-worktrees/`.
- `pnpm dev:factory` (`scripts/factory-ui.ts`) runs Vite over the installed app's daemon instead: it reads that
  daemon's `daemon.json` and `ui-token` from `~/Library/Application Support/10db`, checks over `/health` that it
  answers the Vite origin over CORS and takes the token (`GET /projects`), and runs Vite with `--no-cors` and
  `VITE_DAEMON_URL` and `VITE_DAEMON_TOKEN` (`factory-vite.ts`): CORS off keeps other localhost pages from reading the
  module that inlines the token. The daemon accepts
  the page only when 10db started with `TENDB_DEV_UI_ORIGIN=http://localhost:1420`, which the supervisor passes
  through (`decisions/2026-10-29-dev-ui-over-the-factory.md`). `pnpm dev:factory:enable` and `:disable`
  (`scripts/set-factory-opt-in.ts`, plan in `factory-opt-in.ts`) set and unset it with `launchctl`; they never quit
  or open 10db, because quitting stops running work. `scripts/*.test.ts` run in node, in their own vitest project
  (`scripts/vitest.config.ts`).
- `pnpm --filter @10db/desktop e2e` drives the Vite app in Playwright's WebKit, the WKWebView engine,
  against the real daemon on the fake adapter. It is not the Tauri window. `make live-acceptance` runs the daemon as a plain node process with the browser UI, so the Tauri window (sidecar, tray, close-to-tray, webview) has no scripted coverage and is checked by hand.
  `make setup` installs the browser. Each run picks free ports for its daemon and Vite server
  (`e2e/ports.ts`) and passes the Vite origin to the daemon as `TENDB_DEV_UI_ORIGIN`, so parallel
  gates don't share fixed ports. The ports are probed free on 127.0.0.1 and released before the
  servers bind them, so another process can take one in between; the run then fails at startup
  (`reuseExistingServer: false`, Vite's `--strictPort`) rather than reaching another server. Set
  `E2E_DAEMON_PORT` and `E2E_UI_PORT` to fix them while debugging.
  `pnpm dev` and the Tauri shell keep Vite on 1420.
- The board (`views/board/`) has human columns (parked tasks, never started) left of the derived system columns. `drop-rules.ts` holds the drag rules and the card menu's equivalent moves; both call `POST /tasks/:taskId/move` or `POST /tasks/:taskId/start`. jsdom can't drive dnd-kit's sensors (no layout): unit tests move cards through the menu, and `e2e/loop.spec.ts` drives a keyboard drag in WebKit. The whole card is the drag handle and the one `role="button"` (click or Enter opens `TaskDrawer`, Space picks it up); its menu and a shipped card's pull request link are siblings laid over it, because a button can't hold another control; Enter opens the drawer only when no drag is under way.
- The board's batch sheet (`views/board/batch/`) starts work as the project's delivery mode and current batch allow: in a pull-request project one `POST /projects/:id/batches` (it starts, joins or reopens the batch), in a local one a `POST /tasks/:id/start` per task. Where a task runs is its own (`TaskDto.workspaceMode`: Your folder or Separate copy, with `placementReason`); the project's `workspaceMode` is only the default for new tasks, and `isolate` lists the areas and hazards proposed a separate copy. The sheet (`sheet-mode.ts`) follows the ticked tasks: all in separate copies is `worktrees` (one batch per task or per dependency-linked group, never held by the shared batch), a mix follows the shared batch (`currentBatch`) for the Your folder tasks and adds the copies to the same request. A batch is a separate copy when its `worktreePath` is set, and its "Add a fix task" (in the task drawer's `BatchPanel`) posts the batch id to join that batch.
- Placement (`board/placement.ts`): the card's badge (`placement-badge.tsx`, reason as tooltip), the drawer's badge and control, and the sheet's control (`placement-choice.tsx`) show only while `placementOpen` (the task is open and its latest run is not active; a parked task counts). The control is hidden for a local-delivery project and patches `workspaceMode` alone the moment it is chosen; the daemon's refusal is shown beside it. Settings › General names the project's mode "Default for new tasks" (changeable with work in flight) and edits `isolate`.
- A task's state is said once, on its card (`task-state.ts`: one plain line and a DESIGN.md color; the card's border and dot take the color, a card waiting on the builder gets a 2 px yellow border). The branch, pull request, why a ship failed (with the gate log), Retry, Ship anyway, Add a fix task and Abandon live in the task drawer (`batch-panel.tsx`); the card menu has Retry and Abandon too. Cancel Run (`task-cancel.ts`: an open task whose latest run is not terminal or held) is in both the card menu and the drawer, labelled Cancel Run because the drawer's form already has a Cancel; it asks `cancel-run-modal.tsx`'s confirm, which `BoardColumns` holds, and posts `useCancelWorkstream`. Factory has no Cancel: the refusals ("<task> is running: cancel it first.") point to the card and drawer. There is no strip for a shared branch above the columns: a card says "shared branch" with an indicator (`batch/batch-task-count.ts`: more than one task in the batch), and the drawer's shared-branch section (`BatchPanel`) holds Abandon with `abandonNote`'s explanation as text under the button. The drawer's order is the readable-board spec §6: headline and why, status, What it promises (title, criteria), pull request and CI links, the shared branch, review rounds, then the form (Headline, Why, Title, …). Batch history is not on the Board: a goal's task list in Factory shows each task's pull request on its row (see the Factory bullet below). The app shell's main area is a flex column, and the Board takes the height the system alerts above it leave (never a fixed viewport height); when the strips and the columns' minimum exceed the window, the page scrolls. Each card's menu keeps its own Start.
- Goals on the Board (`goal-strip.tsx`, `goal-drawer.tsx`, `daemon/goal-queries.ts`): a goal with at least one open task is a `GoalStrip` (status dot from `goal-status.ts`, "6 of 11 tasks") in a scroll area above the columns, so the columns keep their minimum height; a goal is never a card. A strip opens `GoalDrawer` (objective, read-only criteria, tasks, blockers from the digest's cards and Blocked tasks), whose Start Ready Tasks opens a second `BatchSheet` with `goal` set, which sends `goalId` to `GET /projects/:id/candidates`. The list comes from `GET /projects/:id/goals`, which never advances a goal's view mark; the Board never calls the digest route. Cards carry the goal's title (`goalTitle`), and the header's Goal select (`All goals` is its first option, so keyboard users can clear it) filters the columns only: strips, the peers map and the header's own Start Ready Tasks count ignore it. `e2e/worktree-board.spec.ts` adopts three briefs and checks the minimum height at both sizes.
- In review (`BoardStatus.InReview`) holds finished tasks whose pull request is open; the daemon derives it from `BatchDto.pr`, and a merge moves the task to Done (`decisions/2026-10-30-done-means-merged.md`). `task-state.ts` (`pullRequestState`) says the checks on the card; a pull request closed without merging puts the task in Blocked, where the card menu and the drawer offer Reopen (`POST /tasks/:id/reopen`) and Close. In review and Blocked cards can't be dragged or dropped on.
- Hold (`task-hold.ts`, `POST /tasks/:taskId/hold`): a started task whose run is queued and has not run has Hold in its card menu and drawer; the run becomes `HELD`, sits in Blocked as "Held: not in the queue" and keeps its worktree. Every other live run shows Hold disabled with why ("<task> is running: cancel it in Factory first"). A held task's menu and drawer offer Start (`POST /tasks/:taskId/start` queues the same run again) and Remove (`POST /tasks/:taskId/remove`, which deletes its worktree and branch when nothing else is in its batch); `decisions/2026-10-29-hold-a-queued-task.md`.
- The Inbox (`views/inbox/`) shows one row per card, except that identical dismissable flags (same project, title and body, no options) share a row with a count (`inbox-rows.ts`). A collapsed flag shows its body's first line and a Dismiss. Its keys are in `use-inbox-keys.ts` and the list the ? button opens is in `inbox-shortcuts.tsx`; change both together.
- `InboxView` draws the Inbox header once, for both Open and Resolved: the title, an `Open n / Resolved` `SegmentedControl` beside it, and an always-rendered xs subtle `?` button on the right. Never draw a header inside a view, or switching moves it. The ? key still works only on Open.
- A `check` card in the Inbox (`views/inbox/`) is the builder's check of finished work in a project with no gate command (`decisions/2026-10-28-optional-gate.md`): it loads the task's changes from `GET /workstreams/:id/changes` and answers Approve, or Send Back with a required note. The board shows the waiting task as Blocked.
- Settings (`views/settings/`) is one route over `sections.ts`. To fill a planned section, set its `planned` to null and replace its arm in `section-body.tsx`.
- The first run (`views/first-run/`) replaces the app shell while `GET /projects` has loaded empty on a live connection (`shell/app-layout.tsx`); while the list loads, or the daemon connects or reconnects, the shell shows. Its three steps are Welcome, Check your setup (`use-setup-check.ts`, rows in `claude-row.ts` and `tool-rows.ts`) and Add a project. The Claude Code login probe starts Claude Code, so it runs once on entering the check and on each Agents recheck, never on a render; nothing in the first run patches the default account (a login added with Add Another Login is a new account, edited like any other).
- `views/project-setup/` is the one project form: `useProjectSetup` serves the first run and the switcher's New Project modal (`shell/new-project-modal.tsx`). The folder is chosen in the native panel (`desktop/choose-folder.ts`) or typed in the browser, then inspected by `POST /folders/inspect`; the fields appear only after a folder passes. Setup then asks `POST /folders/propose-areas` for the folder's areas, which the builder renames, merges, removes and adds to (`area-drafts.ts`), and sends exactly those, handoff 40, with nudge 50, and nothing else; Settings holds the rest. When no proposal comes, the areas start from one `repo` area over `WHOLE_REPOSITORY_GLOBS` (`@10db/contracts`). Create Project does not wait for the proposal: using it early aborts the request and creates with that one area. Choosing another folder or closing the form aborts the request too (the daemon then stops its model call), and a proposal that has not answered in 45 s (`PROPOSAL_MS`) falls back to the one area and says so.
- Factory's header has one filled button, Adopt a Plan… (`views/factory/adopt-plan.tsx`, state in `use-adopt-plan.ts`). It opens the native panel for a `.md` file (`desktop/choose-plan.ts`; a browser has no panel, so it types the path) and posts it to `POST /projects/:id/goals/adopt` (`daemon/goal-queries.ts`). A 400 `{errors}` is an answer, not a failure: the "This plan can't be adopted yet" modal names the file and lists every error with its location (`GoalAdoptIssue.path`, e.g. "Task 3, depends on"); Pick Again… reopens the panel and Cancel closes it. Any other failure shows as an alert. An adopted goal joins Factory's goal list (`goal-list.tsx`).
- Factory's open goal (`factory/goal-detail.tsx`) is four zones, not label/value rows: `GoalBar` (counts from `task-rows.ts` `barCounts`: merged and in review from the digest's progress, the rest from the rows) with Start Ready Tasks… (a `BatchSheet` with `goal` set, as the Board's goal drawer opens), `NeedsYou` (the list's `waitingOn` cards plus each failed run with Retry), `GoalTasks`, then collapsed `SinceYouLooked` and `AboutGoal` and the dimmed `GoalFooter` (`goal-digest.tsx`). The task list replaces the Sessions table and the Pull requests list: `task-rows.ts` `taskRows` joins `useTasks` (every task, so a not-started one has a row), the latest workstream and the batches, says the state once (`taskState` from the Board, prefixed "In review · " for a task in review), and gives only a running row a step and context. A cancelled task has no row. The bar and Needs you come from the list's digest, which events keep fresh; only `SinceYouLooked` reads the answer to `useOpenGoal`. The Not in a goal row still lists sessions (`goal-sessions.tsx`).
- Tests that need the native panel answer Tauri's IPC (`mockIPC` for `plugin:dialog|open`) rather than mocking `choose-folder`: the test setup imports the app, so a module mock registers after the real module loaded.
- `e2e/worktree-board.spec.ts` (runs after `loop.spec.ts`) checks in WebKit, at 1440x900 and 1280x720, that the board's columns keep their minimum height with three open batches. Starting a real worktree batch needs a GitHub origin and a signed-in gh, so `apps/daemon/scripts/seed-worktree-batches.ts` writes the batches and workstreams into the idle daemon's database; it is the one place a process other than the daemon writes the database. `E2E_SCREENSHOT_DIR` makes the spec save a full-window screenshot per size.
- `e2e/loop.spec.ts` creates its project through `POST /projects` before opening the page, because a window with no project opens on the first run; `e2e/first-run.spec.ts` runs first (one worker, name order), scans the three first-run steps with axe in dark and light, and creates nothing.
- The Inbox keys (`use-inbox-keys.ts`) ignore anything inside `data-inbox-keys-ignore`, and a check card is answered with its own buttons, never the digits or Enter.
- Settings › Network hosts (`views/settings/network-hosts-section.tsx`) lists, adds and removes a project's allowed hosts through `/projects/:id/network-hosts`; the daemon's refusal text is shown beside Add Host (`decisions/2026-10-29-project-network-hosts.md`).
- Factory (`views/factory/`) is the project's goals (`GET /projects/:id/goals`, `daemon/goal-queries.ts`), one hairline-divided list in the order `factory/goal-status.ts` sets: open goals by status, Not in a goal, then done goals under a collapsed `Done (n)`. A status's dot color and label come from `board/goal-status.ts`, the same as the Board's goal strips. Every row (`goal-row.tsx`) is a button with `aria-expanded` over a `role="region"`; one is open at a time and Escape closes it. Opening a goal calls `GET /goals/:id/digest` as a mutation (`useOpenGoal`), because that read moves the goal's "last opened" mark: a query would repeat on a remount and find its own window closed. The Δ rows (Waiting on, Deviations, Decisions) come from that answer and every other row from the list, which events keep fresh. A session row (`goal-sessions.tsx`) names its task by `taskHeadline`, else `taskTitle`, and links to `/board?task=<id>&goal=<goalId>` (no `goal` for a task not in a goal); `BoardView` starts its goal filter from the link's `goal`, and Retry stays on the row. A queued or held run names no step (`step-cell.tsx`), and the daemon's digest never counts one as running.
- Goals in the UI: the status look (dot color and label) is one table, `board/goal-status.ts`, shared by the Board's goal strips and Factory's rows, and the colors are DESIGN.md's (Shipping blue, Not started gray, green only once merged). The daemon computes the status, progress and digest; the desktop never derives a goal's status from tasks. Adopt a Plan… is `factory/adopt-plan.tsx`, the goal list `factory/goal-list.tsx`, the Board's strip and drawer `board/goal-strip.tsx` and `board/goal-drawer.tsx`, and the queries `daemon/goal-queries.ts`. Design: `docs/superpowers/specs/2026-10-29-10db-goals-design.md`; decision `decisions/2026-11-02-goals-and-the-brief.md`.
- Settings › Decisions (`views/settings/decisions-section.tsx`, `daemon/judge-queries.ts`) edits the judge's config and OpenRouter key through `/judge`. The key goes by `daemon/judge-secret.ts`, never TanStack Query, and the section shows only Set or Not set. The daemon emits no event for judge changes or calls, so the section invalidates its own queries after each mutation and polls the recent calls every 30 s. When `JudgeStatusDto.off` is true (`TENDB_JUDGE=off`) it says so and disables its controls.
