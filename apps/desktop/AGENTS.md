# apps/desktop

The 10db window: React 19 + Mantine 9 UI built by Vite, inside a Tauri 2 shell (`src-tauri/`).
The UI never touches the database; it talks to the daemon over loopback HTTP and WebSocket.

- Daemon calls go through `src/daemon/client.ts` (Hono typed client over `AppType`). Never
  hand-write a fetch to the daemon. Parse every response with its `@10db/contracts` schema via `readJson`.
- The UI gets its daemon connection from `DaemonProvider` (Tauri `daemon_connection`, or
  `VITE_DAEMON_URL`/`VITE_DAEMON_TOKEN` in the browser); it also polls `/health` and owns the connecting,
  reconnecting and version-mismatch states. Use `useDaemon()` and the hooks in `src/daemon/queries.ts`.
- One event stream (`useEventStream`) invalidates queries by entity type (`INVALIDATIONS`). Don't poll lists.
- `pnpm dev:preview` serves the UI with no token for 10db to run as 10db's own preview command, under the gate's
  sandbox; Open Page hands a tab at the daemon's dev UI origin (`/health`'s `devUiOrigin`) the daemon's address and
  its read-only dev UI token (`GET /dev-ui/connection`; never the app's own token) in the URL's fragment (`daemon/dev-ui-handoff.ts`), which `resolveConnection` keeps in the tab's session storage and
  drops from the address. A copied link never carries it
  (`decisions/2026-11-11-10db-runs-the-preview-while-a-pass-is-open.md`).
- `pnpm dev` (`scripts/dev.sh`) shares one random token, kept in `.dev/ui-token`, between the daemon and Vite.
- `pnpm dev` and `pnpm dev:factory` serve the UI from Vite, which has no CSP of its own; `vite.config.ts` sends the
  window's `img-src` (read from `src-tauri/tauri.conf.json` by `window-csp.ts`, so the two cannot drift), so an image
  or stylesheet `url()` from elsewhere is stopped there as in the app. Only `img-src`: Vite needs inline scripts and
  its own websocket. `e2e/window-csp.spec.ts` checks it in WebKit; jsdom has no CSP.
- MSW 3 intercepts jsdom's `WebSocket` as is; no extra environment option is needed.
- Hooks, query keys and fixtures are scoped per backend entity (`daemon/<entity>-queries.ts`, `test/<entity>-fixtures.ts`), accounts first. An account secret is sent by `daemon/account-secret.ts`, never through TanStack Query, and never kept in UI state.
- Server state lives in TanStack Query; routes are code-based TanStack Router in `src/router.tsx`.
- Mantine components and theme tokens only; see `DESIGN.md`. Use the Mantine MCP server for
  component docs (pinned to our Mantine version).
- Dark by default; every view must work in light mode too.
- The React Compiler is on; don't hand-write `useMemo`/`useCallback` for render performance.
- Tests: Testing Library + MSW. Hit the daemon URL through MSW, never a real daemon.
- Rust in `src-tauri/`: `cargo fmt`, `cargo clippy -- -D warnings` with pedantic lints.
- The app icon's source is `app-icon.svg` ("10" in Geist Bold, "db" in Geist Light, outlined to paths).
  `src-tauri/icons/` is generated from it with `pnpm --filter @10db/desktop tauri icon app-icon.svg`;
  never edit those files by hand.
- The menu-bar icon is `tray-icon.svg`, the same wordmark in black with no tile. It ships as a template
  image, which macOS tints to match the menu bar. `src-tauri/tray-icon.png` is generated from it with
  `pnpm --filter @10db/desktop exec tsx scripts/render-tray-icon.ts`; never edit the PNG by hand.
- The window has no title bar (`titleBarStyle: Overlay`): the traffic lights sit over the header's left
  end, `trafficLightPosition` centres them on its 48 px height, and elements marked
  `data-tauri-drag-region` move the window. The native window's theme follows the app's color scheme
  (`setWindowTheme`), not the system's.
- `pnpm --filter @10db/desktop dev:shell` runs the Tauri shell against the daemon and Vite server that
  `pnpm dev` already runs. It sets `TENDB_EXTERNAL_DAEMON=1`, which makes the shell skip its sidecar.
  Run `pnpm --filter @10db/desktop sidecar` once first: `tauri-build` checks the sidecar files exist.
  `src-tauri/tauri.dev.conf.json` (passed by `dev:shell` only, never by a release build) gives that shell its own
  identifier (`app.10db.desktop.dev`) and product name ("10db Dev"), so it runs beside the installed release app
  instead of being folded into it by the single-instance plugin. `dev:shell` also defaults `TENDB_DATA_DIR` to the
  checkout's `.dev/data`, so the dev window never reads the release app's `~/Library/Application Support/10db`.
  The data directory comes from `TENDB_DATA_DIR`, not from the identifier. `tests/repo` fails if the two configs
  share an identifier or product name.
- Screens for Plan (`src/screens/`, Shape spec §5.5): `ScreenRenderHost` (mounted in the shell) long-polls the daemon for a screen to draw, `drawScreen` loads the app in a hidden, sandboxed `<iframe>` (`/?render=<token>&daemon=…&project=…&screen=…`), `captureFrame` draws the frame with `html-to-image`, and the window answers with the picture or why there is none. A window out of sight refuses at once (`WINDOW_HIDDEN`): it keeps long-polling, so the daemon can't tell. A page opened with `?render=` is the frame, and `src/root.tsx` (`Root`, mounted by `main.tsx`) is where a frame is told from the app: a render page whose address parses gets `RenderApp`, and one that fails parsing (`parseRenderParams` returns null) draws nothing, tells its parent why with a `refused` message, and never becomes the app, which would run under the UI token. Keep that decision in `root.tsx`; don't test for `render` anywhere else. `RenderApp` is the app at one route with no shell (`RenderLayout`), a `readOnly` client that sends GETs only, the project it was told to (and the builder's remembered selection untouched), and a reporter that says when the screen has drawn or failed. A view that reads a daemon route the render token may not (`apps/daemon/src/screens/render-access.ts`) shows that route's 403 in a screenshot: add the read there only when it writes nothing. A read that spans projects, as the Inbox does, filters to `useRenderMode().projectId` in a frame, and a query that throws a plain `Error` on a 403 fails the whole screen, so a frame must not make it (`Screenshot` draws a line instead). The real capture runs only in `e2e/see-screen.spec.ts`; every unit test fakes a seam of it.
- Factory and preview: the installed release app is the factory; it manages the 10db repo and runs its tasks.
  `pnpm dev` (its own `.dev/data`) with `dev:shell` or http://localhost:1420 is the preview: it renders the
  checkout with live reload and never runs tasks. While a task holds the checkout (Your folder / shared mode),
  don't hand-edit it; work in a worktree under `../10db-worktrees/`.
- `pnpm dev:factory` (`scripts/factory-ui.ts`) runs Vite over the installed app's daemon instead: it reads that
  daemon's `daemon.json` and `ui-token` from `~/Library/Application Support/10db`, checks over `/health` that it
  answers the Vite origin over CORS and takes the token (`GET /projects`), and runs Vite with `--no-cors` and
  `VITE_DAEMON_URL` and `VITE_DAEMON_TOKEN` (`factory-vite.ts`): CORS off keeps other localhost pages from reading the
  module that inlines the token. The daemon accepts
  the page only when 10db started with `TENDB_DEV_UI_ORIGIN=http://localhost:1420`, which the supervisor passes
  through (`decisions/2026-10-29-dev-ui-over-the-factory.md`). `pnpm dev:factory:enable` and `:disable`
  (`scripts/set-factory-opt-in.ts`, plan in `factory-opt-in.ts`) set and unset it with `launchctl`; they never quit
  or open 10db, because quitting stops running work. `scripts/*.test.ts` run in node, in their own vitest project
  (`scripts/vitest.config.ts`).
- `pnpm --filter @10db/desktop e2e` drives the Vite app in Playwright's WebKit, the WKWebView engine,
  against the real daemon on the fake adapter. It is not the Tauri window. `make live-acceptance` runs the daemon as a plain node process with the browser UI, so the Tauri window (sidecar, tray, close-to-tray, webview) has no scripted coverage and is checked by hand.
  `make setup` installs the browser. Each run picks free ports for its daemon and Vite server
  (`e2e/ports.ts`) and passes the Vite origin to the daemon as `TENDB_DEV_UI_ORIGIN`, so parallel
  gates don't share fixed ports. The ports are probed free on 127.0.0.1 and released before the
  servers bind them, so another process can take one in between; the run then fails at startup
  (`reuseExistingServer: false`, Vite's `--strictPort`) rather than reaching another server. Set
  `E2E_DAEMON_PORT` and `E2E_UI_PORT` to fix them while debugging.
  `pnpm dev` and the Tauri shell keep Vite on 1420.
- The board (`views/board/`) has human columns (parked tasks, never started) left of the derived system columns. `drop-rules.ts` holds the drag rules and the card menu's equivalent moves; both call `POST /tasks/:taskId/move` or `POST /tasks/:taskId/start`. jsdom can't drive dnd-kit's sensors (no layout): unit tests move cards through the menu, and `e2e/loop.spec.ts` drives a keyboard drag in WebKit. The whole card is the drag handle and the one `role="button"` (click or Enter opens `TaskDrawer`, Space picks it up); its menu and a shipped card's pull request link are siblings laid over it, because a button can't hold another control; Enter opens the drawer only when no drag is under way.
- A Workbench pass's page on the Board (`board/pass-page.ts`, `decisions/2026-11-10-a-pass-page-is-the-workbenchs-everywhere-else.md`): a task its pass holds is In progress unless its run is paused by a usage limit or held (the daemon's `boardStatus`), its card says Workbench in place of Shared branch (`batchTaskCount` counts a pass's batch as one) and, while it waits on the builder, "Waiting on you in the Workbench"; its drawer names the pass's branch with Open Workbench and no batch action (`BatchPanel`), and neither its drawer nor its menu offers Abandon (which the daemon refuses for a pass's batch), Hold or Cancel Run: a page leaves its pass by Take Out. A task taken out keeps its last run in the pass's batch; `boardRun` shows it as a task with no run, so it shares no branch and its drawer offers nothing of the pass's.
- The board's batch sheet (`views/board/batch/`) starts work as the project's delivery mode and current batch allow: in a pull-request project one `POST /projects/:id/batches` (it starts, joins or reopens the batch), in a local one a `POST /tasks/:id/start` per task. Where a task runs is its own (`TaskDto.workspaceMode`: Your folder or Separate copy, with `placementReason`); the project's `workspaceMode` is only the default for new tasks, and `isolate` lists the areas and hazards proposed a separate copy. The sheet (`sheet-mode.ts`) follows the ticked tasks: all in separate copies is `worktrees` (one batch per task or per dependency-linked group, never held by the shared batch), a mix follows the shared batch (`currentBatch`) for the Your folder tasks and adds the copies to the same request. A batch is a separate copy when its `worktreePath` is set, and its "Add a fix task" (in the task drawer's `BatchPanel`) posts the batch id to join that batch.
- Placement (`board/placement.ts`): the card's badge (`placement-badge.tsx`, reason as tooltip), the drawer's badge and control, and the sheet's control (`placement-choice.tsx`) show only while `placementOpen` (the task is open and its latest run is not active; a parked task counts). The control is hidden for a local-delivery project and patches `workspaceMode` alone the moment it is chosen; the daemon's refusal is shown beside it. Settings › General names the project's mode "Default for new tasks" (changeable with work in flight) and edits `isolate`.
- A task's state is said once, on its card (`task-state.ts`: one plain line and a DESIGN.md color; the card's border and dot take the color, a card waiting on the builder gets a 2 px yellow border). The branch, pull request, why a ship failed (with the gate log), Retry, Ship anyway, Add a fix task and Abandon live in the task drawer (`batch-panel.tsx`); the card menu has Retry and Abandon too. Cancel Run (`task-cancel.ts`: an open task whose latest run is not terminal or held) is in both the card menu and the drawer, labelled Cancel Run because the drawer's form already has a Cancel; it asks `cancel-run-modal.tsx`'s confirm, which `BoardColumns` holds, and posts `useCancelWorkstream`. Factory has no Cancel: the refusals ("<task> is running: cancel it first.") point to the card and drawer. There is nothing above the columns for a shared branch: a card says "shared branch" with an indicator (`batch/batch-task-count.ts`: more than one task in the batch), and the drawer's shared-branch section (`BatchPanel`) holds Abandon with `abandonNote`'s explanation as text under the button. The task drawer is `min(640px, 50vw)` wide (a side panel: the Board stays visible) and is built as in the readable-board spec §6: a header (the headline, else the title, with the why under it when there is one, and a dimmed "Add a headline" link to Edit when there is none), **one status line** (`StatusLine`), the notices and alerts, then three tabs, Overview (the default), Reviews (with a count of rounds) and Edit. The status line carries the run's state (or the column's name once the run has finished), the CI phrase (`ciStatus`, which drops the "Pull request open" that `ciLine` says on the card), the Pull request and CI job links, and the run actions (Retry, Start over, Cancel Run, Close task, Start, Remove, Run Next, Hold); there is no column badge and no separate links row. Overview holds What it promises (the criteria, and the title above them only when there is a headline, so the title shows once outside Edit), Waits on (one task a line), Delivery (`BatchPanel`: branch, ship failure, Abandon; its pull request link is the status line's), the latest review (a link to Reviews) and the task ID. Edit holds the form (Headline, Why, Title, Areas, Description, Acceptance criteria, Flow, Risks, landing, placement) and the sticky Cancel / Save Changes bar, which is on Edit alone; the tabs share one component's state, so an edit survives a switch, and closing the drawer with an unsaved edit from any tab still asks to discard. Batch history is not on the Board: a goal's task list in Factory shows each task's pull request on its row (see the Factory bullet below). The app shell's main area is a flex column, and the Board takes the height the reconnecting banner above it leaves (never a fixed viewport height); when the banner and the columns' minimum exceed the window, the page scrolls. Each card's menu keeps its own Start.
- Goals on the Board (`goal-line.tsx`, `daemon/goal-queries.ts`): the Board has no goal strips and no goal drawer; goal detail lives in Factory. A goal is never a card. Choosing a goal in the header's Goal select (`All goals` is its first option, so keyboard users can clear it; a `?goal=` link chooses one too) shows a `GoalLine` beside it: the status dot from `goal-status.ts`, "Idle · 4 in review · 1 ready" (in review from the digest's progress, ready counted from the goal's Ready tasks, zero counts left out), **Start Ready** (disabled with none ready; opens a second `BatchSheet` with `goal` set, which sends `goalId` to `GET /projects/:id/candidates`) and **Open in Factory ›** (navigates to `/factory?goal=<id>`). With All goals nothing shows. The list comes from `GET /projects/:id/goals`, which never advances a goal's view mark; the Board never calls the digest route. Cards carry the goal's title (`goalTitle`, left off while a goal is chosen), and the select filters the columns only: the peers map and the header's own Start Ready Tasks count ignore it. `e2e/worktree-board.spec.ts` adopts three briefs, checks nothing sits above the columns, the minimum height at both sizes, and the line and Open in Factory.
- In review (`BoardStatus.InReview`) holds finished tasks whose pull request is open; the daemon derives it from `BatchDto.pr`, and a merge moves the task to Done (`decisions/2026-10-30-done-means-merged.md`). `task-state.ts` (`pullRequestState`) says the checks on the card; a pull request closed without merging puts the task in Blocked, where the card menu and the drawer offer Reopen (`POST /tasks/:id/reopen`) and Close. In review and Blocked cards can't be dragged or dropped on.
- Hold (`task-hold.ts`, `POST /tasks/:taskId/hold`): a started task whose run is queued and has not run has Hold in its card menu and drawer; the run becomes `HELD`, sits in Blocked as "Held: not in the queue" and keeps its worktree. Every other live run shows Hold disabled with why ("It is running: cancel it first."; a reason never names the task, since the menu and the drawer already show whose it is): the card menu writes it in the item, the drawer puts it in the disabled button's tooltip and writes no sentence under the buttons. A held task's menu and drawer offer Start (`POST /tasks/:taskId/start` queues the same run again) and Remove (`POST /tasks/:taskId/remove`, which deletes its worktree and branch when nothing else is in its batch); `decisions/2026-10-29-hold-a-queued-task.md`.
- The Inbox (`views/inbox/`) shows every project's cards, each naming its project (`shell/project-label.tsx`), narrowed by its own Project filter (`?project=`, `shell/project-filter.tsx`, shared with Factory); the Open count follows the filter, while the sidebar badge counts every project, and 10db's own cards show under any filter. It shows one row per card, except that identical dismissable flags (same project, title and body, no options) share a row with a count, and a Workbench pass's Ready pages (`check` cards whose detail is a `PassCheckDetail`) share one row per pass, "Workbench: n pages ready" with Open Workbench (Enter on the selected row too), which selects the pass's project and opens the Workbench, and each page's title, which opens that page there, with its Sign Off (`pass-ready-row.tsx`, the same sign-off route as the page's composer), which offers neither Approve nor Send Back (`inbox-rows.ts`); a failed turn's flag keeps its own row. A collapsed flag shows its body's first line and a Dismiss. Every other card a pass raises is drawn by its title, body and options; `pass-card-extras.tsx` (an exhaustive switch over `PassCardDetail`'s kinds) adds what the builder acts on outside 10db: a branch the close could not move shows its merge command with Copy command, and a follow-on card links the pull request the later sign-offs went to. Its keys are in `use-inbox-keys.ts` and the list the ? button opens is in `inbox-shortcuts.tsx`; change both together.
